  1. **재무상태표 불일치 기간에 재무상태 사실이 그대로 나감** — §4.4.2 "재무상태표 불일치 기간은 재무상태 지표 전체를 뺀다"를 `FinancialExplainInputBuilder`가 구현하지 않아, 셀레스트라(2715, 실제로 자산총계 180.3억 ≠ 부채총계 251.4억 + 자본총계 −66.7억)의 입력에 `total_assets`·`total_liabilities`·`total_equity`·`capital_stock`·`structure` 섹션이 그대로 들어 있었다. `FIN_DATA_INCONSISTENT` 활성 신호가 있으면 이 여섯 지표를 전부 `unavailable`(사유 `INCONSISTENT_BALANCE`)로 두고 `structure` 섹션을 빼도록 고쳤다. 회귀 테스트: `FinancialExplainInputBuilderTest#inconsistentBalanceSheetExcludesAllStructureFacts`.
  2. **금융형 기업이 매출 원값을 전혀 못 받음** — 금융형이면 매출 관련 사실을 전부(원값 포함) 만들지 않던 것을, §4.4.2 "금융형은 매출 증가율만 계산하지 않는다(영업수익 원값은 남긴다)"에 맞게 고쳤다(`revenue_yoy`만 `unavailable(NOT_APPLICABLE_FORMAT)`, `revenue`/`revenue_prior`는 "영업수익" 이름으로 유지). 다만 §3 표의 "`AccountMapper`가 '영업수익'을 인식하지 못함" 문제 때문에 실제 데이터에서는 아직 이 경로를 타는 금융형 기업이 없다(DB손해보험 등은 "영업수익" 계정 자체가 안 읽힌다) — 코드는 고쳤지만 실제 데이터로는 끝까지 확인하지 못했다. **(정정 2026-09-25, §8.1)** 이 서술은 틀렸다. 주요계정 API에는 "영업수익" 계정이 없고 DB손해보험은 매출 계정 자체가 없다. 매출액이 있는 금융형(SV인베스트먼트 810 등 27개사)은 이 경로를 실제로 타며, 골든셋 810 입력에 "영업수익 91.5억원"이 있다.

### 7.4.1 실제 Anthropic 호출 검증 (2026-09-26)

사용자가 실제 인증키를 `~/.stockinsight/secrets.yml`에 넣은 뒤 골든셋 12개사(§7.4 표)를 대상으로 `--spring.profiles.active=local --app.analysis.financial-explain.run-on-startup=true --app.analysis.financial-explain.golden-set-company-ids=<12개 ID>`로 실제 호출했다. `publish`는 기본값(`false`)을 그대로 뒀다(초안까지만, D-39·§4.4.8 게시 조건 미충족).

**1차 시도 — 전부 `MAX_TOKENS`로 잘림 (문제 발견)**

- 12개사 전부 두 번의 시도(검증 실패 시 1회 재시도, §4.4.7) 모두 `MAX_TOKENS`로 끝나 `REJECTED`로 기록됐다. 원인: `claude-sonnet-5`는 `thinking`을 지정하지 않으면 기본으로 확장 사고를 켜고, 이 사고 토큰이 `max_tokens`(2,000)를 먼저 소진한다. 직접 재현 호출(사고 켬, `max_tokens=8,000`)로 확인: 사고 토큰 약 1,092개 + 본문 약 427개 = 출력 1,519개. `max_tokens`를 8,000으로 올려 12개사를 다시 돌려도 일부(2개사)는 여전히 잘렸다(기업마다 사고 길이가 다름).
- 설치된 SDK(`anthropic-java 2.34.0`)를 직접 확인(`javap`)해 `com.anthropic.models.messages.ThinkingConfigDisabled`가 있고 `MessageCreateParams.Builder.thinking(ThinkingConfigDisabled)` 오버로드가 있음을 확인했다. `claude-sonnet-5`는 이 값을 그대로 받는다(다른 모델·버전 확장 없이 해결 가능, 사용자 지시대로 범위를 넓히지 않았다).
- 결정: [D-44](../decisions/D-41-D-53.md) — 재무 쉬운 설명 호출은 `thinking: {type: "disabled"}`를 명시한다. `AnthropicLlmClient`에 한 줄 추가, `max_tokens`는 기존 2,000 유지. spec/analyses.md §8·§9 갱신(위 내용).

- **분류** (사용자 지시대로 코드는 고치지 않고 분류만 했다)
  1. **단순한 개별 생성 실패**: 없음으로 판단한다. 12개사 전부, 재시도까지 실패했고 특정 소수 사례의 우연한 실패가 아니라 여러 기업에 걸쳐 같은 규칙(10, 4, 2)이 반복된다.
  2. **프롬프트/검증 규칙의 문제로 보이는 것**:
     - 규칙 4(같은 사실 토큰 한 번만)와 "개요는 핵심 한 가지를 먼저 보여주고 손익 섹션이 그 수치를 풀어 쓴다"(§4.4.3)는 프롬프트 지시가 구조적으로 충돌한다(908 사례로 확인). 프롬프트에 "개요에서 쓴 사실 토큰은 다른 섹션에서 다시 쓰지 않는다"처럼 더 명시적인 지시가 필요해 보인다.
     - 규칙 10(분량)의 문장·토큰 수 상한(§4.4.3: 개요 2문장/사실 3개, 손익 4문장/6개 등)이 신호·사실이 많은 기업(872·908·737처럼 활성 신호가 여러 개 묶인 경우)에는 실제로 지키기 빠듯해 보인다(9/12에서 걸림). 상한이 실제 데이터 분포에 맞는지 재검토가 필요하다.
  3. **현재 제품 설계 자체의 문제로 볼 만한 것**: 확실히 이 범주로 분류할 사례는 찾지 못했다. 규칙 2(토큰 이탈, 숫자를 그대로 씀)는 D-17("숫자는 코드가 채우는 자리표시자")·D-38의 핵심 안전장치가 모델에서 안정적으로 지켜지지 않는다는 뜻이라 설계 원칙 자체보다는 "그 원칙을 프롬프트만으로 얼마나 안정적으로 지키게 할 수 있는가"의 문제로 본다 — 다만 이 실패율(2·3번 규칙류가 12개 중 6개)이 이후에도 반복되면 "검증 실패 시 1회 재시도 후 거절"(§4.4.7)만으로 충분한지, 재시도 횟수나 실패 규칙 되먹임 방식(현재는 실패 규칙 번호만 프롬프트에 덧붙임, §4.4.7)을 다시 볼 필요가 있다는 판단 대기 항목으로 남긴다.
- **후속 조치 (코드 변경 없이 기록만, 사용자 판단 대기)**
  1. 프롬프트(`prompts/financial_explain/v1.md`)에 "개요에서 쓴 사실 토큰은 다른 섹션에서 다시 쓰지 않는다"를 명시적으로 추가하는 안.
  2. §4.4.3의 섹션별 문장·토큰 상한을 실제 골든셋 분포로 재보정하는 안(현재 8/12가 여러 활성 신호를 가진 기업이라 상한을 넉넉히 잡아야 할 수 있다).
  3. 검증 실패 시 재시도 상한(현재 1회)을 늘리거나, 실패 규칙별로 더 구체적인 재작성 지시를 주는 안.
  4. 위 어느 것도 이번 세션에서는 적용하지 않았다 — "불필요한 재설계 금지", "근거 없는 대규모 프롬프트 변경 금지"라는 지시에 따라 사용자 승인 후 별도 세션에서 진행한다.
- **비용**: 이번 세션 전체 실제 호출(1차 12건 실패 + 2차 12건 + 단독 검증 1건 + 진단용 재호출 몇 건)에 약 $1.5~2가 들었다(§7.4.1의 표는 2차 12건 합계 $0.27만 반영). 정상 경로(사고 끔, 첫 시도 통과 가정)라면 12건에 약 $0.2 이하로 예상된다 — spec/analyses.md §9 가정과 일치.
- **[미확인, 유지]** 자동 검증을 통과한 뒤의 §4.4.8 사람 검토(사실 일치·반복·자연스러움)는 이번에도 진행하지 못했다 — 자동 검증 자체를 한 건도 통과하지 못했기 때문이다. 위 후속 조치 중 하나로 통과율을 올린 뒤 다시 시도해야 한다.

### 7.4.2 구조적 원인 분석과 조정, 재검증 (2026-09-26)

§7.4.1의 0/12 결과를 "단순히 검증을 느슨하게 만들지 말고 구조적 충돌을 분석하라"는 지시에 따라 다시 봤다. 확인한 내용과 적용한 변경은 [D-45](../decisions/D-41-D-53.md)에 결정으로 남겼다. 요약:

- **history 섹션의 암묵적 판정 제거**: 기존 설계는 흐름 사실(`revenue_yoy_run`, `operating_loss_run`)을 "history에서 과거형, 다만 지금도 이어지는 상태는 sales_profit에서 현재형"이라고 적어 AI가 그때그때 판단하게 했다. 이 두 흐름 사실은 계산 자체가 최신 분기까지 거꾸로 센 값이라 애초에 항상 "지금 이어지는 상태"다. `FinancialExplainInputBuilder.resolveSections()`가 `history`를 여는 조건에서 흐름 사실을 빼(이력 PAST 신호가 있을 때만 열도록) 이 판정을 코드로 고정했다. `FinancialExplainValidator` 규칙 7도 흐름 사실 토큰이 `history`에 나오면 실패로 잡도록 확장했다(완화가 아니라 더 엄격해진 것).

- **분량 상한 대신 문장 결합 예시 추가**: 상한(overview 2문장/3개, sales_profit 4문장/6개 등)은 사실 개수 대비 넉넉하다고 판단해 **올리지 않았다**. 대신 프롬프트 예시가 "토큰 하나당 문장 하나"만 보여줘 생긴 것으로 보고, 여러 사실을 한 문장에 묶는 예시를 추가했다.
- **토큰 이탈(규칙 2·3)은 이번에 코드·프롬프트를 바꾸지 않았다.** JSON 스키마에 정규식 패턴을 넣어 API 단에서 강제하는 방안을 검토했지만, 이 SDK가 구조화 출력의 `pattern` 제약을 생성 단계에서 실제로 강제하는지 확인할 수 없어(추측 금지 원칙) 보류했다(D-45 재검토 조건).

### 7.4.3 잔여 실패 10건 구조 분석 (2026-09-26, 코드·프롬프트 변경 없음)

**분석 방법과 한계**: `REJECTED` 건은 검증을 통과하지 못한 AI 원문을 저장하지 않는다(`FinancialExplainJob`의 `Attempt.rejected(...)`는 `output`을 만들지 않으므로 `result_json`이 null이다 — DRAFT만 저장). 앱 로그도 전체 출력을 남기지 않는다(보안 요구사항, §7.7). 이번 분석은 **추가 Anthropic API 호출 없이** 다음 세 가지만으로 진행했다.

1. `GoldenSetDumpRunner`(`--spring.profiles.active=local,goldenset`, AI 호출 없음)로 12개사의 §4.4.2 입력 JSON을 **현재 코드로 다시 만들어** 실제 무엇이 입력됐는지 확인(골든셋 파일이 D-45 이전 것이라 최신 코드와 다를 수 있어 새로 만들었다).
2. `FinancialExplainValidator` 코드 자체의 판정 로직 검토(정적 분석 — 실행 결과가 아니라 코드 읽기로 확인 가능한 것).

**1) 규칙 2(토큰 이탈) — 716, 908, 2906**

- 검증기는 이 세 건 모두 정확히 잡아 재시도·거절로 이어지게 했다 — 게시본에 새어나간 사례는 0건이다. **검증기가 막아야 할 것을 놓친 적은 없다.**
- 프롬프트는 이미 "절대 금지" 최상위 규칙과 "토큰 문법" 섹션 두 곳에서 "입력에 없는 토큰을 만들지 않는다"를 명시한다. 이번 라운드(D-45 이후 문구 보강 포함)에도 규칙 2는 6→3건으로 줄었을 뿐 0이 되지는 않았다 — 이미 가장 강한 표현을 두 곳에 넣은 상태라, 문구를 더 추가한다고 남은 사례가 사라진다는 근거는 없다.
- 출력 계약(자유 텍스트 문자열)은 "토큰만 쓰고 숫자는 쓰지 않는다"를 생성 단계에서 기계적으로 강제할 수 없는 구조다. JSON 스키마 정규식(`pattern`) 제약으로 API 단에서 강제하는 방안은 [D-45](../decisions/D-41-D-53.md)에서 이미 검토했고, 이 SDK·모델이 구조화 출력 단계에서 `pattern`을 실제로 강제하는지 확인되지 않아 보류했다 — 이번 분석에서도 이를 뒤집을 새 증거는 없다.
- **판정: 현재 수준에서 허용.** 검증기가 이미 정확히 방어하고 있고(재시도 1회 후 거절, 부분 게시 없음), 프롬프트를 더 강하게 미는 것은 근거가 부족하다. 스키마 패턴 제약은 "설계 재검토 필요"급 후보로 남기되, 적용 전에 SDK 동작을 실제로 검증하는 별도 조사가 선행 조건이다(D-45 재검토 조건과 동일, 아직 미해결).

**2) 규칙 4(토큰 반복) — 608, 810, 1016, 1640, 2715**

- **코드로 확정**: `FinancialExplainValidator`의 규칙 4는 `factTokenCount.merge(t.raw(), 1, Integer::sum)`로 토큰의 **원문 문자열 전체**를 키로 센다(`FinancialExplainValidator.java`). `fin.revenue.…`와 `fin.revenue_yoy.…`는 애초에 다른 문자열이라 같은 키로 묶일 수 없다 — **"서로 다른 fact token을 같은 사실로 잘못 판단하는" 경로는 코드 구조상 존재하지 않는다.** 사용자 질문의 두 번째 항목에 대한 답은 "아니오, 그런 오판은 없다"이다. 즉 규칙 4가 잡은 것은 전부 **문자 그대로 같은 토큰의 재사용**이다(사용자 질문의 첫 번째 항목: 그렇다, 실제 중복이다).
- **원인 패턴**: 이 5건은 **전부** `changeStatus: NONE`이다(위 표). D-45에서 추가한 "개요에서 쓴 사실 토큰은 다른 섹션에서 다시 쓰지 않는다 — 개요는 변화량 사실(`_yoy`,`_diff`), 다른 섹션은 원값 사실을 쓴다"는 지시는 **CHANGED 경로**(신호가 있어 변화량 사실과 원값 사실이 둘 다 있는 경우)만 다뤘다. `changeStatus: NONE`이면 애초에 변화량 사실이 없거나 있어도 "핵심 변화"로 지목할 신호가 없어, 개요의 "수준 사실 하나"와 손익 섹션의 "매출(규모)" 서술이 겹칠 때 어떤 사실을 서로 다르게 골라야 하는지 프롬프트가 정해주지 않는다. 이 가설은 이번 라운드 데이터로 뒷받침된다: CHANGED 기업 중 규칙 4가 남은 곳은 0건이다(908도 이전 라운드엔 규칙 4가 있었지만 이번엔 빠졌다) — D-45의 CHANGED 경로 처방이 효과가 있었다는 뜻이고, 동시에 NONE 경로는 손대지 않았다는 뜻이다.
- **판정: 수정 필요.** 근거가 뚜렷하다(5/5 전부 NONE, CHANGED 경로는 이미 해결됨을 이번 라운드가 직접 보여준다). validator를 느슨하게 하지 않고 프롬프트에 NONE 경로 전용 지시(예: "changeStatus가 NONE이면 손익·재무상태 섹션은 개요가 쓰지 않은 사실을 골라 쓴다")를 추가하면 되는, 범위가 좁고 근거가 확실한 수정이다. 이번 세션은 "분석까지만" 요청받았으므로 **적용하지 않았다** — 다음 세션에서 v1.md·spec/financial-explain.md §4.4.3에 반영할지 사용자 승인을 받는다.

**3) 규칙 10(분량) — 608, 716, 810, 2386, 2715**

- D-45 이후 9→5건으로 줄었고, 이번 라운드에서 신호가 가장 많은 908(신호 8개)은 규칙 10을 **통과**했다(직전 라운드엔 실패). "신호가 많은 기업은 상한을 지킬 수 없다"는 §7.4.1의 가설을 이번 데이터가 반박한다.
- 특히 **2386은 신호가 0개**(활성·과거 모두 없음)이고 사실도 15개뿐인, 골든셋에서 가장 단순한 입력 축에 속하는데도 규칙 10만 단독으로 실패했다. 내용량이 아니라 "단순한 내용도 장황하게 풀어 쓰는" 생성 경향이 원인일 가능성이 높다 — 상한을 올려야 할 근거라기보다 문장을 더 간결히 묶어야 한다는 근거다.
- **판정: 현재 수준에서 허용(상한 유지).** 문장 결합 예시를 추가한 것만으로 거의 절반으로 줄었고, 남은 사례는 상한 자체보다 개별 생성의 장황함 문제로 보인다. 상한을 올리는 것은 사용자가 명시적으로 금지한 "완화"에 해당하고, 위 반증 사례(908 통과, 2386 실패) 때문에 근거도 부족하다.

**4) 규칙 7 — 716, 908 (D-45 코드 동작 확인 포함)**

- **D-45 코드는 의도대로 동작한다 — 직접 증거로 확인**: `GoldenSetDumpRunner`로 최신 코드로 입력을 다시 만들어보니, 흐름 사실만 있고 과거 신호가 없는 820·1640은 `sections`에서 `history`가 정확히 빠졌다(§7.4.2 이전 골든셋 파일과의 diff로 확인, `git diff`). 이 두 기업은 이번 라운드에서 규칙 7을 실패하지 않았다(820: 6만, 1640: 8·5·4만 — 직전 라운드엔 둘 다 7이 있었다).
- **716·908은 버그가 아니다**: 두 기업 모두 실제로 `PAST` 상태 신호를 가지고 있어(716: S3, 908: S5~S8) `history` 섹션이 정당하게 열려 있다(코드가 올바르게 판단한 결과). 따라서 이 두 건의 규칙 7 실패는 D-45가 고친 "흐름 사실의 섹션 판정을 AI에 맡기던" 문제가 재발한 것이 아니라, 신호가 많은 입력(716: 3개, 908: 8개 — 골든셋에서 가장 신호가 많은 기업)에서 모델이 여전히 이따금 시제·섹션 배치를 놓치는 잔여 신뢰성 문제로 본다.


`revenue`(매출 원값 자체가 없음, `ACCOUNT_MISSING`)와 `revenue_yoy`(증가율만 못 줌, `NON_KRW`·`SMALL_BASE`·`BASE_NOT_POSITIVE`)는 서로 다른 사유인데 같은 이름("매출")으로 묶여 있다. `revenue_yoy`만 `unavailable`이어도 `revenue`(원값)는 정상적으로 사실표에 있고 `sales_profit` 섹션은 "매출(규모)"로 반드시 그 값을 언급해야 한다(§4.4.3) — 그런데 규칙 8은 이 정상적인 "매출" 언급까지 위반으로 잡는다.

이번에 규칙 8로 실패한 608·716·1640은 **셋 다 `unavailable: [{"metric":"revenue_yoy","reason":"NON_KRW"}]`를 가진 비원화 기업**이다(골든셋 입력 파일로 확인, 회사별 사유 동일). 608·1640은 이번 라운드에 규칙 8이 **유일한** 실패 사유였다 — 즉 **이 버그가 없었다면 608·1640은 통과했을 것이다.** 716도 규칙 8이 빠지면 규칙 6 하나만 남는다. 이 버그는 비원화 기업(또는 매출 증가율만 계산 못 하는 기업 전반)에서 **모델이 무엇을 쓰든 항상 재현**되는, 순수하게 코드 쪽 결함이다 — §7.4.1~§7.4.4에서 분류해 온 "프롬프트 문제/모델 비결정성" 어느 쪽도 아니다.

**보정한 실제 통과율**: 이 버그를 제외하고 보면(가상의 수정, 이번 세션에서는 적용하지 않았다) 608·1640이 통과해 **6/12**가 되고, 진짜로 남는 문제는 716(규칙 6)·820(규칙 3·5·6)·872(규칙 5)·908(규칙 7·10)·2715(규칙 2)·2906(규칙 2) 6건으로 좁혀진다.

**사용자 질문에 대한 답**

1. **필수성**: 규칙 2·3·5·6·7·8은 모두 "판정은 코드, 설명은 AI"와 사실 정확성을 지키는 핵심 안전장치로 하나도 없앨 수 없다. 규칙 10만 정확성이 아니라 스타일(간결함) 문제라 상대적으로 덜 필수적이다.
2. **원인 분류**: 규칙 8(3건)은 **확인된 validator 버그**다. 나머지(2·3·5·6·7·10, 5건)는 검증기·프롬프트가 이미 올바르게 요구하고 있는데 모델이 시도마다 다르게 반응하는 **비결정성**으로 판단한다 — 다만 820의 규칙 6(그리고 어쩌면 3·5도)은 골든셋에서 유일한 "방향이 엇갈리는 신호 묶음" 구조와 관련 있을 가능성이 있어(원문 미확보로 단정은 못 함) 추가 조사 후보로 남긴다.
3. **872·820 해석**: 872는 **같은 입력·프롬프트가 이전엔 통과, 이번엔 실패**했다는 사실 자체가 이 시스템이 확률적임을 보여주는 직접 증거다 — D-46의 결함이 아니다(872는 `changeStatus: CHANGED`라 이번에 바꾼 NONE 경로 코드를 타지 않는다, 코드로 확인 가능). 이런 역전은 "설계가 잘못됐다"는 신호가 아니라 "표본 1개사·1회 호출로는 통과율을 결정론적으로 재현할 수 없다"는 신호로 읽어야 한다.
4. **4/12만으로 추가 설계 변경이 필요한가**: **아니다.** 이번 분석으로 남은 8건 중 3건은 설계가 아니라 구현 버그(수정 대상이지 재설계 대상이 아님)이고, 2건(2715·2906)은 이미 D-45에서 "현재 수준에서 허용"으로 판정한 유형의 재발이며, 나머지(716·820·872·908)는 표본 부족으로 구조적 결론을 내릴 수 없는 비결정성이다. D-38~D-46의 출력 계약·섹션 구조·토큰 문법을 바꿔야 한다는 증거는 이번 라운드에서도 나오지 않았다.
5. **"MVP에 사용할 수 있는 상태"인가**: **인프라·안전장치 관점에서는 그렇다. 커버리지 관점에서는 아직 아니다 — 다만 이 제품은 애초에 부분 커버리지를 정상 상태로 설계했다.**
   - API 안정성(12/12 성공, `MAX_TOKENS`·파싱 실패 0건, 3라운드 연속), 비용(회당 $0.01~0.03, 예산의 5% 미만), 검증·거절·재시도(무한 재시도 없음, 부분 게시 없음), 지문·무효화(D-40·D-42)까지 — 안전하게 동작해야 하는 부분은 세 라운드에 걸쳐 일관되게 정상이었다.
   - 통과한 4건(737·810·1016·2386)의 실제 문장을 사람이 읽는 기준으로 다시 확인했다: 숫자는 전부 토큰, 인과·투자 표현 없음, "초등 고학년이 읽고 이해" 수준의 짧고 담담한 문장, 사실 반복 없음 — **품질 자체는 이미 사용 가능한 수준**이다(§4.4.8 정식 사람 검토는 아직 안 거쳤다는 점은 유지).
   - `changeStatus`가 있는데도 검증을 통과 못 한 기업은 §4.4.6에 이미 정의된 대로 "AI 설명 없이 코드가 만든 숫자·차트·신호만" 보여주면 된다 — 이는 결함이 아니라 설계된 폴백이다. 따라서 "모든 기업이 AI 설명을 가져야 MVP"라는 전제 자체가 이 제품의 설계와 맞지 않는다.
6. **더 개선한다면 우선순위**:
   1. **규칙 8의 `revenue`/`revenue_yoy` 이름 충돌 수정** — 근거가 100% 확정적이고, validator 15줄 이내 수정으로 끝나며, 위험이 전혀 없다(오히려 지금은 정상적으로 옳은 출력을 부당하게 거절하고 있다). 가장 먼저 할 일.
   2. **엇갈리는 신호 묶음(mixedDirection) 처리 조사** — 820 하나뿐이라 표본이 부족하다. 실제로 착수한다면 골든셋에 이런 사례를 1~2개 더 추가해 재현되는지 먼저 확인한 뒤 판단한다(추측만으로 프롬프트를 고치지 않는다).
   3. 그 외(2·5·7·10 잔여, 872 역전)는 표본을 늘리거나(같은 기업을 여러 번 호출) 실제 서비스 트래픽이 쌓인 뒤 다시 보는 것이 이 12개사·1회성 데이터로 계속 미세조정하는 것보다 낫다고 판단한다.
7. **지금 멈추고 UI/서비스 구현으로 넘어가는 것이 적절한가**: **그렇다고 본다.** 이유:
   - 어려운 부분(실제 API 연동, 비용 통제, 검증·재시도·거절, thinking 비활성화, 지문·무효화)은 세 라운드에 걸쳐 반복 확인됐고 전부 안정적이다.
   - 남은 문제는 대부분 "이 고정된 12개사·1회 호출"이라는 작은 표본의 한계 안에 있다 — 화면·게시 흐름이 생겨 실제 트래픽 패턴이 쌓이면 더 대표성 있는 데이터로 AI 튜닝을 이어갈 수 있다.
   - 제품 설계 자체가 부분 커버리지를 정상 상태로 이미 반영하고 있어, 화면·게시 작업이 AI 통과율 100%를 전제로 하지 않는다.
   - 다만 **1번(규칙 8 버그 수정)과 §4.4.8 사람 검토를 최소 1회 진행하는 것**은 API 재호출 없이(사람이 이미 저장된 결과를 읽는 것) 짧게 마치고 넘어가길 권장한다 — 이 프로젝트에서 §4.4.8은 지금까지 한 번도 도달하지 못한 단계다.

**이번 세션에서 적용한 변경: 없음**(분석만 수행, API 호출·코드·프롬프트 변경 없음). 발견한 규칙 8 버그는 기존 설계 의도(spec/financial-explain.md §4.4.2 "금융형은 매출 증가율만 계산하지 않는다")에 이미 맞지 않는 **구현 결함**이라 새 설계 결정(decisions/README.md)이 필요하지 않다고 판단했다.

- **없는 비교 관련 참고(2386)**: `structure` 섹션의 "자본총계는 {total_equity}으로 자본금보다 많아요"는 두 사실 토큰(`total_equity`, `capital_stock`)의 크기를 직접 비교하는 문장이다. §4.4.3이 `structure` 섹션에 요구하는 내용이 정확히 "자본(잠식 여부)"이므로 — 자본총계가 자본금보다 적으면 잠식이라는 정의상 이 비교는 그 요구사항을 말로 푼 것이다(설계 의도와 일치, 절대금지 2번 "새 비교"는 전분기·경쟁사 대비를 말하며 같은 기간 두 재무상태 사실의 크기 비교는 해당하지 않는다). 위반으로 보지 않았지만, 이런 "사실 간 비교"가 늘어나면 §7.2/규칙 9 사전에 명시적으로 허용 범위를 적어 두는 편이 안전하다고 본다(이번엔 적용하지 않음).
- **가독성**: 5건 모두 초등 고학년 수준의 짧고 담담한 문장이었고, 흑자·적자 전환이나 부채비율 상승처럼 복잡한 조합(737)도 "매출 감소 + 이익률 하락 + 순이익은 흑자 + 부채비율 상승 + 영업적자 지속 + 과거 이력 4건"을 문장 4~9개로 무리 없이 전달했다.

### 7.4.7 820(규칙 6)·2906(규칙 2) 반복 실패 원인 조사 (2026-09-26, 새 API 호출 없음)

§7.4.6에서 반복 재현이 확인된 두 사례를 골든셋 입력(현재 코드로 다시 만든 것)과 `FinancialExplainValidator`·`FinancialExplainInputBuilder` 코드를 직접 대조해 원인을 확정했다. 새 API 호출 없이(REJECTED는 원문을 저장하지 않으므로, 2906은 이전 세션에서 확보한 진단 텍스트를, 820은 코드 추적만으로) 진행했다. **둘 다 모델 문제가 아니라 코드 결함이다.**

**820 — 규칙 6: 확인된 validator 버그**

820의 신호 묶음 `S1`(매출 증가, `revenue_yoy` sign `+`) + `S2`(영업이익률 악화, `operating_margin_diff` sign `-`)는 `groups[0].mixedDirection: true`다. §4.4.3·v1.md는 이런 묶음을 정확히 이렇게 쓰라고 **예시로 명시**한다: `"매출이 늘었지만 영업이익률은 낮아졌어요"`(한 문장에 방향이 다른 두 사실을 나란히 놓기).

`FinancialExplainValidator.checkDirection()`(191~215행)을 그대로 옮기면:

```java
String directionalSign = null;
for (TokenRef t : tokens) {
    if (t.kind().equals("fin") && (t.raw().contains("_yoy.") || t.raw().contains("_diff."))) {
        var fact = factByKey.get(t.raw());
        if (fact != null) directionalSign = fact.sign();   // ← 마지막 토큰의 부호로 덮어씀
    }
}
...
if ("+".equals(directionalSign) && hasNegativeWord) failedRules.add("6");
if ("-".equals(directionalSign) && hasPositiveWord) failedRules.add("6");
```

한 문장에 `_yoy`/`_diff` 토큰이 **두 개 이상**이면 `directionalSign`은 문장 안에서 **가장 나중에 나오는 토큰의 부호로 덮어써진다.** "매출이 {revenue_yoy}(+) 늘었지만 영업이익률은 {operating_margin_diff}(-) 낮아졌어요"라는, §4.4.3이 시키는 그대로의 문장을 검사하면: `directionalSign`이 마지막 토큰(`operating_margin_diff`, `-`)으로 덮어써지고, 문장 전체에 긍정어("늘었")와 부정어("낮아졌")가 둘 다 있으므로 `"-".equals(directionalSign) && hasPositiveWord` 조건이 참이 되어 **정확하게 쓴 문장인데도 규칙 6 위반으로 잡힌다.** 이 조건은 모델이 무엇을 쓰든 성립한다 — 즉 방향이 엇갈리는 묶음을 예시 그대로 한 문장에 쓰면 **항상, 결정적으로** 실패한다.

- **분류**
  1. 입력 데이터 특성상 정상적 어려움인가 — 아니다. "방향이 엇갈리는 묶음"은 §4.4.8이 요구하는 정상적인 골든셋 경우이고, 이 데이터 자체에 특별한 결함은 없다.
  2. 입력 구조·프롬프트 계약의 구조적 문제인가 — 아니다. 프롬프트가 요구하는 표현(나란히 놓기)은 §4.4.3의 설계 의도와 정확히 일치한다.
  3. **validator가 잘못 판단하는가 — 그렇다.** 위에서 코드로 확정했다.
  4. 모델 출력 비결정성인가 — 부수적으로만. 이 사건에서 720·5·3·10처럼 매번 다른 부가 규칙이 같이 걸리는 것은 비결정성이지만, **규칙 6 자체는 검증기 버그로 3/3라운드 결정적으로 재현된다.**
  5. 최소 수정으로 해결 가능한가 — 그렇다. 아래 권고 참고.
- **참고**: `mixedDirection: true`가 아니어도, 모델이 서로 다른 부호의 `_yoy`/`_diff` 토큰 두 개를 한 문장에 우연히 묶으면(D-45에서 권장한 "한 문장에 여러 사실을 묶어 써도 된다" 지침과 상호작용) 같은 버그가 발동할 수 있다. 716이 §7.4.4에서 한 번 규칙 6을 보인 것도 같은 메커니즘일 가능성이 있으나(716은 `mixedDirection` 묶음이 없다), 직접 원문을 확보하지 못해 단정하지는 않는다.
- **권고 (적용은 보류, 최소 수정안만 제시)**: `directionalSign` 단일 변수 대신 문장 안에 등장하는 `_yoy`/`_diff` 토큰들의 **부호 집합**을 모은다. 집합의 크기가 1이면 기존 로직 그대로 적용하고, 집합에 `+`와 `-`가 **둘 다** 있으면(= 정당한 엇갈림 문장) 이 검사를 건너뛴다. 정확히 반대로 짝지어 쓰는 것(예: 실제로는 매출이 줄고 이익률이 오른 것을 반대로 서술)까지는 이 최소 수정으로 잡지 못하지만, 토큰 자체가 정확한 사실을 가리키므로(규칙 2로 이미 보장) 그 경우 사람 검토(§4.4.8)에서 걸러진다. 검증기의 다른 부분·출력 계약·D-38~D-46은 바꾸지 않는다.

**2906 — 규칙 2: 확인된 입력 구성(Fact Table) 결함**

2906의 신호 `S2`(`FIN_OPERATING_MARGIN_CHANGE`, `PAST`, 기간 `2025-01.Q2`)는 `factKeys: []`다 — 이 기간에 등록된 사실이 하나도 없다는 뜻이다. 더 중요한 것은 `periods` 배열에 **`2025-01.Q2`가 아예 없다**는 점이다(골든셋 입력에 `periods: [{"key":"2026-01.Q2", ...}]` 단 하나뿐).

`FinancialExplainInputBuilder.build()`(113~141행)를 추적하면 원인이 나온다: `periods` 배열은 `fc.periodLabels`에서만 채워지고, `fc.periodLabels`는 `addIncomeFacts`/`addAnnualFacts`/`addBalanceFacts`/`addFlowFacts` 안의 `label(period, isAnnual)` 호출로만 채워진다 — 이 넷은 **최신 기간**과 **연간(사업연도) 기간**만 다룬다. 신호를 순회하며 `signalRefs`를 만드는 루프(118~133행)는 `signalPeriod.displayKey()`를 신호의 `period` 필드로 그대로 기록하지만, 그 기간에 대해 **`fc.label()`을 호출하지 않는다.** 그 결과 S2처럼 "최신 기간도 아니고 사업연도 대표 기간도 아닌, 자체 사실이 없는 과거 분기"에서 발생한 이력 신호는 — 신호 자체는 `signals`에 정상적으로 들어가고 `history` 섹션도 정당하게 열리지만, **그 신호의 기간을 가리킬 `{per.2025-01.Q2}` 토큰이 입력 어디에도 없다.**

그런데 v1.md의 예시가 정확히 이 패턴을 시킨다: `history: "지난 {per.2025-01.Q4}에는 {sig.S2} 신호가 있었어요."` — 신호와 그 기간을 함께 쓰라는 것이다. 2906의 경우 이 지시를 문자 그대로 따르는 것이 **입력 구조상 불가능하다.** 이전 세션에서 확보한 2906의 실제 진단 출력(사고 비활성화, D-45 이전) — 토큰을 전혀 쓰지 않고 모든 숫자를 원문 그대로 쓴 사례 — 도 이 막다른 지점에서 모델이 토큰 규율 전체를 포기한 결과로 설명할 수 있다. 실제 앱 실행에서는 매번 결과물이 달랐지만(규칙 2 하나만 걸릴 때도, 완전히 원문 숫자로 갈 때도), 4/4 라운드 모두 **`history`를 채우려 시도하면서 규칙 2(또는 그 결과인 규칙 3)에 걸렸다**는 공통점은 이 구조적 공백과 정확히 들어맞는다.

- **분류**
  1. 입력 데이터 특성상 정상적 어려움인가 — 아니다. "최신 기간이 아닌 과거 분기의 이력 신호"는 드문 경우가 아니라 이력 신호의 정의상 흔히 생기는 조합이다.
  2. 입력 구조·프롬프트 계약의 구조적 문제인가 — **부분적으로 그렇다.** 프롬프트는 "이력 신호는 반드시 그 기간과 함께 쓴다"는 전제를 깔고 있는데, 입력 구성이 그 전제를 항상 충족시키지 못한다.
  3. validator가 잘못 판단하는가 — 아니다. 존재하지 않는 토큰을 거부한 것은 정확한 판정이다.
  4. 모델 출력 비결정성인가 — 막다른 지점에 몰렸을 때 **어떻게 실패하는지**(토큰 일부 오류 vs 전면적 원문 숫자)는 비결정적이지만, **막다른 지점 자체는 결정적으로 매번 존재한다.**
  5. 최소 수정으로 해결 가능한가 — 그렇다. 아래 권고 참고.
- **권고 (적용은 보류, 최소 수정안만 제시)**: `FinancialExplainInputBuilder.build()`의 신호 순회 루프(118~133행)에서 `signalPeriod`를 계산한 직후 `fc.label(signalPeriod, isAnnual)`을 호출해, **모든 신호의 기간이 사실 유무와 무관하게 `periods`에 포함되도록** 한다(`isAnnual` 판정은 `derivePeriodKey`가 이미 분기 단위로 돌려주므로 `false` 고정이면 된다 — 이 메서드가 연간 신호에도 쓰이는지는 확인이 더 필요하다). 이것은 **입력 계약의 필드 구성(D-38)을 넓히는 것이 아니라, 이미 있는 필드(`periods`)를 신호 기간 전부에 대해 빠짐없이 채우는 것**이라 D-38의 "코드가 만든 사실표와 신호 참조뿐" 원칙, D-39의 출력 계약, D-42의 지문 구성 어느 것도 바꾸지 않는다. `Fingerprint`가 `periods` 자체를 해시에 넣지는 않으므로(신호·공시번호·unavailable만 사용, D-42) 지문에도 영향이 없다.

|---|---|---|
| 820 / 규칙 6 | validator 버그 (문장 내 다중 부호 토큰을 마지막 값으로 덮어씀) | **validator 버그 수정이 필요함** |

두 사례 모두 **D-38~D-46 설계 자체를 바꿀 필요는 없다.** "판정은 코드, 설명은 AI", "입력에 없는 비교·계산·원인·미래 서술 금지", "데이터 기준일·근거 유지", "데이터 부족은 정상 상태로 취급", "신호 방향 임의 변경 금지", "validator 안전장치 유지" 여섯 원칙 중 어느 것도 위 두 수정으로 완화되지 않는다 — 오히려 검증기(820)는 지금 **정상적으로 옳은 문장을 부당하게 거부**하고 있고, 입력 구성(2906)은 프롬프트가 이미 요구하는 것을 **빠짐없이 주지 못하고** 있어서, 두 수정 모두 기존 원칙을 더 철저히 지키는 방향이다. 새 지표·새 섹션·새 규칙을 추가하지 않는다.

**§4.4.8 골든셋 전체 자동 검증을 계속 추진해야 하는가**

- **이 두 결함을 고치지 않은 채로 골든셋 전체를 다시 돌리는 것은 가치가 낮다.** 820은 규칙 6이, 2906은 규칙 2가 구조적으로 결정적이라 — 모델이 무엇을 하든 검증기·입력 공백이 매번 같은 실패를 강제한다. 재시도 횟수를 늘리거나 프롬프트를 더 다듬어도 이 두 건은 통과할 수 없다.
- **반대로 이 두 결함을 고친 뒤에는 골든셋 전체 재검증을 계속 추진할 가치가 있다.** 두 수정은 범위가 좁고(각각 함수 하나 안쪽) 검증 규칙을 약화하지 않으며, 고치면 최소 두 기업(820·2906)이 통과 후보가 되어 5/12 → 최대 7/12까지 개선될 여지가 있다. 나머지(608·716·908·1640·2715)는 §7.4.5~§7.4.6에서 이미 "모델 비결정성"으로 분류한 잔여 위험이라 이 두 수정과는 별개로 남는다.
- 결론: **골든셋 전체 자동 검증 자체를 중단할 이유는 없지만, 이 두 결함을 먼저 고치지 않고 반복 재실행하는 것은 의미가 없다.** 다음 단계는 (1) 위 두 최소 수정에 대한 승인, (2) 수정·회귀 테스트, (3) 골든셋 재검증 순서를 권장한다.

**이번 조사에서 적용한 변경: 없음**(분석만 수행, 코드·프롬프트·API 호출 없음). 두 수정 모두 기존 설계 의도를 바로잡는 구현 결함이라 새 설계 결정(decisions/README.md)이 필요하지 않다고 판단한다 — 규칙 8 버그와 같은 성격이다.

### 7.4.8 두 수정 적용과 재검증 (2026-09-26, 사용자 승인 후 적용)

§7.4.7의 최소 수정안 두 개를 그대로 적용했다.

- 판정: **프롬프트 계약의 문제(구체적 지침 공백: 이력 신호가 여러 개일 때 같은 문장에 묶어 쓰는 것이 여전히 허용된다는 점을 명시하지 않음) — 확정된 구조적 유인 + 실제 텍스트 미확보로 최종 확정은 아님.** "그냥 모델 비결정성"으로 보지 않는 이유: 이 실패가 정확히 내가 직접 바꾼 필드(`periods`)의 확장 직후, 그 필드를 가장 많이 쓰는 회사에서 처음 나타났다는 인과관계가 뚜렷하다. 코드 수정은 불필요(상한을 올리는 것은 규칙 완화이므로 배제). 프롬프트에 "이력 신호가 여러 개면 같은 문장에 묶어 쓰거나, 오래된 신호는 개별 기간 대신 개수만 언급해도 된다" 같은 지침을 추가하는 안을 후보로 남긴다(적용 안 함).

**908 — 규칙 7 (4/4 라운드 전부 재현, 이번 두 수정과 무관하게 처음부터 있었음)**

- 실패 규칙: 규칙 7이 §7.4.1부터 §7.4.8까지 **모든 라운드에서 빠짐없이** 나타났다(다른 부수 규칙은 라운드마다 바뀌었다: 10,2,4 / 2,7 / 7,10 / 7).
- 입력: 활성 신호 4개(`S1~S4`, 그중 `S3`·`S4`는 STATE) + 이력 신호 4개(`S5~S8`, 전부 CHANGE) = 골든셋에서 **가장 신호가 많은 기업**(8개, 6개 시기 묶음). 이번 수정으로 `S5~S8`의 기간도 전부 라벨이 붙었다(2025-01.Q1·2025-01.Q3·2026-01.Q1·2025-01.Q2).
- 실제 AI 출력: 이번 라운드는 미확보. **과거 진단(사고 비활성화 직후, D-45 이전)**: "history 섹션에 이력 신호 6개(활성·이력 합계 기준)가 한 문장에 배지로 나열됨"이 관찰된 바 있다 — 신호를 개별적으로 풀어 쓰지 못하고 뭉쳐 쓰는 경향이 이미 확인된 적이 있다.
- validator 판단이 올바른가: 과거 진단상 실제로 위반(활성 신호가 history에 섞여 들어감)이 있었으므로 그 사례에서는 옳았다. 이번 라운드는 확인 못함.
- 필요한 정보가 입력에 있었는가: 그렇다.
- 반복될 구조적 이유: **있음, 그리고 재현율이 4/4로 사실상 결정적이다.** 8개 신호·6개 시기 묶음을 활성/이력으로 정확히 나눠 4개 섹션에 배분하는 조합적 복잡도가 골든셋에서 유일하게 이 정도로 큰 회사다.
- 판정: **모델 출력 비결정성(단, "막연한 비결정성"이 아니라 신호 밀도라는 구체적이고 재현 가능한 구조적 원인에 근거)**. 코드·프롬프트 수정이 이 한 회사만을 위해 정당화되지는 않는다고 본다 — 골든셋에 이 정도 밀도의 회사가 1곳뿐이라 일반화된 지침 변경의 위험(다른 회사에 영향)이 이득보다 클 수 있다. §7.4.1에서 이미 "사용자 승인 후 별도 판단" 항목으로 남긴 재시도 횟수 조정이 이 회사에는 더 적합한 완화책일 수 있다(이번엔 판단 보류).

**1640 — 규칙 5 (4/5 라운드, §7.4.4에서만 빠짐)**

- 실패 규칙: 규칙 5. `changeStatus: NONE`이고 활성 신호 둘 다(`S1` 적자 지속, `S2` 자본잠식) STATE다 — 위 "공통 패턴"의 **가장 순수한 사례**(STATE 신호만 있고 CHANGE 신호가 전혀 없어 규칙 5의 `"NONE".equals(changeStatus)` 조건이 항상 참이 된다).
- 실제 AI 출력: 이번 라운드 미확보. 다만 같은 구조(활성 STATE 신호 + `operating_loss_run` 흐름 사실)를 가진 737·820은 실제로 "이어지고 있어요"라는 안전한 표현으로 이 함정을 피해 통과했다 — **회피가 가능함을 대조 사례로 확인했다.**
- validator 판단이 올바른가: 코드는 §4.4.3 문서 그대로 동작한다 — **버그는 아니다.**
- 필요한 정보가 입력에 있었는가: 그렇다.
- 반복될 구조적 이유: **확정.** `changeStatus`가 STATE 신호만으로는 `NONE`으로 고정되는 한(D-38), 그리고 규칙 5가 신호 유무와 무관하게 `NONE`이면 금지하는 한(§4.4.3), 이 조합은 매번 같은 함정이다.
- 판정: **프롬프트 계약의 문제(확정된 구조).** 검증 규칙은 D-39 의도와 일치하므로 완화 대상이 아니다. 최소 보완 후보: v1.md에 "지속·잠식 같은 금지어 대신 '이어지고 있다' 같은 안전한 표현을 쓴다"를 명시적으로 추가한다(D-38~D-46 원칙 유지, 검증 규칙 변경 없음). 적용은 하지 않았다.

**2715 — 규칙 8 (이전엔 규칙 2, 이번에 규칙 8로 바뀜)**

사용자가 다시 확인해 달라고 한 항목이다. **결론부터: validator 오탐이 아니다.**

- 입력(코드로 확정): `unavailable`에 `{"metric":"revenue","reason":"ACCOUNT_MISSING"}`가 있다 — 2715는 매출 계정 자체가 없다(GENERAL 포맷). 그런데 `doNotMention`은 **빈 배열**이다. `FinancialExplainInputBuilder`의 `doNotMention`은 포맷이 `FINANCIAL`일 때만 "매출"을 자동으로 넣는다(`FactCollector` 생성자, 324~326행) — 2715처럼 GENERAL 포맷인데 계정이 없어서 `revenue`가 `unavailable`인 경우는 `doNotMention`에 반영되지 않는다.
- **대조군(1016)**: 1016도 매출 계정이 없다(`revenue: ACCOUNT_MISSING`, 이전 세션에서 확인된 실제 DART API 한계, §8.1). 다만 1016은 `FINANCIAL` 포맷이라 `doNotMention`에 "매출"이 **자동으로, 명시적으로** 들어간다. 1016은 4라운드 내내 안정적으로 통과했고 실제 텍스트도 매출을 전혀 언급하지 않는다("영업이익은 X, 당기순이익은 Y이었어요").
- 이 대조는 "매출 언급 금지"라는 같은 결론이 **회사 포맷에 따라 다른 세기로 전달된다**는 뜻이다 — `unavailable` 목록에만 있으면(2715) 상대적으로 약한 신호, `doNotMention`에 명시되면(1016) 강한 신호다. 규칙 8은 `unavailable`도 검사하므로 둘 다 코드상 "위반 시 걸린다"는 점은 같지만, **모델이 그 지표를 언급하려는 유혹 자체를 억제하는 힘**은 명백한 doNotMention 쪽이 더 강해 보인다(1016의 100% 회피율 대 2715의 반복 실패).
- 만약 2715의 AI 출력이 실제로 "매출"이라는 단어를 썼다면(원문 미확보라 확정 불가) — 이는 **입력에 없는(계산되지 않은) 사실을 언급한 것이 맞다.** §4.4.3의 `sales_profit` 내용 규칙("매출(규모) → 영업이익·영업이익률 순서")이 매출 계정이 아예 없는 회사에는 첫 항목부터 적용할 수 없다는 예외를 명시하지 않은 것도 배경일 수 있다(1016은 이 공백을 실제로는 잘 피해 가고 있지만, 명시적 지침은 아니다).
- validator 판단이 올바른가: **그렇다, 확정.** 계산 못 한 지표를 언급 금지하는 것은 D-38의 핵심이고, 코드는 정확히 그 판정을 했다.
- 반복될 구조적 이유: **있다(추정 근거 있음)** — GENERAL 포맷에서 매출 계정이 없는 경우 `doNotMention`이 채워지지 않는다는 비대칭이 확정된 사실이고, 1016 대비 2715의 반복 실패가 그 비대칭과 상관관계가 있다는 것은 정황적으로 강하지만, 2715의 실제 출력을 못 봤으므로 **최종 확정은 아니다.**
- 판정: **Fact Table/입력 구성의 개선 후보(추정 근거는 강하나 원문 미확보로 확정 아님).** 최소 보완안: `revenue`가 `ACCOUNT_MISSING`이면 포맷과 무관하게 `doNotMention`에 "매출"을 추가한다(1줄 조건 추가, `FactCollector` 생성자 또는 해당 지표를 `unavailable`에 넣는 지점). 이는 검증 규칙을 완화하는 것이 아니라 **금지 신호를 형식에 관계없이 일관되게 강화하는 것**이라 안전장치를 약화하지 않는다. 적용은 하지 않았다.

**§4.4.8 골든셋 전체 검증을 계속 추진할 가치가 있는가**

- 결론: **골든셋 자동 검증을 중단할 이유는 없지만, "12/12를 억지로 맞추는" 방향이 아니라 이번에 찾은 좁고 근거가 확실한 개선 후보를 검증한 뒤 남는 잔차(908 등)는 §4.4.8의 사람 검토·재시도 정책 판단으로 넘기는 것이 맞다.**

3. v1.md의 `history` 규칙에 "이력 신호가 여러 개면 묶어 써도 된다"를 재확인·강화(737, 908에 제한적 도움 가능성).

5. 908은 이번 세션 범위에서 제외하고, 재시도 횟수 조정 등 별도 논의로 남긴다.

### 7.4.10 §7.4.9 권고 3건 적용과 코드 수준 검증 ([D-51](../decisions/D-41-D-53.md), 2026-09-26, 실제 Anthropic 호출 없음)

§7.4.9의 권고 1~3(908 제외, 검증 규칙 완화 없음)을 그대로 적용해 [D-51](../decisions/D-41-D-53.md)로 결정했다. 이번 세션은 그 적용분을 코드·문서·골든셋 수준에서 검증했다 — 실제 Anthropic 재호출과 사람 검토는 하지 않았다(아래 참고).

- **적용 확인**: `v1.md`에 STATE 신호(지속·잠식 금지어 회피) 예시, `history` 묶어쓰기 지침·예시를 추가했다(`FinancialExplainPrompt.PROMPT_VERSION`을 `fx-v2`→`fx-v3`로 올림). `FinancialExplainInputBuilder`의 `FactCollector`가 GENERAL 포맷 + `revenue`가 `ACCOUNT_MISSING`인 경우도 `doNotMention`에 "매출"을 넣도록 고쳤다. 세 변경 모두 D-51 결정문과 코드가 정확히 일치한다.
- **골든셋 입력 고정 파일의 정합성 결함 발견·수정**: `GoldenSetDumpRunner`로 12개사를 현재 코드로 다시 덤프해 저장된 고정 파일과 대조한 결과, 2715(셀레스트라)의 `doNotMention`이 여전히 빈 배열로 남아 있었다 — `doNotMention` 코드 수정이 있었던 시점 이후 골든셋 파일을 다시 뽑지 않아 고정 파일이 코드보다 뒤처져 있었다. 다시 덤프해 `doNotMention: ["매출"]`로 바로잡았다. 나머지 7개 파일(716·737·820·872·908·1640·2906)의 `periods` 라벨 추가분은 이미 §7.4.8에서 반영된 것과 동일해 추가 변경이 없었다(608·810·1016·2386은 애초에 변경 없음 — 결정적 입력 확인).

- **§4.4.8 게시 조건 현재 상태**: **미충족, 변동 없음.** 마지막으로 확인된 실제 Anthropic 호출 결과는 여전히 §7.4.8의 **7/12**다. 이번에 적용한 D-51 세 가지 수정은 코드·프롬프트·골든셋 입력 수준에서는 검증했지만, **실제 모델 출력으로 716·1640·737·2715가 실제로 통과하는지는 아직 확인하지 않았다** — 이 네 건(과 708 제외 판정)의 실제 재검증에는 유효한 Anthropic 인증키로의 실제 호출과 §4.4.8의 사람 검토가 필요하며, 이는 비용이 들고 사람의 판단이 필요한 단계라 사용자 승인 없이 진행하지 않았다.

### 7.4.12 6차 결과(§7.4.11) 원인 재분석 (2026-09-26, read-only — 코드·프롬프트·골든셋 변경 없음)

§7.4.11의 5/12 결과를 사용자 요청으로 다시 분석했다. 이번엔 각 REJECTED 건의 `analysis.input_json`(이번 라운드에 저장된 실제 입력, REJECTED도 입력은 보존됨)을 직접 조회해 신호·기간·`groups`·`doNotMention`·`unavailable` 구조를 확인하고, `FinancialExplainValidator` 코드로 각 규칙의 정확한 판정 조건(§4.4.7)과 대조했다. **원문(REJECTED 출력)은 여전히 확보할 수 없다** — 아래 분석은 전부 입력 구조 + 코드 판정 조건으로 확인 가능한 것과, 그로부터의 추론을 구분해 적는다.

**D-51이 의도한 개선이 실제로 해결한 것 (코드/출력으로 확인)**:
- **STATE 서술(문제 1)**: 1640에서 확정 확인 — 실제 `structure` 출력이 "자본총계는 …로 자본금 …보다 적어요"를 썼고 "잠식" 단어가 없다(DRAFT라 원문 확보). 716도 이전엔 규칙 5(강도어)가 있었는데 이번엔 없다 — 텍스트는 없지만 실패 목록의 변화로 간접 확인된다.
- **history 묶어쓰기(문제 2)**: 716·737 모두 이전에 있던 규칙 7(이력 시제 뒤섞임)이 이번엔 없다 — 간접 확인.
- **doNotMention 비대칭(문제 3)**: 2715에서 확정 — 겨냥했던 규칙 8이 이번엔 전혀 나오지 않았다. `doNotMention`에 "매출"이 반영된 입력(§7.4.10에서 확인)으로 실제 호출한 결과이므로, 코드 수정이 모델 수준에서도 효과가 있었다고 볼 근거가 있다(다만 실제로 "매출"을 안 썼는지는 원문 미확보로 100% 확정은 아니다).

**1) 737·872의 규칙 10 — history 묶어쓰기 지침과 구조적으로 충돌하는가**

`history`의 상한은 문장 수만 3개(사실 토큰은 무제한)다. `groups`를 기간별로 세면 737·872·908 모두 **PAST 신호가 정확히 3개의 서로 다른 기간 그룹**으로 나뉜다(872: 2025-01.Q3/Q4/Q2, 737: 2026-01.Q1/2025-01.Q3/2025-01.Q1, 908: 2026-01.Q1/2025-01.Q1/2025-01.Q2). 묶어쓰기 지침대로 "기간 그룹당 문장 하나"를 완벽히 지켜도 **정확히 3문장**이 필요해 상한에 여유가 전혀 없다. 반면 v1.md의 유일한 실제 예시(101행)는 "3개 신호를 2개 기간 그룹"으로만 보여준다 — **정확히 상한과 같은 3개 그룹 사례를 한 번도 보여주지 않는다.** 도입·전환 문장 하나만 더 붙어도(예: 흔한 서두 표현) 상한을 넘긴다.
- 이것은 **부분적·조건부 구조 충돌이다.** 872는 흐름 사실도 없고 순이익 부호도 영업이익과 같아 `sales_profit`이 병목일 수 없는(2문장이면 충분) 깨끗한 사례라, 872의 규칙 10 재발(fx-v3 2/2, 이전엔 통과)은 **history 자체의 병목**으로 보는 것이 가장 개연성 높다. 737은 `revenue_yoy_run`·`operating_loss_run` 흐름 사실이 둘 다 있고 순이익 부호가 영업이익과 달라 `sales_profit`만으로도 이미 상한에 근접한다(이 병목은 §7.4.8 이전부터 있던 것) — 737의 규칙 10은 history·sales_profit 두 병목이 겹친 것이라 history 지침 하나만의 책임으로 단정할 수 없다.
- **D-45와의 비교**: D-45는 이미 "분량 상한은 사실 개수 대비 넉넉하다, 다만 예시가 부족해 문장을 나누는 경향이 있었다"고 진단하고 "묶어 쓰는 예시"로 해결했다. D-51은 같은 처방을 history에 그대로 적용했지만, D-45 때와 달리 **기간 그룹의 개수 자체가 상한(3)에 닿을 수 있다는 경우(사실 개수가 아니라 기간 개수가 병목)를 확인하지 않고 적용했다** — D-45가 세웠던 "상한 대비 여유 확인" 절차가 이번엔 생략된 것으로 보인다.
- **안전성 원칙 관점**: 규칙 10은 D-38의 "새 계산·없는 사실 지어내기 방지"류 안전장치가 아니라 §4.4.3의 분량·가독성 규정이다. 검증 실패 시 D-39("부분 게시 없음")가 그대로 작동해 사용자에게 잘못된 내용이 새는 것은 아니다 — **안전성은 지켜지고 있고, 대신 정상적으로 안전한 설명이 게시되지 못하는 커버리지 손실이 발생한다.** §4.4.8은 "이력 신호가 여러 개일 때"를 필수 골든셋 경우로 이미 요구하고 있으므로, 이 실패는 §4.4.8이 정확히 의도한 대로 게시 전에 문제를 잡아낸 것이다.

**2) 2715의 STATE 안전 서술 예시 — 입력에 없는 사실을 사실상 요구하는가**

**그렇다, 코드로 확정된다(추정이 아니다).** 2715의 `unavailable`에는 `total_equity`·`capital_stock`을 포함한 재무상태 지표 전체가 `INCONSISTENT_BALANCE`로 들어 있다(자산총계 ≠ 부채총계+자본총계, D-42/§8.3의 기존 방어). 그런데 이 회사는 `FIN_CAPITAL_IMPAIRMENT`(S3, STATE)를 여전히 신호로 갖고 있다(신호 자체는 살아있고 사실만 제거됨, D-38의 "신호와 사실은 별개" 설계와 일치). v1.md의 새 예시(97행)가 가르치는 유일한 "잠식" 안전 서술법은 정확히 이 두 사실(`total_equity`, `capital_stock`)의 비교뿐이다 — **이 회사에는 그 서술법을 쓸 재료 자체가 없다.**
- 다만 S3는 2715에서 PAST 상태라 `history`로 가고, `history`의 기존 지침(badge만으로 묶어 쓰기)으로도 서술 자체는 가능하다(사실 토큰 없이 `{sig.S3}` 배지만 쓰는 것도 허용됨) — 그래서 "예시를 못 따라서 무조건 실패한다"는 결정론적 인과까지는 아니다. 그러나 **v1.md 어디에도 "이 예시에 필요한 사실이 없을 때 무엇을 하라"는 대체 지침이 없다** — 새 예시가 예시로 보여준 패턴 하나만 강조하고 그 패턴이 성립하지 않는 경우(마침 2715가 그 경우)의 대안을 남기지 않은 공백이다.
- 특히 2715는 D-42/§8.3에서 이미 "재무상태표 불일치" 사례로 골든셋에 **의도적으로 포함된** 회사다(§4.4.8의 필수 경우 목록에 있음). 새 지침·예시를 추가할 때 이 회사처럼 이미 알려진 극단 사례들과 교차 검토하는 절차가 없었던 것으로 보인다 — 이는 지침 문구 자체의 문제라기보다 **새 프롬프트 콘텐츠를 기존 골든셋의 알려진 엣지 케이스 전체와 대조하는 절차의 공백**에 가깝다.
- **안전성 원칙 관점**: 규칙 3(토큰 밖 숫자·수량 표현)은 D-38·D-17의 핵심 안전장치(계산은 코드, 숫자는 자리표시자)와 직접 닿아 있다. 이 실패가 "모델이 사실이 없어 숫자를 직접 썼다"는 추정이 맞다면, 이는 규칙 10(분량, 커버리지 문제)보다 **원칙적으로 더 무거운 종류의 실패**다 — 다만 검증기가 이번에도 정확히 잡아 게시를 막았으므로(2/2 REJECTED), 안전장치 자체는 여전히 작동하고 있다.

**3) 1016(입력 byte-identical) — 공유 프롬프트 변경의 전역적 영향으로 설명되는가**

**가장 근거가 강한 해석이다.** 1016은 신호 0개, `history` 없음, `doNotMention`은 D-51 이전부터 이미 채워져 있었다(FINANCIAL 포맷 생성자 로직, GENERAL 전용인 이번 doNotMention 수정과 무관) — D-51의 세 변경 중 어느 것도 **입력 수준에서** 1016과 연결되지 않는다. 그런데도 fx-v2 4라운드 전부 통과 → fx-v3 2라운드 전부 규칙 3·4로 실패(정확히 같은 조합)가 뒤집혔고, 두 fx-v3 시도의 입력은 byte 단위로 동일함을 이번에 직접 재확인했다.
- 모든 입력 수준 변수를 소거했으므로, 남는 설명은 **공유 시스템 프롬프트(SYSTEM_PROMPT = style.md + v1.md, 매 호출에 동일하게 전달됨)의 변화뿐**이다. 메커니즘 후보: (a) 새 예시 2개가 프롬프트에 추가되며 모델이 참고하는 "문체 견본"이 늘어나 전반적인 서술 방식이 미묘하게 바뀌었을 가능성, (b) 프롬프트가 길어지며 앞쪽 절대 금지 목록(7번 "숫자는 토큰으로만")의 상대적 비중·주목도가 낮아졌을 가능성(LLM에서 흔히 보고되는 현상) — 둘 다 **원문 없이는 어느 쪽인지, 혹은 둘 다인지 확인할 수 없다.**
- **기존 전례와의 비교**: D-46 적용 라운드(§7.4.4)에서도 그 결정과 무관한 872·820이 나빠진 사례가 있었고, 그때는 "모델 생성의 비결정성"으로 기록했다(1회씩만 관찰). 이번 1016 사례는 **fx-v3에서 2/2로 재현**됐다는 점에서 그때보다 증거가 더 강하다 — "무관한 회사가 가끔 흔들린다"는 기존 전례를 단순히 반복 적용하기엔 재현 빈도가 더 높다.
- **안전성 원칙 관점**: 이 발견은 세 가지 중 가장 무겁게 봐야 한다. Rule 10(872·737)이나 Rule 3(2715)은 **D-51이 명시적으로 건드린 입력·문구와 직접 연결**되지만, 1016은 **D-51이 전혀 겨냥하지 않은 회사에마저 번진 효과**이기 때문이다. 이는 "좁은 범위의 프롬프트 보완도 공유 시스템 프롬프트 전체의 동작을 바꿀 수 있다"는 뜻이고, 앞으로 프롬프트를 수정할 때마다 "이 회사와 무관해 보이는 다른 회사에도 영향이 갈 수 있다"는 것을 골든셋 전체 재검증 없이는 배제할 수 없다는 방법론적 함의가 있다.

**종합 — D-51 유지 vs 수정 필요 가능성 vs 판단 보류**

| 구분 | 내용 |
|---|---|
| **유지해야 하는 부분** | 세 가지 원칙 자체(STATE 금지어 회피 서술, history 기간별 묶어쓰기, doNotMention 포맷 무관 일관화)는 각자 겨냥한 규칙(5·7·8)을 실제로 해소했다(1640·716·737의 규칙 5·7, 2715의 규칙 8 재현 없음). 규칙 10·Validator 완화나 회사별 예외는 여전히 고려 대상이 아니다 — 검증기는 이번에도 정확히 안전하지 않은/과다한 출력을 걸러냈다(부분 게시 없음, D-39 유지) |
| **수정이 필요할 가능성이 높은 부분** | history 묶어쓰기 지침의 예시가 "기간 그룹 수 = 상한"인 경계 사례를 다루지 않는다(D-45가 사실 개수에 대해 했던 "상한 대비 여유 확인"을 기간 개수에 대해서는 하지 않고 적용함). STATE 안전 서술 예시가 그 예시에 필요한 사실이 없는 경우(2715, 이미 골든셋에 있던 알려진 엣지 케이스)의 대안을 남기지 않는다. 이 둘은 **D-51의 검증된 원칙 자체가 아니라, 그 원칙을 구현한 예시·안내문의 커버리지 공백**이다 |
| **현재 정보만으로 판단하기 어려운 부분** | 1016형 "무관한 회사로의 전역 확산"이 이번 12개사를 넘어 골든셋 밖 다른 회사에도 일반적으로 나타나는지(더 넓은 표본·원문 확보 없이는 판단 불가). 737·908의 규칙 10이 history 병목·sales_profit 병목 중 어느 쪽이 실제 결정타인지(원문 없이는 분리 불가). 716·2906의 규칙 변동이 D-51 이전에도 있었던 수준의 "정상적인" 비결정성 범위 안인지, 아니면 그 범위를 넘어섰는지(비교할 D-51 이전의 다중 표본이 없다) |

**이번 세션에서 적용한 변경: 없음**(요청대로 read-only 설계 분석만 수행, 새 API 호출도 하지 않았다).

### 7.4.15 D-51 경계 조건 최소 보완 ([D-52](../decisions/D-41-D-53.md), 2026-09-26, 코드 변경 있음·API 호출 없음)

§7.4.14가 남긴 "수정이 필요할 가능성이 높은 부분" 두 가지(history 3그룹 경계, STATE 예시의 사실 부재)만 최소 범위로 보완했다. 1016형 전역 확산 문제는 이번 대상에 포함하지 않았다(§7.4.14가 판단 보류로 남긴 그대로 유지).

**적용한 변경(`v1.md`만, 검증 규칙·출력 계약·분량 상한은 전혀 건드리지 않음)**:
1. `history` 묶어쓰기 지침 뒤에 경계 규칙을 추가했다: 기간이 3개 이상이면 (1) 서두·전환 문장 없이 기간당 정확히 한 문장만 쓰고, (2) 그래도 상한(3문장)을 넘으면 가장 오래된 기간부터 개별 기간·배지 대신 **개수만** 언급해 뭉친다("그 밖에도 이전 두 시기에 신호가 있었어요"). 두 경우 모두 "언급하지 않는 값을 지어내지 않는다"를 명시했다. 정확히 3개 기간을 다루는 새 예시를 추가했다(기존 예시는 2개 기간만 보여줬다).
2. STATE 안전 서술(D-51) 문장 뒤에 전제 조건을 추가했다: 그 서술에 쓰는 사실 토큰(`operating_loss_run`, 또는 `total_equity`+`capital_stock`)이 `facts`에 없으면 비교 문장을 만들지 않고 신호를 배지만으로 참조한다. "사실이 없다고 다른 사실이나 숫자를 지어내지 않는다"를 명시했다. 재무상태표 불일치로 그 사실들이 `unavailable`인 경우의 새 예시를 추가했다(2715의 실제 상황을 그대로 재현).
3. `FinancialExplainPrompt.PROMPT_VERSION`을 `fx-v3` → `fx-v4`로 올렸다(코드 한 줄, 지문에는 영향 없음 — D-08).

**바꾸지 않은 것**: `FinancialExplainValidator`(규칙 1~10 전부), `FinancialExplainInputBuilder`(사실·신호·doNotMention 계산 로직), 골든셋 fixture, 섹션별 분량 상한(§4.4.3). 회사별 예외 코드도 추가하지 않았다 — 두 보완 모두 특정 회사가 아니라 "기간 그룹 수가 상한과 같거나 넘을 때"·"서술에 필요한 사실이 없을 때"라는 **일반 조건**으로 썼다.

**설계 의도(수정 전후 비교)**:
- 수정 전(fx-v3, D-51): "이력 신호가 여러 개면 묶어 쓴다"까지만 지시하고, 묶어도 상한을 넘을 수 있는 경우(기간 그룹 수 자체가 상한과 같음)나 안전 서술 예시의 재료가 없는 경우는 다루지 않았다 — 모델이 이 경계에서 무엇을 해야 하는지 스스로 판단해야 했다.
- 수정 후(fx-v4, D-52): 두 경계 모두 **코드가 정한 대로 확정적으로 처리하는 절차**를 프롬프트에 명시했다(D-06의 "판정은 코드" 정신을 프롬프트 안내 수준에서도 지킨 것 — 모델이 "이 상황에서 어떻게 할지" 임의로 결정하지 않고, 명시된 절차만 따르면 된다). 두 경우 모두 "언급하지 않는 값은 지어내지 않는다"는 D-38의 원칙을 그대로 재확인했다 — 즉 수정은 "더 많이 말하게" 하는 것이 아니라 "말할 수 없을 때 안전하게 줄이는 방법"을 알려주는 것이다.
- 검증 규칙은 그대로이므로, 이 보완이 실패했을 때(예: 그래도 규칙 10·3이 발생) 검증기는 여전히 게시를 막는다(D-39) — 이번 보완은 안전장치를 대신하는 것이 아니라 안전장치에 걸리는 빈도를 줄이려는 시도일 뿐이다.

**회귀 확인**: `./gradlew test` 전체 통과(변경 전과 동일 통과 건수 — `v1.md`는 리소스 파일이라 Java 로직·기존 테스트에 영향이 없고, `PROMPT_VERSION` 상수 변경도 하드코딩된 비교가 없어 영향이 없음을 확인했다). `FinancialExplainInputBuilder`·`FinancialExplainValidator` 코드 자체를 바꾸지 않았으므로 사실표·검증 판정 로직에는 애초에 회귀 대상이 없다. 골든셋 fixture(입력 JSON)도 그대로다 — 이번 변경은 AI에게 주는 지시문에만 있어 입력 구성에 영향을 주지 않는다.

- **원문은 이번에도 전부 확보하지 못했다**(8건 REJECTED, D-39·§7.7 설계상 미보존). 아래는 입력 구조로 확정 가능한 것과 그로부터의 추정을 구분한다.

- **정황 근거(추정이지만 근거가 있음)**: `v1.md`의 글자 수는 fx-v2(커밋된 기준) 10,077자 → fx-v4(현재) 13,658자로 **약 35.5% 늘었다**(D-51·D-52 두 라운드 누적). 공통 스타일 가이드(`style.md`, 705자)는 그대로다. 통과율은 이 두 증가 라운드와 정확히 같은 순서로 떨어졌다(7→5→3). 이 상관관계만으로 인과를 확정할 수는 없지만(라운드마다 다른 내용이 추가됐고 표본도 회사당 1~2회뿐), **"프롬프트에 조건부 지침을 추가할수록 관련 없는 규칙(특히 숫자 관련 규칙 3)의 실패가 늘어난다"는 패턴이 이번으로 2회 연속(§7.4.14의 1016, 이번의 810·820·2386·1016) 재현됐다.**

- **구조적 문제로 확정하기엔 부족한 이유**: 여전히 회사당 1회 표본이라, 이 넷이 fx-v4에서도 "가끔은" 통과할 수 있는지(재현율이 4/4인지 1/4인지)는 확인하지 못했다. 원문이 없어 실제로 어떤 표현이 규칙 3을 건드렸는지(정말 숫자를 썼는지, 수량 표현을 썼는지)도 모른다.

**D-38~D-52 원칙과 비교한 평가**

- **안전장치 자체는 이번에도 정확히 작동했다**: 검증기는 8건 모두 정확히 잡아 게시를 막았다(D-39 부분 게시 없음 유지). 규칙 3은 D-17·D-38의 핵심 원칙(숫자는 코드가 채우는 자리표시자로만)과 직접 연결된 규칙인데, 이 규칙이 정확히 그 역할을 했다 — 안전하지 않을 수 있는 출력이 사용자에게 새어나간 적은 없다.
- **그러나 §4.4.8의 목적(골든셋 전체가 안정적으로 통과해 게시할 수 있는 상태를 확인하는 것)과는 정반대 방향으로 움직였다.** 통과율이 두 번의 "좁은 범위 보완" 라운드를 거치며 7→5→3으로 계속 떨어졌다는 것은, **개별 문제를 프롬프트에 조건부로 덧붙이는 이번까지의 접근 자체가 전체 시스템의 안정성을 매 라운드 깎아 먹고 있다는 신호**로 봐야 한다. D-52가 "회사별 예외를 코드에 추가하지 않는다"는 원칙을 지킨 것은 옳았지만, 그 대신 **프롬프트에 조건을 계속 쌓는 방식 자체가 안전하게 확장되지 않는다**는 것이 이번 라운드로 더 뚜렷해졌다.
- **회사별 예외·검증 완화는 여전히 답이 아니다** — 사용자 지시와도 일치하고, 이번 근본 원인(공유 프롬프트 전역 효과로 추정)에 대한 해법도 아니다(개별 회사를 봐주는 것으로는 810·820·2386 같은 "다음에 또 누가 걸릴지 모르는" 문제를 막지 못한다).
- **판단**: 이번 결과만으로 "D-52가 틀렸다"거나 "즉시 되돌려야 한다"고 단정하지 않는다 — 표본이 회사당 1회뿐이고 원문도 없어 구조적 확정과 비결정성을 완전히 분리하지 못했다. 다만 "좁은 범위의 프롬프트 패치를 계속 쌓는" 전략 자체가 이번 라운드로 신뢰도를 잃었다고 본다 — 이 접근을 계속할지, 원문을 확보할 별도 수단을 먼저 마련할지, 아니면 접근 자체(예: v1.md를 통째로 다시 설계하거나, 골든셋 통과를 전제 조건으로 삼지 않는 §7.4.5의 기존 권고로 돌아갈지)를 사용자가 판단해야 한다.

**이번 세션에서 적용한 변경: 없음**(재검증만 진행, 코드·프롬프트·Validator·fixture 전부 D-52 상태 그대로 유지). 다음 조치는 사용자 판단 뒤 진행한다.

  1. REJECTED도 출력(과 첫 시도 출력·첫 시도 실패 규칙)을 저장한다 — 출력은 토큰과 공개 재무 수치에 대한 문장뿐이라(D-38) 민감 정보 위험은 낮지만, §4.4.5 저장 계약과 `FinancialExplainJob`을 바꾸는 설계 변경이다.

**7) Validator·입력·파이프라인에서 찾은 결함** [확인]

1. **Validator 문장 분리 과분할**: `SENTENCE_SPLIT`(`(?<=[요다.])(?=\s|$)`)이 "보다 ", "주요 ", "필요 "처럼 '다/요'로 끝나는 낱말 뒤 공백을 문장 경계로 본다. 컴파일된 검증기로 재현한 결과: D-51 STATE 예시 한 문장 → 2조각, D-51 2기간 history 예시 → 3조각, **D-52 3기간 history 예시 → 4조각이라 `validate()`가 규칙 10을 낸다**("그보다"만 빼면 통과). 즉 **D-52의 경계 예시는 지금 검증기로는 그대로 따라 쓰면 실패하는 예시다.** 통과한 출력 가운데 `structure`에 "…보다 많아요/적어요/낮아졌어요"를 쓴 7건(fx-v3의 608·810·820·1640, fx-v4의 608·1640·2906)은 전부 **실제 2문장이 3조각으로 세어져 상한(3)에 딱 붙어 있다**. 같은 분리 오류는 문장 단위 규칙(5·6·7)에도 영향을 준다(예: 신호 토큰과 강도어가 "보다"를 사이에 두고 다른 조각으로 갈라지면 규칙 5 오탐). 이 결함은 fx-v1부터 있었다 — fx-v2 시절 통과 원문(2386, §7.4.6)에도 "자본금보다 많아요"가 있었다. D-51·D-52는 이 표현을 권장 예시로 넣어 빈도를 높였을 수 있다 [추정].
2. **재시도 안내의 규칙 번호 불일치**: 재시도 문구는 "이전 시도가 다음 규칙 번호를 위반했다: 3"처럼 **검증기 번호(§4.4.7의 1~10)**를 주지만, 프롬프트에 번호가 붙은 목록은 "절대 금지" 1~9뿐이고 두 번호 체계가 다르다. 검증기 3(토큰 밖 숫자) → 프롬프트 3은 "새 판정 금지", 검증기 7(이력 시제) → 프롬프트 7은 "숫자는 토큰으로만", 검증기 8(doNotMention) → 프롬프트 8은 "마크다운 금지", 검증기 10은 프롬프트에 없다. **재시도가 실제 위반을 가리키지 못한다.** 모든 버전에 똑같이 있던 결함이라 fx-v2→fx-v4 하락의 원인은 아니지만, 규칙 3 실패가 재시도로 거의 구제되지 않는 것(fx-v4 구제 1/10)과 맞아떨어진다. §4.4.8의 "재시도 포함 통과"가 사실상 무작위 재추첨에 가깝다는 뜻이다.

| 문제 | 판단 | 근거 |

| 문장 분리 과분할 | **검증 기준이 아니라 계산 오류(결함)** | §4.4.7은 "문장을 요/다/. 종결로 나눠 검사"라고 정했다. 구현은 '다'·'요'로 끝나는 **모든 말** 뒤 공백을 문장 끝으로 셌다. 수정 전 검증기로 새 테스트 7건을 돌리면 5건이 실패했다 — 한 문장이 여러 문장으로 세어진 규칙 10 오탐 3건("보다", "그보다" 두 번, "주요·필요·중요"), 신호와 강도어가 갈라진 규칙 5 오탐 1건, 그리고 **변화 토큰(+)과 "줄었어요"가 "보다"를 사이에 두고 갈라져 방향 불일치를 놓친 규칙 6 미탐 1건**. 나머지 2건(실제 문장이 상한을 넘으면 규칙 10, 마침표 없는 '요' 끝도 경계)은 수정 전후 모두 통과해 기존 엄격함이 유지됨을 확인했다 |

**2) 왜 수정이 필요한가**

- 문장 분리: 통과율 문제가 아니라 **판정이 틀린 문제**다. 규칙 10·5는 정상 문장을 떨어뜨리고, 규칙 6은 실제 방향 오류를 통과시켰다 — 후자는 D-38~D-46의 "신호 방향 임의 변경 금지" 안전장치에 난 구멍이다. D-51·D-52의 권장 예시("자본금보다 적어요", "그보다 앞선")도 이 오류 때문에 그대로 따라 쓰면 실패하는 예시였다.
- 재시도 안내: 두 번째 시도가 "무엇을 고치라고 했는가"를 알 수 없으면, 재시도로 통과했는지·실패했는지가 무엇을 뜻하는지도 해석할 수 없다. §4.4.8의 "재시도 포함 통과"를 믿을 수 있는 수치로 만들기 위한 수정이다.
- 시도 기록: §7.4.9~§7.4.17의 모든 원인 분석이 "원문 미확보"에서 멈췄다. 출력 원문이 있어야 구조적 문제와 비결정성을 가를 수 있고, 검증기를 고친 뒤 과거 출력을 다시 판정할 수 있다.

**4) 기존 Validator 안전성을 어떻게 유지했나**

- **경계를 빼기만 했다.** 새 패턴은 기존 경계 가운데 "보다·주요·필요·중요"로 끝나는 자리만 제외한다. 다른 경계는 하나도 바뀌지 않는다(마침표를 빠뜨린 "…있어요 영업이익은…"도 지금처럼 나뉜다 — 테스트로 고정). 마침표 기준으로 바꾸는 대안은 이 경우를 한 문장으로 합쳐 느슨해지므로 택하지 않았다.
- **규칙별 영향**: 규칙 1·2·4·7·8·9는 문장 수에 영향받지 않거나 문서 전체·토큰 단위라 결과가 같다(규칙 3·8·9의 부분 문자열 검사는 합쳐진 문장에서도 같은 부분 문자열을 본다). 규칙 10은 실제 문장 수로 세고 상한(2·4·3·3)은 그대로다. 규칙 5는 같은 문장에 신호가 있으면 통과, 없으면 여전히 실패. **규칙 6은 토큰과 증감 어휘가 한 문장에 다시 모여 이전에 놓치던 방향 불일치를 잡는다(더 엄격해짐).**
- 제외 목록에 없는 비종결 '다/요' 낱말은 계속 경계로 세진다 — 오판이 남더라도 더 엄격한 쪽이다. 추가는 §4.4.7대로 시도 기록의 오탐 근거가 생길 때만 한다.
- 재시도 안내는 프롬프트에 이미 있는 규칙만 다시 가리키고 새 규칙·완화를 담지 않는다. AI 출력 원문은 여전히 되돌려 주지 않는다.
- 시도 기록은 게시·렌더링·무효화가 읽지 않는다. `publish()`가 상태를 확인하지 않으므로 거절된 출력을 `result_json`에 넣는 방식은 택하지 않았다. 저장 내용은 토큰과 공개 재무 수치에 대한 문장뿐이다(D-38).

**1) 현재 규칙 6이 실제로 하는 일** [확인]

- 사전은 POSITIVE = 늘·증가·높아지·개선·확대·좋아지, NEGATIVE = 줄·감소·낮아지·악화·축소·나빠지다. 최초 구현(fdb0ef4)부터 그대로다.

**2) 과거형 미검출의 정확한 범위** [확인 — 실제 사전으로 판정]

| 어간 | 잡는 형태 | 못 잡는 형태 |
|---|---|---|
| 높아지·낮아지·좋아지·나빠지 (-아/어지다) | 지고, 지는, 지면서, 지다 | **졌어요, 졌고, 졌지만**, 져서, 져, 진, 질, 짐 |
| 늘·줄 (ㄹ 어간) | 늘었어요, 늘어났어요, 늘면서, 늘어난 / 줄었어요, 줄어들었어요, 줄면서, 줄어든 | 느는, 늡니다 / 주는, 줍니다 (ㄹ 탈락. 해요체 출력에는 드물다) |
| 증가·감소·개선·악화·확대·축소 (한자어 + 하다/되다) | 모든 활용형 | 없음 |

- **원인은 어휘 누락이 아니라 음절 축약이다.** '지'에 '-어·-었·-ㄴ·-ㄹ·-ㅁ'이 붙으면 한 음절(져·졌·진·질·짐)로 줄어, "높아지"라는 문자열 자체가 사라진다.
  - 사전은 "어간은 활용형 안에 그대로 들어 있다"는 전제로 부분 문자열을 비교한다. -아/어지다 동사에서는 이 전제가 깨진다.
  - 12개 어간 중 4개가 해당한다.
- 이 4개 어간의 과거형은 드문 형태가 아니라 **출력의 기본형**이다.
  - 65개 섹션에서 높아·낮아 계열은 "높아졌"이 12개 텍스트, "낮아졌"이 9개 텍스트에 나왔다. 사전이 잡는 "높아지·낮아지" 형태는 **0개**였다.
  - 출력은 해요체 과거형으로 쓰인다. `v1.md` 60행의 예시도 "…낮아졌어요", "…높아졌어요"다.
  - 이 예시와 사전은 같은 커밋(fdb0ef4)에서 들어왔다. **프롬프트가 처음부터 검증기가 못 보는 형태를 가르쳐 온 셈이다.**
- 과거형과 별개로, 사전에 없는 동의어(올랐·상승·떨어·하락·커졌·작아졌·많아졌·급증·급감·반등·둔화·회복 등)도 전부 통과한다. 다만 65개 섹션에서는 한 번도 쓰이지 않았다.

**3) 실제 출력에서 규칙 6이 한 일** [확인: 분류·부호 대조 / 추정: 일부 문장의 회사 귀속]

| 분류 | 문장 수 | 예 | 현재 규칙 6 |
|---|---|---|---|
| A. 변화 토큰 + 사전이 잡는 어휘(늘·줄) | 4 | "매출이 {fin.revenue_yoy…} 늘었어요" | 부호와 실제로 대조함 |
| B. 변화 토큰 + "졌" 형태뿐 | 10 | "영업이익률이 {fin.operating_margin_diff…} 높아졌어요", "부채비율은 …{fin.debt_ratio_diff…} 높아졌어요"(7개 변형) | **검사가 비어 있음**(과거형 누락의 직접 영향) |
| C. 증감 어휘는 있으나 변화 토큰 없음 | 10 | "{sig.S1} 매출이 줄면서 {sig.S2} 영업이익률도 낮아졌어요"(신호만), "매출이 늘면서 영업이익률도 높아졌어요"(토큰 없음, 2906), "부채비율은 {fin.debt_ratio…}로 전기말보다 낮아졌어요"(수준 토큰), "매출이 줄어드는 흐름이 {fin.revenue_yoy_run…}째…" | 사전과 무관하게 검사 대상이 아님 |
| D. 흑자·적자 어휘만(순이익, 영업적자 흐름, 이력 서술) | 16 | "당기순이익은 {fin.net_income…}로 전년 동기 적자에서 흑자로 바뀌었어요" | 전환 신호 토큰이 없어 검사 대상이 아님 |

- **방향 표현 40문장 가운데 규칙 6이 실제로 부호와 대조한 것은 4문장(10%)이다.** A 중 "매출이 {…} 줄었고, 영업이익률도 {…} 낮아졌어요" 2문장도 실제로는 "줄" 쪽만 검사됐다.
- 40문장을 모두 골든셋 fixture의 부호·신호 방향과 대조했다. **방향이 틀린 문장은 없었다.**
  - 2906 "영업이익률이 {…} 높아졌어요": `operating_margin_diff` +14.3%p.
  - 2906 "부채비율은 …전기말보다 낮아졌어요": `debt_ratio_diff` −24.2%p.
  - "…{debt_ratio_diff} 높아졌어요" 7개 변형: 후보 회사(716·737·820·872·2386) 모두 +.
  - 토큰이 여러 회사에 공통인 문장은 같은 출력의 다른 문장(순이익 부호, 흐름 사실 등)으로 회사를 좁혔다.
- 즉 지금까지 방향이 맞았던 것은 **모델이 맞게 썼기 때문이지 검증기가 막았기 때문이 아니다.** B·C·D 36문장에서 규칙 6은 아무 판정도 하지 않았다.

부분 문자열 사전은 놓치기만 하는 것이 아니다.

| 입력 | 문장 | 규칙 6 | 이유 |
|---|---|---|---|
| 716 | "{sig.S1} 영업이익이 전년 동기 적자에서 흑자로 바뀌었어요" (S1 = 흑자 전환, POSITIVE. 맞는 문장) | **걸림** | 전환을 설명하는 가장 자연스러운 문장에 "적자"가 함께 들어 있다 |
| 716 | "부채비율은 …{fin.debt_ratio_diff…} 악화됐어요" (+5.6%p. 맞는 문장) | **걸림** | "악화"를 산술 방향 −로 본다. 부채비율 상승은 의미상 악화가 맞다 |
| 716 | 같은 문장을 "개선됐어요"로 (틀린 문장) | 통과 | 부채비율 상승을 "개선"이라 쓴 문장이 통과한다 |
| 716 | "…{fin.operating_margin_diff…} 변화하며 줄곧…" (맞는 문장) | 걸림 | "줄곧"의 "줄" |

- **전환 신호 오탐**
  - 골든셋에서 전환 신호가 있는 716(활성, POSITIVE)과 810·872(이력)에 해당한다.
  - 716은 변화 토큰 두 개가 모두 +라서, 부호가 하나로만 덮어써지던 D-53 이전 버그(§7.4.7)는 생길 수 없다. 그런데도 규칙 6이 두 번 기록됐다(§7.4.6 첫 시도, §7.4.13).
  - 원문이 없어 이 오탐이 원인이라고 단정할 수는 없다 [추정].
- **평가어 문제**
  - 사전은 좋고 나쁨을 뜻하는 "개선·악화·좋아지·나빠지"를 산술 방향인 "증가·감소"와 같은 목록에 넣었다.
  - 부채비율처럼 낮을수록 좋은 지표에서는 두 방향이 반대다. 그래서 맞는 문장이 떨어지고 틀린 문장이 통과한다.
  - 이는 spec/signals-financial.md §3.9("산술 방향은 좋고 나쁨이 아니다")와 D-47에도 어긋난다. `v1.md` 59행도 같은 목록을 준다.
  - 실제 출력에서 "개선·악화"는 한 번도 쓰이지 않았다.

**6) 기존 테스트가 못 잡은 이유** [확인]

- 불일치를 잡는 테스트(`rule6FailsWhenWordingContradictsSign`)는 "줄었어요"만 쓴다. 'ㄹ' 어간이라 과거형에도 어간 음절이 그대로 남는 형태다.
- "낮아졌어요"는 `rule6PassesForMixedDirectionSentenceWithBothSigns`에만 나온다.
  - 부호가 섞여 검사를 건너뛰는 **통과 테스트**라서, "낮아졌"을 잡든 못 잡든 결과가 같다.
  - 그래서 "낮아졌어요는 이미 다루는 표현"이라는 착시를 줬다.
- 전환 테스트는 전환 신호 + "적자로 바뀌었어요" 한 경우뿐이다. "적자에서 흑자로"처럼 두 어휘가 함께 나오는 맞는 문장은 없다.
- 테스트가 사전과 같은 전제("어간이 활용형 안에 들어 있다")로 쓰였다. 다음을 확인하는 테스트는 하나도 없다: 어간별 활용형, 신호만 있는 문장, 수준 토큰 비교, 흐름 사실, 순이익·영업이익의 흑자·적자, 오탐 사례.
- D-53에서도 같은 일이 있었다. `rule6CatchesContradictionAcrossComparativeParticle`를 "높아졌어요"로 쓰자 수정 뒤에도 실패했고, "줄었어요"로 바꾸다가 이 문제가 드러났다(§7.4.18 6).

**7) 단어를 추가하면 해결되는가**

- **B(과거형 축약)는 단어 추가로 닫힌다** [확인].
  - '지다'의 축약 음절은 지·져·졌·진·질·짐(합쇼체까지 치면 집)으로 **닫힌 집합**이다.
  - 4개 어간에 이 형태를 더하면 B 10문장이 모두 실제 검사 대상이 된다.
  - 3)의 대조로 보면 10문장 모두 부호와 맞는다. **관찰된 출력 기준으로는 새로 떨어지는 문장이 없다.** 앞으로의 출력은 다를 수 있다 [추정].
  - 주의: "높아"·"낮아"만 어간으로 두면 안 된다. "높아요·낮아요"는 수준 서술이라 오탐이 생긴다. 축약 음절까지 포함해야 한다.
- **나머지는 단어 추가로 풀리지 않는다.**
  1. 동의어는 열린 집합이다(올랐다·떨어졌다·상승·하락·커졌다 …). 목록 방식은 목록에 없는 표현을 계속 통과시킨다.
  2. 짧은 어간을 늘릴수록 부분 문자열 오탐도 는다("줄곧", "늘 같은", "오늘").
  3. 평가어(개선·악화)의 방향은 지표마다 다르다. 단어 목록이 아니라 지표별 대응표가 필요하다.
  4. "적자에서 흑자로"처럼 출발점과 도착점이 한 문장에 함께 나오는 표현은 어휘가 있는지만으로는 판정할 수 없다.
  5. C·D(40문장 중 26문장)는 사전 문제가 아니라 **어느 문장을 검사하느냐**의 문제다.
     - 신호 방향 검사와 영업이익 부호 검사는 §4.4.7에 이미 적혀 있는데 구현되지 않았다(설계와 구현의 불일치).
     - 신호 방향은 좋고 나쁨(POSITIVE/NEGATIVE)이라서, 산술 어휘와 비교하려면 유형별 대응이 필요하다. 예를 들어 부채비율 급등은 NEGATIVE인데 맞는 표현은 "높아졌어요"다.

**8) D-38~D-53 원칙과 비교**

- **원칙**
  - 방향·심각도는 코드가 판정하고(D-06·D-15), AI는 그 결과를 설명만 한다(D-38 입력, D-39 출력 형식).
  - 숫자는 토큰으로 코드가 채우고(D-17·D-39), 강도 표현은 신호가 있을 때만 쓴다(D-39·규칙 5).
  - 이 구조에서 **AI가 직접 고르는 방향 정보는 방향 어휘뿐이다.** 그것이 코드의 판정과 같은지 보장하는 장치가 규칙 6이다.
- **현재 상태**
  - 코드는 부호와 신호 방향을 정확히 계산한다. 그러나 실제 출력의 90%(36/40)에서 AI가 쓴 방향 어휘는 그 판정과 대조되지 않는다.
  - 즉 "코드가 판정하고 AI는 설명만 한다"는 원칙이 **구조로 보장되지 않고 모델의 준수에만 기대고 있다.**
  - D-53의 문장 분리 결함과 같은 부류다. 기준은 맞게 적혀 있는데 구현이 그 기준을 다 따르지 못한다.
- B(과거형)는 원칙이나 기준을 바꾸는 문제가 아니라 구현 결함이다. C·D·평가어·오탐은 §4.4.7 문구만으로는 판정 방식이 정해지지 않는 부분이 있어, 고치려면 설계 결정이 필요하다.

**9) 판단 — 지금 고칠지, 현재 범위에서 유지할지**

- **막아야 하는 위험인가: 예.**
  - 방향이 틀린 문장은 규칙 6이 존재하는 이유다. 실제 입력에서 실제 검증기가 그런 문장을 통과시키는 것을 재현했고, 게시되면 숫자·배지와 정반대인 방향이 문장으로 나간다.
  - 다만 **관찰된 실제 출력 40문장에서 방향 오류는 0건**이다. 지금까지의 골든셋 결과가 이 결함 때문에 틀렸던 것은 아니다.
- **B(과거형 축약): 다음 실제 재검증(fx-v5) 전에 고치는 것을 권한다.**
  1. **자동 검증과 사람 검토의 분리**: 이대로 재검증하면 방향 표현 대부분이 검사되지 않은 채 "자동 검증 통과"가 된다. 방향 오류를 사람 검토만 잡게 되어, 자동 검증이 맡아야 할 일을 사람 검토가 떠안는다. 골든셋은 §4.4.7대로 검증기의 오탐·미탐을 재는 자리인데, 출력의 기본형을 못 보는 규칙 6으로는 그 측정 자체가 안 된다.
  2. **비교 가능성**: D-53으로 검증기가 이미 바뀌었다(`fxv-2`). fx-v5 뒤에 또 바꾸면 검증기 변경의 효과가 두 번 섞인다. 재검증 전에 함께 반영하면 fx-v5 결과를 한 기준으로 읽을 수 있고, 시도 기록의 `validatorVersion`으로 구분도 된다.
  3. **범위와 위험**: 규칙 6 사전의 활용형 보강과 어간별 테스트만 바꾸면 된다. 판정은 더 엄격해지기만 하고, 관찰된 출력 기준으로 새로 떨어지는 문장이 없다.
  - **새 D-결정은 필요하지 않다고 판단한다.** §4.4.7의 기준(기본형 "높아지다")을 바꾸지 않으며, 사전 조정은 §4.4.7·§4.4.8이 이미 운영 절차로 정해 두었다. 적용할 때는 D-53 본문은 수정하지 않고, 결과를 이 계획서와 code-guide §15에 남긴다.
- **C·D·평가어·전환 오탐: 지금은 고치지 않고 유지하되, 별도 설계 판단 대상으로 둔다.**
  - 판정 방식이 정해지지 않은 부분이 모두 설계 결정이다(G2~G5): 신호 방향과 산술 방향의 대응, 흑자·적자 도착점 판정, 토큰 없는 방향 서술의 허용 여부, 방향을 코드가 렌더링할지. 게다가 바꾸면 `v1.md` 예시(60·77행)와도 충돌한다.
  - 관찰된 출력에서 이 경로의 방향 오류는 0건이다. fx-v5부터는 시도 기록으로 거절 원문까지 볼 수 있으니, 전환 오탐(716 등)이 실제로 몇 번 나는지 원문으로 확인한 뒤 판단하는 편이 근거가 있다.
  - 단, **§4.4.8 통과 뒤 게시를 켜기 전에는 반드시 결론을 내야 한다.** 운영에서는 규칙 6이 방향 오류를 막는 유일한 자동 장치이기 때문이다. 이 결론은 D-결정으로 기록한다.

**이번 단계에서 적용한 변경: 없음.** Validator·`v1.md`·`style.md`·fixture·decisions/README.md는 모두 그대로이고, 새 API 호출도 하지 않았다. 재현은 세션 임시 폴더의 jshell 스크립트로 컴파일된 클래스를 실행했을 뿐이다.

- 구조적 현상이다. 같은 시스템 프롬프트에서 12개 중 10개가 같은 자리에서 같은 방식으로 실패했다.

**B. 과거 기간을 가진 활성 신호의 `history` 배치** [확인: 원문·입력 / 추정: 메커니즘]
- 걸린 신호는 모두 활성인데 `period`가 최신 기간이 아니다.
  - 716 S2: 자본잠식(STATE), 2025 Q2.
  - 737 S3: 부채비율 급등(CHANGE). 같은 회계연도라 활성이고, 기간은 2026 Q1.
  - 908 S3: 영업적자 지속(STATE), 2025 Q1.
  - 908 S4: 자본잠식(STATE), 2025 Q3.
- 모델은 이 신호를 같은 기간의 이력 신호와 한 문장에 묶어 `history`에 썼다. 예(737): "지난 {per.2026-01.Q1}에는 {sig.S3} 신호와 {sig.S7} 신호, {sig.S4} 신호가 있었어요".

- 비결정성이 아니라 계약 충돌이다.
  - 섹션 배치는 상태로 정한다(D-39, 규칙 7).
  - 그런데 입력의 `groups`는 기간·주제로 나뉘어 있다.
  - 프롬프트의 `history` 지침(D-51·D-52)은 "같은 기간에 묶인 신호들을 한 문장에" "기간 하나당 정확히 문장 하나"를 요구한다. 과거 기간을 가진 활성 신호가 그 기간의 이력 신호와 함께 묶이도록 유도된다.
  - 737 S3는 STATE가 아니라 CHANGE라서, D-51의 STATE 서술 불릿으로는 다룰 수 없는 경우다.
- 재시도 안내로는 1/3만 고쳐졌다. 716은 S2를 `structure`로 옮겼다. 737은 같은 S3를 되풀이했다. 908은 S4를 옮긴 대신 S3를 넣었다.

**C. `structure` 사실 토큰 상한과 섹션 내용의 긴장** [확인]
- 이번 규칙 10은 5건 모두 **사실 토큰 수**에서 났다. 문장 수 초과는 22회 중 0건이다.
- 넘친 조합은 5건 모두 같다: 부채비율 셋(`debt_ratio`·`debt_ratio_prior_end`·`debt_ratio_diff`) + 자본 비교 둘(`total_equity`·`capital_stock`).
- 716a2는 `sales_profit`도 7/6이었다. 영업이익률 셋 + 매출·영업이익 + 순이익 둘이다.
- §4.4.3의 `structure` 내용("부채비율 → 자본(잠식 여부)")을 온전히 쓰면 3 + 2 = 5인데 상한은 4다.
- 자본총계·자본금 비교는 D-51이 자본잠식 서술용으로 넣은 예시다. 모델은 이 비교를 **잠식이 아닌 회사에도** 쓴다: `structure` 20개 가운데 17개가 이 짝을 토큰으로 썼고, 표시 값을 복사한 1016a1까지 치면 18개다("…자본금보다 많아요").
  - §7.4.17이 원문 없이 세웠던 "특정 입력용 지침이 무관한 입력으로 번진다"는 가설을 원문으로 확인한 사례다.
- 부채비율 사실이 있는 `structure` 14개 가운데 5개가 5토큰이고, 나머지는 하나를 빼 3~4토큰이다. 같은 회사에서도 시도마다 갈린다(737 4→5, 872 4→5, 820 5→4, 2906 5→3).
- 그래서 분류는 "상한과 내용이 충돌하는 계약(4)이 경계에서 무작위로 드러나는 것(5)"이다. 검증기 오탐은 아니다(상한은 계약값이다).
- 재시도 안내(규칙 10)는 첫 시도에서 걸린 2건을 모두 고쳤다(820·2906). 그러나 다른 규칙으로 재시도한 2회차에서 3건이 새로 넘쳤다(716·737·872).

**D. 1016의 규칙 4** [확인]
- 2회차 `overview`가 "당기순이익은 {fin.net_income…} 수준이에요"를 쓰고 `sales_profit`이 같은 토큰을 다시 썼다.
- D-46의 NONE 우선순위 (2)는 "겹치지 않는 다른 원값(예: `net_income`)"을 예로 든다. 그런데 매출이 없는 금융형(1016)은 `sales_profit` 자체가 영업이익·순이익이라 이 예가 곧 겹치는 사실이다.
- fx-v3에서도 1016은 규칙 4였다(§7.4.11). 이 회사에 대해서는 구조적이다. 프롬프트 예시가 매출이 있는 일반형을 전제한 문제(4)이고, 모델도 "반복 금지"를 어겼다(1).

**E. 검증기가 놓친 오류 — 변화량을 수준처럼 씀** [확인]
- 통과본 두 개의 `overview`가 D-46 프롬프트 예시("영업이익률은 {fin.operating_margin_diff…} 수준이에요")를 그대로 따랐다.
  - 608: 렌더링하면 "영업이익률은 **+1.5%p 수준**이에요"가 된다. 실제 영업이익률은 15.0%이고, +1.5%p는 전년 대비 변화다.
  - 1640: "영업이익률은 **+111.1%p 수준**이에요"가 된다. 실제 영업이익률은 −359.1%라 정반대 인상을 준다.
- 사실 이름은 "영업이익률 변화"인데 문장은 수준을 말한다. 규칙 6은 증감 방향만 보므로 잡을 수 없다(설계상 대상 밖).
- §4.4.8 사람 검토의 "사실 일치" 항목에서 떨어질 문장이다.
- 원인은 모델의 창작이 아니라 **프롬프트 예시 자체**다(D-46이 넣은 NONE 예시).
- 2386은 2회차에 "부채비율은 {…_diff} 수준의 **변화**를 보였어요"로 바르게 썼다.

**그 밖의 방향·비교 서술 — 사람 대조** [확인]
- 검증기가 대조하지 않는 서술을 모두 입력 사실과 맞춰 봤다.
  - 신호 + 수준 토큰 문장: "{sig.S2} 영업이익률은 {…}로 높아졌어요".
  - 토큰 없는 증감: "매출이 줄면서 영업이익률도 낮아졌어요".
  - 흑자·적자 서술: "적자에서 흑자로 바뀌었어요", 순이익의 흑자·적자.
  - 자본총계·자본금 대소 비교 18개(표시 값 복사 1건 포함).
  - "당기순이익은 영업이익과 방향이 달랐어요 / 같은 방향이었어요".
- **틀린 것은 없었다.**
- 1640 `structure`는 배지 하나("{sig.S2}")만으로 된 문장으로 끝난다. 규칙 위반은 아니지만 읽기에 어색하다.
