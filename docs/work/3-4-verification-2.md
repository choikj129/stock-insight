# 3-4 검증 기록 2 (§7.4.22~)

> AI 재무 쉬운 설명의 실제 확인·검증 회차 원문(D-54 이후). **새 회차는 이 파일 끝에 `### 7.4.N` 제목으로 이어 쓰고, 목록은 [3-4 작업 기록](3-4-financial-explain.md#검증-회차-목록)에 한 줄 더한다.**

### 7.4.22 섹션 배정 계약 결정 ([D-54](../decisions/D-54-D-59.md), 2026-09-26, 설계만 — 코드·프롬프트·Validator·InputBuilder·fixture 변경 없음, API 호출 없음)

§7.4.21의 후보 (i)~(iii)을 하나의 계약으로 정했다. 세 문제는 원인이 같다. "코드가 섹션을 정한다"(D-39)가 섹션 목록까지만 적용되고, 섹션 안에서 어떤 신호·사실을 쓸지는 AI의 선택으로 남아 있었다. 그래서 회사별 수정이 아니라 **신호·사실의 섹션 배정을 코드가 한다**는 한 원칙으로 정리했다.

**결정 요약** (자세한 내용은 D-54, spec/financial-explain.md §4.4.2·§4.4.3·§4.4.7)

| 문제 | 계약 |
|---|---|
| (i) 과거 기간을 가진 활성 신호 | 신호마다 코드가 `section`을 정한다(활성 → 주제 섹션, 이력 → `history`). AI 입력의 `period`는 설명 기준 기간이다(활성은 최신 기간). 활성 신호의 `factKeys`는 최신 사실을 가리킨다. 묶음은 한 섹션 안에서만 만든다 |
| (ii) `structure` 구성·상한 | 상한 4는 그대로 둔다. 코드가 부채비율 + 변화량, 그리고 활성 자본잠식일 때만 자본총계·자본금을 배정한다(최대 4). 전기말 부채비율·자산·부채 총계·잠식률은 AI 입력에서 뺀다. 사실끼리의 비교는 코드가 판정한 경우(잠식 신호)에만 쓴다 |
| (iii) D-46 예시 | 개요 사실은 코드가 지정한 변화량 사실뿐이다(`sectionFacts.overview`). "겹치지 않는 원값(예: `net_income`)" 경로와 "{…_diff} 수준이에요" 예시를 없앤다. 변화량은 증감 어휘와 함께 쓴다 |
| 검증(구현 시) | 규칙 6 확장(변화량 토큰에는 같은 부호의 증감 어휘가 필수), 규칙 7 일반화(신호는 `overview`와 자기 `section`에서만), 새 규칙 11(개요·`structure`는 배정된 사실만). 모두 더 엄격해지는 방향이고 상한 값은 그대로 |

**근거가 된 사실** [확인: 로컬 DB·fx-v5 입력]
- 활성 신호 중 발생 기간이 최신보다 앞선 것: 영업적자 지속 421/421, 자본잠식 67/77, 부채비율 급등 59/110. 모두 485개사이고, 그중 429개사는 이력 신호도 있어 `history`가 열린다. 골든셋만의 문제가 아니다.
- 골든셋에서 이런 신호 6개는 모두 `factKeys`가 비어 있었다. 발생 기간의 재무상태 사실이 입력에 없기 때문이다.
- 일반형에는 재무상태 사실이 7~8개 넘어가는데 `structure` 상한은 4다. 새 구성은 최대 4다.

**기존 결정과의 관계**
- 대체하는 것: D-46의 우선순위 (2)와 두 예시("일부 대체됨").
- 구체화하는 것(상태에 표기): D-38(입력 계약), D-39(섹션은 코드), D-51(자본 비교 조건, 이력끼리 묶기).
- 바뀌지 않는 것: D-40·D-42(지문·무효화), D-45, D-52, D-53(규칙을 추가하면 재시도 안내·버전을 함께 고치는 절차를 따른다), 신호 저장(D-29·D-35·D-36), 출력 계약(네 섹션), 게시 조건(§4.4.8).
- D-50의 `cash_flow`도 같은 원칙으로 배정한다.

**다음 재검증에서 볼 것** (구현 뒤. 이번에는 판단만 기록)
- fx-v5 결과와 통과 수를 바로 비교하지 않는다. 입력 구성(`fx-input-3`)·프롬프트(`fx-v6`)·검증기(`fxv-3`)가 함께 바뀌고, 새 규칙 6·11은 fx-v5의 통과본 일부도 떨어뜨리는 방향이기 때문이다. 예: 608·1640의 "수준이에요", 2386의 "수준의 변화를 보였어요".
- 계약이 의도대로 동작하는지는 다음으로 확인한다.
  - 716·737·908에서 활성 신호가 `history`에 나오지 않는다(규칙 7).
  - `structure`의 사실 토큰이 구조적으로 4개를 넘지 않는다(규칙 10).
  - 1016의 규칙 4가 사라진다.
  - 변화량을 수준처럼 쓴 문장이 규칙 6에서 잡힌다.
- 이 결정이 다루지 않는 것: 첫 시도의 기간 라벨·표시 값 복사(§7.4.21 A), G2~G5, 2715 입력의 자기모순. 첫 시도 준수율은 따로 봐야 한다.

### 7.4.23 D-54 구현 (2026-09-26, 코드 변경 있음·실제 API 호출 없음)

§7.4.22의 계약을 코드에 반영했다. 실제 Anthropic 재검증은 하지 않았다(지시대로).

**1) 구조를 어떻게 바꿨나** — 섹션 배정을 입력 구성기 한 곳에서 정하고, 입력에 적고, 검증기가 그 입력을 그대로 검사하게 했다.

| 파일 | 변경 |
|---|---|
| `FinancialExplainInput` | `SignalRef.section`, `Group.section`, `sectionFacts`(섹션 → 사실 키, `overview`·`structure`만)를 추가했다. 신호 `period`의 뜻은 설명 기준 기간이다 |
| `FinancialExplainInputBuilder` (`fx-input-3`) | 활성 신호는 최신 기간·주제 섹션, 이력 신호는 발생 기간·`history`로 둔다. 활성 신호의 `factKeys`는 최신 사실을 가리킨다. 묶음은 (섹션, 기준 기간, 주제)로 만들고 활성 변화 → 활성 상태 → 이력 순으로 정렬한다. 재무상태 사실은 고정 구성(부채비율·변화량, 활성 자본잠식일 때 자본총계·자본금, 부채비율이 없거나 금융형이면 자본총계)만 만든다. 개요 사실은 CHANGED면 첫 묶음 변화량, NONE이면 우선순위 하나를 지정하고 `structure`와 겹치지 않게 뺀다. 섹션은 배정된 사실·신호가 있을 때 연다 |
| `FinancialExplainValidator` (`fxv-3`) | 규칙 6: 변화량 토큰에는 같은 부호의 증감 어휘가 필수(부호가 섞이면 두 방향). 규칙 7: 신호는 자기 `section`에서, 활성은 `overview`에서도. 규칙 11(새): `overview`·`structure`는 `sectionFacts` 안의 사실만. `section`·`sectionFacts`가 없는 과거 입력은 이전 판정 |
| `FinancialExplainPrompt` (`fx-v6`), `v1.md` | 입력 설명에 `section`·`sectionFacts`를 넣었다. 개요는 `sectionFacts.overview`만 쓰고 변화량은 증감 어휘와 함께 쓴다. `structure`는 `sectionFacts.structure`와 자기 섹션 신호만 쓰고, 자본 비교는 두 사실이 배정됐을 때만 한다. `history`에는 이력 신호만 둔다. D-46 예시 두 개("{…_diff} 수준이에요", "예: `net_income`")를 D-54 형태로 바꿨다. 재시도 안내의 규칙 6·7을 고치고 규칙 11을 더했다 |
| 골든셋 fixture 12개 | `GoldenSetDumpRunner`로 로컬 DB에서 다시 만들었다(AI 호출 없음). 입력 계약이 바뀌었으므로 다음 재검증의 "저장 입력 = fixture" 대조 기준을 새 계약으로 맞춘 것이다 |

바꾸지 않은 것: 출력 스키마(네 섹션), `style.md`, 규칙 1~5·8~10의 판정과 상한, 문장 분리, 지문 구성 방식(입력 구성 버전만 오른다), 무효화(신호 자연키·사실 기간 기준), 게시 경로(`publish=false`), 신호 계산·저장(`signal` 패키지).

**2) D-54에서 모호했던 부분을 어떻게 판단했나**

| 쟁점 | 판단 | 근거 |
|---|---|---|
| 뺀 재무상태 사실을 값 스냅샷에 남기나 | 남기지 않는다. D-54 본문의 "스냅샷에는 그대로 있다"를 정정했다 | 스냅샷은 AI 토큰을 렌더링하기 위한 것이다(§4.4.5). 입력에 없는 사실을 담으면 입력과 스냅샷의 대응이 깨지고, 쓰일 곳이 없다. 화면은 재무 요약(코드)에서 보여 준다 |
| `sales_profit`도 배정하나 | 배정하지 않는다(D-54 범위대로). 규칙 11은 `sectionFacts`에 키가 있는 섹션만 본다 | D-54가 개요·`structure`·신호만 배정했고, 연간 사실처럼 두 섹션이 함께 쓰는 사실이 있다. 재검토 조건(토큰 초과 반복)을 그대로 둔다 |
| 개요에 지정한 사실을 `sales_profit`이 써도 되나 | 막지 않는다. 한 번만 쓰는 규칙 4로 충분하다 | 개요가 배지만 쓰고 변화량을 안 쓸 수도 있다. 그때 손익 섹션이 쓰는 것은 계약 위반이 아니다 |
| 재무상태표 불일치 + 활성 자본잠식 | 사실 없이 `structure`를 연다(배지만) | D-54 표의 네 번째 줄과 D-52("사실이 없으면 배지만")를 그대로 따른다. 섹션을 열지 않으면 활성 신호가 갈 곳이 없어 규칙 7과 충돌한다 |
| 과거 입력 JSON | 새 필드가 null이면 검증기는 이전 판정 | `AnalysisRepository`가 과거 행의 `input_json`을 레코드로 읽는다. 과거 결과는 다시 검증하지 않지만 null에서 예외가 나지 않아야 한다 |
| "매출 증가율은 {…}예요" | 통과로 둔다 | 사실 이름의 "증가"가 증감 어휘로 세진다. 증가율을 값으로 말하는 것은 사실과 맞다. 막을 대상은 수준 지표 이름에 변화량을 붙인 문장이다(§7.4.21 E: "영업이익률은 {…_diff} 수준이에요") |

**3) 검증**

- `./gradlew test`: **223건 전부 통과**(기존 208 + 새 15, 실패 0).
  - 새 테스트: 검증기 9건(`d54ContractOutputPasses`, 변화량을 수준으로 쓴 문장, 부호가 섞인 문장의 두 방향, 활성 신호가 자기 섹션을 벗어남, 활성은 개요 허용·이력은 불허, 개요·`structure`의 배정 밖 사실, 배정 없는 섹션, 과거 입력), 입력 구성 6건(code-guide/README.md §14).

**4) 보안·데이터 무결성**

- AI로 가는 입력에는 여전히 공시번호·내부 ID·원천 계정명이 없다(기존 테스트 유지). `sectionFacts`에는 사실 키만 들어간다. 새 자유 문자열은 없어 프롬프트 주입 경로도 늘지 않았다.
- 입력은 계속 결정적이다(같은 데이터 → 같은 JSON, `buildIsDeterministicForSameData`). `sectionFacts`는 삽입 순서를 지키는 불변 맵이다.
- 지문: 입력 구성 버전이 `fx-input-3`으로 바뀌어 기존 초안은 다음 실행에서 다시 생성 대상이 된다(D-42의 의도대로). 게시본은 없다(`publish=false`).
- 무효화: 게시본의 스냅샷이 참조한 신호 자연키와 사실의 기간·기준으로 판정하므로 영향이 없다. 신호 스냅샷은 발생 기준일(`occurredOn`)을 그대로 담아 배지 → 타임라인 연결도 그대로다.
- 과거 행: 새 필드가 null이어도 읽기·검증에서 예외가 나지 않는다(`legacyInputWithoutSectionFieldsUsesStatusRuleAndSkipsRule11`).
- 로컬 DB는 바꾸지 않았다. fixture 덤프 앱은 끝난 뒤 종료했다.

**5) 남은 것**

- 실제 Anthropic 재검증(프롬프트 `fx-v6`, 검증기 `fxv-3`). fx-v5 통과 수와 바로 비교하지 않는다(§7.4.22). 볼 것은 이렇다.
  - 716·737·908의 규칙 7이 사라지는지.
  - `structure`의 규칙 10이 사라지는지.
  - 1016의 규칙 4가 사라지는지.

**G. 716 전환 신호 오탐** [확인]

**K. `history`의 시간 순서 오류 — 검증기가 놓친 오류** [확인]
- 908 최종 초안의 `history`는 이렇다: "지난 {per.2026-01.Q1}에는 … {per.2025-01.Q1}에는 {sig.S6} … 그보다 앞선 {per.2025-01.Q2}에는 {sig.S7} 신호가 있었어요". 2025년 2분기는 1분기보다 **뒤**이므로 "그보다 앞선"은 사실과 다르다.
- 원인: 입력 `groups`의 순서가 시간순이 아니다. 묶음 정렬은 "최고 심각도 → 최근 기간"이다(D-54가 "기존대로" 유지). 그래서 `history` 묶음이 2026 Q1(HIGH) → 2025 Q1(S6, HIGH) → 2025 Q2(S7, MEDIUM) 순으로 들어간다. 모델은 이 순서를 따르면서 D-52 예시의 "그보다 앞선" 틀을 붙였다.
- 908a1은 시간순(2026 Q1 → 2025 Q2 → 2025 Q1)으로 바르게 썼다. 같은 입력에서 갈렸으므로 겉으로는 (6) 비결정성이다. 그러나 원인은 (4) 입력 계약(`history` 묶음이 시간순이 아님)과 (5) 프롬프트 예시(시간순을 전제한 "그보다 앞선")의 조합이다.
- fx-v5에서는 이 형태가 0건이었다. fx-v5의 908 `history`에는 활성 신호가 섞여 묶음 구성이 달랐다. D-54가 활성 신호를 빼면서 이력 묶음만 남았고, 그 결과 심각도 순서와 시간 순서가 어긋나는 입력이 처음 생겼다. D-54가 묶음 정렬을 "기존대로"로 두면서 이 상호작용을 따져 보지 않았다.

**2) 질문별 판단**

**(1) 규칙 6이 일반 증감과 흑자·적자 전환을 같은 방식으로 판단하는 것이 맞나 → 아니다.** [확인]
- 증감은 한 변화량의 방향이다. 어휘 하나와 부호 하나를 대조하는 지금 방식이 맞고, 실제로 잘 동작한다: fx-v6에서 변화 토큰 문장 33/33이 부호와 맞았고 오탐은 0이다.
- 흑자·적자는 수준의 상태다. 전환 문장에는 출발·도착 두 상태가 들어간다. "도착 상태와 반대 단어가 있으면 실패"라는 검사는 가장 정확한 문장("적자에서 흑자로")을 떨어뜨린다(716 2/2).
- 도착점 패턴을 더하는 개별 패치로는 두 상태가 다른 틀로 나오는 문장의 뒤바뀜을 가를 수 없다. 예: 872의 "적자였던 전년 동기와 달리 흑자를 냈어요"(같은 "…와 달리" 틀이 통과본 4곳).
- 결론: 흑자·적자는 코드가 부호로 정하는 사실이다(D-47). 상태 사실로 입력에 주고, 글자는 코드가 렌더링한다.
  - "흑자"·"적자"는 조사가 같아(둘 다 받침 없음) G4를 미룬 활용·조사 문제가 없다.
  - 증감 동사는 지금처럼 AI가 쓰고, 신호 유형별 산술 방향 대응표로 신호만 있는 문장까지 대조를 넓힌다.

**(2) `history` 순서는 입력 구성에서 보장하나, AI 설명 계약에서 보장하나 → 입력 구성이 보장하고, 검증기는 순서만 확인한다.** [확인]
- 기간 사이의 선후는 코드가 아는 사실이다(기간 종료일). AI가 기간 키로 정렬하면 새 계산이 된다(결산월이 다른 키, 같은 해의 연간·분기).
- 원인은 입력이었다. 묶음 순서가 "심각도 → 최근성"이라, 908은 2025 Q1(HIGH)이 2025 Q2(MEDIUM)보다 먼저 왔다. 모델은 입력 순서에 D-52 예시의 "그보다 앞선"을 붙였다. 같은 입력에서 908a1은 스스로 시간순으로 고쳐 썼다.
- "고르는 순서"(중요도, 최대 4개)와 "서술 순서"(시간)를 나눈다. D-52의 "가장 오래된 기간부터 뭉친다"도 시간순을 전제했다.
- 프롬프트 지시만으로 요구하는 방식은 D-54의 활성 신호 배치 문제(입력이 반대로 유도하면 재시도 안내로 1/3)와 같은 구조라 택하지 않는다.
- 입력을 시간순으로 주면 검증기는 `history`의 기간 토큰이 입력 순서대로인지만 기계적으로 보면 된다(규칙 7 확장).

**(3) `sales_profit`도 코드가 사실을 배정해야 하나 → 그렇다. `history`까지 포함해 모든 섹션을 배정한다.** [확인: 모의 / 추정: 효과]
- D-54의 재검토 조건("`sales_profit` 토큰 초과가 반복되면")이 충족됐다(fx-v6 첫 시도 6/12).
- 원인은 `structure`(§7.4.21 C)와 같다. 상한보다 많은 재료를 주고 선택을 맡겼다.
- §4.4.3이 조건을 정해 둔 순이익 문장도 AI가 판정했다(820·872가 부호가 같은데 넣음).
- `history`는 사실을 배정하지 않는다(배지와 기간만). 근거는 두 가지다.
  - 통과본의 `history`는 모두 사실 없이 썼고, 사실을 쓴 시도(872a1)는 반복으로 실패했다.
  - D-54가 "모든 사실 배정"을 기각한 이유("연간 사실을 `sales_profit`과 `history`가 함께 씀")가 이것으로 없어진다.
- 그러면 입력 사실표는 배정된 사실의 합집합이 되고, 한 사실은 한 섹션에만 있다. 규칙 4가 구조적으로 성립한다.
- 부수 효과: 2715의 입력 자기모순이 해소된다. 이력 신호의 `factKeys`가 비고, 금지 용어와 모순되는 사실은 배정하지 않는다.

**(4) 코드가 판정하지 않은 비교를 막는 데 현재 계약의 빈틈은 무엇인가** [확인]
- (a) **정의의 빈틈**: 프롬프트 절대 금지 2의 "새 비교"는 외부 비교(전분기·경쟁사·업계)만 들었다. 입력 안 두 값의 비교를 막은 것은 D-54의 `structure` 자본 비교 한 곳뿐이다.
- (b) **재료의 빈틈**: 입력이 비교 재료는 주고 관계는 주지 않았다.
  - `revenue_prior`·`operating_margin_prior`는 변화량과 같은 정보라 필요 없는 재료다. D-54가 `debt_ratio_prior_end`를 뺀 것과 같은 이유다.
  - `sign` 필드는 상태를 AI가 글자로 옮기게 했다.
- (c) **검증의 빈틈**: 규칙 6은 변화 토큰이 있는 문장만 본다. 신호만 있는 문장, 흑자·적자 문장, 비교 어휘 문장은 대조하지 않는다. §7.4.19 분류로는 방향 표현의 90%가 대상 밖이었다.
- (d) **예시의 빈틈**: 프롬프트 예시 자체가 대조할 수 없는 형태를 가르친다.
  - "{sig.S1} 매출이 늘면서 영업이익률도 높아졌어요": 배지 하나로 두 지표의 증감을 말한다.
  - "적자에서 흑자로": 글자로 쓴 상태.
- (e) **순서의 빈틈**: 시간 관계 어휘("그보다 앞선")의 근거인 순서를 입력이 보장하지 않았다.
- D-55는 (a)를 "관계 목록과 근거"로 정의하고, (b)는 D-54 보완의 배정(전년 원값 제외, 상태 사실)으로, (c)는 규칙 6 대응표·규칙 12·규칙 13으로, (d)는 예시 교체로, (e)는 입력 순서와 규칙 7 확장으로 닫는다.

**5) 트레이드오프**
- **얻는 것**
  - 방향·상태·순서·비교가 모두 코드 판정에 묶인다. 운영에서 규칙 6이 유일한 방향 안전장치라는 위험(§7.4.19 9)이 닫힌다.
  - 716의 구조적 거절이 사라진다.
  - `sales_profit` 초과와 규칙 4 반복이 구조적으로 성립하지 않는다.
- **잃는 것**
  - AI 문장의 자유도가 줄어든다. 두 값의 "비슷함"·"폭" 같은 풍부한 서술을 못 한다. 그 정보는 값을 나란히 놓아 독자에게 맡기고, 추이는 차트(코드)가 보여 준다(D-38).
  - 연간 사실·연속 흐름이 상한 때문에 빠지는 회사가 생긴다(모의 3곳).
  - 변화가 크다: 입력 구성·프롬프트·검증기·렌더러(상태 사실 표시)·fixture가 모두 바뀐다.
- **위험**
  - 규칙 13 어휘 목록의 미탐·오탐.
  - 예시 교체가 불충분하면 첫 시도 준수율이 떨어진다.
  - 지침 누적의 부작용(§7.4.16·§7.4.17의 가설). 완화: D-51의 금지어 우회 설명 일부를 상태 토큰으로 대체해 지운다.
- **개별 패치를 택하지 않은 이유**
  - 전환 검사에 도착점 패턴, 규칙 9에 단어 추가, 입력 정렬만 하는 방식을 검토했다.
  - 716과 908은 고쳐진다. 하지만 흑자·적자 뒤바뀜, 신호만 있는 문장, 새 비교 표현은 계속 대조되지 않는다.
  - 다음 재검증에서 같은 틈의 다른 증상이 나오면 또 패치해야 한다.

### 7.4.26 D-55 구현 전 타당성 검토 (2026-09-26, 설계만 — 코드·프롬프트·Validator·fixture·DB 변경 없음, API 호출 없음)

D-55와 D-54 보완을 구현하기 전에 D-38~D-55, product.md, 현재 코드, fx-v5·fx-v6 시도 원문 45개로 다시 판단했다. 판단 근거로 read-only 스크립트 두 개를 세션 임시 폴더에서 돌렸다(저장소 파일은 읽기만 했다).
- 관계 어휘 스캔: 45개 원문의 문장마다 관계 어휘와 근거를 대조했다.
- `sales_profit` 모의 배정: fixture 12개에 적용했다.

**결론**: 방향은 타당하다. 다만 구현하면 곧바로 문제가 될 틈 다섯 가지가 있어 D-55 본문과 D-54 보완을 고쳤다. 고친 D-55가 다음 구현의 기준이다.

**1) 질문별 판단**

**(1) 코드가 판정한 관계로 제한하는 것이 제품 목적에 맞나 → 맞다. 단, 이익의 증감은 코드가 줘야 한다.** [확인]
- product.md §8은 "변화의 방향·심각도를 계산한다(코드) / 사용자가 이해할 말로 풀어 쓴다(AI)"로 나누고, §12 질문 4는 AI가 판정하는 설계를 D-06 위반으로 본다.
- AI가 말하는 관계(늘었다, 흑자로 돌아섰다, 더 크다, 그보다 앞선)는 모두 판정이다. 코드가 판정한 관계로 제한하는 것은 원칙을 문장 수준까지 적용하는 일이다.
- **초안의 틈**: 영업이익에는 변화량 사실이 없다(D-35: 증가율 % 제외). 그래서 전환 신호가 없으면 "영업이익이 늘었어요"를 쓸 근거가 없었다.
  - 이것은 §4 "무엇이 얼마나 변했나"의 가장 기본적인 문장을 막는다.
  - D-35가 뺀 것은 작은 기준값에서 과장되는 **증가율 수치**다. 방향은 화면의 지표 보기도 보여 준다(D-47).
- 보정: 최신·전년 영업이익이 모두 흑자면 코드가 **방향 관계**(R2)를 준다. 수치는 주지 않는다.
  - 골든셋에서 해당하는 곳은 608·810·872·1016·2906이다.
  - 모두 적자면 방향을 주지 않는다. 산술 방향 "늘었다"가 손실에 대한 말로 읽히기 어렵고, "적자 폭"은 코드가 판정하지 않은 관계다.

**(2) 상태·증감·대소·시간 순서를 하나의 계약으로 묶는 것이 맞나 → 계약은 하나, 판정은 종류별로 따로.** [확인]
- 네 가지는 "AI가 두 값·두 기간 사이를 말로 단정한다"는 같은 성질이다. 그래서 허용 목록 하나(R1~R9), 금지 목록 하나, 프롬프트 한 절로 묶는 것이 맞다.
- 참·거짓 조건은 종류마다 다르다.
  - 증감: 부호 일치.
  - 흑자·적자: 코드 표시.
  - 대소: 근거 존재.
  - 시간: 순서.
- 규칙 하나로 합치면 재시도 안내가 무엇을 고치라는지 흐려진다(D-53의 교훈). 규칙 6·12·13·7로 나눈다.
- **초안의 틈**: 규칙 13이 근거를 한데 묶어 "근거가 있으면 비교 어휘 허용"으로 읽혔다. 관계 스캔에서 2715 "…전년 동기 {…}과 비슷한 수준이었어요"가 영업이익 짝을 근거로 통과했다.
  - 보정: **근거는 관계 종류별**이다. "보다 + 크기 어휘"는 같은 지표의 증감 근거나 자본잠식 신호, "달리"는 전환·상태 차이가 근거다.
  - 근거가 있을 수 없는 어휘(비슷·같은 수준·훨씬·폭)는 늘 금지다.

**(3) `sales_profit` 코드 배정이 D-54 원칙과 일관되나 → 일관된다. 두 가지를 보정했다.** [확인: 모의]

  - 증감(비교 기준 포함), 영업이익 증감(흑자끼리), 전환, 상태, 이어짐.

  - 비슷함.
  - 신호 없는 정도 표현.
  - 서로 다른 지표 사이의 크기 비교.

1. **전환의 정의** (D-54 보완 우선순위 6, "전환의 정의") [확인: DB]

   - 2026년 2분기 2,487개사 기준 수치:
     - 영업이익 부호가 바뀐 곳 494(19.9%). 그중 전환 신호의 영업이익률 조건(양쪽 2% 이상)을 넘는 곳 276 → **약 218곳(8.8%)이 이 빈칸**이다. 금융형 분기처럼 신호를 연간으로만 판정하는 경우도 여기 든다.

     - 배지·개요·"전환" 같은 강도 표현은 신호가 있을 때만 쓴다(규칙 5·7 그대로).

**6) "코드가 관계를 판정하고 AI는 허용된 관계만 쓴다"가 흐름 전체에서 유지되는가** [확인]
- **입력**: 관계는 사실표 부호, 신호 방향, `relations`, `history` 순서로만 준다. 전년 원값·순이익 전년 값은 배정되지 않아 AI가 스스로 방향을 끌어낼 재료가 없다. 모든 섹션이 배정되어 AI가 고르는 것도 없다.
- **생성**: 프롬프트는 관계 표와 "목록 밖 관계는 차례로 적기만"을 준다. 흑자·적자 글자는 코드 토큰이 만든다.
- **검증**: 판정은 입력만 보고, 관계 방향을 표시 문자열에서 다시 계산하지 않는다(`rule6FollowsRelationValueNotDisplayValues`).
- **저장·렌더링**: 상태·전환 사실은 스냅샷 원값·출처와 함께 저장되고 렌더러가 닫힌 문구로 바꾼다. 무효화는 사실의 기간·기준 공시번호로 그대로 동작한다.
- **14차 통과본 12개**: 증감·흑자적자·대소·시간 관계 문장 모두 같은 문장에 코드가 준 근거가 있다. 흑자·적자는 모두 토큰으로 나왔다.
- **남는 틈**: 절 단위 귀속, 열린 어휘(목록 밖 비교 어휘, "이익을 냈다" 같은 서술형 동의어), 토큰과 주어의 불일치. 모두 관찰 0건이며 사람 검토 항목이다(§7.4.26 5).

**7) 보안·입력 검증 점검** [확인]
- **렌더러(결함, 고침)**: `render()`가 토큰 값만 HTML 이스케이프하고 토큰 사이의 AI 문장을 그대로 붙였다. 화면 코드가 아직 없어 노출된 적은 없지만, AI 출력을 신뢰하는 구조였다. 결과 전체를 이스케이프하도록 바꾸고 테스트했다(`renderEscapesAiTextBetweenTokens…`).
- **내부 용어 노출(미탐, 고침)**: 위 5의 규칙 9.
- **입력 주입 경로**: 새 필드는 모두 코드 상수다(관계 종류·값, 상태·전환 표시 문구, 사실 이름). 외부 문자열은 여전히 기업명뿐이고 `<data>` 구분자와 "데이터일 뿐" 지시가 그대로다(D-38).
- **검증기 견고성**: `relations`·`sectionFacts`가 없는 과거 입력은 판정을 건너뛴다. 관계 항목은 키 개수를 확인한 뒤 읽고, 모르는 종류는 무시한다. 형식이 다른 기간 키는 순서 검사를 건너뛴다(없는 기간은 규칙 2가 잡는다).
- **비밀값·로그**: 인증키·프롬프트 로그 경로는 바뀌지 않았다. 새 사실 키(`fin.net_income_status.2026-01.Q2` 등)는 gitleaks 허용 정규식(`^fin\.[a-z]+(?:_[a-z]+)*\.…`)에 맞는다.
- **DB 변경**: 로컬 개발 DB의 `analysis` 행 삭제 두 번은 사용자 승인 후에만 했다.

### 7.4.31 fx-v11 2차 사람 검토 — 개요 완전성 계약 정리 ([D-57](../decisions/D-54-D-59.md), 2026-09-27, 설계 먼저·구현은 로컬까지. 실제 API 재생성은 하지 않음)

§7.4.30의 사람 검토에서 가장 중요하게 지적된 것은 872에서 영업이익률 변화(+28.7%p)가 개요에도, 다른 섹션에도 나타나지 않고 사라진 것이다. 이번 절은 그 원인을 D-54·D-55·`fx-input-5`·`fx-v11`·`fxv-6`과 관련 테스트를 다시 검토해 정리하고(D-57), 함께 지적된 표현 문제(C·D·E)를 반영하며, 기간 라벨 복사(F)는 분석만 하고 별도 과제로 남긴다.

**1) 원인 분석** [확인: 코드·시도 원문]

- `assignSectionFacts`(입력 구성기)는 `changeStatus=CHANGED`일 때 **첫 신호 묶음의 모든 변화·전환 사실**을 `sectionFacts.overview`에 담는다(코드에 forEach로 되어 있어, 신호가 둘이면 둘 다 담는다).
- `v1.md`의 섹션 규칙 표는 "첫 번째 신호 묶음의 **핵심 한 가지만**"이라고 적어, 배정과 반대되는 지시를 준다. 같은 문서의 다른 문장("목록에 있는 사실은 되도록 모두 쓴다")과도 어긋난다.
- 골든셋 12개사 가운데 첫 묶음에 신호가 둘 이상인 곳은 **737·820·872·908** 네 곳이다(나머지 8곳은 개요 사실이 0~1개라 이 문제와 무관하다).
- fx-v11 실제 시도(22회, §7.4.30)에서 이 네 곳의 실제 동작:
  - **872**: 두 시도 모두 영업이익률 변화(`operating_margin_diff`)를 완전히 버렸다 — "핵심 한 가지"를 문자 그대로 따른 것이다.
  - **737·820·908**: 통과한 시도에서는 오히려 "핵심 한 가지"를 어기고 두 사실을 모두 썼다(같은 프롬프트의 "모두 쓴다" 문장을 따른 것으로 보인다).
  - 즉 같은 계약 충돌 앞에서 모델의 선택이 회사마다 갈렸다. 이것은 비결정성이 아니라 **프롬프트 안의 모순**이 낳은 결과다.
- 규칙 11("개요 사실은 다른 섹션에서 다시 못 씀")과 겹치면서, 개요가 버린 사실은 다른 어떤 섹션에도 배정되어 있지 않으므로 **쓸 곳 자체가 없다**. AI의 실수가 아니라 계약의 빈틈이다.

**2) 대안 모의: 개요 배정을 하나로 줄이는 방법** [확인: 모의 실행]

입력 구성을 바꿔 개요에는 첫 신호 하나의 변화 사실만 배정하고, 나머지 신호(예: 872의 S2 영업이익률 변화)는 `sales_profit` 우선순위 2(활성 신호의 근거 사실)로 자연스럽게 넘기는 방법을 실제 코드로 모의했다.

- 문제: `sales_profit`은 이미 우선순위 1~7로 상한(6)까지 촘촘히 채워져 있다. 개요에서 풀려난 사실(예: `operating_margin_diff`)이 우선순위 2에서 먼저 들어가면서, 뒤쪽 우선순위(3. 순이익 상태·전환, 관계 단위라 2칸을 함께 씀)가 상한을 넘어 **완전히 탈락**한다.
- 737로 재현: 개요 사실을 하나(`revenue_yoy`)로 줄이면 `operating_margin`+`operating_margin_diff`가 우선순위 2로 들어가 5칸을 채우고, 우선순위 3의 순이익 전환(`net_income`+`net_income_turn`, 2칸)이 6칸 상한을 넘어 **버려진다** — 872와 같은 문제가 다른 회사·다른 사실로 옮겨갈 뿐이다.
- **판단**: 입력 계약을 바꾸는 이 방법은 "사실을 임의로 생략하지 않는다"는 이번 지시에 어긋난다. 채택하지 않는다(D-57 "검토한 대안").

**3) 결정: 개요 완전성을 규칙 11에 더한다** (D-57)

- 개요(`overview`)는 배정된 사실을 **모두** 써야 한다. 새 규칙 번호를 만들지 않고 기존 규칙 11(섹션 배정)을 확장한다 — "배정 밖 금지"와 "배정은 다 쓰기"는 같은 계약의 양면이다.
- **완전성은 개요에만 적용한다.** `sales_profit`·`structure`는 그대로 "배정 밖 금지"만 본다.
  - `sales_profit`을 함께 검사하면 기존 검증기 테스트 10여 건(`rule6FollowsRelationValueNotDisplayValues`, `rule6EvaluativeWordsNeedSignalWithSameDirection`, `rule12ForbidsStateWordsOutsideTokens` 등)이 깨진다 — 이 테스트들은 `sectionFacts.sales_profit`의 일부만 쓴 문장으로 **다른 규칙 하나만** 확인하도록 짜여 있고, 완전성과는 무관한 목적이다. 이 자유는 D-54 보완이 의도한 것이다(우선순위 목록에서 무엇을 어떻게 묶어 쓸지는 AI가 정한다).
  - `structure`는 고정 구성(부채비율+변화량, 잠식이면 자본총계·자본금)이라 실제로는 늘 전부 쓰인다. 그 이유는 완전성 규칙이 아니라 **구성 자체가 작고 정형화**되어 있기 때문이다. 강제로 넓힐 이유가 없다.
- 입력 계약(`fx-input-5`, `assignSectionFacts`)은 바꾸지 않는다. 개요가 둘을 배정받으면 AI가 둘 다 설명하게 만드는 쪽으로 프롬프트·검증기를 맞춘다.
- 버전: 검증기 `fxv-7`, 프롬프트 `fx-v12`. 입력 구성은 `fx-input-5` 그대로다.

- **737**: 1회차는 배지 위치(규칙 14, "매출은 {…}로 {sig.S1} 전년 같은 분기보다 줄었어요") — fx-v11에서는 이 회사가 배지를 문장 앞에 바르게 뒀었다(회차 간 흔들림). 2회차(재시도 뒤)는 "영업이익과 달리 당기순이익은 다른 상태를 보였고, 영업적자가 …이어지고 있어요"로, `net_income`·상태·전환 토큰을 하나도 안 쓴 채 "달리"만 남겨 규칙 13(근거 없는 대조)에 걸렸다. 1회차에는 같은 내용을 "당기순이익은 {net_income}로 영업이익과 달리, … {net_income_turn} 돌아섰어요"로 토큰과 함께 정확히 썼었다 — **재시도 중 모델이 문장을 다시 쓰다가 토큰을 놓친, AI 출력 품질 문제**다. - **2386**: 1회차는 개요·`sales_profit`·`structure` 전체가 토큰 없이 표시 값을 그대로 옮겼다("부채비율은 지난 회계연도 말보다 +0.8%p 높아졌어요" 등 — 회사 전체가 규칙 3). 첫 시도 라벨·표시 값 복사(§7.4.21 A, 항목 F)가 유난히 넓게 번진 경우다. 2회차(토큰은 고쳤지만)는 "부채비율은 …{debt_ratio_diff} **변화했어요**"로 썼다 — 방향 어휘(늘다/줄다/높아지다/낮아지다) 없이 방향 중립 동사를 써서 규칙 6(증감 근거와 어휘 불일치)에 걸렸다. **이번 골든셋에서 처음 관찰된 형태**다 — 사실 오류는 아니고(+0.8%p는 실제로 "높아졌다"), 방향 어휘를 일부러 피한 것으로 보인다. 표본 1건이라 패턴인지 우연인지는 다음 재검증에서 다시 봐야 한다.

**3) 항목별 분석**

**(1) 배지와 문장의 결합** [확인]
- **원인**: 렌더러(`AnalysisRenderer.render`)는 `{sig}`를 배지 이름 글자로 바꾼다.
  - 배지 이름에는 지표와 방향이 들어 있다("매출 큰 폭 감소").
  - 규칙 14대로 문장 앞에 둔 배지 뒤에 주어("매출은")가 오면 지표 이름이 두 번 겹친다.
  - 사람 검토 자료는 이 글자 렌더링을 읽었다.
- **설계와의 차이**: 설계상 배지는 칩이다(§4.4.4, D-56 결정 5). 그런데 렌더러 결과는 이스케이프된 문자열 하나라 화면이 어디가 배지인지 알 수 없다. 지금 구조로는 칩을 그릴 수 없다.
- **해법이 가능한 이유**: 규칙 14가 배지 자리를 둘로 제한했다. 문장·절의 맨 앞(앞머리 배지)과 "… 신호" 앞(이름 배지)이다. 렌더러가 이 둘을 기계적으로 가를 수 있다. D-56이 기각한 "UI가 배지를 옮기기"와 달리 옮기지 않고 모양만 바꾼다.
- **판단**: 렌더러 수준의 실제 결함이다. 프롬프트·검증기 문제가 아니다. 재생성 없이 저장된 초안에 적용된다.

**(1-a) 배지가 붙는 지표** [확인: fx-v10~v12 시도 원문 전수]
- **검사의 틈**: 규칙 14는 자리만 보고, 배지 뒤의 주어가 그 신호의 지표인지는 보지 않는다. R9("지표마다 자기 배지")의 검사는 방향(규칙 6)뿐이다.
- **통과한 초안에서 나온 사례**
  - 716(fx-v12) "[흑자 전환] 영업이익률은 18.0%였어요": 영업이익 전환 배지를 영업이익률 문장에 붙였다.
  - 737(fx-v11) "[영업이익률 큰 폭 악화] 영업이익은 …으로 영업이익률은 …였어요".
  - 872(fx-v12) "매출은 360.0억원이었어요. [매출 큰 폭 증가] 매출이 전년 같은 분기보다 많이 늘었어요": 배지를 말로 되풀이하는, 사실 없는 문장이다.
- **거절된 시도에서 나온 사례**: 908(fx-v11·fx-v12 2회차)은 "[매출 큰 폭 감소] 매출이 줄었어요"를 따로 떼어 `sales_profit`이 5·6문장이 됐다(규칙 10).
- **출처**: 프롬프트의 R9 예시가 "{sig.S1} 매출이 늘었지만 {sig.S2} 영업이익률은 …"이다. 배지 뒤에 사실이 없는 형태를 예시로 가르친다. spec/financial-explain.md §4.4.3 표도 같다.
- **판단**: 계약(R9)의 검사 틈과 프롬프트 예시의 문제다. 신호를 다른 지표에 붙이면 읽는 사람에게 틀린 귀속이 되므로 표현 문제로 두지 않는다.

**(2) 서로 다른 지표를 "로"로 잇기** [확인]
- **같은 지표의 값과 비교**("영업이익은 {…}로 전년 같은 분기 {…}보다 늘었어요")는 R2의 정해진 형태다. 이 "로"는 "…이고, 그것이 …보다"의 뜻이고, 관계의 근거(두 토큰·방향 관계)가 문장 안에 있다.
- **서로 다른 지표**("영업이익은 {…}로 영업이익률은 {…}였어요")의 "로"는 "…여서 …"로 읽혀, 한 값이 다른 값을 낳은 것처럼 들린다.
  - 코드가 주지 않은 관계(파생·인과)다. D-55 "늘 쓰지 않는 관계"와 같은 성격이고, D-56 결정 4가 프롬프트로 금지했다.
- **지시만으로는 지켜지지 않았다**: 검증기가 보지 않으므로 초안에 남았다. fx-v10 3개(716·1640·2386), fx-v11 3개(737·1640·2386), fx-v12 1개(1640)다.
- **판단**: 표현처럼 보이지만 관계 계약의 문제다. 기계적으로 가를 수 있으므로 검증기로 옮긴다. 가르는 조건은 토큰 뒤 "(으)로" 다음, 같은 절에서 "은·는·이·가"가 붙은 말 뒤에 다른 지표 묶음의 토큰이 오는 것이다.

**(3) 금액 지표의 증감 표현** [확인: 입력 구성·검증기·D-35·D-55]
- **지금 AI가 표현할 수 있는 것**

  | 지표 | 코드가 주는 것 | AI가 쓸 수 있는 말 | 쓸 수 없는 말 |
  |---|---|---|---|
  | 매출 | 값, 전년 같은 기간 대비 증가율(%, 원화이고 기준값 이상일 때만 `revenue_yoy`), 같은 방향 연속 분기(`revenue_yoy_run`), 매출 신호 | "매출은 {값}", "전년 같은 분기보다 {증가율} 늘었어요", "매출 감소가 {n분기}째" | 전년 값과의 비교(전년 원값은 배정하지 않음, D-54 보완), 차이·배수 |
  | 영업이익 | 값, 전년 값(부호가 같을 때), 방향 관계 R2(둘 다 흑자일 때 UP·DOWN·SAME), 전환 사실, 영업적자 흐름 | "{값}로 전년 같은 분기 {전년 값}보다 늘었어요"(R2), "{전환} 돌아섰어요", 둘 다 적자면 두 값을 차례로 | 증가율(%), 차이, "적자 폭이 줄었다" |
  | 순이익 | 값, 상태·전환 사실, 상태 차이(R5) | "{값}로, 전년 같은 분기에 비해 {전환} 돌아섰어요", "영업이익과 달리 {상태}" | 전년 대비 방향·증가율 |
  | 영업이익률·부채비율 | 수준(%), 변화폭(%p, `_diff`), 신호 | "{수준}", "{변화폭} 높아졌어요" | 증가율(%)로 바꿔 말하기 |
  | 자본총계·자본금 | 값(활성 자본잠식일 때만) | 배지와 "자본금 {…}보다 적어요" | 그 밖의 비교 |

- **세 표현은 입력에서 이미 갈라져 있다**: "금액의 증가"(R2, 방향만), "증가율 N%"(`revenue_yoy`), "변화폭 N%p"(`_diff`)는 서로 다른 사실 토큰이다.
  - AI는 숫자를 만들 수 없다(규칙 3의 토큰 밖 숫자·"두 배" 같은 수량 표현 금지, 절대 금지 1).
  - "2.1억위안으로 전년 같은 분기 1.4억위안보다 늘었어요"는 두 토큰과 R2(UP)만으로 쓴 문장이다.
- **금액 증가율은 더하지 않는다**
  - 영업이익은 전년 같은 기간이 음수인 곳이 약 1/3이라, 증가율이 정의되지 않거나 부호가 뒤집힌다(D-35).
  - 둘 다 흑자여도 작은 기준값에서 과장된다. 872는 4.9억원 → 114.2억원으로 약 +2,231%다(두 값에서 계산한 참고치이고, 입력에 없는 수).
  - R2가 방향을, 두 토큰이 크기를 보여 준다. 비교는 읽는 사람이 한다(D-39·D-55).
  - `sales_profit`은 이미 상한(6)에 붙어 있다(908). 사실을 더하면 분량 긴장이 커진다.
- **이 과정에서 찾은 틈 두 가지와 표현 한 가지**
  - **(3-b) 부호가 섞인 문장의 방향 뒤바뀜**: 규칙 6은 문장 안에 두 방향 어휘가 모두 있는지만 본다.
    - 820 개요의 두 증감 어휘를 서로 바꾼 문장이 통과한다(1)의 표).
    - 개요 2사실 형태(D-57, 4개사)가 바로 이 모양이다.
    - 지금까지 부호가 섞인 문장 4개에서 뒤바뀐 사례는 없지만, 사실 오류가 그대로 통과하는 길이다.
  - **(3-c) 정도 어휘**: "많이"는 규칙 5의 강도 표현에 없다.
    - "영업이익은 {…}로 전년 같은 분기 {…}보다 많이 늘었어요"는 신호 없이도 통과한다. 금액 지표는 방향만 받고 크기 판정은 받지 않는다.
    - 실제로 나온 것은 872의 신호 문장 1건뿐이다(신호가 있어 허용되는 자리).
  - **(3-a) 부호와 증감 어휘의 겹침**: "-69.3% 줄었고", "-37.5%p 낮아졌어요"처럼 부호와 어휘가 같은 방향을 두 번 말한다. fx-v12 최종 출력 12개 가운데 5개사, 변화량 7개다.
    - D-56은 부호로 변화량을 표시했다. 하지만 문장 안에서는 증감 어휘와 %p 단위가 이미 변화량임을 보인다.
    - 규칙 6이 증감 어휘와 부호의 일치를 보장한다(3-b를 고친 뒤에는 절 단위로). 그래서 문장 안 변화량의 부호는 빼도 정보가 줄지 않는다.

- **5-a 12개월이 아닌 회계연도**: 2386의 사업보고서는 분할 신설 뒤 첫 회계연도 2025-11-01~2025-12-31(2개월)인데 라벨이 "2025년(연간)"이다.
