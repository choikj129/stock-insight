### 7.2 구현 범위 (Sonnet 구현 세션용)

첫 AI 기능이므로 공통 골격(`analysis` 테이블, LLM 어댑터, 동기화)을 최소한으로 함께 만든다. 다른 분석 종류와 관리자 화면은 만들지 않는다.

1. **마이그레이션 V5: `analysis`** (architecture.md §4.2)
   - 컬럼: `id`, `target_type`(COMPANY), `target_key`, `analysis_kind`(`financial_explain`), `fingerprint`, `status`(DRAFT/PUBLISHED/REJECTED/FAILED/HIDDEN), `result_json` jsonb, `input_json` jsonb, `value_snapshot` jsonb, `schema_version`, `prompt_version`, `model`, `input_builder_version`, `rule_version`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cost_usd` numeric, `failure_reasons` jsonb, `attempt_count`, `created_at`, `published_at`, `is_current` boolean.
   - 대상·분석 종류당 게시본(`is_current`)은 최대 1개(부분 유일 인덱스). 인덱스: (`target_type`, `target_key`, `analysis_kind`, `fingerprint`).
2. **`financial` 패키지: 비율 공식 공유**
   - 증가율·비율·영업이익률 계산(현재 `FinancialSignalCalculator`의 private 메서드)을 `financial` 패키지의 공개 계산으로 옮기고, 계산기가 그것을 쓰게 바꾼다. 결과는 같아야 한다(기존 신호 테스트가 수정 없이 통과).
   - 지표별 사유 코드(`ACCOUNT_MISSING`, `BASE_NOT_POSITIVE`, `SMALL_BASE`, `NOT_APPLICABLE_FORMAT`, 재무상태표 불일치)를 판정하는 계산을 같은 곳에 둔다. 기준값은 신호 규칙 카탈로그와 같은 값을 쓴다(한 곳에서 정의).
   - 기간 라벨(12월 결산 / 그 밖)과 연간 기간 키(`YYYY-MM.FY`).
3. **`analysis` 패키지**
   - `FinancialExplainInputBuilder`: 재무 요약 + `CompanySignalService.findByCompany` → spec/financial-explain.md §4.4.2 입력(사실표, 신호 선별·묶음·순서, `changeStatus`, 섹션, `unavailable`, `doNotMention`). 같은 데이터면 바이트 단위로 같은 JSON(정렬·형식 고정).
   - 지문 계산(§4.4.6), 값 스냅샷 생성(§4.4.5).
   - `FinancialExplainValidator`: §4.4.7 규칙 1~10 + §7 공통 규칙. 한국어 문장 분리, 증감·흑자/적자 어휘 사전, 금지 표현 사전은 코드 상수로.
   - `AnalysisRenderer`(화면 전 단계의 조립용): 토큰 → 값 스냅샷 치환, HTML 이스케이프, 무효화 판단(참조 신호 철회·출처 공시번호 변경).
   - `AnalysisService`: 상태 전이(§6.3), 게시본 교체, 실패 횟수·24시간 재시도·3회 중단(§6.1).
   - `FinancialExplainJob`: 작업명 `analysis-financial-explain`, 기본 cron `0 30 7 * * *`, `run-on-startup`, 대상 = `company.ai_covered` ∪ 설정의 골든셋 목록(`ai_covered` 채우는 코드가 아직 없어 지금은 골든셋만), 일일·월간 예산(비용 USD 상한, 모든 분석 종류가 공유), **`publish` 설정 기본 false(초안만 저장, [D-39](../decisions/D-01-D-40.md))**. 실행 요약을 `pipeline_run`에 남긴다.
     - **실제 구현과 다른 점**: §6.2가 정한 "동시 호출 수 설정(초기값 4)"은 만들지 않고 대상을 순차 처리한다. 이번 세션은 정확성(검증·재시도·무효화·예산)을 우선했고, 동시 호출은 이후 처리량이 문제가 될 때 세마포어 등으로 추가해도 순차 처리와 같은 결과를 내므로 별도 설계 없이 미뤘다.
4. **`analysis/llm`**
   - `LlmClient` 인터페이스(시스템 프롬프트, 사용자 입력, 출력 스키마 → JSON 문자열 + 사용량). Anthropic Java SDK 구현과 테스트용 가짜. 구조화 출력·`max_tokens`·타임아웃·재시도(통신 오류만)는 SDK 버전에 맞춰 구현 세션에서 확인한다.
   - 인증키 `ANTHROPIC_API_KEY`: 비밀값 파일(D-30)에서 읽는다. `secrets.example.yml`에 키 이름만 추가한다. 키가 없으면 작업은 호출 없이 실패로 기록한다.
   - 모델은 설정값(초기 Claude Sonnet 5). 프롬프트·입력 전문을 로그에 남기지 않는다(토큰 수·지연·결과 상태만).
5. **프롬프트**: `src/main/resources/prompts/common/style.md`(스타일 가이드, §8), `prompts/financial_explain/v1.md`(역할·금지·섹션 규칙·토큰 문법·예시), `schema.json`(§4.4.4). 입력 JSON은 구분자로 감싸고 그 안의 지시를 따르지 않도록 명시한다. 시스템 프롬프트는 고정 문자열로 캐시되게 한다.
6. **정적 콘텐츠**: 제한 코드별 쉬운 문구, 신호 유형별 배지 이름, 면책·AI 생성 표시 문구. 코드 상수 또는 리소스 파일.
7. **골든셋 도구**: 로컬 DB에서 골든셋 기업의 §4.4.2 입력 JSON을 뽑아 `src/test/resources/golden/financial_explain/`에 저장하는 개발용 실행 경로(인증키 불필요, `GoldenSetDumpRunner`, `--spring.profiles.active=local,goldenset`로만 동작). **구현하지 않은 것**: 저장된(고정된) 입력 JSON 파일을 다시 읽어 AI로 초안을 재생성하는 별도 경로 — 지금은 `FinancialExplainJob`이 항상 DB에서 새로 입력을 만든다. 프롬프트·모델을 바꿔 같은 입력으로 비교하려면(§4.4.8) 이 경로가 필요하며, 다음 세션 과제로 남긴다.

### 8.2 이슈 2 — 비원화 금액 표시 형식 미정 → **수정 ([D-41](../decisions/D-41-D-53.md))**

### 8.3 이슈 3 — `AnalysisRenderer.isInvalidated()`의 과잉 무효화 → **수정 ([D-42](../decisions/D-41-D-53.md))**

| 항목 | 내용 |

### 8.4 `FIN_DATA_STALE`(최신 재무 미확인)의 판정·생명주기 → **수정 ([D-43](../decisions/D-41-D-53.md))**

이 문제는 이슈 3을 검토하다 발견했다. 처음에는 판단 대기로 두었다가 이어서 결정했다. 현재 코드(`FinancialSignalJob`, `FinancialSignalCalculator.isStale`, `CompanySignalService.applyFinancial`)와 로컬 DB(공시 8,641건, 접수일 2026-08-11~09-23, 재무 보고서의 공시번호)로 확인했다.

| 항목 | 내용 |
|---|---|
| 원인 1: 재판정 계기 없음 | 신호 작업은 "규칙 버전 + 그 기업 재무 마지막 변경 시각"이 바뀐 기업만 다시 판정한다. 이 신호가 잡아야 할 기업은 새 보고서가 들어오지 않아 재무가 바뀌지 않는 기업이다. 그래서 첫 전체 실행 뒤에는 새로 기한이 지나는 기업이 다시 판정되지 않는다. 판정일(`asOf`)을 쓰는 규칙은 이 신호 하나뿐이다. 현재 활성 3건은 모두 첫 전체 실행(2026-09-25) 때 이미 기한이 지나 있던 기업이다 |
| 원인 2: 기한이 일부 기업에 짧음 | 2026년 반기보고서 원 공시 2,457건 중 27건(모두 ACTIVE)이 유예(8/21) 뒤인 8/25~9/1에 접수되었다. 같은 기업들이 2025년 3분기와 2026년 1분기에도 종료 후 약 60일에 냈다(60일째가 토요일이면 다음 월요일). 외국 기업은 사업보고서를 약 120일에 냈다. 45일·90일 기준이면 이 기업들에게 분기마다 3~10일 동안 "기한이 지났다"는 틀린 표시가 나간다. 법령상 근거는 [미확인] |
| 원인 3: 말일 계산 | 종료일에 3개월을 더해 9월 30일 → 12월 30일이 된다. 3분기 → 사업보고서 기한이 하루 이르다(2월 말 결산 등도 같다) |
| 원인 4: 해소가 철회 | 계산기는 최신 기간의 데이터 한계만 활성으로 만든다. 다음 보고서가 오면 옛 근거 키는 초안에 없어 철회(D-36: 틀린 것으로 밝혀짐)가 되고, 철회 수와 철회 급증 경고에 들어간다 |

| 판단 | 수정. 가장 긴 기한(분·반기 60일, 사업 120일, 다음 기간 종료 월의 말일 기준, 달력일, 유예 7일)을 쓴다. 판정할 때 "시간만으로 결과가 바뀔 수 있는 다음 날"(STALE이 아니면 기한일 + 8일, STALE이면 없음)을 남기고, 그날이 지난 기업만 추가로 다시 판정한다. 해소(최신 기간이 P보다 뒤로 감)는 이력, 같은 P에서 성립하지 않게 되면 철회다. 기한과 말일 계산이 바뀌므로 규칙 버전을 `fin-2`로 올린다 |
| 관계 | D-35 목록 그대로. D-36 세 상태를 그대로 적용한다(구현의 해소 = 철회를 바로잡음). D-34 시차는 유예가 흡수한다. D-42와 함께 쓰면 STALE 변화는 재생성·무효화를 일으키지 않는다 |

### 8.6 다음 구현 세션 범위

1. **금액 서식 (D-41)**: 한 곳의 서식 코드로 금액(한국어 수 단위 + 통화명)을 만든다. AI 입력의 표시 값과 렌더링이 같은 코드를 쓴다. 렌더러는 스냅샷의 원값·단위·통화로 서식을 만든다.
2. **제공 조건 (D-41)**: `revenue_yoy_run`을 최신 기간 `revenue_yoy`와 같은 조건일 때만 넣는다. 사실 이름에서 판정어("지속")를 빼 "매출 같은 방향 연속 분기 수"처럼 바꾼다(D-39의 판정어 규칙과 충돌하지 않게).
3. **무효화 (D-42)**: 스냅샷의 신호 자연키로 현재 상태·방향을, 사실의 기간·기준으로 현재 공시번호를 조회해 판정한다. 이를 위해 신호 자연키 목록 조회, 기간·기준별 현재 공시번호 조회를 각 서비스(`signal`, `financial`)에 추가한다. 입력 전체 재구성을 없앤다.
4. **지문 (D-42)**: 데이터 한계 코드 대신 `unavailable` 집합을 쓴다. 지문 구성이 바뀌므로 입력 구성 버전을 올린다(`fx-input-2`). 게시본이 아직 없으므로(publish=false) 재생성 비용 문제는 없다.
5. **렌더링 헤더·한계 문구 (D-42)**: 최신 기간과 데이터 한계 문구를 현재 값으로 만든다.
6. **골든셋 입력 다시 뽑기**: 서식·제공 조건이 바뀌므로 `src/test/resources/golden/financial_explain/` 12개를 `GoldenSetDumpRunner`로 다시 만든다.
7. **최신 재무 미확인 (D-43)**
   - 기한 계산을 규칙 카탈로그 한 곳에 둔다: 다음 기간 종료 월의 말일, 60·120일, 유예 7일. 규칙 버전은 `fin-2`로 올린다.
   - 판정이 "다음 시간 재판정일"을 돌려주고, 작업이 그 날을 체크포인트와 함께 남긴다. 작업은 기존 계기에 더해 그 날이 지난 기업을 대상에 넣는다. 저장 위치(체크포인트 확장 등)는 구현에서 정하고, 스키마를 바꾸면 V6 마이그레이션으로 한다.
   - 상태 전이: 초안에 없는 `STALE(P)`는 최신 기간이 P보다 뒤면 이력, 아니면 철회로 한다. 이 규칙은 신호 저장 규칙(D-36을 구현하는 곳)에 두고, 계산기는 이전 상태를 모르는 순수 함수로 둔다. 이력 전환은 철회 수에 넣지 않는다.
   - 계산값에 기한일을 남긴다.
   - §8.5의 STALE 경계 조건을 테스트한다. 3-3에서 빠진 12·3·6월 결산 기한 테스트도 여기서 채운다.
   - `fin-2`로 모든 신호의 규칙 버전이 바뀌면 AI 지문도 바뀐다. 4번(`fx-input-2`)과 같은 세션에서 하면 초안 재생성이 한 번으로 끝난다. 게시본은 아직 없다.
8. **문서**: 이 절의 결과(테스트 수, 골든셋 변화, 재판정 계기 동작)를 기록한다. code-guide/README.md의 신호 작업 흐름(§7)·알려진 한계(§15)도 고친다.

하지 않는 것: `AccountMapper` 변경, STALE을 뺀 신호 규칙·문턱값 변경, 다른 데이터 한계 신호의 근거 키·상태 처리(§3 판단 대기), 기업별 제출 기한 구분, 휴일 계산, 환율 환산, 화면, 실제 Anthropic 호출(§7.4의 미확인 항목은 이 수정 뒤 진행하는 것이 효율적이다: 입력 서식이 바뀌기 때문).

§8.6의 1~8번을 모두 구현했다. 설계(D-41~D-43)를 임의로 바꾸지 않았고, 구현 방식은 아래와 같이 정했다.

- V6 마이그레이션이 기존 로컬 DB에 정상 적용됨을 확인했다(`flyway_schema_history` v5→v6).
- `financial-signal` 작업을 `--spring.profiles.active=local --app.signal.financial-signal.run-on-startup=true`로 1회 실행했다. 규칙 버전이 `fin-1`→`fin-2`로 바뀌어 **전체 재판정**이 일어났다: 대상 2,545, 처리 2,545, 실패 0, 반영(신호) 9,203, 철회 0. 재실행 뒤 `company_signal` 전체 9,203건이 `rule_version = 'fin-2'`임을 확인했다(**규칙 버전 변경이 정상 반영**).

- 같은 앱을 재기동해 `financial-signal`을 다시 실행하니(재무 데이터 변경 없음, 재판정일도 아직 도래 전) **대상 0**이었다(**재판정 시점이 지난 기업만 다시 계산됨을 확인** — 아직 아무 기업도 재판정일에 도달하지 않았으므로 전부 건너뛴 것이 기대한 결과다. 재판정일 도달 시 실제로 대상에 들어가는지는 `FinancialSignalStaleJobTest`가 고정 시계로 확인한다, 아래 참고).
