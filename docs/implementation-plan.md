#### 3-3.1 구현 중 확정한 사항 (문서에 세부 규칙이 없던 부분)

설계 문서(§6, ai-analysis.md §3.7)에 정확한 규칙이 없어 구현 세션에서 정한 것들이다. 실제 데이터와 충돌한 것은 아니고, 문서의 일반 원칙(D-36 등)에서 합리적으로 도출했다.

| 판단 | 정한 규칙 | 근거 |
|---|---|---|
| 신호를 몇 개 기간에 대해 판정하는가 | 최근 12분기·3개 사업연도의 **개별 보고서마다** 따로 판정하고 자연키(근거 키에 기간이 들어간다)로 저장한다. 이번 계산에 없는 과거 신호는 존재만으로 이력(PAST)이 되고, 조건 자체가 사라지면 철회된다 | D-36이 "이력" 상태를 만든 이유(정정으로 과거 신호가 사실이 아니게 됨)는 과거 기간도 다시 판정 대상이라는 뜻이다. 근거 키 예시("2026-01-01:H1")도 기간마다 다른 키를 전제한다 |
| 연간 3개년 값의 출처 | 최근 3개 사업보고서 각각의 당기 값을 쓴다(사업보고서 하나의 당기·전기·전전기 3개 컬럼을 쓰지 않는다) | 초기 적재가 이미 최근 4개 연도의 사업보고서를 따로 받아 두므로, 각 연도를 그 해 보고서 자체의 판정 단위로 다루는 쪽이 "판정 단위는 보고서 하나"(§3.7 공통)에 더 맞는다 |
| 부채비율 급등의 발생 시점 | 회계연도 안에서 조건이 처음 성립한 분기로 고정한다(그 뒤 분기에도 조건이 이어져도 값을 옮기지 않는다) | §3.7이 부채비율 급등을 "변화" 유형이면서도 발생 기준일만은 상태 신호처럼 "처음 성립한 기간"으로 정의했다. 회계연도당 한 건이라는 제약과 앙립하려면 첫 성립 분기의 값에 고정하는 것이 유일하게 일관된 해석이다 |
| 빈 기간(연속 끊김) 판정 | 두 분기 종료일 차이가 45~135일이면 이어진 것으로 본다(엄격한 회계달력 계산 대신 근사치) | 결산기 변경·비12월 결산까지 다루는 정확한 회계달력 로직은 이번 범위를 넘는다. 실제 분기 간격(약 91일)에 넉넉한 여유를 둔 근사치로도 빠진 분기(약 180일 이상 차이)를 안정적으로 구분한다 |
| 지표별 계산 불가 사유 코드(`ACCOUNT_MISSING`, `SMALL_BASE` 등) | 재무 요약 구조에 미리 채워 두지 않고, 신호 계산기가 판정 시점에 원시 값으로부터 그때그때 판단한다 | 이번 범위의 유일한 소비자가 신호 계산기이고, 화면·AI 입력(4단계)이 아직 없다. 화면을 만들 때 필요하면 재무 요약에 사유 코드 필드를 추가한다(재수집 없이 가능) |

## 3. 발견한 문제와 판단 대기

| 문제 | 내용 | 제안 |
|---|---|---|
| 상장폐지 기업이 EXCLUDED로 남음 | 고유번호 파일과 기업개황은 상장폐지 기업의 종목코드를 계속 준다(예: 하나은행 004940, 쌍방울). 실제 동기화에서 상장사 3,994개 중 1,238개가 이런 "기타 시장"이었다. 기업개황 법인구분이 E(기타)로 바뀌므로 현재 코드는 이런 기업을 DELISTED가 아니라 EXCLUDED(OTHER_MARKET)로 저장한다. 수집 대상에서 빠지는 결과는 같지만 "상장폐지" 표시와 감지일이 남지 않는다 | 이전에 KOSPI·KOSDAQ이던 기업의 법인구분이 E가 되면 DELISTED로 바꾸는 규칙을 기업 목록 동기화에 추가. 기존 동작 변경이라 이번 작업에서는 하지 않음 |
| 확정 뒤 ACTIVE가 된 기업의 과거 공시 | 코넥스→코스닥 이전상장 기업은 이전 날짜의 공시를 받지 않는다 (D-31 한계) | 필요해지면 해당 기업만 고유번호 지정 조회로 채움 |
| 같은 이름 원 공시가 여럿일 때 정정 연결 | 앞선 것 중 가장 최근 것에 연결하므로 드물게 틀릴 수 있다 (D-31 한계) | 화면·분석에서 문제가 되면 원문의 정정 대상 정보 활용 검토 |
| 과거 날짜에 공시가 뒤늦게 추가되는지 | 확정 후 다시 읽지 않으므로, 접수일이 지난 날짜에 공시가 추가되면 놓친다. 아직 사례를 확인하지 못했다 | 데이터 점검(4단계 전)에서 확정 날짜의 건수를 가끔 다시 세어 비교 |
| 재무 초기 적재 속도 | 2025 회계연도 전체(4개 보고서, 보고서 약 18,000벌) 적재에 20분 이상 걸렸다(계정 행을 한 줄씩 insert). 3년 초기 적재는 1시간 안팎으로 예상된다. 호출 수 문제는 아니다 | 3-2 설계·동작은 그대로 두고, 필요하면 계정 행을 배치 insert로 바꾼다(동작 변경 없음) |

### 4.3 수집 대상과 시점

| 항목 | 규칙 |
|---|---|
| 대상 기업 | ACTIVE 기업 (`CompanyService.activeCompanyIdsByDartCorpCode`) |
| 호출 단위 | (`bsns_year`, `report_code`) × 기업 100개 묶음. `fs_div`는 지정하지 않는다(응답에 둘 다 온다) |
| 초기 적재 | `bsns_year` = 올해−3 ~ 올해 × 4개 보고서 종류. 체크포인트가 없는 기업·기간만 묶는다. 약 26묶음 × 16 ≈ 420호출 |
| 증분 계기 | `disclosure`의 PERIODIC 공시(원 공시·정정 모두). 보고서명은 `base_report_name`을 쓴다 |
| 조회 키 계산 | `사업보고서 (YYYY.MM)` → (YYYY, 11011). `반기보고서 (YYYY.MM)` → (YYYY, 11012). `분기보고서 (YYYY.MM)` → 결산월 m 기준 MM이 m+3개월째면 11013, m+9개월째면 11014 (12월 결산: 03→11013, 09→11014. 6월 결산: 09→11013, 03→11014). 결산월이 없거나 어느 쪽도 아니면 그 공시를 오류로 남긴다. 그 밖의 정기공시(등록법인결산서류 등)는 무시한다 |
| 적재 기간 밖 | 조회 키의 `bsns_year`가 올해−3보다 작으면 무시한다(실제: 삼부토건 2019 사업보고서 정정) |
| 실행 시점 | 매일 06:30(공시 목록 수집 06:00 뒤) 한 번. 장중 없음. 한 실행 호출 상한(기본 500) |
| 실행 기록 | `pipeline_run` 작업명 `financial-sync`. 요약에 초기 적재·증분 대상 수를 나눠 적는다 |

**체크포인트** (`ingest_checkpoint`)

- 소스 `DART_FINANCIAL`, 대상 키 `고유번호:bsns_year:report_code`(예: `00126380:2026:11012`).
- 원천 버전 = 이 기업·기간에서 처리한 계기 공시번호 중 가장 큰 값. 초기 적재로 받았으면 null.
- 다시 받을 대상: 체크포인트가 없는 초기 적재 기간, 원천 버전보다 큰 계기 공시가 있는 기간(null은 모든 계기보다 작다고 본다), 직전 결과가 ERROR인 기간.
- 결과: 응답에 기업이 있으면 SUCCESS, 없으면 NO_DATA(계기 공시가 새로 올 때까지 다시 받지 않는다). 묶음 호출이 종료 대상이 아닌 오류로 실패하면 묶음의 기업 모두 ERROR.
- 응답의 기간 종료 월이 계기 보고서명의 월과 다르면 저장하지 않고 ERROR("기간 불일치").

### 4.4 기간·정정·연결/별도 처리 규칙

| 규칙 | 내용 |
|---|---|
| 기간 식별 | 저장 시 손익 행의 `thstrm_dt`("YYYY.MM.DD ~ YYYY.MM.DD")에서 `fiscal_year_start`, `period_end`를 읽는다. 손익 행이 없거나 형식이 다르면 그 기업·기간 ERROR |
| 저장 단위 | 한 기업·조회 키의 응답(연결·별도 모두)을 한 트랜잭션에서 통째로 바꾼다(기존 보고서와 계정 행 삭제 후 삽입, 또는 같으면 그대로). 응답에서 빠진 `fs_div`의 기존 보고서는 지운다 |
| 정정 | 계기 공시가 오면 다시 받아 바꾼다. 이전 값은 남기지 않는다. `[첨부정정]`처럼 값이 그대로면 `receipt_no`와 값이 같아 사실상 변경 없음 |
| 연결/별도 | 저장은 둘 다. 선택(연결 우선)은 읽을 때 (4단계) |
| 전년 비교 | 같은 보고서의 당기·전기 값으로 (4단계 지표 계산에서, ai-analysis.md §3.5) |
| 4분기 | 연간 − 3분기 누적. 전년 대비 비교는 하지 않는다(D-35로 변경, §6) |
| 비교 제외 | 기준(연결/별도)·통화가 다르거나 회계연도가 12개월이 아닌 기간 (4단계) |

### 4.5 업종별 예외 처리 범위

- 수집·저장은 업종과 무관하게 똑같이 한다(금융형 계정도 원천 그대로 저장).
- 재무제표 형식(일반/금융)은 유동자산 유무로 코드가 읽을 때 판별한다. 산업코드는 쓰지 않는다.
- 금융형은 필요한 계정이 있는 지표만 계산하고, 부채비율 신호를 만들지 않으며 "금융업 지표 해석 제한" 신호를 둔다 (ai-analysis.md §3.5, 4단계).
- 금융업 전용 지표(순이자손익 등)는 MVP에서 쓰지 않는다. 필요가 확인되면 매핑만 추가한다(다시 수집하지 않아도 된다).
- 비원화 기업: 비율·변화율은 계산하고, 금액 순위(AI 적용 대상, 동종업계 매출 상위)에서는 뺀다.

### 4.6 코드 계산 영역과 AI 설명 영역

| 코드 (수집·계산·판정) | AI (설명) |
|---|---|
| 응답 해석: 금액 파싱, 기간 식별, 조회 키 계산, 정정 반영 | — |
| 계정명 → 지표 키 매핑(영업이익 두 이름, 당기순이익 중복은 작은 `ord`), 재무제표 형식 판별 | — |
| 4분기 단독값, 영업이익률, 부채비율, 전년 동기 대비 증가율, 연속 기간 수(지속) | — |
| 연결/별도 선택, 비교 제외 판단(기준·통화·기간 불규칙), 계산하지 않은 지표와 이유 | 계산하지 않은 이유를 쉬운 말로 전한다(예: 은행은 부채비율로 보지 않는 이유) |
| 신호 판정(방향·심각도·발생 기준일), 같은 시기 공시 연결 | 코드가 준 신호·연결을 "무엇이 언제 얼마나 변했나"로 풀어 쓴다 |
| 숫자 자리표시자 채우기, 출처(공시번호)·기준일(기간 종료일) 표시 | 숫자는 자리표시자로만 쓴다. 계산·추정·방향 판단을 하지 않는다 |

3-2에서 구현하는 것은 이 표의 첫 줄(응답 해석과 저장)뿐이다. 나머지는 4단계에서 이 설계를 따른다.

### 6.3 신호 발생량 기준선

규칙 초기값(ai-analysis.md §3.7)을 이 데이터에 적용한 결과. 2026년 2분기, 일반형·원화 2,437개사. 구현 후 같은 데이터로 다시 돌려 비교하는 회귀 기준으로 쓴다.

| 신호 | 발생 기업 비율 |
|---|---|
| 매출 +30% 이상 / −20% 이하 (기준값 50억 원으로 측정) | 18.4% / 8.2% |
| 영업이익률 ±10%p (양쪽 매출 50억 원 이상으로 측정) | 18.7% |
| 흑자·적자 전환 (양쪽 영업이익률 2% 이상) | 11.2% |
| 부채비율 급등 (+50%p & 200% 이상) | 3.6% |
| 자본잠식 부분 / 완전 | 2.7% / 0.4% |
| 영업적자 4분기 이상 연속 (12월 결산) | 17.9% |

- 기업당 한 분기 신호 수(측정 조건: 매출 ±, 영업이익률 ±5%p, 누적 기준 전환, 부채비율 급등, 자본잠식): 0개 49%, 1개 28%, 2개 17%, 3개 5%, 4개 0.3%. 최종 규칙(영업이익률 ±10%p, 전환과 중복 제외)에서는 이보다 적다.
- 측정은 기준값 50억 원으로 했다. 규칙의 기준값은 10억 원이므로 매출·영업이익률 신호는 이보다 조금 많아진다. 전환과 겹치는 영업이익률 신호는 규칙상 빠지므로 조금 줄어든다. 구현 후 실제 값을 이 표에 추가한다.

### 6.4 구현 범위 (Sonnet 구현 세션용)

기존 수집 코드(3-1, 3-2)의 관례를 따른다: 서비스를 통한 패키지 간 접근, JdbcClient, `IngestCheckpointRepository`, `PipelineRunRecorder`, 가짜 데이터 + Testcontainers 테스트.

1. **마이그레이션 V4: `company_signal`** (architecture.md §4.2)
   - 컬럼: `id`, `company_id`(FK), `signal_type` varchar(50), `basis_key` varchar(50), `nature`(STATE/CHANGE), `direction`(POSITIVE/NEGATIVE/UNCERTAIN), `severity`(LOW/MEDIUM/HIGH), `occurred_on` date, `persistence` integer, `calc_values` jsonb, `watch_metrics` jsonb, `source_receipt_no` varchar(14) null, `status`(ACTIVE/PAST/WITHDRAWN), `rule_version` varchar(20), `first_detected_at`, `last_evaluated_at`, `status_changed_at`.
   - 유일: (`company_id`, `signal_type`, `basis_key`). 인덱스: (`company_id`, `status`), (`company_id`, `occurred_on` desc).
2. **`financial` 패키지 (읽기)**
   - 계정 매핑(ai-analysis.md §3.5): 영업이익 두 이름, 당기순이익은 작은 `ord`(값이 다르면 경고 로그), 형식 판별(유동자산).
   - `FinancialSummaryService.summarize(companyId)` → §3.8 재무 요약: 시계열 기준 고정, 분기 시계열(4분기 파생과 유효 조건), 연간, 재무상태, 플래그·사유 코드, 재무상태표 항등식 점검, 라벨. 한 기업의 보고서와 계정 행을 한 번에 읽는다.
   - `FinancialService`에 기업별 재무 마지막 변경 시각 조회 추가(신호 계산 대상 판단용).
3. **`signal` 패키지**
   - 규칙 카탈로그: 유형 코드·성격·확인 지표, 문턱값·심각도 구간 상수, 규칙 버전(초기 `fin-1`).
   - `FinancialSignalCalculator`: 재무 요약 → 신호 초안 목록. DB 없이 동작하는 순수 계산(단위 테스트 대상). §3.7의 판정·근거 키·발생 기준일·지속·계산값·상태(활성/이력) 규칙.
   - `CompanySignalService.applyFinancial(companyId, 초안, 규칙 버전)`: 자연키 upsert. 이번 초안에 없는 그 기업의 `FIN_*` 신호는 철회. 상태가 바뀔 때만 `status_changed_at`을 갱신한다.
4. **`ingest`가 아닌 `signal`의 작업**: `FinancialSignalJob`(작업명 `financial-signal`, cron `0 0 7 * * *`, `run-on-startup`), 체크포인트 `SIGNAL_FINANCIAL`(원천 버전 = `규칙 버전:재무 마지막 변경 시각`), 실행 요약(대상 기업, 유형별 신호 수, 활성·이력·철회 수, 데이터 한계 수), 철회 급증 경고(architecture.md §4.4).
5. **테스트**
   - 계산기 단위: 유형마다 경계값(예: +29.9%·+30%, −19.9%·−20%, 9.9%p·10%p, 영업이익률 1.9%·2%, +49.9%p·+50%p, 199%·200%), 기준값 미만, 금융형·비원화 제외, 전환이 있으면 영업이익률 신호 없음, 부채비율 급등은 회계연도에 한 건, 적자 지속의 빈 기간·무효 4분기, 자본잠식 구간, 지속 계산, 데이터 한계 조건, 최신 재무 미확인 기한(12·3·6월 결산).
   - 재무 요약: 기간 중간에 연결이 생긴 기업(빈 기간), 4분기 파생 유효·무효, 항등식 불일치, `영업이익(손실)`, 당기순이익 중복 값 불일치, 비12월 결산 라벨·분기 번호.
   - 실제 데이터 샘플: 로컬 DB에서 기업 몇 개의 보고서·계정 행을 JSON으로 뽑아 `src/test/resources/financial/`에 두고 기대 신호·플래그를 검증한다(삼성전자, 모아텍 3월 결산, 양지사 6월 결산·별도만, KB금융 금융형, 크리스탈신소재 CNY, 셀레스트라 항등식 불일치, 아시아종묘 결산기 변경, 갤럭시아에스엠 기준 전환). 공개 공시 데이터이며 인증키가 들어가지 않는다.
   - 통합(Testcontainers): 작업이 신호를 저장, 데이터 변화 없이 재실행하면 변경 없음, 계정 값 정정 → 같은 자연키 갱신 또는 철회, 새 분기 도착 → 이전 변화 신호가 이력으로, 규칙 버전 변경 → 전체 재판정, 체크포인트로 바뀐 기업만 계산.
6. **실제 확인**: 로컬 DB 전체로 1회 실행. 유형별 발생 비율을 §6.3 기준선과 비교해 기록하고, 신호가 난 기업 10곳을 골라 DART 원문 수치와 대조한다. 실행 시간을 기록한다.
7. **문서**: 이 문서 §1·§2, product.md §13 구현 현황, README 실행 방법.

|---|---|
| 재작성·반올림이 변화로 보임 | 변화는 같은 보고서의 당기·전기로만 판정 |
| 연결·별도가 섞인 추이 | 시계열 기준 고정, 빈 기간 표시, 기준 전환 데이터 한계 |
| 작은 기준값의 과장된 증가율 | 기준값 미만은 증가율 대신 사유 코드, 신호 없음 |
| 계절성을 변화로 오인 | 전분기 대비 변화율·신호 없음 |
| 파생 4분기 오류 | 유효 조건, 전년 비교 없음 |
| 금융업 수치를 일반 기업처럼 해석 | 금융형 제외 규칙과 데이터 한계 신호, "영업수익" 표시 |
| 통화 혼동 | 통화 표시, 매출 기반 신호는 원화만 |
| 원천 오류(항등식 불일치) | 해당 기간 재무상태표 지표·신호 제외 |
| 정정 뒤 틀린 신호가 남음 | 재무 변경 시각으로 다시 판정, 철회 상태 |
| 오래된 숫자를 최신으로 오인 | 모든 지표에 기간 종료일, 최신 재무 미확인 신호 |
| 투자 판단으로 오인 | 사실만 말하는 이름, 방향은 실적·재무 건전성 영향 기준, 밸류에이션·예측 지표 없음, AI는 자리표시자만 |
| 신호 과다 | 문턱값·기준값, 기업당 분기 0~4개(기준선), AI 입력은 최대 8개 선별 |

보안: 이 단계는 새 외부 입력이 없다. 계산은 DB 값만 쓰고, AI 입력은 코드가 만든 키·값과 정적 사유 코드뿐이다(원천 계정명 문자열을 프롬프트에 넣지 않는다). 문턱값은 코드 상수와 규칙 버전으로만 바꾼다. 운영 설정으로 바꾸게 하면 실수 하나로 대량 철회·재판정이 일어날 수 있기 때문이다.

### 7.2 구현 범위 (Sonnet 구현 세션용)

첫 AI 기능이므로 공통 골격(`analysis` 테이블, LLM 어댑터, 동기화)을 최소한으로 함께 만든다. 다른 분석 종류와 관리자 화면은 만들지 않는다.

1. **마이그레이션 V5: `analysis`** (architecture.md §4.2)
   - 컬럼: `id`, `target_type`(COMPANY), `target_key`, `analysis_kind`(`financial_explain`), `fingerprint`, `status`(DRAFT/PUBLISHED/REJECTED/FAILED/HIDDEN), `result_json` jsonb, `input_json` jsonb, `value_snapshot` jsonb, `schema_version`, `prompt_version`, `model`, `input_builder_version`, `rule_version`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cost_usd` numeric, `failure_reasons` jsonb, `attempt_count`, `created_at`, `published_at`, `is_current` boolean.
   - 대상·분석 종류당 게시본(`is_current`)은 최대 1개(부분 유일 인덱스). 인덱스: (`target_type`, `target_key`, `analysis_kind`, `fingerprint`).
2. **`financial` 패키지: 비율 공식 공유**
   - 증가율·비율·영업이익률 계산(현재 `FinancialSignalCalculator`의 private 메서드)을 `financial` 패키지의 공개 계산으로 옮기고, 계산기가 그것을 쓰게 바꾼다. 결과는 같아야 한다(기존 신호 테스트가 수정 없이 통과).
   - 지표별 사유 코드(`ACCOUNT_MISSING`, `BASE_NOT_POSITIVE`, `SMALL_BASE`, `NOT_APPLICABLE_FORMAT`, 재무상태표 불일치)를 판정하는 계산을 같은 곳에 둔다. 기준값은 신호 규칙 카탈로그와 같은 값을 쓴다(한 곳에서 정의).
   - 기간 라벨(12월 결산 / 그 밖)과 연간 기간 키(`YYYY-MM.FY`).
3. **`analysis` 패키지**
   - `FinancialExplainInputBuilder`: 재무 요약 + `CompanySignalService.findByCompany` → ai-analysis.md §4.4.2 입력(사실표, 신호 선별·묶음·순서, `changeStatus`, 섹션, `unavailable`, `doNotMention`). 같은 데이터면 바이트 단위로 같은 JSON(정렬·형식 고정).
   - 지문 계산(§4.4.6), 값 스냅샷 생성(§4.4.5).
   - `FinancialExplainValidator`: §4.4.7 규칙 1~10 + §7 공통 규칙. 한국어 문장 분리, 증감·흑자/적자 어휘 사전, 금지 표현 사전은 코드 상수로.
   - `AnalysisRenderer`(화면 전 단계의 조립용): 토큰 → 값 스냅샷 치환, HTML 이스케이프, 무효화 판단(참조 신호 철회·출처 공시번호 변경).
   - `AnalysisService`: 상태 전이(§6.3), 게시본 교체, 실패 횟수·24시간 재시도·3회 중단(§6.1).
   - `FinancialExplainJob`: 작업명 `analysis-financial-explain`, 기본 cron `0 30 7 * * *`, `run-on-startup`, 대상 = `company.ai_covered` ∪ 설정의 골든셋 목록(`ai_covered` 채우는 코드가 아직 없어 지금은 골든셋만), 일일·월간 예산(비용 USD 상한, 모든 분석 종류가 공유), **`publish` 설정 기본 false(초안만 저장, [D-39](decisions.md))**. 실행 요약을 `pipeline_run`에 남긴다.
     - **실제 구현과 다른 점**: §6.2가 정한 "동시 호출 수 설정(초기값 4)"은 만들지 않고 대상을 순차 처리한다. 이번 세션은 정확성(검증·재시도·무효화·예산)을 우선했고, 동시 호출은 이후 처리량이 문제가 될 때 세마포어 등으로 추가해도 순차 처리와 같은 결과를 내므로 별도 설계 없이 미뤘다.
4. **`analysis/llm`**
   - `LlmClient` 인터페이스(시스템 프롬프트, 사용자 입력, 출력 스키마 → JSON 문자열 + 사용량). Anthropic Java SDK 구현과 테스트용 가짜. 구조화 출력·`max_tokens`·타임아웃·재시도(통신 오류만)는 SDK 버전에 맞춰 구현 세션에서 확인한다.
   - 인증키 `ANTHROPIC_API_KEY`: 비밀값 파일(D-30)에서 읽는다. `secrets.example.yml`에 키 이름만 추가한다. 키가 없으면 작업은 호출 없이 실패로 기록한다.
   - 모델은 설정값(초기 Claude Sonnet 5). 프롬프트·입력 전문을 로그에 남기지 않는다(토큰 수·지연·결과 상태만).
5. **프롬프트**: `src/main/resources/prompts/common/style.md`(스타일 가이드, §8), `prompts/financial_explain/v1.md`(역할·금지·섹션 규칙·토큰 문법·예시), `schema.json`(§4.4.4). 입력 JSON은 구분자로 감싸고 그 안의 지시를 따르지 않도록 명시한다. 시스템 프롬프트는 고정 문자열로 캐시되게 한다.
6. **정적 콘텐츠**: 제한 코드별 쉬운 문구, 신호 유형별 배지 이름, 면책·AI 생성 표시 문구. 코드 상수 또는 리소스 파일.
7. **골든셋 도구**: 로컬 DB에서 골든셋 기업의 §4.4.2 입력 JSON을 뽑아 `src/test/resources/golden/financial_explain/`에 저장하는 개발용 실행 경로(인증키 불필요, `GoldenSetDumpRunner`, `--spring.profiles.active=local,goldenset`로만 동작). **구현하지 않은 것**: 저장된(고정된) 입력 JSON 파일을 다시 읽어 AI로 초안을 재생성하는 별도 경로 — 지금은 `FinancialExplainJob`이 항상 DB에서 새로 입력을 만든다. 프롬프트·모델을 바꿔 같은 입력으로 비교하려면(§4.4.8) 이 경로가 필요하며, 다음 세션 과제로 남긴다.

  1. **재무상태표 불일치 기간에 재무상태 사실이 그대로 나감** — §4.4.2 "재무상태표 불일치 기간은 재무상태 지표 전체를 뺀다"를 `FinancialExplainInputBuilder`가 구현하지 않아, 셀레스트라(2715, 실제로 자산총계 180.3억 ≠ 부채총계 251.4억 + 자본총계 −66.7억)의 입력에 `total_assets`·`total_liabilities`·`total_equity`·`capital_stock`·`structure` 섹션이 그대로 들어 있었다. `FIN_DATA_INCONSISTENT` 활성 신호가 있으면 이 여섯 지표를 전부 `unavailable`(사유 `INCONSISTENT_BALANCE`)로 두고 `structure` 섹션을 빼도록 고쳤다. 회귀 테스트: `FinancialExplainInputBuilderTest#inconsistentBalanceSheetExcludesAllStructureFacts`.
  2. **금융형 기업이 매출 원값을 전혀 못 받음** — 금융형이면 매출 관련 사실을 전부(원값 포함) 만들지 않던 것을, §4.4.2 "금융형은 매출 증가율만 계산하지 않는다(영업수익 원값은 남긴다)"에 맞게 고쳤다(`revenue_yoy`만 `unavailable(NOT_APPLICABLE_FORMAT)`, `revenue`/`revenue_prior`는 "영업수익" 이름으로 유지). 다만 §3 표의 "`AccountMapper`가 '영업수익'을 인식하지 못함" 문제 때문에 실제 데이터에서는 아직 이 경로를 타는 금융형 기업이 없다(DB손해보험 등은 "영업수익" 계정 자체가 안 읽힌다) — 코드는 고쳤지만 실제 데이터로는 끝까지 확인하지 못했다. **(정정 2026-09-25, §8.1)** 이 서술은 틀렸다. 주요계정 API에는 "영업수익" 계정이 없고 DB손해보험은 매출 계정 자체가 없다. 매출액이 있는 금융형(SV인베스트먼트 810 등 27개사)은 이 경로를 실제로 타며, 골든셋 810 입력에 "영업수익 91.5억원"이 있다.
- 위 두 수정 뒤 `./gradlew test`(기존 테스트 + 이번 세션에 추가한 테스트 전체) 재실행, 전부 통과.
- **잘못된 키로 실제 Anthropic API에 한 번 호출**(`AnthropicLlmClient`, 네트워크 확인용, 일회성 수동 테스트 후 삭제)해 401 오류가 `LlmException`으로 정상 변환되고 예외 메시지에 인증키가 전혀 없음을 확인했다(§7.7의 "데이터 유출" 대응).
- **[미확인]** 실제(유효한) Anthropic 인증키로 골든셋 12개사의 초안을 실제로 생성하고 §4.4.7 자동 검증·§4.4.8 사람 검토를 거치는 절차는 이번 세션에서 하지 않았다(사용자가 지금은 건너뛰기로 결정, 2026-09-25). 진행하려면: (1) `~/.stockinsight/secrets.yml`에 `ANTHROPIC_API_KEY` 설정, (2) `--spring.profiles.active=local`로 기동하고 `app.analysis.financial-explain.golden-set-company-ids`에 위 12개 ID를 설정, (3) `FinancialExplainJob.run()`을 한 번 실행(예: 관리용 엔드포인트가 없으므로 `run-on-startup: true`로 임시 기동하거나 테스트 코드에서 직접 호출), (4) `analysis` 테이블의 DRAFT 행을 사람이 §4.4.8 기준으로 검토, (5) 첫 시도/재시도 통과율·토큰·비용·지연을 이 절에 기록.

| 위험 | 막는 곳 |
|---|---|
| 새 계산·새 비교 | 입력에 분기 시계열 없음(D-38), 토큰 밖 숫자·수량 표현 금지, 전분기·업계 비교 금지어 |

### 8.1 이슈 1 — `AccountMapper`의 "영업수익" 미인식 → **유지(코드 수정 없음), 기록 정정**

| 항목 | 내용 |
|---|---|
| 기록된 원인 | "금융형 매출 계정은 보통 '영업수익'인데 `AccountMapper`가 '매출액'만 찾아 DB손해보험 등은 매출 사실이 비어 있다" |
| 실제 확인 | 저장된 계정 행 전체에 "영업수익"이 **없다**(매출 계열은 "매출액" 26,600행과 "이자수익" 685행뿐). DB손해보험의 보고서에는 매출 계정 자체가 없다(자산·부채·자본·손익 합계, 보험계약자산·부채, 이자수익·비용, 영업이익(손실) 등 20행). OpenDART 주요계정 API는 증권·투자 같은 금융형의 영업수익을 "매출액"으로 주고(금융형 56개사 중 27개사), 은행·보험에는 매출 계정을 주지 않는다 |
| 현재 동작 | 올바르다. 금융형 + "매출액" → 사실 이름 "영업수익"으로 원값 제공, 증가율은 `unavailable(NOT_APPLICABLE_FORMAT)`(골든셋 SV인베스트먼트 810에서 실제로 확인: "영업수익 91.5억원"). 은행·보험 → `revenue` `unavailable(ACCOUNT_MISSING)`, `doNotMention`에 "매출"(골든셋 DB손해보험 1016) |

| AI 입력 계약 영향 | 없다. §4.4.2의 "영업수익은 사실 이름 '영업수익'으로만"은 매출액 계정을 가진 금융형에 이미 적용되고 있다 |
| 판단 | 유지. 관찰되지 않은 계정명을 매핑에 미리 넣지 않는다(D-32: 매핑은 다시 수집 없이 나중에 추가할 수 있다). ai-analysis.md §3.5에 확인 사실과 "실제 응답에서 확인한 계정명만 매핑한다"를 적었다 |
| 인접 문제(수정) | `revenue_yoy_run`이 매출 증가율을 주지 않는 경우(금융형·비원화·기준값 미만)에도 입력에 들어갈 수 있다. 골든셋 GRT(608, CNY)는 `revenue_yoy`가 `NON_KRW`로 빠졌는데 `revenue_yoy_run`(3분기)이 있다. D-41로 "최신 기간 `revenue_yoy`를 줄 수 있을 때만" 주도록 정했다 |
| 관계 | D-32(원천 보존·읽을 때 매핑), D-35(금융형 매출 신호 제외)와 일치. D-38 입력 계약 변경 없음 |

### 8.3 이슈 3 — `AnalysisRenderer.isInvalidated()`의 과잉 무효화 → **수정 ([D-42](decisions.md))**

| 항목 | 내용 |
|---|---|
| 원인 | 화면을 그릴 때 입력 전체를 다시 만들어 지문이 다르면 무효로 판정한다. 지문에는 입력 보고서 공시번호 집합, 입력 신호의 상태·심각도·규칙 버전, 데이터 한계 코드가 모두 들어 있다 |
| 과잉 무효화 | 새 분기 보고서가 오면 공시번호 집합이 바뀌고 이전 활성 신호가 이력이 되어 **항상** 무효화된다(D-40은 "새 보고서만으로는 내리지 않는다"). 제출 기한 직후 AI 적용 대상 대부분의 설명이 한꺼번에 사라지고, 생성이 3회 실패하면(§6.1) 틀리지 않은 설명이 관리자 조치 전까지 가려진다. 규칙 버전을 올리면 신호가 그대로여도 모든 게시본이 내려간다. "최신 재무 미확인"처럼 날짜로 바뀌는 데이터 한계도 게시본을 내린다 |
| 불필요한 재생성 | 지문에 데이터 한계 코드가 들어 있어, 입력 사실은 그대로인데 "최신 재무 미확인"만 바뀌어도 다시 생성한다. 새 보고서·정정·신호 변경에 따른 재생성은 필요한 재생성이다(최신 기간을 설명해야 한다) |
| 성능 | 조회 경로(화면)가 기업의 재무 요약·신호 전체로 입력을 다시 만든다. 분석 생성과 같은 비용이 페이지를 볼 때마다 든다 |
| 판단 | 수정. "안전하다"는 이유로 유지하지 않는다: 틀리지 않은 설명을 내리는 것도 사용자에게 근거 있는 설명을 주지 못하는 실패이고, D-40이 명시적으로 막은 동작이다. 무효화는 스냅샷이 참조한 신호의 철회·방향 변경과 참조 사실 보고서의 공시번호 변경만 본다. 지문은 데이터 한계 코드 대신 `unavailable` 항목을 쓴다. 헤더의 최신 기간과 데이터 한계 문구는 렌더링 시점의 현재 값으로 보여 준다 |
| 관계 | D-40의 결정을 그대로 구현하는 쪽으로 구체화(D-42). D-36(철회 상태)과 D-37(스냅샷 기준의 사실은 기준 전환 뒤에도 맞다)을 판정 근거로 쓴다 |

### 8.4 `FIN_DATA_STALE`(최신 재무 미확인)의 판정·생명주기 → **수정 ([D-43](decisions.md))**

이 문제는 이슈 3을 검토하다 발견했다. 처음에는 판단 대기로 두었다가 이어서 결정했다. 현재 코드(`FinancialSignalJob`, `FinancialSignalCalculator.isStale`, `CompanySignalService.applyFinancial`)와 로컬 DB(공시 8,641건, 접수일 2026-08-11~09-23, 재무 보고서의 공시번호)로 확인했다.

| 항목 | 내용 |
|---|---|
| 원인 1: 재판정 계기 없음 | 신호 작업은 "규칙 버전 + 그 기업 재무 마지막 변경 시각"이 바뀐 기업만 다시 판정한다. 이 신호가 잡아야 할 기업은 새 보고서가 들어오지 않아 재무가 바뀌지 않는 기업이다. 그래서 첫 전체 실행 뒤에는 새로 기한이 지나는 기업이 다시 판정되지 않는다. 판정일(`asOf`)을 쓰는 규칙은 이 신호 하나뿐이다. 현재 활성 3건은 모두 첫 전체 실행(2026-09-25) 때 이미 기한이 지나 있던 기업이다 |
| 원인 2: 기한이 일부 기업에 짧음 | 2026년 반기보고서 원 공시 2,457건 중 27건(모두 ACTIVE)이 유예(8/21) 뒤인 8/25~9/1에 접수되었다. 같은 기업들이 2025년 3분기와 2026년 1분기에도 종료 후 약 60일에 냈다(60일째가 토요일이면 다음 월요일). 외국 기업은 사업보고서를 약 120일에 냈다. 45일·90일 기준이면 이 기업들에게 분기마다 3~10일 동안 "기한이 지났다"는 틀린 표시가 나간다. 법령상 근거는 [미확인] |
| 원인 3: 말일 계산 | 종료일에 3개월을 더해 9월 30일 → 12월 30일이 된다. 3분기 → 사업보고서 기한이 하루 이르다(2월 말 결산 등도 같다) |
| 원인 4: 해소가 철회 | 계산기는 최신 기간의 데이터 한계만 활성으로 만든다. 다음 보고서가 오면 옛 근거 키는 초안에 없어 철회(D-36: 틀린 것으로 밝혀짐)가 되고, 철회 수와 철회 급증 경고에 들어간다 |
| 테스트 | §6.4가 요구한 "최신 재무 미확인 기한(12·3·6월 결산)" 단위 테스트가 없다(`src/test`에 STALE 테스트 0건) |
| 판단 | 수정. 가장 긴 기한(분·반기 60일, 사업 120일, 다음 기간 종료 월의 말일 기준, 달력일, 유예 7일)을 쓴다. 판정할 때 "시간만으로 결과가 바뀔 수 있는 다음 날"(STALE이 아니면 기한일 + 8일, STALE이면 없음)을 남기고, 그날이 지난 기업만 추가로 다시 판정한다. 해소(최신 기간이 P보다 뒤로 감)는 이력, 같은 P에서 성립하지 않게 되면 철회다. 기한과 말일 계산이 바뀌므로 규칙 버전을 `fin-2`로 올린다 |
| 관계 | D-35 목록 그대로. D-36 세 상태를 그대로 적용한다(구현의 해소 = 철회를 바로잡음). D-34 시차는 유예가 흡수한다. D-42와 함께 쓰면 STALE 변화는 재생성·무효화를 일으키지 않는다 |

### 8.6 다음 구현 세션 범위

1. **금액 서식 (D-41)**: 한 곳의 서식 코드로 금액(한국어 수 단위 + 통화명)을 만든다. AI 입력의 표시 값과 렌더링이 같은 코드를 쓴다. 렌더러는 스냅샷의 원값·단위·통화로 서식을 만든다.
2. **제공 조건 (D-41)**: `revenue_yoy_run`을 최신 기간 `revenue_yoy`와 같은 조건일 때만 넣는다. 사실 이름에서 판정어("지속")를 빼 "매출 같은 방향 연속 분기 수"처럼 바꾼다(D-39의 판정어 규칙과 충돌하지 않게).
3. **무효화 (D-42)**: 스냅샷의 신호 자연키로 현재 상태·방향을, 사실의 기간·기준으로 현재 공시번호를 조회해 판정한다. 이를 위해 신호 자연키 목록 조회, 기간·기준별 현재 공시번호 조회를 각 서비스(`signal`, `financial`)에 추가한다. 입력 전체 재구성을 없앤다.
4. **지문 (D-42)**: 데이터 한계 코드 대신 `unavailable` 집합을 쓴다. 지문 구성이 바뀌므로 입력 구성 버전을 올린다(`fx-input-2`). 게시본이 아직 없으므로(publish=false) 재생성 비용 문제는 없다.
5. **렌더링 헤더·한계 문구 (D-42)**: 최신 기간과 데이터 한계 문구를 현재 값으로 만든다.
6. **골든셋 입력 다시 뽑기**: 서식·제공 조건이 바뀌므로 `src/test/resources/golden/financial_explain/` 12개를 `GoldenSetDumpRunner`로 다시 만든다.
7. **최신 재무 미확인 (D-43)**
   - 기한 계산을 규칙 카탈로그 한 곳에 둔다: 다음 기간 종료 월의 말일, 60·120일, 유예 7일. 규칙 버전은 `fin-2`로 올린다.
   - 판정이 "다음 시간 재판정일"을 돌려주고, 작업이 그 날을 체크포인트와 함께 남긴다. 작업은 기존 계기에 더해 그 날이 지난 기업을 대상에 넣는다. 저장 위치(체크포인트 확장 등)는 구현에서 정하고, 스키마를 바꾸면 V6 마이그레이션으로 한다.
   - 상태 전이: 초안에 없는 `STALE(P)`는 최신 기간이 P보다 뒤면 이력, 아니면 철회로 한다. 이 규칙은 신호 저장 규칙(D-36을 구현하는 곳)에 두고, 계산기는 이전 상태를 모르는 순수 함수로 둔다. 이력 전환은 철회 수에 넣지 않는다.
   - 계산값에 기한일을 남긴다.
   - §8.5의 STALE 경계 조건을 테스트한다. 3-3에서 빠진 12·3·6월 결산 기한 테스트도 여기서 채운다.
   - `fin-2`로 모든 신호의 규칙 버전이 바뀌면 AI 지문도 바뀐다. 4번(`fx-input-2`)과 같은 세션에서 하면 초안 재생성이 한 번으로 끝난다. 게시본은 아직 없다.
8. **문서**: 이 절의 결과(테스트 수, 골든셋 변화, 재판정 계기 동작)를 기록한다. code-guide.md의 신호 작업 흐름(§7)·알려진 한계(§15)도 고친다.

하지 않는 것: `AccountMapper` 변경, STALE을 뺀 신호 규칙·문턱값 변경, 다른 데이터 한계 신호의 근거 키·상태 처리(§3 판단 대기), 기업별 제출 기한 구분, 휴일 계산, 환율 환산, 화면, 실제 Anthropic 호출(§7.4의 미확인 항목은 이 수정 뒤 진행하는 것이 효율적이다: 입력 서식이 바뀌기 때문).

§8.6의 1~8번을 모두 구현했다. 설계(D-41~D-43)를 임의로 바꾸지 않았고, 구현 방식은 아래와 같이 정했다.

- 실제(유효한) Anthropic 인증키로 재생성·게시는 이번에도 하지 않았다(사용자 지시, §7.4와 같은 사유). 이번 수정으로 입력 서식·지문 구성이 바뀌었으므로, 실제 생성은 이 수정 이후에 진행하는 것이 맞다(§8.6에서 이미 그렇게 정했다).
