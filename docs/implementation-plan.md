### 실제 API 응답으로 확인한 사실 (2026-09-25)

| 항목 | 확인 내용 | 설계 반영 |
|---|---|---|
| 식별자 | 공시번호(`rcept_no`)는 14자리. 앞 8자리는 대개 접수일이지만 아닐 수 있다(45일 8,641건 중 45건은 접수일이 1일 이상 뒤). 거래소공시는 뒤 6자리가 8·9로 시작하는 번호대를 쓴다 | 공시번호를 자연키·근거 키로 쓰고, 날짜는 공시번호에서 뽑지 않는다 |
| 기준일 | `rcept_dt`(YYYYMMDD) 접수일. 조회 조건(`bgn_de`·`end_de`)은 이 날짜 기준이다 | 접수일 = 공시의 기준일, 공시 신호의 발생 기준일 |
| 유형 구분 | `pblntf_ty`로 조회하며 응답 항목에는 유형 필드가 없다 → 조회한 유형으로 저장. 거래소공시에는 시장조치·안내(상장적격성 실질심사, 매매거래정지 등)도 들어 있다 | 유형별로 따로 조회 |
| 정정 | 정정은 새 공시번호로 오고 보고서명 앞에 `[기재정정]`·`[첨부정정]`·`[첨부추가]`가 붙는다. 원 공시번호는 주지 않는다. 한 원 공시에 정정이 여러 번(실제 7회) 이어지고, 공급계약처럼 2년 넘게 이어지기도 한다. 이전 판에는 비고 "정"이 나중에 붙고 최신판에만 없다. 거래소공시는 정정 제출이 원 공시의 기타정보(공백 여러 칸 뒤 괄호, 예: "(임시주주총회)")를 빼거나 바꿔 낸다. `[정정명령부과]` 표시도 나온다 | 코드가 기타정보를 뗀 보고서명으로 연결 (D-31) |
| 최종본만 조회 | `last_reprt_at=Y`면 정정된 원 공시가 빠진다 (2026-08-14 정기공시 2,594 → 2,485건) | `N`으로 원 공시까지 저장 |
| 비고 | 한 글자 표시의 조합(예: "코정", "정연"). 유·코·채·넥·공(소관), 연(연결), 정(이후 정정), 철(철회) | 원문 저장, 정정 판단은 연결로 |
| 보고서명 | 끝 공백과 연속 공백이 많다 (거래소공시) | 공백 정리 후 저장 |
| 공시 없는 날 | 주말은 모든 유형이 013. 마지막 페이지를 넘긴 요청도 013 | 013 = 빈 페이지, 날짜는 "데이터 없음"으로 확정 |
| 조회 제한 | 기업 미지정 시 3개월 넘으면 100 오류 | 하루 단위 조회라 해당 없음 |
| 분량 | 평일 A 4건, B 38건, I 171건(2페이지) 수준. 반기보고서 마감일(08-14) A 2,594건(26페이지), I 299건(3페이지) | 초기 적재 3년 ≈ 3,300 + 추가 페이지 호출 |
| ACTIVE 조건 | 응답에는 비상장 기타법인(E, 종목코드 없음)과 코넥스·리츠 등 범위 밖 상장사가 섞인다. 법인구분(`corp_cls`)은 조회 시점 값이다(상장폐지 기업은 과거 공시도 E) | 법인구분이 아니라 `company` 상태로 거른다 |
| 공시 없는 평일 | 2026-09-24·25는 모든 유형이 013 (추석 연휴 9/24~26) | 휴장일에도 날짜는 "데이터 없음"으로 확정. 휴장일 테이블 없이 동작한다 |

#### 2.1 실제 실행 결과 (로컬, 2026-09-25)

| 실행 | 결과 |
|---|---|
| 기업 목록 동기화 | 호출 3,995, 실패 0, 약 28분. 상장사(종목코드 있음) 3,994 → ACTIVE 2,553, EXCLUDED 1,441 (KONEX 107, 스팩 71, 리츠 25, 기타 시장 1,238) |
| 공시 목록 수집 (적재 기간 45일로 줄여 실행) | 138 날짜·유형, 호출 205, 실패 0, 45초. 받은 공시 9,956건 중 ACTIVE 기업 8,641건 저장(정기 2,729, 주요사항 839, 거래소 5,073). 정정 공시 1,819건 중 580건 원 공시 연결 |
| 로그·저장소 | 인증키가 로그와 저장소 파일 어디에도 없음을 확인 |

- 정정 연결 규칙을 실제 데이터로 점검하면서 기타정보를 연결 기준에서 빼도록 고쳤다(연결 559 → 580건). 다른 공시 유형의 공시에 연결된 경우는 0건이다.
- 연결되지 않은 정정은 대부분 원 공시가 적재 기간 앞에 있다. 표본 6건을 기업 지정 조회로 확인하니 원 공시가 1개월~2년 반 전이었다. 기본 적재 기간(3년)에서는 대부분 연결되고, 그보다 오래된 원 공시만 남는다.
- 호출량 추정: 45일 205호출 → 3년 약 5,000호출. 한 실행 상한 3,000으로 이틀에 나눠 받는다. 저장량은 3년 약 21만 건 수준이다.
- 이 실행은 확인용이며, 로컬 DB에 45일치가 남아 있다. 기본 설정으로 실행하면 남은 기간만 이어서 받는다.

## 3. 발견한 문제와 판단 대기

| 문제 | 내용 | 제안 |
|---|---|---|
| 상장폐지 기업이 EXCLUDED로 남음 | 고유번호 파일과 기업개황은 상장폐지 기업의 종목코드를 계속 준다(예: 하나은행 004940, 쌍방울). 실제 동기화에서 상장사 3,994개 중 1,238개가 이런 "기타 시장"이었다. 기업개황 법인구분이 E(기타)로 바뀌므로 현재 코드는 이런 기업을 DELISTED가 아니라 EXCLUDED(OTHER_MARKET)로 저장한다. 수집 대상에서 빠지는 결과는 같지만 "상장폐지" 표시와 감지일이 남지 않는다 | 이전에 KOSPI·KOSDAQ이던 기업의 법인구분이 E가 되면 DELISTED로 바꾸는 규칙을 기업 목록 동기화에 추가. 기존 동작 변경이라 이번 작업에서는 하지 않음 |
| 확정 뒤 ACTIVE가 된 기업의 과거 공시 | 코넥스→코스닥 이전상장 기업은 이전 날짜의 공시를 받지 않는다 (D-31 한계) | 필요해지면 해당 기업만 고유번호 지정 조회로 채움 |
| 같은 이름 원 공시가 여럿일 때 정정 연결 | 앞선 것 중 가장 최근 것에 연결하므로 드물게 틀릴 수 있다 (D-31 한계) | 화면·분석에서 문제가 되면 원문의 정정 대상 정보 활용 검토 |
| 과거 날짜에 공시가 뒤늦게 추가되는지 | 확정 후 다시 읽지 않으므로, 접수일이 지난 날짜에 공시가 추가되면 놓친다. 아직 사례를 확인하지 못했다 | 데이터 점검(4단계 전)에서 확정 날짜의 건수를 가끔 다시 세어 비교 |

## 4. 다음 단계: 3-2 재무 요약 수집

| 항목 | 계획 |
|---|---|
| 소스 | OpenDART 다중회사 주요계정 API(`fnlttMultiAcnt`). 사업연도 × 보고서 종류(1분기·반기·3분기·사업) 단위로 ACTIVE 기업을 100개씩 묶어 호출한다 |
| 저장 | `financial_summary` 테이블 (V3 마이그레이션): 기업, 회계연도, 기간 구분, 연결/별도, 기간 종료일, 통화, 핵심 계정, 출처 공시번호. **연결과 별도를 모두 저장**하고 "연결 우선" 선택은 읽을 때 한다 (D-14) |
| 계정 매핑 | 주요계정 API의 계정명을 코드의 매핑 표로 핵심 계정 컬럼에 연결한다. 모르는 계정명은 오류가 아니라 경고로 남긴다 |
| 손익 값 | 원천 값(당기, 당기누적)을 그대로 저장한다. 분기 단독값 계산은 4단계 지표 계산에서 한다 (architecture.md §4.3) |
| 초기 적재 | 최근 3년 + 올해의 보고서. 약 25묶음 × 4년 × 4보고서 ≈ 400호출 |
| 증분 계기 | 3-1에서 들어온 정기공시(PERIODIC) 중 아직 반영하지 않은 공시번호. 보고서명(정정 표시를 뗀 이름, 예: "반기보고서 (2026.06)")에서 사업연도와 보고서 종류를 해석해 해당 묶음을 다시 받는다. 정정 공시도 같은 경로로 반영된다 |
| 체크포인트 | 기업·연도·보고서별 (`DART_FINANCIAL`, 원천 버전 = 공시번호). 응답에 없는 기업은 "데이터 없음"으로 두고, 해당 정기공시가 들어올 때만 다시 받는다 (제출 기한 폴링 없음) |
| 실행 기록 | `pipeline_run` 작업명 `financial-sync` |

이미 확인한 것 (2026-09-25, 사업보고서 2025 실제 응답 1건):

- 기업·연결/별도(`fs_div` CFS/OFS)마다 재무상태표 9개, 손익계산서 5종 계정. **현금흐름 없음** (D-14에 기록).
- `당기순이익(손실)`이 `ord`만 다르게 두 번 나온다(손익계산서, 포괄손익 부분). 매핑할 때 중복을 처리해야 한다.
- 항목마다 출처 공시번호(`rcept_no`), 당기·전기·전전기 금액과 기간(`thstrm_dt` 등), 통화가 있다. 금액은 쉼표가 든 문자열이다.

| 항목 | 이유 | 확인 방법 |
|---|---|---|
| 주요계정의 당기금액·당기누적금액 의미 | 분기 보고서에서 손익 값이 3개월치인지 누적인지에 따라 4단계 계산이 달라진다 | 실제 1분기·반기 응답 비교 |

| 정정 후 응답의 공시번호 | 주요계정 응답의 `rcept_no`가 정정본으로 바뀌는지에 따라 증분 계기와 체크포인트 버전이 달라진다 | 정정된 사업보고서가 있는 기업(예: 2026-08 정정 사례) 응답 확인 |
| 금융업 계정명 | 은행·보험사에서 계정명이 다를 수 있다 | 일반 제조업·은행·보험사 응답 비교 |

그 뒤(4단계 전): 감사의견·주요사항보고서 구조화 API, 사업보고서 원문 저장과 섹션 추출, 휴장일 테이블과 데이터 신선도 점검, 상장폐지 표시 규칙(§3).

### 완료 기준

- 인증키 없이 실행되는 테스트: 클라이언트(실제 응답 샘플), 동기화 규칙(가짜 OpenDART + Testcontainers), 계정 매핑·보고서명 해석(단위 테스트).
- 인증키로 로컬에서 실제 초기 적재를 1회 실행하고, 재무 건수와 호출 수를 기록한다.
- 이 문서의 진행 현황과 architecture.md(데이터 모델·수집 규칙)를 구현 결과에 맞춰 갱신한다.

### 하지 않는 것

신호 판정과 재무 지표 계산(4단계), 화면, AI, 시세·뉴스 모듈.

## 5. 구현할 때 점검할 제품 경계

product.md를 기준으로 구현 중 판단이 필요할 때 적용한다.

| 경계 | 점검 질문 | 근거 |
|---|---|---|
| 판정 ↔ 설명 | 방향·심각도·선별·연결을 코드가 하고 있는가? AI 프롬프트나 출력에 판정이 들어가 있지 않은가? | product.md §8, D-06 |
| 변화 ↔ 상태 | 새 화면·데이터가 "무엇이 언제 얼마나 변했나"에 답하는가, 상태 나열인가? | product.md §4, §11-1, D-28 |
| 연결 ↔ 나열 | 데이터를 보여 줄 때 변화·다른 데이터와 연결되는가? 연결 없는 목록이 늘어나지 않는가? | product.md §11-2, §12 |
| 이해 ↔ 판단 | 예측·추천·가치 판정·종합 평가·근거 없는 인과가 들어가지 않는가? | product.md §10, ai-analysis.md §7.2 |
| 근거 | 결과에 출처(공시번호·재무 기간)와 기준일을 붙일 수 있는가? 수집 단계에서 출처 식별자를 버리지 않는가? | product.md §11-5 |
| 핵심 ↔ 선택 모듈 | OpenDART만으로 동작하는가? 시세·뉴스가 없을 때의 동작이 정의되어 있는가? | D-22 |
| 시간 | 수집·신호 데이터에 발생 시점이 남는가? 이력을 덮어쓰지 않는가? | D-29 |

3-1 점검 결과: 공시는 공시번호(근거)와 접수일(기준일)을 반드시 저장하고, 정정 전 공시를 지우지 않으며(시간), 원 공시 연결은 코드가 한다(판정 ↔ 설명). 화면·AI·신호는 추가하지 않았다.
