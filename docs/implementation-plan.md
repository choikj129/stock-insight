| 로그·저장소 | 인증키가 로그와 저장소 파일 어디에도 없음을 확인 |

- 정정 연결 규칙을 실제 데이터로 점검하면서 기타정보를 연결 기준에서 빼도록 고쳤다(연결 559 → 580건). 다른 공시 유형의 공시에 연결된 경우는 0건이다.
- 연결되지 않은 정정은 대부분 원 공시가 적재 기간 앞에 있다. 표본 6건을 기업 지정 조회로 확인하니 원 공시가 1개월~2년 반 전이었다. 기본 적재 기간(3년)에서는 대부분 연결되고, 그보다 오래된 원 공시만 남는다.
- 호출량 추정: 45일 205호출 → 3년 약 5,000호출. 한 실행 상한 3,000으로 이틀에 나눠 받는다. 저장량은 3년 약 21만 건 수준이다.
- 이 실행은 확인용이며, 로컬 DB에 45일치가 남아 있다. 기본 설정으로 실행하면 남은 기간만 이어서 받는다.

| 문제 | 내용 | 제안 |
|---|---|---|
| 상장폐지 기업이 EXCLUDED로 남음 | 고유번호 파일과 기업개황은 상장폐지 기업의 종목코드를 계속 준다(예: 하나은행 004940, 쌍방울). 실제 동기화에서 상장사 3,994개 중 1,238개가 이런 "기타 시장"이었다. 기업개황 법인구분이 E(기타)로 바뀌므로 현재 코드는 이런 기업을 DELISTED가 아니라 EXCLUDED(OTHER_MARKET)로 저장한다. 수집 대상에서 빠지는 결과는 같지만 "상장폐지" 표시와 감지일이 남지 않는다 | 이전에 KOSPI·KOSDAQ이던 기업의 법인구분이 E가 되면 DELISTED로 바꾸는 규칙을 기업 목록 동기화에 추가. 기존 동작 변경이라 이번 작업에서는 하지 않음 |

| 같은 이름 원 공시가 여럿일 때 정정 연결 | 앞선 것 중 가장 최근 것에 연결하므로 드물게 틀릴 수 있다 (D-31 한계) | 화면·분석에서 문제가 되면 원문의 정정 대상 정보 활용 검토 |
| 과거 날짜에 공시가 뒤늦게 추가되는지 | 확정 후 다시 읽지 않으므로, 접수일이 지난 날짜에 공시가 추가되면 놓친다. 아직 사례를 확인하지 못했다 | 데이터 점검(4단계 전)에서 확정 날짜의 건수를 가끔 다시 세어 비교 |

### 4.3 수집 대상과 시점

| 항목 | 규칙 |
|---|---|
| 대상 기업 | ACTIVE 기업 (`CompanyService.activeCompanyIdsByDartCorpCode`) |
| 호출 단위 | (`bsns_year`, `report_code`) × 기업 100개 묶음. `fs_div`는 지정하지 않는다(응답에 둘 다 온다) |
| 초기 적재 | `bsns_year` = 올해−3 ~ 올해 × 4개 보고서 종류. 체크포인트가 없는 기업·기간만 묶는다. 약 26묶음 × 16 ≈ 420호출 |
| 증분 계기 | `disclosure`의 PERIODIC 공시(원 공시·정정 모두). 보고서명은 `base_report_name`을 쓴다 |
| 조회 키 계산 | `사업보고서 (YYYY.MM)` → (YYYY, 11011). `반기보고서 (YYYY.MM)` → (YYYY, 11012). `분기보고서 (YYYY.MM)` → 결산월 m 기준 MM이 m+3개월째면 11013, m+9개월째면 11014 (12월 결산: 03→11013, 09→11014. 6월 결산: 09→11013, 03→11014). 결산월이 없거나 어느 쪽도 아니면 그 공시를 오류로 남긴다. 그 밖의 정기공시(등록법인결산서류 등)는 무시한다 |
| 적재 기간 밖 | 조회 키의 `bsns_year`가 올해−3보다 작으면 무시한다(실제: 삼부토건 2019 사업보고서 정정) |
| 실행 시점 | 매일 06:30(공시 목록 수집 06:00 뒤) 한 번. 장중 없음. 한 실행 호출 상한(기본 500) |
| 실행 기록 | `pipeline_run` 작업명 `financial-sync`. 요약에 초기 적재·증분 대상 수를 나눠 적는다 |

**체크포인트** (`ingest_checkpoint`)

- 소스 `DART_FINANCIAL`, 대상 키 `고유번호:bsns_year:report_code`(예: `00126380:2026:11012`).
- 원천 버전 = 이 기업·기간에서 처리한 계기 공시번호 중 가장 큰 값. 초기 적재로 받았으면 null.
- 다시 받을 대상: 체크포인트가 없는 초기 적재 기간, 원천 버전보다 큰 계기 공시가 있는 기간(null은 모든 계기보다 작다고 본다), 직전 결과가 ERROR인 기간.
- 결과: 응답에 기업이 있으면 SUCCESS, 없으면 NO_DATA(계기 공시가 새로 올 때까지 다시 받지 않는다). 묶음 호출이 종료 대상이 아닌 오류로 실패하면 묶음의 기업 모두 ERROR.
- 응답의 기간 종료 월이 계기 보고서명의 월과 다르면 저장하지 않고 ERROR("기간 불일치").

### 4.4 기간·정정·연결/별도 처리 규칙

| 규칙 | 내용 |
|---|---|
| 기간 식별 | 저장 시 손익 행의 `thstrm_dt`("YYYY.MM.DD ~ YYYY.MM.DD")에서 `fiscal_year_start`, `period_end`를 읽는다. 손익 행이 없거나 형식이 다르면 그 기업·기간 ERROR |
| 저장 단위 | 한 기업·조회 키의 응답(연결·별도 모두)을 한 트랜잭션에서 통째로 바꾼다(기존 보고서와 계정 행 삭제 후 삽입, 또는 같으면 그대로). 응답에서 빠진 `fs_div`의 기존 보고서는 지운다 |
| 정정 | 계기 공시가 오면 다시 받아 바꾼다. 이전 값은 남기지 않는다. `[첨부정정]`처럼 값이 그대로면 `receipt_no`와 값이 같아 사실상 변경 없음 |
| 연결/별도 | 저장은 둘 다. 선택(연결 우선)은 읽을 때 (4단계) |
| 전년 비교 | 같은 보고서의 당기·전기 값으로 (4단계 지표 계산에서, ai-analysis.md §3.5) |
| 4분기 | 연간 − 3분기 누적, 전년 4분기 = 사업보고서 전기 − 3분기 보고서 전기누적 (4단계) |
| 비교 제외 | 기준(연결/별도)·통화가 다르거나 회계연도가 12개월이 아닌 기간 (4단계) |

### 4.5 업종별 예외 처리 범위

- 수집·저장은 업종과 무관하게 똑같이 한다(금융형 계정도 원천 그대로 저장).
- 재무제표 형식(일반/금융)은 유동자산 유무로 코드가 읽을 때 판별한다. 산업코드는 쓰지 않는다.
- 금융형은 필요한 계정이 있는 지표만 계산하고, 부채비율 신호를 만들지 않으며 "금융업 지표 해석 제한" 신호를 둔다 (ai-analysis.md §3.5, 4단계).
- 금융업 전용 지표(순이자손익 등)는 MVP에서 쓰지 않는다. 필요가 확인되면 매핑만 추가한다(다시 수집하지 않아도 된다).
- 비원화 기업: 비율·변화율은 계산하고, 금액 순위(AI 적용 대상, 동종업계 매출 상위)에서는 뺀다.

| 신호 판정(방향·심각도·발생 기준일), 같은 시기 공시 연결 | 코드가 준 신호·연결을 "무엇이 언제 얼마나 변했나"로 풀어 쓴다 |
| 숫자 자리표시자 채우기, 출처(공시번호)·기준일(기간 종료일) 표시 | 숫자는 자리표시자로만 쓴다. 계산·추정·방향 판단을 하지 않는다 |

3-2에서 구현하는 것은 이 표의 첫 줄(응답 해석과 저장)뿐이다. 나머지는 4단계에서 이 설계를 따른다.

### 4.7 구현 범위 (Sonnet 구현 세션용)

기존 공시 수집(3-1)의 구조와 관례를 그대로 따른다: `DartApi`/`DartClient`, `IngestCheckpointRepository`, `PipelineRunRecorder`, `TransactionTemplate`, 호출 상한·이어 받기, 종료 대상 오류 처리, JdbcClient 저장, 가짜 OpenDART + Testcontainers 테스트.

1. **마이그레이션 V3**: §4.2의 두 테이블.
2. **`ingest/dart`**
   - `DartApi.fetchKeyAccounts(List<String> corpCodes, int bsnsYear, String reportCode)` → `List<DartKeyAccount>`. 요청은 `fnlttMultiAcnt.json`, `corp_code`는 쉼표로 이은 최대 100개. 013은 빈 목록, 그 밖의 상태 코드는 기존 `DartStatus` 규칙(020·010·800 등은 실행 중단, 021·100은 묶음 오류).
   - `DartKeyAccount` 레코드: §4.1의 원천 필드를 문자열 그대로(`rcept_no`, `reprt_code`, `bsns_year`, `corp_code`, `fs_div`, `sj_div`, `account_nm`, `ord`, `thstrm_dt`, 금액 5종, `currency`).
3. **`financial` 패키지**
   - `FinancialService.replace(companyId, bsnsYear, reportCode, List<...> 응답 행)`: 기간 식별·금액 파싱·저장(§4.4). 저장 결과(신규/변경/같음) 반환.
   - `PeriodicReportName`(또는 유사 이름): `base_report_name` → (보고서 종류, 기간 종료 연월) 해석과 결산월로 조회 키 계산. 단위 테스트 대상.
   - 금액 파서: 쉼표·음수·`"-"`·빈 값.
   - 읽기용으로는 테스트에 필요한 최소 조회만 둔다. 지표 매핑·계산은 만들지 않는다.
4. **`disclosure`/`company` 조회 추가**: 계기 공시 목록(PERIODIC, 기업 ID·공시번호·`base_report_name`), ACTIVE 기업의 결산월.
5. **`ingest/financial`**: `FinancialSyncJob`(초기 적재 + 계기), `FinancialSyncProperties`(`cron` 기본 `0 30 6 * * *`, `run-on-startup`, `max-calls-per-run` 기본 500, `initial-load-years` 기본 3), 스케줄러. 계기 대상 먼저, 초기 적재는 그 뒤. 같은 조회 키의 기업을 100개씩 묶는다.
6. **테스트 샘플**(인증키로 받아 `src/test/resources/dart/`에 일부만 남김, README에 출처 기록):
   - `fnlttMultiAcnt` 2025/11012: 삼성전자(연결·별도), 모아텍(3월 결산), 양지사(별도만), KB금융(금융형) — 3개월·누적 필드, 기간, 형식 차이
   - 2025/11011: 삼성전자 — 사업보고서 필드(`bfefrmtrm`, 누적 없음), 당기순이익 중복
   - 2025/11011: 한일철강 — 정정 후 `rcept_no` 20260806000290
   - 013 응답(아직 제출 전 기간), 금액 `"-"`가 있는 행
7. **테스트**
   - 단위: 금액 파싱, 기간 식별(12월·3월·6월 결산, 3개월 값의 누적 기간 문자열), 보고서명 → 조회 키(6월 결산 3분기 → 다음 해 11014 포함), 결산월 없음·불일치.
   - 클라이언트: 실제 샘플로 필드 매핑, 013 → 빈 목록, 쉼표로 이은 `corp_code`, 인증키 비노출.
   - 동기화(가짜 OpenDART + Testcontainers): 초기 적재 100개 묶음·호출 상한 이어 받기, 응답에 없는 기업 NO_DATA 후 재호출 안 함, 정정 계기로 다시 받아 값·공시번호 교체, 값이 같은 재조회는 변경 없음, 적재 기간 밖 계기 무시, 기간 불일치 ERROR, 종료 대상 오류 시 실행 중단, ACTIVE 기업 없음 거부, 응답에서 빠진 `fs_div` 삭제.
8. **실제 확인**: 인증키로 로컬 초기 적재 1회. 호출 수·보고서 수·NO_DATA 수를 이 문서에 기록하고, 삼성전자·모아텍·양지사·KB금융·테라뷰(GBP)의 저장 결과를 확인한다.
9. **문서**: 이 문서 §1·§2 진행 현황, README 실행 방법, product.md §13 구현 현황.

## 5. 구현할 때 점검할 제품 경계

product.md를 기준으로 구현 중 판단이 필요할 때 적용한다.

| 경계 | 점검 질문 | 근거 |
|---|---|---|
| 판정 ↔ 설명 | 방향·심각도·선별·연결을 코드가 하고 있는가? AI 프롬프트나 출력에 판정이 들어가 있지 않은가? | product.md §8, D-06 |
| 변화 ↔ 상태 | 새 화면·데이터가 "무엇이 언제 얼마나 변했나"에 답하는가, 상태 나열인가? | product.md §4, §11-1, D-28 |
| 연결 ↔ 나열 | 데이터를 보여 줄 때 변화·다른 데이터와 연결되는가? 연결 없는 목록이 늘어나지 않는가? | product.md §11-2, §12 |
