# stock-insight 시스템 설계

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (MVP 기준) |
| 최종 수정 | 2026-09-25 |
| 관련 문서 | [제품 정의](product.md), [데이터·AI 분석 명세](ai-analysis.md), [설계 결정 기록](decisions.md) |

이 문서는 stock-insight의 현재 확정된 시스템 설계를 정의하는 기준 문서다. 설계가 바뀌면 이 문서를 먼저 고치고, 결정의 배경은 [설계 결정 기록](decisions.md)에 남긴다. AI 분석의 입력·출력·검증 세부는 [데이터·AI 분석 명세](ai-analysis.md)를 따른다. 제품이 무엇을 위해 존재하고 어떤 원칙을 지키는지는 [제품 정의](product.md)를 따른다. 이 문서는 그 목적을 시스템으로 구현하는 방법을 다룰 뿐, 제품의 목적 자체를 정의하지 않는다.

## 1. 개요

### 1.1 서비스 목표

제품의 목적과 판단 기준은 [제품 정의](product.md)가 최상위 기준이다: **Stock Insight는 기업의 변화와 그 맥락을 이해시켜주는 서비스다.** 이 문서는 그 목적을 시스템으로 구현하는 방법을 정한다.

- 전달 방식: **기업을 초등학생도 이해할 수 있도록 설명한다.** 이것은 목적이 아니라 목적을 전달하는 문체·눈높이다 (product.md §11-6).
- 이 서비스는 투자 판단을 제공하지 않는다. 주가 예측, 목표가격, 매수·매도 추천은 만들지 않는다.

### 1.2 확정 요구사항

| 항목 | 결정 |
|---|---|
| 대상 시장 | 국내 상장 주식(KOSPI·KOSDAQ)부터 시작한다. 해외 주식은 추후 확장한다 |
| 회원 | MVP는 로그인 없이 시작한다. 관심기업·이력은 추후 확장한다 |
| 시세 | 일별 시세로 시작한다. 단, 상업적 이용과 화면 게시가 허용된 소스를 확보한 뒤에 켠다 (§4.1, [D-22](decisions.md)) |
| 역할 분담 | 계산과 판단은 코드가, 설명은 AI가 담당한다 |
| 개발 | 백엔드 개발자 1인. 화면은 Thymeleaf + htmx |
| 구조 | MSA를 고려하지 않는다 |
| 인프라 | AWS 최소 구성으로 시작하고 규모에 따라 확장한다 |
| MVP | 과도하게 복잡하지 않게 구성한다 |

### 1.3 설계 원칙

1. **조회 경로에 AI가 없다.** 사용자가 페이지를 볼 때는 DB만 읽는다. AI는 백그라운드 파이프라인에서만 호출하며, MVP에는 실시간 AI 호출이 없다.
2. **계산과 판단은 코드, 설명은 AI.** 지표 계산, 순위, 신호의 방향·심각도 판정, 이벤트 추출, 분석 대상 선별은 코드가 한다. AI는 코드가 만든 결과와 원문을 쉬운 말로 설명한다. 코드가 계산한 숫자는 AI가 직접 쓰지 않고 코드가 채워 넣는다.
3. **상태 비교형 파이프라인.** 있어야 할 분석 결과를 계산하고, 현재 결과와 다른 것만 생성한다. 작업 큐와 이벤트 전달을 두지 않는다.
4. **서버는 1대로 시작하되 상태는 앱 밖에 둔다.** 데이터는 RDS와 S3에만 있으므로 앱 서버는 언제든 교체하거나 늘릴 수 있다.
5. **나중에 바꾸기 비싼 것만 지금 결정한다.** 나머지는 도입 조건이 생겼을 때 결정한다 (§12).
6. **투자 판단을 제공하지 않는다.** 모든 AI 콘텐츠에 AI 생성 표시, 출처, 데이터 기준일, 면책 문구를 붙인다.

## 2. 전체 아키텍처

### 2.1 구성도

```
사용자 ─HTTPS─▶ Route 53 ─▶ EC2 (퍼블릭 서브넷, 인바운드 80/443만)
                            ├─ Caddy: TLS 자동 발급·갱신, 리버스 프록시
                            └─ Spring Boot 앱 (단일 프로세스)
                                 ├─ 공개 웹: Thymeleaf 페이지 + JSON(검색·차트)
                                 ├─ 관리자: 비공개 포트 (SSM 포트 포워딩으로만 접근)
                                 └─ 스케줄러: 수집 → 신호·이벤트 계산 → 분석 동기화
                    │                     │                      │
          RDS PostgreSQL            S3 (공시 원문)         외부: OpenDART · Claude API
          (프라이빗 서브넷)                                   · 선택 모듈: 시세 소스, 네이버 검색 API

운영: ECR(이미지) · SSM(접속·배포·비밀값) · CloudWatch(로그·알람) · AWS Budgets
배포: GitHub Actions ─OIDC─▶ ECR 푸시 ─▶ SSM Run Command로 서버에서 compose 갱신
```

### 2.2 구성 요소와 책임

| 구성 요소 | 책임 |
|---|---|
| Route 53 | 도메인 DNS, 외부 헬스체크 |
| EC2 (1대) | Caddy와 Spring Boot 앱을 Docker Compose로 실행 |
| Caddy | TLS 인증서 자동 발급·갱신, 앱으로 리버스 프록시 |
| Spring Boot 앱 | 공개 웹, 관리자, 스케줄러(수집·신호 계산·분석 동기화)를 한 프로세스에서 실행 |
| RDS PostgreSQL | 정형 데이터, 분석 결과, 실행 로그 |
| S3 | 공시 원문(사업보고서 등) 보관. 재수집 없이 다시 파싱하기 위함 |
| ECR | 앱 컨테이너 이미지 |
| SSM | 서버 접속(Session Manager), 배포 명령(Run Command). 비밀값은 AWS 도입 후 Parameter Store를 원본으로 삼는다 (§8) |
| CloudWatch | 로그, 알람 |
| AWS Budgets | AWS 비용 알림 |
| 외부 서비스 | OpenDART, Claude API. 선택 모듈로 시세 소스, 네이버 검색 API (§4.1) |

### 2.3 런타임 구조

- 앱은 단일 프로세스다. 공개 웹, 관리자, 스케줄러가 함께 실행된다.
- 스케줄러는 설정값 `app.scheduler.enabled`로 켜고 끈다. 서버를 늘리면 스케줄러는 한 대에서만 켠다.
- 관리자 화면은 별도 포트에서 동작하며 보안 그룹에 열지 않는다. SSM 포트 포워딩으로만 접근한다.
- 수집과 AI 호출처럼 오래 걸리는 작업은 가상 스레드와 동시 실행 수 제한으로 처리해 웹 응답에 영향을 주지 않는다.
- 캐시는 TTL 기반(5~10분)만 쓰고 명시적 무효화는 하지 않는다. 서버가 여러 대가 되어도 동작이 달라지지 않게 하기 위함이다.

### 2.4 AWS 구성

| 리소스 | 구성 |
|---|---|
| VPC | 퍼블릭 서브넷(EC2, 이후 ALB)과 프라이빗 서브넷(RDS). NAT 게이트웨이 없음 |
| EC2 | t4g.small(ARM, 메모리 2GB)로 시작하고, 부족하면 t4g.medium. 보안 그룹 인바운드는 80/443만 |
| RDS | PostgreSQL 17, db.t4g.micro, 단일 AZ, 퍼블릭 접근 끔, 저장 암호화, 자동 백업 7일 |
| S3 | 공시 원문 버킷. 퍼블릭 접근 차단, 암호화 |
| 기타 | Route 53, ECR, SSM, CloudWatch, AWS Budgets |

**월 비용 대략치** (서울 리전, 온디맨드 기준)

| 항목 | 금액 |
|---|---|
| EC2 | 약 $15~30 |
| RDS + 스토리지 20GB | 약 $20 |
| 퍼블릭 IPv4 | 약 $4 |
| Route 53, S3, ECR, CloudWatch | 약 $3~5 |
| **합계** | **약 $45~65** |

- 사용하지 않는 것: NAT 게이트웨이(월 $40 이상), ALB(서버 1대에서는 이득 없음), CloudFront·WAF(트래픽이 생기면 도입).
- t4g는 ARM 인스턴스이므로 컨테이너 이미지를 arm64로 빌드한다.
- 단일 서버·단일 AZ이므로 배포 중 수십 초 중단과 장애 시 서비스 중단을 감수한다. 배포는 장 마감 후나 새벽에 한다.
- 사용량이 안정되면 Savings Plans로 할인을 받는다.

## 3. 주요 기술 선택

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | Java 21 (LTS) | 가상 스레드로 I/O가 많은 수집·AI 호출을 단순하게 처리한다. 현재 빌드 설정의 Java 17을 21로 올린다. 로컬·CI·운영 이미지 모두 같은 버전을 쓴다 |
| 프레임워크 | Spring Boot 4 | 초기화된 프로젝트, 개발자 숙련도 |
| 화면 | Thymeleaf + htmx | 서버 렌더링으로 SEO를 기본 확보한다. 언어와 배포 단위가 하나이고, 세션·CSRF 보호가 기본 제공된다 |
| 스타일·차트 | Tailwind(standalone CLI, Node 불필요) 또는 순수 CSS, Lightweight Charts(주가), Chart.js(재무) | 프론트 빌드 체인 최소화. CSS 방식은 화면 구현을 시작할 때 정한다 (나중에 바꿔도 비용이 작다) |
| 데이터 접근 | Spring Data JPA + JdbcClient, Flyway | 일반 CRUD는 JPA, 시세·재무 대량 upsert는 JDBC |
| DB | PostgreSQL 17 (RDS) | JSONB로 분석 결과 저장, 자동 백업·복구, 확장 경로 |
| 캐시 | Caffeine (TTL) | 프로세스 내부, 추가 인프라 없음 |
| 스케줄 | Spring `@Scheduled` (Asia/Seoul) | 작업 수가 적고 단일 프로세스 |
| 외부 호출 | RestClient, Jsoup | 단순 재시도와 호출 간격 조절로 충분하다. Jsoup은 공시 원문 HTML 파싱용 |
| AI | Anthropic Java SDK + 얇은 어댑터 | 구조화 출력, 프롬프트 캐싱, 추후 Batch API를 제약 없이 쓴다 |
| 테스트 | JUnit, Testcontainers, 실제 응답 샘플 기반 파서 테스트 | 공시 원문 파서가 가장 깨지기 쉬운 부분이다 |
| 빌드·배포 | Gradle `bootBuildImage`, Docker Compose, GitHub Actions(OIDC) | Dockerfile 없이 이미지를 만들고, 장기 AWS 키를 두지 않는다 |

**사용하지 않는 기술** (도입 조건은 §12)

Redis, 메시지 큐(SQS·Kafka·RabbitMQ), Kubernetes·ECS, ALB, CloudFront·WAF, ShedLock, Resilience4j, Spring AI·LangChain4j, pg_trgm, pgvector, Spring Modulith, 별도 에러 추적 서비스.

## 4. 데이터

### 4.1 데이터 소스

**핵심 소스 (MVP 필수)**

| 데이터 | 소스 | MVP 범위 |
|---|---|---|
| 기업 목록·고유번호·종목코드 | OpenDART 고유번호 파일 | 대상 종목 범위(§4.3) |
| 기업 개황 (시장 구분, 산업코드 포함) | OpenDART | 대상 종목 범위 |
| 공시 목록 | OpenDART 공시검색. 정기공시(A)·주요사항보고(B)·거래소공시(I) | 대상 종목 범위, 최근 3년 |
| 사업보고서 원문 | OpenDART 원문 → S3 | AI 적용 대상 기업 |
| 재무 | OpenDART 다중회사 주요계정 API (호출당 최대 100개사, 2015년 이후). 재무상태표·손익계산서 주요계정만, 현금흐름 없음 | 대상 종목 범위, 최근 3년 |
| 감사의견 등 | OpenDART 정기보고서 주요정보 API | 대상 종목 범위 |
| 주요사항(증자·사채 발행 등) | OpenDART 주요사항보고서 API (구조화 제공 범위 안에서) | 대상 종목 범위 |

OpenDART의 호출 한도는 인증키당 하루 20,000건이다. 짧은 시간에 과도하게 호출하면 이용이 제한될 수 있으므로 호출 간격을 둔다.

**선택 모듈 (이용 허락 확인 후 켠다)**

| 데이터 | 소스 | 상태 |
|---|---|---|
| 일별 시세 | 상업적 이용과 화면 게시가 허용된 유료 라이선스 소스 (예: KRX Data Marketplace) | 견적·계약 전. 확보 전까지 시세 기능은 꺼 둔다 |
| 뉴스 | 네이버 검색 API. 제목·링크·발행 시각만 저장 | 약관 확인 전. 확인 전까지 뉴스 기능은 꺼 둔다 |

- 공공데이터포털의 금융위원회 주식시세정보는 공공누리 제4유형(출처표시, 상업적 이용 금지, 변경 금지)이고, KRX OPEN API는 비상업적 이용만 허용하며 제3자 제공을 금지한다. 두 소스 모두 공개 서비스의 화면 게시와 계산에 쓰지 않는다. 개발 중 시험용으로도 쓰지 않는다.
- 선택 모듈이 꺼져 있어도 핵심 기능(기업 이해, 재무, 공시, 리스크, 향후 전망, 경쟁사 비교)은 모두 동작한다. 모듈이 꺼져 있을 때 보여 줄 대체 화면은 §6.2에 정한다.
- 거시·산업 통계는 사용하지 않는다.

산업 맥락은 외부 통계 대신 두 가지로 구성한다.
1. 사업보고서의 산업·시장 서술 (기업 이해 분석이 요약)
2. 동종업계 기업과의 재무 비교 지표 (코드가 계산)

### 4.2 데이터 모델

| 테이블 | 핵심 내용 |
|---|---|
| `company` | 대리키, 이름(종목명), 정식 사명, 초성, 산업코드, 결산월, DART 고유번호, 상태(ACTIVE: 대상 종목 범위 / EXCLUDED: 범위 밖 상장사 / DELISTED: 상장폐지), 제외 사유, AI 적용 대상 여부 |
| `security` | company_id, 종목코드, ISIN, 시장, 주식 종류, 통화, 상장·상장폐지일 |
| `company_alias` | 검색용 별칭 (사명 변경 전 이름 포함) |
| `price_daily` | security_id + 거래일, 시가·고가·저가·종가·거래량, 전일 대비, 등락률, 시가총액, 조정계수 (시세 모듈) |
| `market_holiday` | 휴장일 (거래소 연간 휴장일을 매년 등록) |
| `financial_report` | 주요계정 응답의 기업·기간·연결/별도 한 벌. 기업, 조회 키(`bsns_year`, 보고서 종류), 연결/별도, **회계연도 시작일**, 기간 구분(1분기·반기·3분기·연간), **기간 종료일**, 통화, 출처 공시번호(`rcept_no`). 자연키 = 기업 + 조회 키 + 연결/별도 ([D-32](decisions.md), [D-33](decisions.md)) |
| `financial_line` | 보고서의 계정 한 줄을 원천 그대로. 재무제표 구분(재무상태표/손익계산서), 계정명, 순서(`ord`), 금액 5종(당기, 당기누적, 전기, 전기누적, 전전기). 현금흐름 없음(D-14). 계정명 → 지표 키 매핑은 저장하지 않고 코드가 읽을 때 한다 |
| `disclosure` | 공시번호(자연키), 기업, 공시 유형(정기·주요사항·거래소), 보고서명(공백 정리), 정정 표시와 기타정보를 뗀 보고서명(원 공시 연결 기준), 정정 표시(기재정정·첨부정정·첨부추가 등), **접수일**(기준일), 제출인, 비고 원문(마지막으로 읽은 값), 원 공시. 정정 전 공시도 지우지 않는다. 원 공시 연결은 코드가 한다(§4.4, [D-31](decisions.md)) |
| `document_section` | 기업, 공시번호, 섹션 키, 정제 텍스트, 파서 버전 |
| `news_item` | 기업, 제목, URL, 발행 시각 |
| `competitor` | 기업 쌍, 출처(AI/수동), 상태(검토 대기/확정/해제), 근거 |
| `company_signal` | 기업, 신호 유형, 근거 키, 성격(상태/변화), 방향, 심각도, **발생 기준일**(재무 기간 종료일 또는 공시 접수일), **지속**(같은 방향이 이어진 연속 기간 수), 계산값, 확인 지표, 활성 여부, 최초 감지·마지막 판정 시각. **자연키 = 기업 + 신호 유형 + 근거 키**. 조건이 사라져도 행을 지우지 않고 비활성으로 남겨 변화 이력으로 쓴다 |
| `corporate_event` | 기업, 이벤트 유형, 날짜, 근거 |
| `content_entry` | 용어, 공시 유형, 신호 유형, 이벤트 유형, 확인 지표 설명 (정적 콘텐츠) |
| `analysis` | 대상 유형(기업/경쟁사 쌍)과 대상 키, 분석 종류, 지문, 상태, 결과 JSON, **값 스냅샷**, 스키마 버전, 프롬프트 버전, 모델, 토큰·비용, 오류, 시도 횟수, 생성 시각, 현재 게시본 여부 |
| `ingest_checkpoint` | 소스, 대상 키, 원천 버전(예: 고유번호 파일의 변경일), 결과(성공/데이터 없음/오류), 연속 오류 횟수, 마지막 시도·성공 시각. 증분 수집과 초기 적재 재개에 쓴다 |
| `pipeline_run` | 작업명, 상태(실행 중/성공/부분 처리/실패), 시작·종료 시각, 처리·실패 건수, 메시지. 부분 처리는 호출 상한에 닿아 다음 실행이 이어서 처리한다는 뜻이다 |

- 재무 비율, 4분기 단독값, 재무제표 형식(일반/금융), 동종업계 비교 지표는 저장하지 않고 코드로 계산한다.
- `analysis`는 덮어쓰지 않고 새 행을 추가한다. 화면은 현재 게시본만 읽는다.
- `analysis`의 값 스냅샷은 생성 당시 AI에 준 자리표시자 값이다. 화면은 현재 데이터가 아니라 이 스냅샷으로 숫자를 채운다. 그래야 설명 문장과 숫자가 어긋나지 않는다.
- 경쟁사 쌍의 대상 키는 두 기업 ID를 정렬해 만든다.
- 동기 호출에서 AI 호출 1회는 분석 결과 1건이므로 호출 로그를 `analysis`에 함께 기록한다.

### 4.3 데이터 규칙

나중에 바꾸기 비싼 규칙이므로 MVP부터 지킨다.

| 항목 | 규칙 |
|---|---|
| 대상 종목 범위 | KOSPI·KOSDAQ 상장 보통주. 시장 구분은 OpenDART 기업 개황으로 판단한다. 우선주는 보통주 기업에 속한 종목으로만 저장하고 별도 페이지를 만들지 않는다. 스팩, 리츠, ETF·ETN, KONEX는 제외한다. 범위 밖 상장사도 `company`에 EXCLUDED 상태와 제외 사유로 저장한다([D-27](decisions.md)). 이후 수집·분석은 ACTIVE 기업만 대상으로 한다 |
| 범위 판정 세부 | 스팩은 사명의 "스팩"·"기업인수목적", 리츠는 "리츠"·"부동산투자회사"로 판정한다. ETF·ETN은 OpenDART 기업 목록에 상장사로 나오지 않는다. 우선주 종목코드는 OpenDART가 제공하지 않으므로 시세 모듈 도입 때 채운다. 종목코드는 영문이 섞인 6자리일 수 있다 |
| 식별자 | 모든 테이블은 내부 대리키를 쓴다. DART 고유번호·종목코드·ISIN은 속성이다. 기업과 종목을 분리한다 |
| 상장폐지·사명 변경 | 상장폐지 기업은 페이지를 유지하고 상태를 표시하며 수집·분석을 멈춘다. 사명이 바뀌면 이전 이름을 별칭으로 남긴다 |
| 시간 | 시각은 UTC(timestamptz)로 저장하고 KST로 표시한다. 거래일은 DATE. 스케줄은 Asia/Seoul 기준 |
| 금액 | 원 단위 NUMERIC과 통화 컬럼. 억·조 단위 변환은 표시 계층에서 한다 |
| 회계 기간 | 회계연도 시작일 + 기간 구분(1분기·반기·3분기·연간) + 기간 종료일. 모두 응답의 손익 기간(`thstrm_dt`)에서 읽는다. `bsns_year`(= 보고서 기간 종료일의 연도)와 결산월로 회계연도를 계산하지 않는다. 12월 결산을 가정하지 않는다 ([D-33](decisions.md)) |
| 손익 값 | 분기·반기 보고서의 당기 값은 3개월 단독, 당기누적은 회계연도 누적이다. 사업보고서는 연간 값만 있다. 4분기 단독 = 연간 − 3분기 누적(같은 회계연도). 기간 문자열은 3개월 값에도 누적 기간을 보여 주므로 값의 의미는 필드로 판단한다 |
| 재무 기준 | 연결과 별도를 모두 저장하고, 읽을 때 기간마다 연결을 우선하고 연결이 없으면 별도를 쓴다. 쓴 기준을 화면에 표시한다. 각 기간의 값은 그 기간 보고서의 최신 정정본이다(API가 최신본만 준다) |
| 변화 계산 | 전년 동기 대비 변화는 같은 보고서 안의 당기·전기 값으로 계산한다(재작성·단위 차이가 변화로 잡히지 않게). 추이는 각 기간 보고서의 당기 값으로 그린다. 기준(연결/별도)이나 통화가 다른 기간끼리는 비교하지 않는다. 12개월이 아닌 회계연도는 "기간 불규칙"으로 표시하고 전년 동기 비교를 하지 않는다 |
| 재무제표 형식 | 응답에 유동자산이 있으면 일반형, 없으면 금융형(은행·보험·증권·카드 등. 유동/비유동 구분이 없고 매출액이 없을 수 있다)으로 코드가 판별한다. 산업코드로 판별하지 않는다(지주회사 64992는 대부분 일반형) |
| 수정주가 | 소스가 주는 전일 대비 값으로 기준가(종가 − 전일 대비)를 구하고, 기준가와 전일 종가의 비율로 조정계수를 만든다. 전일 대비 값이 없으면 등락률을 누적한다 |
| 휴장일 | 주말과 `market_holiday`에 등록된 날을 휴장일로 본다. 거래소가 발표한 다음 해 휴장일을 매년 12월에 등록한다. 수집 누락과 휴장을 구분하기 위함이다 |
| 원문 보관 | 공시 원문만 S3에 보관한다. 시세·뉴스는 다시 받을 수 있으므로 보관하지 않는다 |
| 분석 결과 | 스키마 버전, 지문, 프롬프트 버전, 모델, 값 스냅샷을 반드시 기록한다 |
| AI 적용 대상 | 최근 연간 매출액(원화, 연결 우선) 기준 상위 약 300개 + 관리자 추가 기업. 매출액이 없는 금융형 기업과 비원화 기업은 순위에서 빠지므로 관리자 추가로 보완한다([D-23](decisions.md)). 분기마다 다시 계산하고 `company`의 AI 적용 대상 여부로 저장한다. 대상에서 빠진 기업은 마지막 분석을 기준일과 함께 유지하고 더 갱신하지 않는다 |

### 4.4 수집 일정

| 작업 | 주기 (KST) |
|---|---|
| 기업 목록 동기화 (신규 상장·상장폐지·사명 변경) | 매일 새벽 |
| 공시 목록 수집 | 장중 30분 간격(당일분) + 매일 새벽 기업 목록 동기화 뒤(전날 확정, 초기 적재 이어 받기) |
| 재무 수집 (정기공시 계기) | 매일 새벽 공시 목록 수집 뒤 1회 ([D-34](decisions.md)) |
| 원문 수집 (사업보고서) | 재무 수집과 함께 (AI 적용 대상, 3-3 이후) |
| 시세 수집 → 순위 계산 (시세 모듈) | 소스 반영 시점에 1회 |
| 뉴스 수집 (뉴스 모듈) | 하루 2~3회. AI 적용 대상 기업과 당일 일일 변동 후보 |
| 신호·이벤트 계산 | 수집 직후 |
| 분석 동기화 | 신호 계산 후 |
| 데이터 신선도·범위 점검 | 매일 아침 |

- **기업 목록 동기화**: 고유번호 파일에서 종목코드가 있는 기업을 고르고, 목록에서 사라진 기업은 상장폐지로 표시한다(실제 폐지일이 아니라 감지일을 기록한다). 기업개황은 처음 보는 기업, 고유번호 파일의 변경일이 바뀐 기업, 직전 오류, 30일 이상 지난 기업 순으로 다시 받는다. 30일 재확인은 코넥스→코스닥 이전상장처럼 변경일에 드러나지 않는 변화를 잡기 위함이다. 상장사 수가 1,000개 미만이거나 기존보다 10% 넘게 줄면 잘못된 응답으로 보고 상장폐지 처리 없이 중단한다. 실제로는 고유번호 파일과 기업개황이 상장폐지 기업의 종목코드를 계속 주므로(2026-09-25: 종목코드 있는 3,994개 중 1,238개가 법인구분 "기타"), 이런 기업은 DELISTED가 아니라 EXCLUDED(기타 시장)로 저장된다. 수집 대상에서 빠지는 것은 같다. 상장폐지 표시 규칙은 implementation-plan.md §3에서 판단한다.
- **공시 목록 수집** ([D-31](decisions.md)):
  - 기업을 지정하지 않고 접수일 하루 × 공시 유형 단위로 끝 페이지까지 읽는다(페이지당 100건. 기업 미지정 조회는 기간이 3개월로 제한된다). 응답에는 비상장 기타법인과 범위 밖 상장사의 공시도 섞여 오므로 고유번호로 ACTIVE 기업을 골라 저장한다. 응답의 법인구분은 제출 당시가 아니라 조회 시점 값이므로 쓰지 않는다.
  - 정정 전 원 공시도 받는다(최종보고서만 검색하지 않음). 공시번호로 한 번만 저장하고, 다시 읽으면 비고 등 바뀐 값만 갱신한다.
  - 정정 연결: 보고서명 앞의 `[기재정정]`·`[첨부정정]`·`[첨부추가]` 등은 같은 보고서명으로 이미 제출된 보고서의 후속 제출이라는 뜻이다. 같은 기업에서 정정 표시와 기타정보(원본에서 공백 여러 칸 뒤의 부가 설명)를 뗀 보고서명이 같은 최초 제출 중 공시번호가 앞서는 가장 최근 것에 연결한다. 원 공시가 늦게 들어와도 저장할 때마다 다시 연결한다. 원 공시가 수집 기간 밖이면 연결하지 않는다. 한 원 공시의 최신본은 연결된 묶음에서 공시번호가 가장 큰 것이다.
  - 비고의 "정"(이후 정정 있음) 표시는 원 공시에 나중에 붙는다. 확정된 날짜는 다시 읽지 않으므로 정정 여부는 비고가 아니라 연결로 판단한다.
  - 체크포인트는 날짜·유형 단위(`DART_DISCLOSURE`, 키 예: `2026-08-14:A`)다. 그 날짜가 끝난 뒤(KST)에 오류 없이 읽어야 확정되고, 확정된 날짜는 다시 읽지 않는다. 장중 실행은 당일분만 읽고, 새벽 실행은 당일 → 확정 전·오류 날짜 → 아직 읽지 않은 날짜(초기 적재) 순으로 읽는다. 실행 기록에는 당일·미확정·초기 적재 대상 수를 나눠 남긴다.
  - 한 날짜·유형을 끝 페이지까지 읽지 못하고 호출 상한에 닿으면 기록하지 않고 다음 실행에서 처음부터 다시 읽는다.
  - ACTIVE 기업이 없으면(기업 목록 동기화 전) 실행하지 않는다. 공시 없이 날짜만 확정되는 것을 막기 위함이다.
  - 한계: 날짜를 확정한 뒤에 ACTIVE가 된 기업(코넥스→코스닥 이전상장 등)의 그 이전 공시는 받지 않는다.
- **재무 수집** ([D-32](decisions.md)~[D-34](decisions.md)):
  - 다중회사 주요계정 API를 `bsns_year` × 보고서 종류(1분기 11013, 반기 11012, 3분기 11014, 사업 11011) 단위로 ACTIVE 기업 100개씩 묶어 호출한다. 응답에는 연결·별도가 함께 온다(둘 다, 별도만, 연결만인 기업이 있다).
  - 초기 적재: 올해 포함 4개 `bsns_year` × 4개 보고서 종류. 응답에 없는 기업은 "데이터 없음"으로 두고 정기공시가 들어올 때만 다시 받는다.
  - 증분: 공시 목록 수집이 저장한 정기공시(원 공시와 모든 정정)를 계기로 그 기업·기간을 다시 받는다. 보고서명(정정 표시를 뗀 이름)의 종류와 기간 종료 연월로 조회 키를 정한다: 사업보고서 → 11011, 반기보고서 → 11012, 분기보고서 → 결산월 기준 3개월째면 11013, 9개월째면 11014. `bsns_year` = 기간 종료 연도. 응답의 기간 종료 월이 보고서명과 다르면 오류로 남긴다. 적재 기간보다 오래된 기간은 받지 않는다.
  - 체크포인트: `DART_FINANCIAL`, 키 `고유번호:bsns_year:보고서종류`, 원천 버전 = 처리한 계기 공시번호 중 가장 큰 것. 이보다 큰 정기공시가 들어오면 다시 받는다. `[첨부정정]`처럼 재무 값이 바뀌지 않는 정정은 다시 받아도 공시번호와 값이 그대로다.
  - 다시 받으면 그 기업·기간의 보고서와 계정 행을 응답으로 바꾼다. 금액 문자열은 쉼표를 떼고, 빈 값·"-"는 값 없음으로 저장한다.
- **OpenDART 오류 처리**: 인증키 오류, 호출 한도 초과(020), 점검(800), 재시도 후 통신 실패는 실행 전체를 멈춘다. 그 밖의 오류는 해당 기업만 오류로 기록하고 다음 실행에서 다시 시도한다. 통신 오류와 5xx만 재시도한다. 요청 URL에 인증키가 들어 있으므로 예외 메시지와 로그에 URL을 남기지 않는다.
- **실행 순서**: 수집 → 신호·이벤트 계산 → 분석 동기화는 하나의 순차 실행으로 묶는다. 같은 작업이 겹쳐 실행되지 않게 한다. 장중 공시 수집만 별도로 돈다.
- **초기 적재**: 대상 종목의 3년 재무(약 420호출)를 호출 한도 안에서 나눠 받는다. `ingest_checkpoint`에 남은 대상을 기준으로 이어 받고, "데이터 없음"으로 확인된 대상은 반복 요청하지 않는다. 다중회사 API(호출당 100개사)를 쓰면 재무 적재는 수백 건의 호출로 끝난다. 공시 목록 3년은 약 3,300(날짜 × 유형) 호출에 추가 페이지가 붙는다(정기보고서 제출 마감일은 정기공시만 하루 26페이지). 한 실행 상한 3,000호출로 두어 번에 나눠 받는다.
- **데이터 점검**: 받아야 할 데이터를 받았는지, 값이 정상 범위인지(단위 이상, 누락 기간, 거래정지가 아닌데 거래량 0) 매일 확인하고 이상하면 알림을 보낸다. 받아야 할 날짜는 휴장일 규칙으로 판단한다.

## 5. 데이터·AI 분석 구조

상세 명세는 [데이터·AI 분석 명세](ai-analysis.md)를 따른다.

### 5.1 분석 계층

```
원천 데이터 ─[코드]─▶ 지표·순위·신호·이벤트 ─[AI]─▶ 1차 분석 ─[AI]─▶ 2차 분석 ─[코드]─▶ 화면 조립
```

- **코드 산출물**: 재무 지표, 등락 순위, 동종업계 비교, 기업 신호(방향·심각도), 향후 이벤트
- **1차 분석**: 원천 데이터와 코드 산출물을 입력으로 쓴다 (기업 이해, 재무 쉬운 설명, 일일 변동)
- **2차 분석**: 1차 분석 결과와 코드 산출물을 입력으로 쓴다 (향후 전망, 경쟁사 비교). 원문을 다시 읽지 않으므로 저렴하다

### 5.2 분석 종류

| 분석 | 계층 | 대상 | 재생성 기준 (지문) |
|---|---|---|---|
| 기업 이해 | 1차 | AI 적용 대상 | 최신 사업보고서 |
| 재무 쉬운 설명 | 1차 | AI 적용 대상 | 최신 재무 기간 |
| 일일 변동 (시세 모듈) | 1차 | 등락 상위 중 근거가 있는 기업 (AI 적용 대상과 무관) | 거래일 + 근거 |
| 향후 전망 | 2차 | AI 적용 대상 | 기업 이해 결과 + 재무 기간 + 선별 신호 (최소 7일 간격) |
| 경쟁사 비교 | 2차 | 확정 경쟁사 쌍 | 두 기업의 1차 분석 결과 |

### 5.3 향후 전망 요약

향후 전망은 **예측이 아니라 앞으로 지켜볼 점**을 설명한다. 주요 요인, 긍정 요인, 부정 요인, 확인할 지표·이벤트, 불확실성으로 구성한다.

- 요인의 방향과 심각도, 선별은 코드가 기업 신호로 판정한다.
- AI는 요인·신호·지표별 설명만 쓰고, 어느 섹션에 둘지는 코드가 신호의 방향으로 정한다.
- 주가 예측, 목표가격, 실적 수치 예측, 가치 판정, 매수·매도 추천은 하지 않는다.

세부는 [데이터·AI 분석 명세 §5](ai-analysis.md#5-향후-전망-분석)를 따른다.

### 5.4 분석 동기화

1. 기업과 분석 종류마다 기대 지문을 계산한다.
2. 같은 지문의 결과가 이미 게시되었거나 관리자가 숨겼으면 건너뛴다.
3. 생성하고 검증한다. 통과하면 게시하고, 실패하면 이전 게시본을 유지한다.
4. 1차 분석을 먼저, 2차 분석을 나중에 처리한다.
5. 일일 AI 예산 안에서만 실행한다.
6. 프롬프트 변경은 자동 재생성 조건이 아니다. 관리자가 예산을 정해 점진적으로 재생성한다.

### 5.5 AI 사용 방식

- 초기 기본 모델은 Claude Sonnet 5로 하고, 골든셋 비교(상위 모델 포함) 후 분석 종류별로 확정한다. 모델은 설정값이다.
- 동기 호출, 구조화 출력(JSON 스키마), 고정 시스템 프롬프트에 프롬프트 캐싱을 적용한다.
- 운영 AI 비용 예상 (AI 적용 대상 약 300개 기준): 핵심 범위만이면 월 약 $20~45, 시세 모듈의 일일 변동을 켜면 월 약 $40~70. 최초 전체 생성에 약 $70이 별도로 든다.

## 6. 화면

### 6.1 페이지와 URL

| 페이지 | URL | 내용 |
|---|---|---|
| 홈 | `/` | 검색, 관리자가 고른 주요 기업, 최근 주요 변화(새 변화 신호·주요 공시)가 생긴 기업. 시세 모듈을 켜면 거래대금 기준 인기 기업과 상승·하락 상위를 추가 |
| 기업 상세 | `/stocks/{종목코드}` | §6.2 |
| 기업 비교 | `/compare/{종목코드A}-vs-{종목코드B}` | 코드가 만든 데이터 비교와 두 기업의 한 줄 요약. 확정 경쟁사 쌍이면 AI 비교 설명 추가 |
| 용어 | `/terms/{용어}` | 용어 설명 |

- URL은 종목코드 기반으로 고정한다. 사명은 URL에 쓰지 않는다.
- 비교 URL은 종목코드 순서로 정규화하고 canonical을 지정한다.

### 6.2 기업 상세 구성

기업 상세는 **변화를 먼저, 상태는 그 맥락으로** 배치한다 (product.md §11-1, §14, [D-28](decisions.md)). 섹션 순서는 아래 표의 순서다.

| 섹션 | 코드가 만드는 부분 | AI가 만드는 부분 |
|---|---|---|
| 개요 | 기본 정보 | 한 줄 요약 (기업 이해) |
| **최근 변화** | 변화 타임라인: 변화 신호와 이벤트를 발생 시점 순으로 배치하고, 각 변화에 같은 시기의 관련 공시·재무 근거를 연결 | 변화별 쉬운 설명 (향후 전망의 신호별 설명을 재사용) |
| 앞으로 지켜볼 점 (향후 전망) | 확인할 지표·현재 값, 향후 이벤트 날짜, 불확실 신호 배치, 부제·면책 | 요인·지표·불확실성 설명, 한 줄 정리 (향후 전망) |
| 재무 | 차트, 지표 (변화율 중심) | 쉬운 설명 (재무 쉬운 설명) |
| 주가 (시세 모듈) | 수정 시계열 차트, 등락률. 모듈이 꺼져 있으면 외부 시세 페이지 링크만 | 최근 변동 이유 (일일 변동). 근거가 없으면 코드 템플릿 문장. 최근 5거래일 안의 결과만 표시 |
| 리스크 | 현재 위험 신호(상태·부정 신호)와 유형별 정적 설명 | 사업상 위험 서술 (기업 이해) |
| 사업구조·제품·고객 | — | 기업 소개와 사업 서술 (기업 이해) |
| 경쟁사 | 확정 경쟁사 목록, 비교 링크 | — |
| 공시 전체 | 공시 목록(근거 원문 탐색용), 공시 유형 설명(정적) | — |

- 향후 전망 분석(ai-analysis.md §5)의 긍정·부정 요인 설명은 "최근 변화" 섹션에서 변화별 설명으로 보여 주고, 확인할 지표·이벤트·불확실성은 "앞으로 지켜볼 점"에서 보여 준다. 분석 자체는 바꾸지 않고 화면 배치만 나눈다.
- 뉴스(뉴스 모듈)는 변화 신호·이벤트와 연결된 것만 해당 변화의 근거로 보여 준다. 기업별 최신 뉴스를 단순 나열하는 목록은 만들지 않는다 (product.md §12 예시).
- 모든 AI 콘텐츠에 AI 생성 표시, 출처, 데이터 기준일을 붙인다. 이 문구는 코드가 붙인다.
- 본문의 전문용어는 코드가 용어 사전과 매칭해 툴팁을 단다.
- AI 적용 대상이 아닌 기업도 "최근 변화" 타임라인(코드)과 유형별 정적 설명은 보여 준다. AI 설명은 AI 적용 대상 기업에만 있고, 일일 변동은 예외다.

### 6.3 렌더링 규칙

- SEO에 필요한 핵심 콘텐츠는 첫 HTML에 포함한다. htmx는 검색 자동완성, 탭·기간 전환, 차트 데이터에만 쓴다.
- sitemap을 제공하고, 메타 설명은 한 줄 요약에서 가져온다.
- 모바일 우선으로 설계한다.
- 공개 페이지는 사용자와 무관하게 만든다. 개인화 기능은 나중에 별도 htmx 조각으로 붙인다. 이렇게 해야 페이지 캐시(CDN)와 충돌하지 않는다.
- AI 출력은 제한된 마크다운만 허용하고 sanitizer를 거쳐 렌더링한다.
- 검색은 전 종목과 별칭(초성 포함)을 메모리 인덱스에 올려 처리한다.

## 7. 프로젝트 구조

기준 패키지는 `org.stockinsight`이다. Gradle 모듈은 하나로 두고 기능별로 패키지를 나눈다.

```
src/main/java/org/stockinsight/
├── company/     기업·종목·별칭·검색·경쟁사
├── market/      휴장일, 시세·수정 시계열·등락 순위 (시세 모듈)
├── financial/   재무 요약·지표 계산·동종업계 비교
├── disclosure/  공시·원문 섹션 추출·향후 이벤트 추출
├── news/        뉴스 저장·기업 매칭
├── signal/      기업 신호 규칙 카탈로그·신호 계산
├── analysis/    분석 종류 정의·입력 구성·지문·동기화·검증·게시
│   └── llm/     Anthropic SDK 어댑터·프롬프트 로더
├── content/     정적 콘텐츠(용어·유형 설명)
├── ingest/      외부 API 클라이언트(dart, price, naver)·원문 S3 저장·수집 스케줄
├── web/         공개 페이지 컨트롤러·JSON 엔드포인트·뷰 모델
├── admin/       관리자(비공개 포트)
└── common/      설정·보안·예외·공통 유틸

src/main/resources/
├── prompts/        분석 종류별 프롬프트(v{n}.md)·출력 스키마(schema.json)·공통 스타일 가이드
├── db/migration/   Flyway 마이그레이션
└── templates/      Thymeleaf 템플릿
```

- 다른 패키지의 리포지토리나 엔티티를 직접 쓰지 않고 서비스를 통해 접근한다.
- 스케줄은 `ingest`, `signal`, `analysis`에만 두고 `app.scheduler.enabled`로 켜고 끈다.
- 컨트롤러는 얇게 두고, 서비스는 뷰와 무관한 DTO를 반환한다. 나중에 `/api/v1`을 붙이기 쉽게 하기 위함이다.
- Gradle 멀티모듈은 쓰지 않는다.

## 8. 보안

MVP는 로그인이 없고 실시간 AI 호출이 없으므로 개인정보 유출과 AI 비용 공격 위험이 구조적으로 없다. 남은 위험에는 아래를 적용한다.

| 영역 | 대응 |
|---|---|
| AWS 계정 | 루트 계정에 MFA를 걸고 사용하지 않는다. 개인 계정도 MFA를 쓴다 |
| 권한 | EC2 인스턴스 역할은 최소 권한(SSM 파라미터 읽기, 지정 S3 버킷, ECR 이미지 받기, 로그 쓰기)만 가진다. GitHub Actions는 OIDC 역할로 ECR 푸시와 SSM 명령만 허용한다. 장기 액세스 키를 두지 않는다 |
| 네트워크 | 보안 그룹 인바운드는 80/443만 연다. SSH 포트를 열지 않고 SSM Session Manager로 접속한다. RDS는 퍼블릭 접근을 끄고 EC2 보안 그룹에서만 접근하며 TLS를 쓴다 |
| 관리자 | 외부에 열지 않은 포트 + SSM 포트 포워딩 + 앱 인증(관리자 계정 1개, 자격 증명은 비밀값 파일). 공개 포트에서는 관리자 경로에 응답하지 않는다 |
| 비밀값 | **저장소 밖 비밀값 파일**을 앱이 기동 시 직접 읽는다 ([D-30](decisions.md)). 로컬(터미널·IntelliJ 공통)은 `~/.stockinsight/secrets.yml`, 운영은 `/etc/stockinsight/secrets.yml`(소유자만 읽기). 경로는 `STOCKINSIGHT_SECRETS`로 바꿀 수 있고, 같은 이름의 환경 변수가 파일보다 우선한다. 저장소에는 값 없는 `secrets.example.yml`만 둔다. 운영 파일은 AWS 도입 시 Parameter Store(SecureString)의 값으로 배포 단계에서 만든다. 커밋 이력은 CI의 gitleaks와 GitHub secret scanning으로 검사한다. Flyway용 DB 계정을 앱 계정과 분리한다 |
| 비용 | AWS Budgets 알림, Anthropic 월 지출 한도, 앱 내부 AI 예산(일·월). Anthropic API 키는 개발용과 운영용을 분리한다 |
| AI 입력 | 공시·뉴스 텍스트는 신뢰할 수 없는 데이터로 취급한다. AI에는 도구나 권한을 주지 않는다(텍스트 입력 → JSON 출력). 데이터는 구분자로 감싸고, 데이터 안의 지시를 따르지 않도록 명시한다 |
| AI 출력 | 스키마·참조·숫자·금지 표현을 검증한 뒤 게시한다. 렌더링할 때 이스케이프와 sanitizer를 거친다 |
| 웹 | Thymeleaf 자동 이스케이프, CSRF 보호, CSP 등 보안 헤더, 검색 API 호출 속도 제한 |
| 외부 호출 | 허용된 호스트만 호출한다. 뉴스 링크를 따라가 본문을 가져오지 않는다. 응답 크기와 타임아웃을 제한한다 |
| 데이터 | RDS 자동 백업 7일 + 월 1회 스냅샷. S3 퍼블릭 차단·암호화. 로그 30일 보관 |
| 의존성 | Dependabot, 컨테이너 이미지 정기 재빌드 |
| 법·신뢰 | 면책 문구, AI 생성 표시, 출처·기준일, 개인정보처리방침(접속 로그 등) |

회원 기능을 도입할 때 추가할 사항은 §11.2를 따른다.

## 9. 운영

| 항목 | 방식 |
|---|---|
| 환경 | 로컬(Docker Compose PostgreSQL)과 운영 두 개. 스테이징 대신 관리자의 초안 미리보기를 쓴다 |

| 알람 | EC2 상태 체크, RDS 저장공간·CPU, 외부 헬스체크, 파이프라인 실패, 데이터 신선도. 알림은 SNS 이메일 한 곳으로 모은다 |

| 정기 작업 | 매년 12월 다음 해 휴장일 등록, 분기마다 AI 적용 대상 재계산 |
| AI 호출 한도 | Anthropic 조직의 사용 등급별 분당 토큰 한도 안에서 동시 호출 수를 정한다. 대량 생성 전에 등급을 확인한다 |
| 비용 집중 시기 | 정기보고서 제출 기한 직후(3월 말, 5월 중순, 8월 중순, 11월 중순)에 재무 설명·향후 전망 재생성이 몰린다. 월 예산 안에서 며칠에 나눠 처리되는 것을 허용한다 |
| 장애 대응 | 원천 데이터나 AI에 장애가 나도 마지막 데이터와 게시본을 기준일과 함께 유지한다. 서비스를 멈추지 않는다 |
| 런북 | 인프라를 구성할 때 `docs/runbook.md`로 작성한다. AWS 구성 체크리스트, 복구 절차(RDS 특정 시점 복구, 인스턴스 재생성), 키 교체 절차를 담는다 |
| 오류 신고 | 이메일 또는 외부 폼 링크 |

## 10. MVP 범위

**핵심 범위 (OpenDART만으로 동작)**

| 영역 | 포함 |
|---|---|
| 데이터 | 대상 종목 범위(§4.3)의 기업·재무 요약·공시 |
| AI 적용 대상 | 매출액 기준 상위 약 300개 + 관리자 추가 |
| AI 분석 | 기업 이해, 재무 쉬운 설명, 향후 전망, 확정 경쟁사 쌍 비교 |
| 코드 산출 | 재무 지표, 동종업계 비교, 기업 신호, 향후 이벤트, 용어 매칭 |
| 정적 콘텐츠 | 용어, 공시 유형, 신호 유형, 이벤트 유형, 확인 지표 설명 (AI 초안 + 사람 검토) |
| 화면 | 홈, 기업 상세, 기업 비교, 용어 |
| 관리자 | 재생성, 숨김, 초안 미리보기, 경쟁사 확정, 실행 로그 |
| 인프라 | EC2, RDS, S3, Route 53, ECR, SSM, CloudWatch, AWS Budgets |
| 신뢰·법 | 면책, AI 생성 표시, 출처·기준일, 개인정보처리방침 |

**선택 모듈 (이용 허락 확보 시 MVP에 포함)**

| 모듈 | 포함 기능 |
|---|---|
| 시세 | 일별 시세, 수정 시계열 차트, 상승·하락 상위, 거래대금 기준 인기 기업, 일일 변동 분석 |
| 뉴스 | 변화 신호·이벤트와 연결된 뉴스, 향후 전망의 "확인이 필요한 보도", 일일 변동의 근거 |

### 구현 순서

1. 선택 모듈의 이용 허락 확인을 시작한다. 결과를 기다리지 않고 다음 단계로 진행한다.
2. 프로젝트 기반(빌드, 로컬 DB, 마이그레이션, CI)을 만든다.
3. OpenDART 수집과 초기 적재를 구현한다.
4. 코드 산출물(재무 지표, 신호, 이벤트)과 AI 없는 화면을 만든다. 이 단계만으로도 쓸 만해야 한다.
5. AWS에 비공개로 배포해 운영 경로를 먼저 검증한다.
6. AI 파이프라인을 만들고 골든셋 20개로 1차 분석을 다듬은 뒤 2차 분석을 추가한다.
7. AI 적용 대상 약 300개로 넓히고 SEO·보안을 점검한 뒤 공개한다.
8. 이용 허락이 확보된 선택 모듈을 켠다.

진행 현황과 다음 단계의 상세 계획은 [구현 계획](implementation-plan.md)에서 관리한다.

## 12. 의도적으로 제외한 기능과 도입 조건

### 12.1 도입하지 않는 기능

| 기능 | 이유 |
|---|---|
| 주가 예측, 목표가격, 적정 주가 | 서비스 원칙(기업 이해) 위반, 투자자문 규제 위험 |
| 매수·매도 추천, 종목 추천 | 같음 |
| 실적 수치 예측 (매출·이익 전망치) | 예측은 서비스 범위가 아니다. 향후 전망은 요인과 확인할 점만 설명한다 |
| 저평가·고평가 등 가치 판정, 종합 평가 | 투자 판단에 해당한다 |
| 증권사 컨센서스·실적 추정치 표시 | 예측 성격의 외부 데이터이며 라이선스가 필요하다. 도입하려면 서비스 원칙부터 다시 검토한다 |

### 12.2 나중에 도입할 기능

| 기능 | 제외 이유 | 도입 조건 |
|---|---|---|
| 로그인, 관심기업, 조회 이력 | 개인정보·보안 범위 최소화 | 공개 후 재방문 사용자 확인 |
| 실시간 AI (임의 쌍 비교, 질문) | 인증 없이는 비용 공격 경로가 된다 | 로그인 도입 후 사용자별 한도와 함께 |
| 조회가 많은 임의 쌍의 AI 비교 | MVP 단순화 | 비교 페이지 조회 데이터 확보 후, 매일 상위 K쌍만 예산 상한 안에서 |
| 포트폴리오 분석 | 로그인 전제, 규제 검토 필요 | 로그인 + 법률 검토 |
| 시세 모듈 (일별 시세와 이를 쓰는 기능) | 무료 소스는 상업적 이용과 재배포를 허용하지 않는다 | 상업적 이용과 화면 게시가 허용된 소스의 계약 |
| 뉴스 모듈 | 약관 미확인 | 네이버 검색 API 약관에서 공개 서비스 게시가 허용됨을 확인 |
| 장중·실시간 시세 | 라이선스 비용 | 사용자 요구 확인 + 라이선스 계약 |
| 해외 주식 | 범위 관리 | 국내 서비스 안정화 후 |
| 거시·산업 외부 통계 | MVP 단순화 | 향후 전망 품질 검토에서 산업 맥락 부족이 확인될 때 |
| 전체 재무제표 정규화 (현금흐름·부문별) | 화면에 필요하지 않음 | 해당 정보를 화면에 보여 줄 때 |
| 산업 설명 페이지 | 범위 관리 | 업종 페이지를 도입할 때 |
| 전 종목 AI 적용 + Batch API | 소규모에서는 이득이 작고 품질 검증이 우선 | 약 300개 기업의 품질 확인 후 |
| 다중 모델 운용 | 평가와 캐시가 모델별로 분리된다 | 특정 분석 종류에서 품질·비용 문제가 측정될 때 |
| 뉴스 AI 관련성 분류 | 규칙 매칭으로 충분 | 오매칭이 문제가 될 때 |
| 조회수 기반 인기 기업 | 트래픽이 필요 | 일정 수준의 방문자 확보 후 |
| 자동 품질 평가 (AI 채점) | 수동 검토로 충분 | 전 종목 적용 시 |
| 사이트 내 오류 신고 폼 | 공개 쓰기 경로를 만들지 않기 위함 | 로그인 도입 후 |
| CloudFront·WAF, ALB·다중 서버, Multi-AZ, IaC | 현재 규모에서 비용 대비 이득 없음 | §11.1의 단계별 조건 |
| Redis, 메시지 큐, MSA, Kubernetes | 필요 없음 | 측정된 병목이 있을 때만 |
