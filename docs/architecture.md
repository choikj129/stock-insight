# stock-insight 시스템 설계

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (MVP 기준) |
| 최종 수정 | 2026-09-24 |
| 관련 문서 | [데이터·AI 분석 명세](ai-analysis.md), [설계 결정 기록](decisions.md) |

이 문서는 stock-insight의 현재 확정된 시스템 설계를 정의하는 기준 문서다. 설계가 바뀌면 이 문서를 먼저 고치고, 결정의 배경은 [설계 결정 기록](decisions.md)에 남긴다. AI 분석의 입력·출력·검증 세부는 [데이터·AI 분석 명세](ai-analysis.md)를 따른다.

## 1. 개요

### 1.1 서비스 목표

주식 전문가가 아닌 일반 투자자가 기업을 쉽게 이해할 수 있도록, 외부에서 수집한 기업 데이터를 이해하기 쉬운 설명으로 바꿔 제공한다.

- 핵심 컨셉: **기업을 초등학생도 이해할 수 있도록 설명한다.**
- 이 서비스는 투자 판단을 제공하지 않는다. 주가 예측, 목표가격, 매수·매도 추천은 만들지 않는다.

### 1.2 확정 요구사항

| 항목 | 결정 |
|---|---|
| 대상 시장 | 국내 상장 주식(KOSPI·KOSDAQ)부터 시작한다. 해외 주식은 추후 확장한다 |
| 회원 | MVP는 로그인 없이 시작한다. 관심기업·이력은 추후 확장한다 |
| 시세 | 일별 시세로 시작한다 |
| 역할 분담 | 계산과 판단은 코드가, 설명은 AI가 담당한다 |
| 개발 | 백엔드 개발자 1인. 화면은 Thymeleaf + htmx |
| 구조 | MSA를 고려하지 않는다 |
| 인프라 | AWS 최소 구성으로 시작하고 규모에 따라 확장한다 |
| MVP | 과도하게 복잡하지 않게 구성한다 |

### 1.3 설계 원칙

1. **조회 경로에 AI가 없다.** 사용자가 페이지를 볼 때는 DB만 읽는다. AI는 백그라운드 파이프라인에서만 호출하며, MVP에는 실시간 AI 호출이 없다.
2. **계산과 판단은 코드, 설명은 AI.** 지표 계산, 순위, 신호의 방향·심각도 판정, 이벤트 추출, 분석 대상 선별은 코드가 한다. AI는 코드가 만든 결과와 원문을 쉬운 말로 설명한다. 코드가 계산한 숫자는 AI가 직접 쓰지 않고 코드가 채워 넣는다.
3. **상태 비교형 파이프라인.** 있어야 할 분석 결과를 계산하고, 현재 결과와 다른 것만 생성한다. 작업 큐와 이벤트 전달을 두지 않는다.
4. **서버는 1대로 시작하되 상태는 앱 밖에 둔다.** 데이터는 RDS와 S3에만 있으므로 앱 서버는 언제든 교체하거나 늘릴 수 있다.
5. **나중에 바꾸기 비싼 것만 지금 결정한다.** 나머지는 도입 조건이 생겼을 때 결정한다 (§12).
6. **투자 판단을 제공하지 않는다.** 모든 AI 콘텐츠에 AI 생성 표시, 출처, 데이터 기준일, 면책 문구를 붙인다.

## 2. 전체 아키텍처

### 2.1 구성도

```
사용자 ─HTTPS─▶ Route 53 ─▶ EC2 (퍼블릭 서브넷, 인바운드 80/443만)
                            ├─ Caddy: TLS 자동 발급·갱신, 리버스 프록시
                            └─ Spring Boot 앱 (단일 프로세스)
                                 ├─ 공개 웹: Thymeleaf 페이지 + JSON(검색·차트)
                                 ├─ 관리자: 비공개 포트 (SSM 포트 포워딩으로만 접근)
                                 └─ 스케줄러: 수집 → 신호·이벤트 계산 → 분석 동기화
                    │                     │                      │
          RDS PostgreSQL            S3 (공시 원문)         외부: OpenDART · 시세 소스
          (프라이빗 서브넷)                                   · 네이버 검색 API · Claude API

운영: ECR(이미지) · SSM(접속·배포·비밀값) · CloudWatch(로그·알람) · AWS Budgets
배포: GitHub Actions ─OIDC─▶ ECR 푸시 ─▶ SSM Run Command로 서버에서 compose 갱신
```

### 2.2 구성 요소와 책임

| 구성 요소 | 책임 |
|---|---|
| Route 53 | 도메인 DNS, 외부 헬스체크 |
| EC2 (1대) | Caddy와 Spring Boot 앱을 Docker Compose로 실행 |
| Caddy | TLS 인증서 자동 발급·갱신, 앱으로 리버스 프록시 |
| Spring Boot 앱 | 공개 웹, 관리자, 스케줄러(수집·신호 계산·분석 동기화)를 한 프로세스에서 실행 |
| RDS PostgreSQL | 정형 데이터, 분석 결과, 실행 로그 |
| S3 | 공시 원문(사업보고서 등) 보관. 재수집 없이 다시 파싱하기 위함 |
| ECR | 앱 컨테이너 이미지 |
| SSM | 서버 접속(Session Manager), 배포 명령(Run Command), 비밀값(Parameter Store) |
| CloudWatch | 로그, 알람 |
| AWS Budgets | AWS 비용 알림 |
| 외부 서비스 | OpenDART, 시세 소스, 네이버 검색 API, Claude API |

### 2.3 런타임 구조

- 앱은 단일 프로세스다. 공개 웹, 관리자, 스케줄러가 함께 실행된다.
- 스케줄러는 설정값 `app.scheduler.enabled`로 켜고 끈다. 서버를 늘리면 스케줄러는 한 대에서만 켠다.
- 관리자 화면은 별도 포트에서 동작하며 보안 그룹에 열지 않는다. SSM 포트 포워딩으로만 접근한다.
- 수집과 AI 호출처럼 오래 걸리는 작업은 가상 스레드와 동시 실행 수 제한으로 처리해 웹 응답에 영향을 주지 않는다.
- 캐시는 TTL 기반(5~10분)만 쓰고 명시적 무효화는 하지 않는다. 서버가 여러 대가 되어도 동작이 달라지지 않게 하기 위함이다.

### 2.4 AWS 구성

| 리소스 | 구성 |
|---|---|
| VPC | 퍼블릭 서브넷(EC2, 이후 ALB)과 프라이빗 서브넷(RDS). NAT 게이트웨이 없음 |
| EC2 | t4g.small(ARM, 메모리 2GB)로 시작하고, 부족하면 t4g.medium. 보안 그룹 인바운드는 80/443만 |
| RDS | PostgreSQL 17, db.t4g.micro, 단일 AZ, 퍼블릭 접근 끔, 저장 암호화, 자동 백업 7일 |
| S3 | 공시 원문 버킷. 퍼블릭 접근 차단, 암호화 |
| 기타 | Route 53, ECR, SSM, CloudWatch, AWS Budgets |

**월 비용 대략치** (서울 리전, 온디맨드 기준)

| 항목 | 금액 |
|---|---|
| EC2 | 약 $15~30 |
| RDS + 스토리지 20GB | 약 $20 |
| 퍼블릭 IPv4 | 약 $4 |
| Route 53, S3, ECR, CloudWatch | 약 $3~5 |
| **합계** | **약 $45~65** |

- 사용하지 않는 것: NAT 게이트웨이(월 $40 이상), ALB(서버 1대에서는 이득 없음), CloudFront·WAF(트래픽이 생기면 도입).
- t4g는 ARM 인스턴스이므로 컨테이너 이미지를 arm64로 빌드한다.
- 단일 서버·단일 AZ이므로 배포 중 수십 초 중단과 장애 시 서비스 중단을 감수한다. 배포는 장 마감 후나 새벽에 한다.
- 사용량이 안정되면 Savings Plans로 할인을 받는다.

## 3. 주요 기술 선택

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | Java 21 이상 (가능하면 25 LTS) | 가상 스레드로 I/O가 많은 수집·AI 호출을 단순하게 처리한다. 현재 빌드 설정의 Java 17에서 올린다 |
| 프레임워크 | Spring Boot 4 | 초기화된 프로젝트, 개발자 숙련도 |
| 화면 | Thymeleaf + htmx | 서버 렌더링으로 SEO를 기본 확보한다. 언어와 배포 단위가 하나이고, 세션·CSRF 보호가 기본 제공된다 |
| 스타일·차트 | Tailwind(standalone CLI, Node 불필요) 또는 순수 CSS, Lightweight Charts(주가), Chart.js(재무) | 프론트 빌드 체인 최소화 |
| 데이터 접근 | Spring Data JPA + JdbcClient, Flyway | 일반 CRUD는 JPA, 시세·재무 대량 upsert는 JDBC |
| DB | PostgreSQL 17 (RDS) | JSONB로 분석 결과 저장, 자동 백업·복구, 확장 경로 |
| 캐시 | Caffeine (TTL) | 프로세스 내부, 추가 인프라 없음 |
| 스케줄 | Spring `@Scheduled` (Asia/Seoul) | 작업 수가 적고 단일 프로세스 |
| 외부 호출 | RestClient, Jsoup | 단순 재시도와 호출 간격 조절로 충분하다. Jsoup은 공시 원문 HTML 파싱용 |
| AI | Anthropic Java SDK + 얇은 어댑터 | 구조화 출력, 프롬프트 캐싱, 추후 Batch API를 제약 없이 쓴다 |
| 테스트 | JUnit, Testcontainers, 실제 응답 샘플 기반 파서 테스트 | 공시 원문 파서가 가장 깨지기 쉬운 부분이다 |
| 빌드·배포 | Gradle `bootBuildImage`, Docker Compose, GitHub Actions(OIDC) | Dockerfile 없이 이미지를 만들고, 장기 AWS 키를 두지 않는다 |

**사용하지 않는 기술** (도입 조건은 §12)

Redis, 메시지 큐(SQS·Kafka·RabbitMQ), Kubernetes·ECS, ALB, CloudFront·WAF, ShedLock, Resilience4j, Spring AI·LangChain4j, pg_trgm, pgvector, Spring Modulith, 별도 에러 추적 서비스.

## 4. 데이터

### 4.1 데이터 소스

| 데이터 | 소스 | MVP 범위 |
|---|---|---|
| 기업 목록·고유번호·종목코드 | OpenDART 고유번호 파일 | 전 상장사 |
| 기업 개황 | OpenDART | 전 상장사 |
| 공시 목록 | OpenDART | 전 상장사 |
| 사업보고서 원문 | OpenDART 원문 → S3 | AI 적용 대상 기업 |
| 재무 | OpenDART 주요계정 API (초기 적재는 다중회사 API) | 전 상장사, 최근 3~5년 |
| 감사의견 등 | OpenDART 정기보고서 주요정보 API | 전 상장사 |
| 주요사항(증자·사채 발행 등) | OpenDART 주요사항보고서 API (구조화 제공 범위 안에서) | 전 상장사 |
| 일별 시세 | 공공데이터포털 주식시세 또는 KRX. 약관 확인 후 결정 (§13) | 전 상장사 |
| 뉴스 | 네이버 검색 API. 제목·요약·링크만 저장 | AI 적용 대상 기업 |
| 거시·산업 통계 | 사용하지 않음 | — |

산업 맥락은 외부 통계 대신 두 가지로 구성한다.
1. 사업보고서의 산업·시장 서술 (기업 이해 분석이 요약)
2. 동종업계 기업과의 재무 비교 지표 (코드가 계산)

### 4.2 데이터 모델

| 테이블 | 핵심 내용 |
|---|---|
| `company` | 대리키, 이름, 초성, 산업코드, 결산월, DART 고유번호, 상태 |
| `security` | company_id, 종목코드, ISIN, 시장, 주식 종류, 통화, 상장·상장폐지일 |
| `company_alias` | 검색용 별칭 |
| `price_daily` | security_id + 거래일, 시가·고가·저가·종가·거래량, 등락률, 시가총액 |
| `financial_summary` | 기업, 회계연도, 기간 구분, 연결/별도, 기간 종료일, 통화, 핵심 계정(약 15개), 출처 공시번호 |
| `disclosure` | 공시번호, 기업, 보고서명, 유형, 제출 시각 |
| `document_section` | 기업, 공시번호, 섹션 키, 정제 텍스트, 파서 버전 |
| `news_item` | 기업, 제목, URL, 발행 시각 |
| `competitor` | 기업 쌍, 출처(AI/수동), 확정 여부, 근거 |
| `company_signal` | 기업, 신호 유형, 성격(상태/변화), 방향, 심각도, 근거 참조, 계산값, 확인 지표, 활성 여부 |
| `corporate_event` | 기업, 이벤트 유형, 날짜, 근거 |
| `content_entry` | 용어, 공시 유형, 신호 유형, 이벤트 유형, 확인 지표 설명 (정적 콘텐츠) |
| `analysis` | 대상, 분석 종류, 지문, 상태, 결과 JSON, 스키마 버전, 프롬프트 버전, 모델, 토큰·비용, 오류, 생성 시각, 현재 게시본 여부 |
| `pipeline_run` | 작업명, 시작·종료 시각, 처리 건수, 오류 |

- 재무 비율과 동종업계 비교 지표는 저장하지 않고 코드로 계산한다.
- `analysis`는 덮어쓰지 않고 새 행을 추가한다. 화면은 현재 게시본만 읽는다.
- 동기 호출에서 AI 호출 1회는 분석 결과 1건이므로 호출 로그를 `analysis`에 함께 기록한다.

### 4.3 데이터 규칙

나중에 바꾸기 비싼 규칙이므로 MVP부터 지킨다.

| 항목 | 규칙 |
|---|---|
| 식별자 | 모든 테이블은 내부 대리키를 쓴다. DART 고유번호·종목코드·ISIN은 속성이다. 기업과 종목을 분리한다 |
| 시간 | 시각은 UTC(timestamptz)로 저장하고 KST로 표시한다. 거래일은 DATE. 스케줄은 Asia/Seoul 기준 |
| 금액 | 원 단위 NUMERIC과 통화 컬럼. 억·조 단위 변환은 표시 계층에서 한다 |
| 회계 기간 | 회계연도 + 기간 구분(1분기·반기·3분기·연간) + 기간 종료일 + 결산월. 12월 결산을 가정하지 않는다. 분기 단독값은 누적값에서 계산한다(4분기 = 연간 − 3분기 누적) |
| 수정주가 | 소스가 주는 일별 등락률을 누적해 수정 시계열을 만든다 |
| 휴장일 | 소스에 해당 거래일 데이터가 없으면 휴장으로 본다. 휴장일 테이블은 두지 않는다 |
| 원문 보관 | 공시 원문만 S3에 보관한다. 시세·뉴스는 다시 받을 수 있으므로 보관하지 않는다 |
| 분석 결과 | 스키마 버전, 지문, 프롬프트 버전, 모델을 반드시 기록한다 |

### 4.4 수집 일정

| 작업 | 주기 (KST) |
|---|---|
| 기업 목록 동기화 (신규 상장·상장폐지·사명 변경) | 매일 새벽 |
| 공시 수집 → 정기보고서면 재무·원문 수집 | 장중 30분 간격 + 저녁 |
| 시세 수집 → 순위 계산 | 소스 반영 시점에 1회 |
| 뉴스 수집 | 하루 2~3회 |
| 신호·이벤트 계산 | 수집 직후 |
| 분석 동기화 | 신호 계산 후 |
| 데이터 신선도·범위 점검 | 매일 아침 |

- **초기 적재**: 전 상장사 3~5년 재무와 1~2년 시세를 호출 한도 안에서 며칠에 나눠 받는다. 중단된 지점부터 재개할 수 있게 만든다.
- **데이터 점검**: 받아야 할 데이터를 받았는지, 값이 정상 범위인지(거래량 0, 단위 이상, 누락 기간) 매일 확인하고 이상하면 알림을 보낸다.

## 5. 데이터·AI 분석 구조

상세 명세는 [데이터·AI 분석 명세](ai-analysis.md)를 따른다.

### 5.1 분석 계층

```
원천 데이터 ─[코드]─▶ 지표·순위·신호·이벤트 ─[AI]─▶ 1차 분석 ─[AI]─▶ 2차 분석 ─[코드]─▶ 화면 조립
```

- **코드 산출물**: 재무 지표, 등락 순위, 동종업계 비교, 기업 신호(방향·심각도), 향후 이벤트
- **1차 분석**: 원천 데이터와 코드 산출물을 입력으로 쓴다 (기업 이해, 재무 쉬운 설명, 일일 변동)
- **2차 분석**: 1차 분석 결과와 코드 산출물을 입력으로 쓴다 (향후 전망, 경쟁사 비교). 원문을 다시 읽지 않으므로 저렴하다

### 5.2 분석 종류

| 분석 | 계층 | 대상 | 재생성 기준 (지문) |
|---|---|---|---|
| 기업 이해 | 1차 | AI 적용 대상 | 최신 사업보고서 |
| 재무 쉬운 설명 | 1차 | AI 적용 대상 | 최신 재무 기간 |
| 일일 변동 | 1차 | 등락 상위 중 근거가 있는 기업 | 거래일 + 근거 |
| 향후 전망 | 2차 | AI 적용 대상 | 기업 이해 결과 + 재무 기간 + 선별 신호 (최소 7일 간격) |
| 경쟁사 비교 | 2차 | 확정 경쟁사 쌍 | 두 기업의 1차 분석 결과 |

### 5.3 향후 전망 요약

향후 전망은 **예측이 아니라 앞으로 지켜볼 점**을 설명한다. 주요 요인, 긍정 요인, 부정 요인, 확인할 지표·이벤트, 불확실성으로 구성한다.

- 요인의 방향과 심각도, 선별은 코드가 기업 신호로 판정한다.
- AI는 요인·신호·지표별 설명만 쓰고, 어느 섹션에 둘지는 코드가 신호의 방향으로 정한다.
- 주가 예측, 목표가격, 실적 수치 예측, 가치 판정, 매수·매도 추천은 하지 않는다.

세부는 [데이터·AI 분석 명세 §5](ai-analysis.md#5-향후-전망-분석)를 따른다.

### 5.4 분석 동기화

1. 기업과 분석 종류마다 기대 지문을 계산한다.
2. 현재 게시본의 지문과 같으면 건너뛴다.
3. 생성하고 검증한다. 통과하면 게시하고, 실패하면 이전 게시본을 유지한다.
4. 1차 분석을 먼저, 2차 분석을 나중에 처리한다.
5. 일일 AI 예산 안에서만 실행한다.
6. 프롬프트 변경은 자동 재생성 조건이 아니다. 관리자가 예산을 정해 점진적으로 재생성한다.

### 5.5 AI 사용 방식

- 초기 기본 모델은 Claude Sonnet 5로 하고, 골든셋 비교(상위 모델 포함) 후 분석 종류별로 확정한다. 모델은 설정값이다.
- 동기 호출, 구조화 출력(JSON 스키마), 고정 시스템 프롬프트에 프롬프트 캐싱을 적용한다.
- 운영 AI 비용 예상: 월 약 $40~70 (AI 적용 대상 약 300개 기준).

## 6. 화면

### 6.1 페이지와 URL

| 페이지 | URL | 내용 |
|---|---|---|
| 홈 | `/` | 인기 기업(거래대금·시가총액 기준), 상승·하락 상위, 검색 |
| 기업 상세 | `/stocks/{종목코드}` | §6.2 |
| 기업 비교 | `/compare/{종목코드A}-vs-{종목코드B}` | 코드가 만든 데이터 비교와 두 기업의 한 줄 요약. 확정 경쟁사 쌍이면 AI 비교 설명 추가 |
| 용어 | `/terms/{용어}` | 용어 설명 |

- URL은 종목코드 기반으로 고정한다. 사명은 URL에 쓰지 않는다.
- 비교 URL은 종목코드 순서로 정규화하고 canonical을 지정한다.

### 6.2 기업 상세 구성

| 섹션 | 코드가 만드는 부분 | AI가 만드는 부분 |
|---|---|---|
| 개요 | 기본 정보 | 한 줄 요약, 기업 소개 (기업 이해) |
| 사업구조·제품·고객 | — | 기업 이해 |
| 재무 | 차트, 지표 | 쉬운 설명 (재무 쉬운 설명) |
| 주가 | 수정 시계열 차트, 등락률 | 최근 변동 이유 (일일 변동). 근거가 없으면 코드 템플릿 문장 |
| 뉴스·공시 | 목록, 공시 유형 설명(정적) | — |
| 경쟁사 | 확정 경쟁사 목록, 비교 링크 | — |
| 리스크 | 현재 위험 신호(상태·부정 신호)와 유형별 정적 설명 | 사업상 위험 서술 (기업 이해) |
| 향후 전망 | 섹션 구성, 신호 배치, 지표 값, 향후 이벤트 날짜, 부제·면책 | 요인·신호·지표별 쉬운 설명 (향후 전망) |

- 모든 AI 콘텐츠에 AI 생성 표시, 출처, 데이터 기준일을 붙인다. 이 문구는 코드가 붙인다.
- 본문의 전문용어는 코드가 용어 사전과 매칭해 툴팁을 단다.
- AI 적용 대상이 아닌 기업은 코드가 만든 부분만 보여 준다.

### 6.3 렌더링 규칙

- SEO에 필요한 핵심 콘텐츠는 첫 HTML에 포함한다. htmx는 검색 자동완성, 탭·기간 전환, 차트 데이터에만 쓴다.
- sitemap을 제공하고, 메타 설명은 한 줄 요약에서 가져온다.
- 모바일 우선으로 설계한다.
- 공개 페이지는 사용자와 무관하게 만든다. 개인화 기능은 나중에 별도 htmx 조각으로 붙인다. 이렇게 해야 페이지 캐시(CDN)와 충돌하지 않는다.
- AI 출력은 제한된 마크다운만 허용하고 sanitizer를 거쳐 렌더링한다.
- 검색은 전 종목과 별칭(초성 포함)을 메모리 인덱스에 올려 처리한다.

## 7. 프로젝트 구조

기준 패키지는 `org.stockinsight.stockinsight`이다. Gradle 모듈은 하나로 두고 기능별로 패키지를 나눈다.

```
src/main/java/org/stockinsight/stockinsight/
├── company/     기업·종목·별칭·검색·경쟁사
├── market/      시세·수정 시계열·등락 순위
├── financial/   재무 요약·지표 계산·동종업계 비교
├── disclosure/  공시·원문 섹션 추출·향후 이벤트 추출
├── news/        뉴스 저장·기업 매칭
├── signal/      기업 신호 규칙 카탈로그·신호 계산
├── analysis/    분석 종류 정의·입력 구성·지문·동기화·검증·게시
│   └── llm/     Anthropic SDK 어댑터·프롬프트 로더
├── content/     정적 콘텐츠(용어·유형 설명)
├── ingest/      외부 API 클라이언트(dart, price, naver)·원문 S3 저장·수집 스케줄
├── web/         공개 페이지 컨트롤러·JSON 엔드포인트·뷰 모델
├── admin/       관리자(비공개 포트)
└── common/      설정·보안·예외·공통 유틸

src/main/resources/
├── prompts/        분석 종류별 프롬프트(v{n}.md)·출력 스키마(schema.json)·공통 스타일 가이드
├── db/migration/   Flyway 마이그레이션
└── templates/      Thymeleaf 템플릿
```

- 다른 패키지의 리포지토리나 엔티티를 직접 쓰지 않고 서비스를 통해 접근한다.
- 스케줄은 `ingest`, `signal`, `analysis`에만 두고 `app.scheduler.enabled`로 켜고 끈다.
- 컨트롤러는 얇게 두고, 서비스는 뷰와 무관한 DTO를 반환한다. 나중에 `/api/v1`을 붙이기 쉽게 하기 위함이다.
- Gradle 멀티모듈은 쓰지 않는다.

## 8. 보안

MVP는 로그인이 없고 실시간 AI 호출이 없으므로 개인정보 유출과 AI 비용 공격 위험이 구조적으로 없다. 남은 위험에는 아래를 적용한다.

| 영역 | 대응 |
|---|---|
| AWS 계정 | 루트 계정에 MFA를 걸고 사용하지 않는다. 개인 계정도 MFA를 쓴다 |
| 권한 | EC2 인스턴스 역할은 최소 권한(SSM 파라미터 읽기, 지정 S3 버킷, ECR 이미지 받기, 로그 쓰기)만 가진다. GitHub Actions는 OIDC 역할로 ECR 푸시와 SSM 명령만 허용한다. 장기 액세스 키를 두지 않는다 |
| 네트워크 | 보안 그룹 인바운드는 80/443만 연다. SSH 포트를 열지 않고 SSM Session Manager로 접속한다. RDS는 퍼블릭 접근을 끄고 EC2 보안 그룹에서만 접근하며 TLS를 쓴다 |
| 관리자 | 외부에 열지 않은 포트 + SSM 포트 포워딩 + 앱 인증 |
| 비밀값 | SSM Parameter Store(SecureString)에 둔다. 리포지토리에 넣지 않고 GitHub secret scanning을 켠다. Flyway용 DB 계정을 앱 계정과 분리한다 |
| 비용 | AWS Budgets 알림, Anthropic 월 지출 한도, 앱 내부 일일 AI 예산 |
| AI 입력 | 공시·뉴스 텍스트는 신뢰할 수 없는 데이터로 취급한다. AI에는 도구나 권한을 주지 않는다(텍스트 입력 → JSON 출력). 데이터는 구분자로 감싸고, 데이터 안의 지시를 따르지 않도록 명시한다 |
| AI 출력 | 스키마·참조·숫자·금지 표현을 검증한 뒤 게시한다. 렌더링할 때 이스케이프와 sanitizer를 거친다 |
| 웹 | Thymeleaf 자동 이스케이프, CSRF 보호, CSP 등 보안 헤더, 검색 API 호출 속도 제한 |
| 외부 호출 | 허용된 호스트만 호출한다. 뉴스 링크를 따라가 본문을 가져오지 않는다. 응답 크기와 타임아웃을 제한한다 |
| 데이터 | RDS 자동 백업 7일 + 월 1회 스냅샷. S3 퍼블릭 차단·암호화. 로그 30일 보관 |
| 의존성 | Dependabot, 컨테이너 이미지 정기 재빌드 |
| 법·신뢰 | 면책 문구, AI 생성 표시, 출처·기준일, 개인정보처리방침(접속 로그 등) |

회원 기능을 도입할 때 추가할 사항은 §11.2를 따른다.

## 10. MVP 범위

| 영역 | 포함 |
|---|---|
| 데이터 | 전 상장사의 기업·시세·재무 요약·공시. 뉴스는 AI 적용 대상 기업만 |
| AI 적용 대상 | 시가총액 상위 약 300개 |
| AI 분석 | 기업 이해, 재무 쉬운 설명, 일일 변동, 향후 전망, 확정 경쟁사 쌍 비교 |
| 코드 산출 | 등락 순위, 재무 지표, 동종업계 비교, 기업 신호, 향후 이벤트, 용어 매칭 |
| 정적 콘텐츠 | 용어, 공시 유형, 신호 유형, 이벤트 유형, 확인 지표 설명 (AI 초안 + 사람 검토) |
| 화면 | 홈, 기업 상세, 기업 비교, 용어 |
| 관리자 | 재생성, 숨김, 초안 미리보기, 경쟁사 확정, 실행 로그 |
| 인프라 | EC2, RDS, S3, Route 53, ECR, SSM, CloudWatch, AWS Budgets |
| 신뢰·법 | 면책, AI 생성 표시, 출처·기준일, 개인정보처리방침 |

### 구현 순서

1. 착수 전 확인 사항(§13)을 정리하고 데이터 소스를 확정한다.
2. 기업 목록, 시세, 재무, 공시를 수집하고 AI 없는 상세 페이지를 만든다. 이 단계만으로도 쓸 만해야 한다.
3. 기업 신호와 향후 이벤트를 계산한다.
4. 분석 동기화, 검증, 초안 미리보기를 만들고 골든셋 20개로 1차 분석을 다듬는다.
5. 향후 전망과 경쟁사 비교(2차 분석)를 추가한다.
6. 약 300개 기업으로 확대하고 SEO·보안을 점검한 뒤 공개한다.

| 단계 | 도입 조건 | 변경 | 앱 코드 변경 |

| 0 | — | 현재 구성 | — |
| 1 | 트래픽 증가, 크롤러·공격 | CloudFront(필요하면 WAF) 추가, 인스턴스·DB 크기 확대 | 없음 (캐시 헤더만) |
| 2 | 로그인 도입 또는 무중단 필요 | ALB + 웹 서버 2대 이상(오토스케일링 그룹 또는 ECS), 스케줄러는 1대만, Spring Session JDBC, RDS Multi-AZ, IaC | 설정 위주 |
| 3 | 전 종목·해외 확장, 실시간 AI 증가 | 워커 분리(ECS 서비스), Batch API, 필요하면 SQS·ElastiCache·읽기 복제본 | 워커 진입점 분리 |

### 11.2 기능 확장

| 기능 | 현재 준비된 것 | 도입할 때 할 일 |
|---|---|---|
| 데이터 소스 추가 | `ingest`의 소스별 클라이언트 구조 | 클라이언트 추가 |
| AI 모델 변경 | 분석 종류별 모델 설정, 결과별 모델·프롬프트 버전 기록 | 골든셋 비교 후 설정 변경, 점진 재생성 |
| 분석 추가 | 분석 종류 = 입력 구성 + 프롬프트 + 스키마 + 지문 규칙 | 네 가지를 한 세트로 추가 |
| 전 종목 AI 적용 | 요청 구성과 실행의 분리 | Batch API 실행기 추가 |
| 회원·관심기업 | 사용자와 무관한 공개 페이지 | 소셜 로그인만 사용(비밀번호 저장 안 함), Spring Session JDBC, 사용자 데이터 별도 스키마, 모든 사용자 리소스에 소유자 확인, 개인정보처리방침 갱신 |
| 알림 | 분석 게시 이력, 신호 변화 | 관심기업의 새 게시본·신호를 구독해 알림 |
| 실시간 비교·질문 | 1차 분석 결과(2차 분석 입력으로 재사용) | 로그인 필수, 사용자별 한도, 결과 캐시. 질문은 읽기 전용 도구와 필요하면 pgvector. AI 요청에 사용자 식별정보를 넣지 않는다 |
| 포트폴리오 분석 | 기업별 분석 재사용 구조 | 보유 종목의 1차 분석 결과만 입력. 도입 전 규제 검토 |
| 해외 주식 | 기업·종목 분리, 통화·결산월·시장 필드 | 해외 소스 클라이언트, 해외 공시 체계용 신호 규칙 |
| 모바일 앱 | 뷰와 무관한 서비스 계층 | `/api/v1` JSON과 토큰 인증 |

## 12. 의도적으로 제외한 기능과 도입 조건

### 12.1 도입하지 않는 기능

| 기능 | 이유 |
|---|---|
| 주가 예측, 목표가격, 적정 주가 | 서비스 원칙(기업 이해) 위반, 투자자문 규제 위험 |
| 매수·매도 추천, 종목 추천 | 같음 |
| 실적 수치 예측 (매출·이익 전망치) | 예측은 서비스 범위가 아니다. 향후 전망은 요인과 확인할 점만 설명한다 |
| 저평가·고평가 등 가치 판정, 종합 평가 | 투자 판단에 해당한다 |
| 증권사 컨센서스·실적 추정치 표시 | 예측 성격의 외부 데이터이며 라이선스가 필요하다. 도입하려면 서비스 원칙부터 다시 검토한다 |

### 12.2 나중에 도입할 기능

| 기능 | 제외 이유 | 도입 조건 |
|---|---|---|
| 로그인, 관심기업, 조회 이력 | 개인정보·보안 범위 최소화 | 공개 후 재방문 사용자 확인 |
| 실시간 AI (임의 쌍 비교, 질문) | 인증 없이는 비용 공격 경로가 된다 | 로그인 도입 후 사용자별 한도와 함께 |
| 조회가 많은 임의 쌍의 AI 비교 | MVP 단순화 | 비교 페이지 조회 데이터 확보 후, 매일 상위 K쌍만 예산 상한 안에서 |
| 포트폴리오 분석 | 로그인 전제, 규제 검토 필요 | 로그인 + 법률 검토 |
| 장중·실시간 시세 | 라이선스 비용 | 사용자 요구 확인 + 라이선스 계약 |
| 해외 주식 | 범위 관리 | 국내 서비스 안정화 후 |
| 거시·산업 외부 통계 | MVP 단순화 | 향후 전망 품질 검토에서 산업 맥락 부족이 확인될 때 |
| 전체 재무제표 정규화 (현금흐름·부문별) | 화면에 필요하지 않음 | 해당 정보를 화면에 보여 줄 때 |
| 산업 설명 페이지 | 범위 관리 | 업종 페이지를 도입할 때 |
| 전 종목 AI 적용 + Batch API | 소규모에서는 이득이 작고 품질 검증이 우선 | 약 300개 기업의 품질 확인 후 |
| 다중 모델 운용 | 평가와 캐시가 모델별로 분리된다 | 특정 분석 종류에서 품질·비용 문제가 측정될 때 |
| 뉴스 AI 관련성 분류 | 규칙 매칭으로 충분 | 오매칭이 문제가 될 때 |
| 조회수 기반 인기 기업 | 트래픽이 필요 | 일정 수준의 방문자 확보 후 |
| 자동 품질 평가 (AI 채점) | 수동 검토로 충분 | 전 종목 적용 시 |
| 사이트 내 오류 신고 폼 | 공개 쓰기 경로를 만들지 않기 위함 | 로그인 도입 후 |
| CloudFront·WAF, ALB·다중 서버, Multi-AZ, IaC | 현재 규모에서 비용 대비 이득 없음 | §11.1의 단계별 조건 |
| Redis, 메시지 큐, MSA, Kubernetes | 필요 없음 | 측정된 병목이 있을 때만 |
