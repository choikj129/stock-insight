## D-01. 모듈러 모놀리스, 단일 프로세스

- **결정**: Spring Boot 코드베이스 하나, 프로세스 하나로 공개 웹, 관리자, 스케줄러를 실행한다. 모듈은 패키지로 나눈다.
- **이유**: 1인 개발·운영에서는 배포, 디버깅, 트랜잭션을 한 곳에서 처리하는 이득이 가장 크다. MVP 부하에서는 프로세스를 나눠도 얻는 것이 없다.
- **검토한 대안**
  - 마이크로서비스: 운영 비용이 과하다.
  - web·worker 프로세스 분리: 서버 1대에서는 메모리 낭비다.
  - 서버리스: 오래 걸리는 작업과 Java 콜드 스타트에 불리하다.
- **재검토 조건**: 수집·AI 작업이 웹 응답에 영향을 주거나 서버를 2대 이상으로 늘릴 때 워커를 분리한다.

## D-02. 화면은 Thymeleaf + htmx 서버 렌더링

- **결정**: 페이지는 서버에서 렌더링한다. htmx는 검색 자동완성, 탭 전환, 차트 데이터 같은 보조 인터랙션에만 쓴다.
- **이유**: 검색 유입이 중요한 콘텐츠형 서비스라 SEO가 기본으로 필요하다. 백엔드 개발자 1인에게 언어와 배포 단위가 하나인 것이 유리하다. 세션과 CSRF 보호가 기본 제공된다.
- **검토한 대안**
  - Next.js + API: 스택과 배포가 2개가 된다.
  - React SPA: SEO에 불리하다.
- **재검토 조건**: 모바일 앱을 출시하거나 인터랙션이 많은 기능의 비중이 커지면 `/api/v1`과 별도 프론트를 추가한다.

## D-03. RDS PostgreSQL 단일 DB

- **결정**: 정형 데이터, 분석 결과 JSON, 실행 로그를 모두 RDS PostgreSQL 하나에 둔다.
- **이유**
  - JSONB로 분석 결과를 저장할 수 있다.
  - 자동 백업과 특정 시점 복구로 운영 부담이 줄어든다.
  - 상태를 앱 서버 밖에 두어야 서버를 교체하거나 늘릴 수 있다.
  - 나중에 pgvector를 쓸 수 있다.
- **검토한 대안**
  - EC2에 직접 설치: 백업·복구를 직접 운영해야 하고, 서버와 상태가 묶인다.
  - MySQL: JSON과 확장 기능이 상대적으로 약하다.
  - NoSQL: 데이터가 관계형 중심이다.
- **재검토 조건**: 읽기 부하가 커지면 읽기 복제본, 가용성 요구가 생기면 Multi-AZ를 도입한다.

## D-04. AWS 최소 구성 (EC2 1대 + RDS + S3)

- **결정**: EC2 1대, RDS 단일 AZ, S3에 Route 53, ECR, SSM, CloudWatch를 더한다. NAT 게이트웨이, ALB, CloudFront는 쓰지 않는다.
- **이유**: 월 $45~65 수준이다. 상태가 앱 밖에 있으므로 ALB, 오토스케일링, ECS로 자연스럽게 확장할 수 있다.
- **검토한 대안**
  - Lightsail: 확장할 때 EC2·RDS로 옮겨야 한다.
  - ECS Fargate + ALB: 월 $90~150이고 IaC가 사실상 필수다.
  - Elastic Beanstalk: 내부 동작이 불투명하다.
  - EKS: 과하다.
- **감수하는 것**: 배포 중 수십 초 중단, 단일 서버·AZ 장애 시 서비스 중단.
- **재검토 조건**: [시스템 설계 §11.1](architecture.md#111-인프라-확장-단계)의 단계별 조건.

## D-05. SSH 없는 운영 접근, 비공개 관리자

- **결정**: 서버 접속과 배포는 SSM으로 한다. 관리자 화면은 외부에 열지 않은 포트에서 동작하며 SSM 포트 포워딩과 앱 인증을 거쳐야 접근할 수 있다. GitHub Actions는 OIDC 역할을 쓴다.
- **이유**: 외부에 노출되는 공격면을 최소화하고, 장기 키와 관리자 인증 기능을 운영하는 부담을 없앤다.
- **검토한 대안**: SSH와 키 관리, 공개 관리자 화면과 로그인, 외부 접근 제어 서비스.
- **재검토 조건**: 관리자가 여러 명이 될 때.

## D-06. 계산과 판단은 코드, 설명은 AI

- **결정**: 지표 계산, 순위, 신호의 방향·심각도 판정, 이벤트 추출, 분석 대상 선별은 코드가 한다. AI는 코드 산출물과 원문을 쉬운 말로 설명한다.
- **이유**: 숫자와 판정의 정확성·일관성을 확보하고, 결과를 검증할 수 있게 한다. 입력 토큰이 줄고, 투자 판단 표현이 끼어들 여지가 줄어든다.
- **검토한 대안**: AI가 원문에서 직접 판단 (환각, 일관성, 검증 문제).
- **재검토 조건**: 없음. 핵심 원칙이다.

## D-07. 상태 비교형 분석 동기화

- **결정**: 작업 큐와 이벤트 없이, 스케줄 실행마다 기대 지문과 현재 게시본을 비교해 다른 것만 생성한다.
- **이유**
  - 이벤트를 놓쳐 갱신이 누락되는 문제가 없다.
  - 배포나 재시작으로 끊겨도 다음 실행이 이어받는다.
  - 코드가 적고, "왜 갱신되지 않았나"를 지문 두 개 비교로 확인할 수 있다.
- **검토한 대안**
  - 이벤트 + DB 작업 큐: 부품이 늘고, 유실 대비 전수 점검이 결국 따로 필요하다.
  - 메시지 브로커: 인프라가 추가된다.
- **재검토 조건**: 작업량이 커져 워커를 분리할 때 SQS를 검토한다.

## D-08. 원천 버전 지문, 프롬프트 변경은 수동 재생성

- **결정**: 지문은 원천 식별자(공시번호, 재무 기간, 선별 신호 집합, 1차 분석 결과 ID)로 만든다. 입력 내용 해시는 쓰지 않는다. 프롬프트·모델 변경은 자동 재생성 조건이 아니다.
- **이유**: 파서를 개선하거나 매일 바뀌는 값(시세, 뉴스)이 입력에 섞여 대량 재생성이 일어나는 것을 막는다. 대량 재생성은 예산을 정해 의도적으로만 한다.
- **검토한 대안**: 입력 내용 해시 (비용 폭주 위험).
- **재검토 조건**: 없음.

## D-09. AI 동기 호출과 단일 모델, Batch API 보류

- **결정**: MVP는 동기 호출과 기본 모델 1종(분석 종류별로 설정 가능)을 쓴다. Batch API는 전 종목에 AI를 적용할 때 도입한다.
- **이유**
  - 약 300개 규모에서 Batch로 아끼는 돈은 월 수십 달러 수준인데, 비동기 상태 관리가 추가된다.
  - 프롬프트를 개발할 때는 결과를 즉시 봐야 한다.
  - 모델을 섞으면 평가와 캐시가 모델별로 나뉜다.
- **검토한 대안**: Batch 기본 + 다중 모델.
- **재검토 조건**: AI 적용 대상을 전 종목으로 늘릴 때, 특정 분석 종류에서 품질·비용 문제가 측정될 때.

## D-10. Anthropic SDK 직접 사용

- **결정**: 공식 Java SDK를 얇은 어댑터(`analysis/llm`) 뒤에 둔다.
- **이유**: 구조화 출력, 프롬프트 캐싱, Batch API를 제약 없이 쓸 수 있다. 여러 AI 제공사를 묶는 추상화 라이브러리는 이런 기능의 지원이 늦거나 제한적이다.
- **검토한 대안**: Spring AI, LangChain4j.
- **재검토 조건**: 여러 AI 제공사를 동시에 써야 할 때.

## D-11. MVP에 실시간 AI 없음

- **결정**: 모든 AI 분석은 미리 생성한다. 기업 비교의 AI 설명은 확정 경쟁사 쌍만 만들고, 그 외 쌍은 코드가 만든 데이터 비교만 보여 준다.
- **이유**: 로그인 없는 공개 서비스에서 실시간 AI는 비용 공격 경로가 된다. 의미 있는 비교는 대부분 경쟁사 쌍이다.
- **검토한 대안**: 실시간 생성 + 봇 차단, 호출 한도, 예산 상한.
- **재검토 조건**: 로그인을 도입한 뒤.

## D-12. 로그인 없는 MVP

- **결정**: MVP에는 회원 기능이 없다.
- **이유**: 개인정보 보호 범위와 보안 부담을 최소화하고 개발 범위를 줄인다.
- **재검토 조건**: 공개 후 재방문 사용자가 확인될 때.

## D-13. 일별 시세, 등락률 누적 수정 시계열

> 상태: 대체됨(D-22). 무료 시세 소스를 공개 서비스에 쓸 수 없음을 확인해 시세를 선택 모듈로 바꾸고 조정계수 계산 방식을 바꿨다.

- **결정**: 일별 시세만 수집한다. 수정 시계열은 소스가 주는 일별 등락률을 누적해 만든다.
- **이유**: 실시간 시세는 라이선스 비용이 크고 기업 이해 서비스에 필수가 아니다. 별도의 권리 이벤트 데이터 없이도 액면분할·무상증자로 차트가 끊기는 문제를 해결할 수 있다.
- **재검토 조건**: 사용자 요구가 확인되고 라이선스 계약이 가능할 때.

## D-14. 재무는 주요계정 기반 요약

- **결정**: OpenDART 주요계정 API로 핵심 계정(재무상태표·손익계산서 항목)을 가로형 테이블에 저장한다. 비율은 코드로 계산한다. 연결 재무제표를 우선하고 없으면 별도 재무제표를 쓴다.
- **이유**: MVP 화면과 분석에 필요한 범위다. 전체 재무제표 정규화(회사별 계정 매핑, 업종별 구조 차이)는 비용이 크다.
- **재검토 조건**: 현금흐름이나 부문별 정보를 화면에 보여 줄 때.

## D-15. 기업 신호로 방향·심각도 판정

- **결정**: 재무, 공시, 동종업계 비교, 데이터 한계를 규칙으로 판정해 `company_signal`에 저장한다. 리스크 섹션과 향후 전망은 모두 기업 신호를 근거로 한다. 성격(상태/변화)과 방향으로 두 섹션의 신호를 나눈다.
- **이유**
  - D-06 원칙을 구현하는 방법이다.
  - 리스크와 향후 전망이 같은 근거를 공유하면서도 화면에서 중복되지 않는다.
  - 신호 집합이 지문이 되므로 재생성 기준이 명확하다.
- **검토한 대안**: AI가 리스크와 전망을 직접 판단.
- **재검토 조건**: 규칙으로 표현하기 어려운 유형이 늘어날 때. 그 경우에도 방향 판정은 코드에 둔다.

## D-16. 향후 전망은 2차 분석, 투자 판단 표현 금지

- **결정**
  - 향후 전망의 입력은 기업 이해 결과, 재무 지표, 선별 신호, 최근 뉴스 제목이다(2차 분석).
  - AI는 요인·신호·지표별 설명만 쓰고, 어느 섹션에 둘지는 코드가 신호의 방향으로 정한다.
  - 주가 예측, 목표가격, 실적 수치 예측, 가치 판정, 매수·매도 추천을 하지 않는다.
- **이유**
  - 원문을 다시 읽지 않아 저렴하다 (호출당 약 $0.03).
  - AI가 신호의 방향을 바꿀 수 없다.
  - 서비스 원칙을 지킨다.
- **검토한 대안**
  - 원문 기반으로 AI가 자유롭게 서술: 비용이 크고, AI가 판단하게 되며, 검증이 어렵다.
  - 증권사 컨센서스 활용: 예측 성격이고 라이선스가 필요하다.
- **재검토 조건**: 품질 검토에서 산업 맥락이 부족하다고 확인되면 외부 산업 통계를 입력에 추가한다.

## D-17. 숫자는 자리표시자로 코드가 채움

- **결정**: 코드가 계산한 수치는 AI가 자리표시자로만 쓰고 코드가 값을 채운다. 원문을 인용한 수치는 입력 원문에 있어야 한다.
- **이유**: 수치 오류를 원천적으로 막고, 표기를 일관되게 하며, 검증을 단순하게 만든다.

## D-18. 나중에 바꾸기 비싼 규칙의 선결정

- **결정**
  - 내부 대리키를 쓰고, 기업과 종목을 분리하고, 통화·결산월·시장 필드를 둔다.
  - 시각은 UTC로 저장하고, 금액은 원 단위 NUMERIC으로 저장한다.
  - 회계 기간 모델을 정하고, 분석 결과에 스키마 버전을 둔다.
  - URL은 종목코드 기반으로 한다.
- **이유**: 해외 확장, SEO, 데이터 이력 때문에 나중에 바꾸면 이전 비용이 크다. 지금 정하는 비용은 거의 없다.

## D-19. 공개 페이지는 사용자와 무관하게

- **결정**: 공개 페이지에 사용자별 내용을 넣지 않는다. 개인화는 나중에 별도 htmx 조각으로 붙인다. 캐시는 TTL 기반만 쓴다.
- **이유**: CDN 캐시와 다중 서버 확장이 쉬워진다.

## D-20. 뉴스는 제목·링크만, 규칙 매칭

- **결정**
  - AI 적용 대상 기업의 뉴스만 수집한다.
  - 제목에 사명이나 별칭이 있으면 기업과 연결한다.
  - 본문은 저장하거나 재게시하지 않는다.
  - 향후 전망에서 뉴스는 보조 역할만 한다.
- **이유**: 저작권, 비용, 단순성. 뉴스 기사의 방향은 코드로 신뢰성 있게 판정할 수 없으므로 판단 근거로 쓰지 않는다.
- **재검토 조건**: 오매칭이 문제가 되면 AI 관련성 분류를 도입한다.

## D-21. AI 적용 대상은 시가총액 상위 약 300개부터

> 상태: 대체됨(D-23). 시가총액은 시세 데이터가 필요하므로 선정 기준을 바꿨다. "좁게 시작해 품질을 먼저 검증한다"는 이유는 그대로 유지한다.

- **결정**: 기본 데이터는 전 상장사를 수집하고, AI 분석은 시가총액 상위 약 300개 기업부터 적용한다.
- **이유**: 병목은 비용보다 품질 검증이다. 좁은 범위에서 먼저 검증한다.
- **재검토 조건**: 품질을 확인한 뒤 전 종목으로 넓히고 Batch API를 도입한다.

## D-22. 핵심 기능은 OpenDART만으로 동작, 시세·뉴스는 선택 모듈

- **결정**
  - 핵심 기능(기업 이해, 재무, 공시, 리스크, 향후 전망, 경쟁사 비교)은 OpenDART와 Claude API만으로 동작하게 만든다.
  - 시세(일별 시세, 차트, 등락 순위, 일일 변동)와 뉴스는 이용 허락을 확인한 뒤 켜는 선택 모듈로 둔다.
  - AI 적용 대상 선정, 동종업계 정의, 처리 순서에는 시세를 쓰지 않는다.
  - 시세 모듈을 켜면 수정 시계열의 조정계수는 기준가(종가 − 전일 대비)와 전일 종가의 비율로 만든다. 전일 대비 값이 없는 소스라면 등락률을 누적한다.
- **이유**
  - 무료 시세 소스는 공개 서비스에 쓸 수 없다. 공공데이터포털 주식시세정보는 공공누리 제4유형(상업적 이용 금지, 변경 금지)이고, KRX OPEN API는 비상업적 이용만 허용하며 제3자 제공을 금지한다.
  - 유료 라이선스의 비용과 조건이 정해지지 않았다. 이 상태에서 핵심 기능이 시세에 의존하면 구현 일정과 설계가 라이선스 결정에 묶인다.
  - 기업 이해 서비스의 핵심 가치는 공시와 재무에서 나온다.
  - 기준가 기반 조정계수는 반올림된 등락률을 누적할 때 생기는 오차가 없다.
- **검토한 대안**
  - 무료 소스 사용: 약관 위반이다.
  - 유료 라이선스 계약 후 착수: 일정이 계약에 묶인다.
  - 시세 없는 서비스로 확정: 차트와 등락 기능을 영구히 포기하게 된다.
- **재검토 조건**: 유료 시세 라이선스의 견적과 조건이 확인될 때(시세 모듈), 네이버 검색 API 약관이 확인될 때(뉴스 모듈).

## D-23. AI 적용 대상은 매출액 상위 약 300개 + 관리자 추가

- **결정**: 최근 연간 매출액 기준 상위 약 300개와 관리자가 추가한 기업에 AI 분석을 적용한다. 분기마다 다시 계산해 `company`에 저장한다. 대상에서 빠진 기업은 마지막 분석을 기준일과 함께 유지하고 더 갱신하지 않는다.
- **이유**
  - 시가총액은 시세 데이터가 필요하다(D-22).
  - 매일 다시 계산하면 경계에 있는 기업이 대상에 들어갔다 빠졌다 하며 생성과 중단이 반복된다.
  - 금융업처럼 매출액으로 비교하기 어려운 기업은 관리자 추가로 보완한다.
- **재검토 조건**: 시세 모듈을 도입한 뒤 시가총액 기준을 함께 쓸지 검토한다. 품질을 확인한 뒤 전 종목으로 넓히고 Batch API를 도입한다.

## D-24. 휴장일은 연간 휴장일 테이블로 관리

- **결정**: 주말과 `market_holiday`에 등록된 날을 휴장일로 본다. 거래소가 발표한 다음 해 휴장일을 매년 12월에 등록한다.
- **이유**: "소스에 데이터가 없으면 휴장"으로 판단하면 수집 누락이나 소스 지연을 휴장으로 오판해 데이터 신선도 점검이 동작하지 않는다. 휴장일은 연 15일 안팎이라 수동 등록 부담이 작다.
- **검토한 대안**
  - 데이터 유무로 추정: 누락과 휴장을 구분할 수 없다.
  - 공휴일 API 연동: 거래소 고유의 휴장일(연말 휴장 등)이 반영되지 않는다.

## D-25. 참조는 자연키, 분석 결과는 값 스냅샷 포함

- **결정**
  - 기업 신호는 기업 + 유형 + 근거 키의 자연키로 식별한다. 지문과 AI 출력의 신호 참조는 자연키를 쓴다.
  - 분석 결과는 AI에 준 자리표시자 값을 스냅샷으로 함께 저장하고, 화면은 스냅샷으로 숫자를 채운다.
  - 화면은 분석 결과의 현재 스키마 버전과 직전 버전을 함께 지원한다.
- **이유**
  - 신호를 다시 계산할 때마다 대리키가 바뀌면 지문이 바뀌어 불필요한 재생성이 반복된다.
  - 동종업계 중앙값처럼 나중에 바뀌는 값을 현재 데이터로 채우면 설명 문장과 숫자가 어긋난다.
  - 구현 후에 바꾸면 저장된 결과를 모두 다시 만들어야 하므로 지금 정한다.

## D-26. 경쟁사는 상호 선택 시 자동 확정

- **결정**: AI가 후보 목록 안에서 경쟁사를 고르고, 두 기업이 서로를 고르면 코드가 확정한다. 한쪽만 골랐으면 관리자 검토 대기로 둔다.
- **이유**: 약 300개 기업에서 최대 5개씩 나오는 제안을 모두 사람이 확정하면 운영 부담이 크다. 상호 선택은 코드 규칙으로 판단할 수 있는 신뢰 신호다.
- **검토한 대안**
  - 전부 관리자가 확정: 운영 부담이 크다.
  - AI 선택 즉시 확정: 오류가 그대로 화면에 노출된다.
- **재검토 조건**: 자동 확정된 쌍에서 오류가 자주 발견될 때.

## D-27. 대상 범위 밖 상장사도 상태로 저장

- **결정**: KONEX, 스팩, 리츠처럼 대상 종목 범위 밖의 상장사도 `company`에 저장하고 상태를 EXCLUDED, 제외 사유를 함께 기록한다. 이후 수집·분석은 ACTIVE 기업만 대상으로 한다.
- **이유**
  - 범위 밖 기업을 저장하지 않으면 코넥스→코스닥 이전상장이나 사명 변경으로 범위에 들어올 때 처음부터 다시 판정해야 하고, 왜 빠졌는지 확인할 방법이 없다.
  - 상장폐지 감지와 범위 판정이 같은 기업 목록을 기준으로 동작해 규칙이 단순해진다.
  - 상장사는 수천 개 수준이라 저장 비용이 무시할 만하다.
- **검토한 대안**: 범위 밖 기업은 저장하지 않고 수집 체크포인트에만 남기기 (제외 사유와 이력을 알 수 없다).
