## D-01. 모듈러 모놀리스, 단일 프로세스

- **결정**: Spring Boot 코드베이스 하나, 프로세스 하나로 공개 웹, 관리자, 스케줄러를 실행한다. 모듈은 패키지로 나눈다.
- **이유**: 1인 개발·운영에서는 배포, 디버깅, 트랜잭션을 한 곳에서 처리하는 이득이 가장 크다. MVP 부하에서는 프로세스를 나눠도 얻는 것이 없다.
- **검토한 대안**
  - 마이크로서비스: 운영 비용이 과하다.
  - web·worker 프로세스 분리: 서버 1대에서는 메모리 낭비다.
  - 서버리스: 오래 걸리는 작업과 Java 콜드 스타트에 불리하다.
- **재검토 조건**: 수집·AI 작업이 웹 응답에 영향을 주거나 서버를 2대 이상으로 늘릴 때 워커를 분리한다.

## D-02. 화면은 Thymeleaf + htmx 서버 렌더링

- **결정**: 페이지는 서버에서 렌더링한다. htmx는 검색 자동완성, 탭 전환, 차트 데이터 같은 보조 인터랙션에만 쓴다.
- **이유**: 검색 유입이 중요한 콘텐츠형 서비스라 SEO가 기본으로 필요하다. 백엔드 개발자 1인에게 언어와 배포 단위가 하나인 것이 유리하다. 세션과 CSRF 보호가 기본 제공된다.
- **검토한 대안**
  - Next.js + API: 스택과 배포가 2개가 된다.
  - React SPA: SEO에 불리하다.
- **재검토 조건**: 모바일 앱을 출시하거나 인터랙션이 많은 기능의 비중이 커지면 `/api/v1`과 별도 프론트를 추가한다.

## D-03. RDS PostgreSQL 단일 DB

- **결정**: 정형 데이터, 분석 결과 JSON, 실행 로그를 모두 RDS PostgreSQL 하나에 둔다.
- **이유**
  - JSONB로 분석 결과를 저장할 수 있다.
  - 자동 백업과 특정 시점 복구로 운영 부담이 줄어든다.
  - 상태를 앱 서버 밖에 두어야 서버를 교체하거나 늘릴 수 있다.
  - 나중에 pgvector를 쓸 수 있다.
- **검토한 대안**
  - EC2에 직접 설치: 백업·복구를 직접 운영해야 하고, 서버와 상태가 묶인다.
  - MySQL: JSON과 확장 기능이 상대적으로 약하다.
  - NoSQL: 데이터가 관계형 중심이다.
- **재검토 조건**: 읽기 부하가 커지면 읽기 복제본, 가용성 요구가 생기면 Multi-AZ를 도입한다.

## D-04. AWS 최소 구성 (EC2 1대 + RDS + S3)

- **결정**: EC2 1대, RDS 단일 AZ, S3에 Route 53, ECR, SSM, CloudWatch를 더한다. NAT 게이트웨이, ALB, CloudFront는 쓰지 않는다.
- **이유**: 월 $45~65 수준이다. 상태가 앱 밖에 있으므로 ALB, 오토스케일링, ECS로 자연스럽게 확장할 수 있다.
- **검토한 대안**
  - Lightsail: 확장할 때 EC2·RDS로 옮겨야 한다.
  - ECS Fargate + ALB: 월 $90~150이고 IaC가 사실상 필수다.
  - Elastic Beanstalk: 내부 동작이 불투명하다.
  - EKS: 과하다.
- **감수하는 것**: 배포 중 수십 초 중단, 단일 서버·AZ 장애 시 서비스 중단.
- **재검토 조건**: [시스템 설계 §11.1](architecture.md#111-인프라-확장-단계)의 단계별 조건.

## D-05. SSH 없는 운영 접근, 비공개 관리자

- **결정**: 서버 접속과 배포는 SSM으로 한다. 관리자 화면은 외부에 열지 않은 포트에서 동작하며 SSM 포트 포워딩과 앱 인증을 거쳐야 접근할 수 있다. GitHub Actions는 OIDC 역할을 쓴다.
- **이유**: 외부에 노출되는 공격면을 최소화하고, 장기 키와 관리자 인증 기능을 운영하는 부담을 없앤다.
- **검토한 대안**: SSH와 키 관리, 공개 관리자 화면과 로그인, 외부 접근 제어 서비스.
- **재검토 조건**: 관리자가 여러 명이 될 때.

## D-06. 계산과 판단은 코드, 설명은 AI

- **결정**: 지표 계산, 순위, 신호의 방향·심각도 판정, 이벤트 추출, 분석 대상 선별은 코드가 한다. AI는 코드 산출물과 원문을 쉬운 말로 설명한다.
- **이유**: 숫자와 판정의 정확성·일관성을 확보하고, 결과를 검증할 수 있게 한다. 입력 토큰이 줄고, 투자 판단 표현이 끼어들 여지가 줄어든다.
- **검토한 대안**: AI가 원문에서 직접 판단 (환각, 일관성, 검증 문제).
- **재검토 조건**: 없음. 핵심 원칙이다.

## D-07. 상태 비교형 분석 동기화

- **결정**: 작업 큐와 이벤트 없이, 스케줄 실행마다 기대 지문과 현재 게시본을 비교해 다른 것만 생성한다.
- **이유**
  - 이벤트를 놓쳐 갱신이 누락되는 문제가 없다.
  - 배포나 재시작으로 끊겨도 다음 실행이 이어받는다.
  - 코드가 적고, "왜 갱신되지 않았나"를 지문 두 개 비교로 확인할 수 있다.
- **검토한 대안**
  - 이벤트 + DB 작업 큐: 부품이 늘고, 유실 대비 전수 점검이 결국 따로 필요하다.
  - 메시지 브로커: 인프라가 추가된다.
- **재검토 조건**: 작업량이 커져 워커를 분리할 때 SQS를 검토한다.

## D-08. 원천 버전 지문, 프롬프트 변경은 수동 재생성

- **결정**: 지문은 원천 식별자(공시번호, 재무 기간, 선별 신호 집합, 1차 분석 결과 ID)로 만든다. 입력 내용 해시는 쓰지 않는다. 프롬프트·모델 변경은 자동 재생성 조건이 아니다.
- **이유**: 파서를 개선하거나 매일 바뀌는 값(시세, 뉴스)이 입력에 섞여 대량 재생성이 일어나는 것을 막는다. 대량 재생성은 예산을 정해 의도적으로만 한다.
- **검토한 대안**: 입력 내용 해시 (비용 폭주 위험).
- **재검토 조건**: 없음.

## D-09. AI 동기 호출과 단일 모델, Batch API 보류

- **결정**: MVP는 동기 호출과 기본 모델 1종(분석 종류별로 설정 가능)을 쓴다. Batch API는 전 종목에 AI를 적용할 때 도입한다.
- **이유**
  - 약 300개 규모에서 Batch로 아끼는 돈은 월 수십 달러 수준인데, 비동기 상태 관리가 추가된다.
  - 프롬프트를 개발할 때는 결과를 즉시 봐야 한다.
  - 모델을 섞으면 평가와 캐시가 모델별로 나뉜다.
- **검토한 대안**: Batch 기본 + 다중 모델.
- **재검토 조건**: AI 적용 대상을 전 종목으로 늘릴 때, 특정 분석 종류에서 품질·비용 문제가 측정될 때.

## D-10. Anthropic SDK 직접 사용

- **결정**: 공식 Java SDK를 얇은 어댑터(`analysis/llm`) 뒤에 둔다.
- **이유**: 구조화 출력, 프롬프트 캐싱, Batch API를 제약 없이 쓸 수 있다. 여러 AI 제공사를 묶는 추상화 라이브러리는 이런 기능의 지원이 늦거나 제한적이다.
- **검토한 대안**: Spring AI, LangChain4j.
- **재검토 조건**: 여러 AI 제공사를 동시에 써야 할 때.

## D-11. MVP에 실시간 AI 없음

- **결정**: 모든 AI 분석은 미리 생성한다. 기업 비교의 AI 설명은 확정 경쟁사 쌍만 만들고, 그 외 쌍은 코드가 만든 데이터 비교만 보여 준다.
- **이유**: 로그인 없는 공개 서비스에서 실시간 AI는 비용 공격 경로가 된다. 의미 있는 비교는 대부분 경쟁사 쌍이다.
- **검토한 대안**: 실시간 생성 + 봇 차단, 호출 한도, 예산 상한.
- **재검토 조건**: 로그인을 도입한 뒤.

## D-12. 로그인 없는 MVP

- **결정**: MVP에는 회원 기능이 없다.
- **이유**: 개인정보 보호 범위와 보안 부담을 최소화하고 개발 범위를 줄인다.
- **재검토 조건**: 공개 후 재방문 사용자가 확인될 때.

## D-13. 일별 시세, 등락률 누적 수정 시계열

> 상태: 대체됨(D-22). 무료 시세 소스를 공개 서비스에 쓸 수 없음을 확인해 시세를 선택 모듈로 바꾸고 조정계수 계산 방식을 바꿨다.

- **결정**: 일별 시세만 수집한다. 수정 시계열은 소스가 주는 일별 등락률을 누적해 만든다.
- **이유**: 실시간 시세는 라이선스 비용이 크고 기업 이해 서비스에 필수가 아니다. 별도의 권리 이벤트 데이터 없이도 액면분할·무상증자로 차트가 끊기는 문제를 해결할 수 있다.
- **재검토 조건**: 사용자 요구가 확인되고 라이선스 계약이 가능할 때.

## D-14. 재무는 주요계정 기반 요약

- **결정**: OpenDART 주요계정 API로 핵심 계정(재무상태표·손익계산서 항목)을 가로형 테이블에 저장한다. (저장 형태는 D-32에서 보고서·계정 행 저장으로 바꿨다. 주요계정 API 사용, 비율은 코드 계산, 연결 우선은 유지한다.) 비율은 코드로 계산한다. 연결 재무제표를 우선하고 없으면 별도 재무제표를 쓴다.
- **이유**: MVP 화면과 분석에 필요한 범위다. 전체 재무제표 정규화(회사별 계정 매핑, 업종별 구조 차이)는 비용이 크다.
- **재검토 조건**: 현금흐름이나 부문별 정보를 화면에 보여 줄 때.
- **확인 (2026-09-25, 실제 응답)**: 다중회사 주요계정 API는 기업·연결/별도마다 재무상태표 9개(유동·비유동 자산, 자산총계, 유동·비유동 부채, 부채총계, 자본금, 이익잉여금, 자본총계)와 손익계산서 5종(매출액, 영업이익, 법인세차감전 순이익, 당기순이익, 총포괄손익. 당기순이익은 두 번 나온다) 계정만 준다. 현금흐름 계정은 없다. 결정은 그대로 두고, product.md §7의 현금흐름은 제품이 관찰할 대상으로, MVP 데이터 범위와 구분해 적는다.

## D-15. 기업 신호로 방향·심각도 판정

- **결정**: 재무, 공시, 동종업계 비교, 데이터 한계를 규칙으로 판정해 `company_signal`에 저장한다. 리스크 섹션과 향후 전망은 모두 기업 신호를 근거로 한다. 성격(상태/변화)과 방향으로 두 섹션의 신호를 나눈다.
- **이유**
  - D-06 원칙을 구현하는 방법이다.
  - 리스크와 향후 전망이 같은 근거를 공유하면서도 화면에서 중복되지 않는다.
  - 신호 집합이 지문이 되므로 재생성 기준이 명확하다.
- **검토한 대안**: AI가 리스크와 전망을 직접 판단.
- **재검토 조건**: 규칙으로 표현하기 어려운 유형이 늘어날 때. 그 경우에도 방향 판정은 코드에 둔다.

## D-16. 향후 전망은 2차 분석, 투자 판단 표현 금지

- **결정**
  - 향후 전망의 입력은 기업 이해 결과, 재무 지표, 선별 신호, 최근 뉴스 제목이다(2차 분석).
  - AI는 요인·신호·지표별 설명만 쓰고, 어느 섹션에 둘지는 코드가 신호의 방향으로 정한다.
  - 주가 예측, 목표가격, 실적 수치 예측, 가치 판정, 매수·매도 추천을 하지 않는다.
- **이유**
  - 원문을 다시 읽지 않아 저렴하다 (호출당 약 $0.03).
  - AI가 신호의 방향을 바꿀 수 없다.
  - 서비스 원칙을 지킨다.
- **검토한 대안**
  - 원문 기반으로 AI가 자유롭게 서술: 비용이 크고, AI가 판단하게 되며, 검증이 어렵다.
  - 증권사 컨센서스 활용: 예측 성격이고 라이선스가 필요하다.
- **재검토 조건**: 품질 검토에서 산업 맥락이 부족하다고 확인되면 외부 산업 통계를 입력에 추가한다.

## D-17. 숫자는 자리표시자로 코드가 채움

- **결정**: 코드가 계산한 수치는 AI가 자리표시자로만 쓰고 코드가 값을 채운다. 원문을 인용한 수치는 입력 원문에 있어야 한다.
- **이유**: 수치 오류를 원천적으로 막고, 표기를 일관되게 하며, 검증을 단순하게 만든다.

## D-18. 나중에 바꾸기 비싼 규칙의 선결정

- **결정**
  - 내부 대리키를 쓰고, 기업과 종목을 분리하고, 통화·결산월·시장 필드를 둔다.
  - 시각은 UTC로 저장하고, 금액은 원 단위 NUMERIC으로 저장한다.
  - 회계 기간 모델을 정하고, 분석 결과에 스키마 버전을 둔다.
  - URL은 종목코드 기반으로 한다.
- **이유**: 해외 확장, SEO, 데이터 이력 때문에 나중에 바꾸면 이전 비용이 크다. 지금 정하는 비용은 거의 없다.

## D-19. 공개 페이지는 사용자와 무관하게

- **결정**: 공개 페이지에 사용자별 내용을 넣지 않는다. 개인화는 나중에 별도 htmx 조각으로 붙인다. 캐시는 TTL 기반만 쓴다.
- **이유**: CDN 캐시와 다중 서버 확장이 쉬워진다.

## D-20. 뉴스는 제목·링크만, 규칙 매칭

- **결정**
  - AI 적용 대상 기업의 뉴스만 수집한다.
  - 제목에 사명이나 별칭이 있으면 기업과 연결한다.
  - 본문은 저장하거나 재게시하지 않는다.
  - 향후 전망에서 뉴스는 보조 역할만 한다.
- **이유**: 저작권, 비용, 단순성. 뉴스 기사의 방향은 코드로 신뢰성 있게 판정할 수 없으므로 판단 근거로 쓰지 않는다.
- **재검토 조건**: 오매칭이 문제가 되면 AI 관련성 분류를 도입한다.

## D-21. AI 적용 대상은 시가총액 상위 약 300개부터

> 상태: 대체됨(D-23). 시가총액은 시세 데이터가 필요하므로 선정 기준을 바꿨다. "좁게 시작해 품질을 먼저 검증한다"는 이유는 그대로 유지한다.

- **결정**: 기본 데이터는 전 상장사를 수집하고, AI 분석은 시가총액 상위 약 300개 기업부터 적용한다.
- **이유**: 병목은 비용보다 품질 검증이다. 좁은 범위에서 먼저 검증한다.
- **재검토 조건**: 품질을 확인한 뒤 전 종목으로 넓히고 Batch API를 도입한다.

## D-22. 핵심 기능은 OpenDART만으로 동작, 시세·뉴스는 선택 모듈

- **결정**
  - 핵심 기능(기업 이해, 재무, 공시, 리스크, 향후 전망, 경쟁사 비교)은 OpenDART와 Claude API만으로 동작하게 만든다.
  - 시세(일별 시세, 차트, 등락 순위, 일일 변동)와 뉴스는 이용 허락을 확인한 뒤 켜는 선택 모듈로 둔다.
  - AI 적용 대상 선정, 동종업계 정의, 처리 순서에는 시세를 쓰지 않는다.
  - 시세 모듈을 켜면 수정 시계열의 조정계수는 기준가(종가 − 전일 대비)와 전일 종가의 비율로 만든다. 전일 대비 값이 없는 소스라면 등락률을 누적한다.
- **이유**
  - 무료 시세 소스는 공개 서비스에 쓸 수 없다. 공공데이터포털 주식시세정보는 공공누리 제4유형(상업적 이용 금지, 변경 금지)이고, KRX OPEN API는 비상업적 이용만 허용하며 제3자 제공을 금지한다.
  - 유료 라이선스의 비용과 조건이 정해지지 않았다. 이 상태에서 핵심 기능이 시세에 의존하면 구현 일정과 설계가 라이선스 결정에 묶인다.
  - 기업 이해 서비스의 핵심 가치는 공시와 재무에서 나온다.
  - 기준가 기반 조정계수는 반올림된 등락률을 누적할 때 생기는 오차가 없다.
- **검토한 대안**
  - 무료 소스 사용: 약관 위반이다.
  - 유료 라이선스 계약 후 착수: 일정이 계약에 묶인다.
  - 시세 없는 서비스로 확정: 차트와 등락 기능을 영구히 포기하게 된다.
- **재검토 조건**: 유료 시세 라이선스의 견적과 조건이 확인될 때(시세 모듈), 네이버 검색 API 약관이 확인될 때(뉴스 모듈).

## D-23. AI 적용 대상은 매출액 상위 약 300개 + 관리자 추가

- **결정**: 최근 연간 매출액 기준 상위 약 300개와 관리자가 추가한 기업에 AI 분석을 적용한다. 분기마다 다시 계산해 `company`에 저장한다. 대상에서 빠진 기업은 마지막 분석을 기준일과 함께 유지하고 더 갱신하지 않는다.
- **이유**
  - 시가총액은 시세 데이터가 필요하다(D-22).
  - 매일 다시 계산하면 경계에 있는 기업이 대상에 들어갔다 빠졌다 하며 생성과 중단이 반복된다.
  - 금융업처럼 매출액으로 비교하기 어려운 기업은 관리자 추가로 보완한다.
- **재검토 조건**: 시세 모듈을 도입한 뒤 시가총액 기준을 함께 쓸지 검토한다. 품질을 확인한 뒤 전 종목으로 넓히고 Batch API를 도입한다.

## D-24. 휴장일은 연간 휴장일 테이블로 관리

- **결정**: 주말과 `market_holiday`에 등록된 날을 휴장일로 본다. 거래소가 발표한 다음 해 휴장일을 매년 12월에 등록한다.
- **이유**: "소스에 데이터가 없으면 휴장"으로 판단하면 수집 누락이나 소스 지연을 휴장으로 오판해 데이터 신선도 점검이 동작하지 않는다. 휴장일은 연 15일 안팎이라 수동 등록 부담이 작다.
- **검토한 대안**
  - 데이터 유무로 추정: 누락과 휴장을 구분할 수 없다.
  - 공휴일 API 연동: 거래소 고유의 휴장일(연말 휴장 등)이 반영되지 않는다.

## D-25. 참조는 자연키, 분석 결과는 값 스냅샷 포함

- **결정**
  - 기업 신호는 기업 + 유형 + 근거 키의 자연키로 식별한다. 지문과 AI 출력의 신호 참조는 자연키를 쓴다.
  - 분석 결과는 AI에 준 자리표시자 값을 스냅샷으로 함께 저장하고, 화면은 스냅샷으로 숫자를 채운다.
  - 화면은 분석 결과의 현재 스키마 버전과 직전 버전을 함께 지원한다.
- **이유**
  - 신호를 다시 계산할 때마다 대리키가 바뀌면 지문이 바뀌어 불필요한 재생성이 반복된다.
  - 동종업계 중앙값처럼 나중에 바뀌는 값을 현재 데이터로 채우면 설명 문장과 숫자가 어긋난다.
  - 구현 후에 바꾸면 저장된 결과를 모두 다시 만들어야 하므로 지금 정한다.

## D-26. 경쟁사는 상호 선택 시 자동 확정

- **결정**: AI가 후보 목록 안에서 경쟁사를 고르고, 두 기업이 서로를 고르면 코드가 확정한다. 한쪽만 골랐으면 관리자 검토 대기로 둔다.
- **이유**: 약 300개 기업에서 최대 5개씩 나오는 제안을 모두 사람이 확정하면 운영 부담이 크다. 상호 선택은 코드 규칙으로 판단할 수 있는 신뢰 신호다.
- **검토한 대안**
  - 전부 관리자가 확정: 운영 부담이 크다.
  - AI 선택 즉시 확정: 오류가 그대로 화면에 노출된다.
- **재검토 조건**: 자동 확정된 쌍에서 오류가 자주 발견될 때.

## D-27. 대상 범위 밖 상장사도 상태로 저장

- **결정**: KONEX, 스팩, 리츠처럼 대상 종목 범위 밖의 상장사도 `company`에 저장하고 상태를 EXCLUDED, 제외 사유를 함께 기록한다. 이후 수집·분석은 ACTIVE 기업만 대상으로 한다.
- **이유**
  - 범위 밖 기업을 저장하지 않으면 코넥스→코스닥 이전상장이나 사명 변경으로 범위에 들어올 때 처음부터 다시 판정해야 하고, 왜 빠졌는지 확인할 방법이 없다.
  - 상장폐지 감지와 범위 판정이 같은 기업 목록을 기준으로 동작해 규칙이 단순해진다.
  - 상장사는 수천 개 수준이라 저장 비용이 무시할 만하다.
- **검토한 대안**: 범위 밖 기업은 저장하지 않고 수집 체크포인트에만 남기기 (제외 사유와 이력을 알 수 없다).

## D-28. 기업 상세는 변화를 먼저 보여 준다

- **결정**
  - 기업 상세의 섹션 순서를 개요 → **최근 변화(타임라인)** → 앞으로 지켜볼 점 → 재무 → (주가) → 리스크 → 사업구조 → 경쟁사 → 공시 전체로 둔다 (architecture.md §6.2).
  - "최근 변화" 타임라인은 코드가 변화 신호와 지난 이벤트를 발생 시점 순으로 배치하고, 같은 시기의 관련 공시·재무 근거를 연결해 만든다. 설명은 향후 전망 분석의 신호별 설명을 재사용하고, 새 AI 분석 종류는 추가하지 않는다.
  - 뉴스(뉴스 모듈)는 변화 신호·이벤트와 연결된 것만 보여 준다. 기업별 최신 뉴스 나열 목록은 만들지 않는다.
- **이유**
  - 제품 정의(product.md §1, §11-1, §14)는 "현재 상태"가 아니라 "변화와 그 맥락"을 중심에 둔다. 기존 구성(개요·사업구조·재무·뉴스·공시·리스크·향후 전망을 데이터 종류별로 나열)은 상태 나열에 가까웠다.
  - 변화 판정(신호)과 설명(향후 전망)은 이미 설계에 있었으므로 화면 배치만 바꾸면 된다. AI 비용과 분석 구조는 그대로다 (D-09, D-16 유지).
  - 연결 없는 뉴스 나열은 product.md §12의 판단 기준을 통과하지 못한다.
- **검토한 대안**
  - "최근 변화 요약" AI 분석을 새로 추가: 향후 전망과 입력이 대부분 겹쳐 비용과 관리 대상만 늘어난다.
  - 기존 데이터 종류별 구성 유지: 제품 정의와 어긋난다.
- **재검토 조건**: 화면 구현 후 사용자가 변화 타임라인보다 개요·재무를 먼저 찾는다는 근거가 생길 때.

## D-29. 변화 신호는 발생 시점·지속성과 함께 이력으로 남긴다

- **결정**
  - `company_signal`에 발생 기준일(재무 기간 종료일 또는 공시 접수일)과 지속(같은 방향이 이어진 연속 기간 수)을 둔다.
  - 조건이 사라진 신호는 지우지 않고 비활성으로 남긴다. 비활성 신호는 변화 이력(타임라인)에 쓴다. (D-36에서 비활성을 이력과 철회로 나눴다. 타임라인에는 이력만 쓴다.)
  - 변화와 근거(같은 시기의 공시·재무)의 연결은 코드 규칙으로 조회 시점에 계산하고 저장하지 않는다 (ai-analysis.md §3.3).
  - AI는 원문이 밝힌 원인을 출처와 함께 옮기거나, 코드가 연결한 근거를 "같은 시기에 함께 일어난 사실"로 전한다. 원문 근거 없는 인과 단정은 금지 표현으로 다룬다 (ai-analysis.md §7.2).
- **이유**
  - product.md §4의 "언제 변했는가", "일시적인가 지속적인가", "무엇과 관련되어 있는가"에 코드로 답하기 위한 최소 속성이다.
  - 신호 테이블을 구현한 뒤에 이력 보존과 발생 시점을 추가하면 과거 변화를 다시 계산해야 하므로 구현 전에 정한다.
  - "왜"를 AI가 추정하게 두면 D-06(판정은 코드)과 product.md §11-5(근거 없는 설명 금지)에 어긋난다.
- **검토한 대안**
  - 활성 신호만 유지: 변화의 흐름(이력)을 보여 줄 수 없다.
  - 연결 결과를 테이블로 저장: 규칙을 바꿀 때마다 다시 만들어야 한다. 조회 비용이 문제가 될 때 검토한다.

## D-30. 비밀값은 저장소 밖 파일에서 앱이 직접 읽는다

- **결정**
  - API 키 등 비밀값은 저장소 밖의 YAML 파일에 두고, 앱이 기동할 때 `spring.config.import`로 직접 읽는다.
    - 로컬: `~/.stockinsight/secrets.yml` (없어도 기동)
    - 운영: `/etc/stockinsight/secrets.yml` (소유자만 읽기, 없으면 기동 실패)
    - 경로는 환경 변수 `STOCKINSIGHT_SECRETS`로 바꿀 수 있다.
  - 파일의 키 이름은 환경 변수 이름과 같게 한다(`DART_API_KEY` 등). 같은 이름의 환경 변수가 있으면 환경 변수가 우선한다.
  - 저장소에는 값 없는 `secrets.example.yml`만 두고, `.gitignore`와 CI의 gitleaks로 유출을 막는다.
  - AWS를 도입하면 Parameter Store(SecureString)를 원본으로 삼고, 배포 단계에서 운영 파일을 만든다. 앱은 바꾸지 않는다.
- **이유**
  - Windows 터미널, IntelliJ, 운영 서버가 모두 "앱이 파일을 읽는" 같은 방식으로 동작한다. 환경 변수는 터미널과 IDE에 따로 설정해야 해서 어긋나기 쉽다.
  - 파일이 저장소 폴더 밖에 있으므로 `.gitignore` 실수가 있어도 커밋될 수 없다.
  - 아직 AWS 계정이 없어도 쓸 수 있고, 추가 의존성이 없다.
- **검토한 대안**
  - 환경 변수만 사용: 터미널·IntelliJ·서버에 각각 설정해야 한다.
  - 앱이 SSM Parameter Store를 직접 읽음: 모든 환경에서 같지만 지금은 AWS가 없다. AWS 도입 후 재검토한다.
  - 저장소 안의 git 제외 `.env` 파일: 평문 파일이 저장소 폴더에 있어 실수로 커밋될 위험이 남는다.
  - 1Password CLI, SOPS, 외부 비밀값 서비스: 1인 운영에 비해 도구·비용이 늘어난다.
- **재검토 조건**: AWS를 도입할 때 운영 파일 생성 방식을 정하고, 로컬도 SSM을 직접 읽게 할지 검토한다.

## D-31. 공시는 날짜·유형 단위로 모두 받고, 정정 이력을 남기며 원 공시 연결은 코드가 한다

- **결정**
  - OpenDART 공시검색을 기업 지정 없이 접수일 하루 × 공시 유형(정기공시 A, 주요사항보고 B, 거래소공시 I) 단위로 끝 페이지까지 읽고, ACTIVE 기업의 공시만 저장한다.
  - 정정 전 원 공시도 받는다(`last_reprt_at=N`). 공시는 공시번호로 한 번만 저장하고 지우지 않는다.
  - 정정 공시(보고서명 앞 `[기재정정]`·`[첨부정정]`·`[첨부추가]` 등)는 코드가 원 공시에 연결한다. 원 공시 = 같은 기업, 정정 표시와 기타정보(원본에서 공백 여러 칸 뒤에 붙는 부가 설명)를 뗀 보고서명이 같은 최초 제출 중 공시번호가 앞서는 가장 최근 것.
  - 체크포인트는 날짜·유형 단위이며, 그 날짜가 끝난 뒤에 읽어야 확정된다. 확정된 날짜는 다시 읽지 않는다.
- **이유**
  - 기업별 조회는 ACTIVE 기업 수(약 2,500)만큼 호출이 필요하지만, 날짜 단위 조회는 초기 적재 3년이 약 3,300호출 + 추가 페이지로 끝나고 증분은 하루 몇 호출이다.
  - 최종본만 받으면 나중에 정정된 원 공시가 목록에서 빠진다(실제: 2026-08-14 정기공시 2,594건 → 최종본만 2,485건). "언제 무엇을 밝혔고 언제 고쳤는가"는 변화의 이력이다 (D-29).
  - OpenDART는 원 공시의 공시번호를 주지 않는다. 공식 정의상 보고서명은 "공시구분 + 보고서명 + 기타정보"이고 정정 표시는 "같은 보고서명으로 이미 제출된 보고서"에 대한 후속 제출이므로, 기타정보를 뺀 보고서명이 연결 기준이 된다(실제로 거래소공시 정정은 기타정보를 빼거나 바꿔 낸다). 연결은 판정이므로 코드가 한다 (D-06).
  - 비고의 "정"(이후 정정 있음) 표시는 원 공시에 나중에 붙는다. 확정된 날짜를 주기적으로 다시 읽는 대신 정정 여부를 연결로 판단하면 호출이 늘지 않는다.
- **검토한 대안**
  - 기업별 조회: 호출 수가 많고, 날짜 단위로 확정 여부를 관리하기 어렵다.
  - 최종본만 저장: 정정 이력이 사라지고, 신호·분석이 참조한 공시번호가 목록에서 없어질 수 있다.
  - 최근 7일을 매일 다시 읽어 비고를 갱신: 정정은 수개월 뒤에도 나오므로(실제: 6월 원 공시에 9월 정정) 7일로는 부족하고, 연결로 판단하면 필요 없다.
- **한계**
  - 같은 기업이 같은 이름의 보고서를 여러 번 최초 제출하면(예: 유상증자결정 두 건) 정정은 앞선 것 중 가장 최근 것에 연결된다. 실제와 다를 수 있다.
  - 원 공시가 수집 기간 밖이면 연결하지 않는다. 공급계약 정정은 2년 넘게 이어지기도 한다.
  - 원 공시와 정정의 보고서명 본문이 다르면 연결하지 않는다(실제: "단일판매ㆍ공급계약체결"과 "…(자율공시)").
  - 날짜를 확정한 뒤에 ACTIVE가 된 기업(코넥스→코스닥 이전상장 등)의 그 이전 공시는 받지 않는다.
- **재검토 조건**: 연결 오류가 화면·분석에서 문제가 될 때(공시 원문의 정정 대상 정보 활용 검토), 이전상장 기업의 과거 공시가 필요할 때(해당 기업만 고유번호 지정 조회로 채움).

## D-32. 재무는 주요계정 응답을 보고서·계정 행 그대로 저장하고, 해석은 코드가 읽을 때 한다

- **결정**
  - 다중회사 주요계정 API 응답을 `financial_report`(기업·기간·연결/별도 한 벌)와 `financial_line`(계정 한 줄)에 원천 그대로 저장한다. 계정명·순서(`ord`)·재무제표 구분과 금액 5종(당기, 당기누적, 전기, 전기누적, 전전기)을 모두 남긴다.
  - 연결(CFS)과 별도(OFS)는 응답에 있는 대로 모두 저장한다. "연결 우선"은 읽을 때 코드가 고른다.
  - 계정명을 지표 키(매출액, 영업이익 등)로 바꾸는 매핑, 재무제표 형식(일반/금융) 판별, 4분기 단독값, 비율은 저장하지 않고 코드가 읽을 때 계산한다.
  - 정정되면 같은 기간의 행을 최신 응답으로 바꾼다. 이전 값은 보관하지 않는다. 행에는 응답의 공시번호(`rcept_no`)를 남긴다.
- **이유**
  - 계정 구성이 기업마다 다르다(2026-09-25 실제 응답): 일반 기업은 15행, 금융형 기업은 17~20행이고 매출액·유동/비유동 구분이 없거나 이자수익·예수부채 같은 계정이 온다. 영업이익은 "영업이익"과 "영업이익(손실)" 두 이름으로 온다. 가로형 컬럼은 이 차이를 담으려면 컬럼이 계속 늘고, 모르는 계정은 버려야 한다.
  - 변화를 같은 보고서의 전기 값과 비교하려면(D-33) 계정마다 금액 5종이 필요하다. 가로형이면 계정 × 금액 수만큼 컬럼이 생긴다.
  - 원천 행을 남기면 매핑 규칙을 바꿔도 다시 받지 않고 다시 계산할 수 있다. 같은 응답에 이미 들어 있는 값이므로 호출·수집 범위를 늘리는 것이 아니다.
  - 주요계정 API는 최신 정정본의 값만 준다(실제: 정정 후 응답의 `rcept_no`가 `[기재정정]` 공시번호). 이전 값은 다시 받을 수 없으므로 보관해도 확인할 방법이 없다. 정정 이력은 공시(D-31)에, 값의 변화 이력은 신호(D-29)와 분석 스냅샷(D-25)에 남는다.
- **검토한 대안**
  - 가로형(D-14 원안): 금융형 계정과 금액 5종을 담기 어렵고, 모르는 계정을 버려야 한다.
  - 필요한 계정만 행으로 저장: 매핑을 바꿀 때마다 다시 받아야 한다.
  - 정정 전 값도 버전으로 보관: API가 주지 않는다.
- **재검토 조건**: 현금흐름·부문 정보가 필요해 전체 재무제표 API를 쓸 때(D-14 재검토 조건과 같다).

## D-33. 재무 기간은 응답의 기간으로 식별하고, 변화는 같은 보고서의 당기·전기 비교로 계산한다

- **결정**
  - 기간은 응답의 손익 기간(`thstrm_dt`의 시작일 ~ 종료일)으로 식별한다. 회계연도는 **회계연도 시작일**로 식별하고(같은 회계연도의 1분기·반기·3분기·사업보고서가 같은 시작일을 가진다), 기간 구분(1분기·반기·3분기·연간)과 기간 종료일을 함께 저장한다. 손익 행이 없는 응답은 확인하지 못했다(표본 1,079벌 모두 있음). 없으면 그 기업·기간을 오류로 남긴다.
  - API의 `bsns_year`는 조회 키로만 쓴다. `bsns_year` = 그 보고서 기간 종료일의 연도다.
  - 분기·반기 보고서의 손익 당기 값(`thstrm_amount`)은 그 3개월 단독값, 당기누적(`thstrm_add_amount`)은 회계연도 시작부터의 누적이다. 사업보고서는 연간 값만 있다. 4분기 단독값 = 연간 − 3분기 누적(같은 회계연도).
  - 변화(전년 동기 대비)는 **같은 보고서 안의 당기 값과 전기 값**으로 계산한다. 추이(차트)는 각 기간 보고서의 당기 값으로 그린다.
  - 변화율은 같은 기준(연결끼리, 별도끼리)이고 같은 통화일 때만 계산한다.
- **이유**
  - 3월·6월 결산 기업은 같은 회계연도의 보고서가 서로 다른 `bsns_year`를 갖는다(실제: 3월 결산 모아텍의 `bsns_year=2025` 분기보고서는 2025.04~ 회계연도, 사업보고서는 2024.04~2025.03 회계연도. 6월 결산 양지사의 3분기는 `bsns_year=2026`). 결산월(`company.fiscal_month`)도 믿을 수 없다(실제: 결산월이 12월로 등록된 만호제강이 2025.07~2026.06 사업보고서를 냈다). 응답의 기간만이 기업의 실제 회계기간을 나타낸다.
  - 손익 기간 문자열(`thstrm_dt`)은 3개월 단독값에도 누적 기간을 보여 준다. 값의 의미는 필드로 판단해야 한다(실제: 삼성전자 1분기 79.1조 + 2분기 단독 74.6조 = 반기 누적 153.7조, 표본 3,120행에서 같은 규칙).
  - 다음 해 보고서의 전기 값은 회계정책 변경 등으로 재작성된다(실제: 삼성생명 2024년 자본총계가 2025년 보고서에서 16% 다르다). 서로 다른 보고서의 값을 빼면 실제 변화가 아닌 기준 변경이 변화로 보인다. 같은 보고서의 당기·전기는 같은 기준이다.
  - 보고서마다 반올림 단위가 다를 수 있다(원 단위 ↔ 백만원 반올림, 차이 0.1% 미만). 4분기 단독값처럼 보고서를 넘나드는 계산에는 이 오차가 남는다.
- **검토한 대안**
  - `bsns_year` + 보고서 종류를 회계연도로 사용: 비12월 결산 기업의 회계연도가 어긋난다.
  - 결산월로 회계연도 계산: 결산월 변경 기업에서 틀린다.
  - 모든 변화를 기간별 저장값끼리 계산: 재작성·단위 차이가 변화로 잡힌다.
- **한계**: 결산기 변경으로 12개월이 아닌 회계연도는 코드가 기간 길이로 알아내 "기간 불규칙"으로 표시하고 전년 동기 비교를 하지 않는다.

## D-34. 재무 수집은 정기공시를 계기로 하루 한 번 한다

- **결정**
  - 초기 적재: 최근 3년(조회 연도 기준 올해 포함 4개 `bsns_year`) × 4개 보고서 종류를 ACTIVE 기업 100개씩 묶어 받는다(약 420호출).
  - 증분: 공시 목록 수집이 저장한 정기공시(원 공시와 모든 정정)를 계기로, 그 기업·기간을 다시 받는다. 보고서명(예: "반기보고서 (2026.06)")에서 보고서 종류와 기간 종료 연월을 읽어 조회 키를 정한다. 분기보고서의 1분기·3분기 구분은 결산월로 정하고, 응답의 기간 종료 월이 보고서명과 다르면 오류로 남긴다.
  - 실행은 매일 새벽 공시 목록 수집 뒤 한 번이다. 장중에는 하지 않는다.
  - 적재 기간보다 오래된 기간의 정정 공시(실제: 2019년 사업보고서 정정)는 받지 않는다.
- **이유**
  - 정기공시가 재무가 바뀌는 유일한 계기다. 제출 기한을 추정해 폴링하지 않아도 된다.
  - 9월에 접수된 ACTIVE 기업 정기공시 30건(정정 포함, 가장 늦은 것은 이틀 전 접수)이 모두 주요계정 API에 있었고 공시번호도 같았다(2026-09-25 확인). 새벽 한 번이면 전날 공시까지 반영된다. 당일 접수분의 반영 시차는 확인하지 못했다.
  - 재무 변화는 분기 단위 변화이고, 신호·분석 갱신도 하루 단위면 충분하다.
- **검토한 대안**: 장중 공시 수집마다 재무 수집(architecture.md 원안) — 호출과 실행이 늘지만 얻는 것이 몇 시간의 시차뿐이다.
- **재검토 조건**: 당일 공시가 다음 날에도 API에 없는 사례가 확인될 때(재시도 규칙 추가).

## D-35. 재무 신호는 같은 보고서의 전년 동기 비교로 판정하는 6개 유형과 데이터 한계로 시작한다

- **결정**
  - 재무 신호는 6개 유형으로 시작한다(ai-analysis.md §3.4·§3.6).
    - 변화: 매출 큰 폭 증감, 영업이익률 큰 폭 변화, 흑자·적자 전환(영업이익), 부채비율 급등
    - 상태: 영업적자 지속, 자본잠식
  - 데이터 한계 신호: 재무 이력 부족, 금융업 지표 해석 제한, 매출액 없음, 재무 기준 전환, 결산기 변경, 재무 데이터 불일치, 최신 재무 미확인.
  - 변화 판정은 **같은 보고서 안의 당기·전년 동기 값**으로만 한다(분기·반기·3분기 보고서는 3개월 단독끼리, 사업보고서는 연간끼리). 4분기 단독값(보고서를 넘나드는 계산)과 전분기 대비 변화로는 신호를 만들지 않는다.
  - 비율 신호(매출·영업이익률)는 전년 동기 매출이 기준값(분기 10억 원, 연간 40억 원) 이상일 때만 만든다. 비원화 기업과 금융형 기업은 매출 기반 신호(매출 증감, 영업이익률)를 만들지 않는다.
  - 흑자·적자 전환은 양쪽 기간 모두 영업이익률 절댓값 2% 이상일 때만 만든다. 매출액이 없는 기업은 연간(사업보고서)으로만 판정한다.
  - 판정 기준값(문턱값·심각도 구간)은 코드의 규칙 카탈로그에 두고 규칙 버전을 붙인다. 버전이 바뀌면 전체를 다시 계산한다.
  - 초안에서 뺀 것: "매출 성장 가속·둔화"(증가율의 변화, 분기 단위에서 잡음이 크다. 대신 지속으로 "몇 분기째 같은 방향인가"를 준다), "높은 부채비율"(업종 맥락 없는 절대 수준 판정은 오해를 만든다. 변화인 부채비율 급등과 객관적 기준인 자본잠식만 둔다).
- **이유** (2026-09-25 로컬 저장 데이터: ACTIVE 2,545개사, 2025 전체·2026 상반기 보고서 27,346벌)
  - 다음 해 보고서에서 전기 값이 재작성되는 경우가 2분기 값만 봐도 약 4%(7,000여 값 중 280)였다. 같은 해 1분기+2분기 단독이 반기 누적과 다른 경우도 2.2%(103/4,629)였고, 보고서를 넘나들어 계산한 4분기 매출이 음수인 기업이 12개였다. 같은 보고서 비교만 이 오차에서 자유롭다.
  - 전분기 대비는 계절성이 크다(2026년 2분기 매출은 1분기 대비 중앙값 +10.7%). 전년 동기 대비가 "변했는가"에 더 정확하다.
  - 기준값이 작으면 증가율이 의미를 잃는다(전년 동기 분기 매출 50억 원 미만 기업의 증가율 상위 5%가 +634%).
  - 영업이익 부호만 보면 한 분기에 20%의 기업이 흑자·적자가 바뀐다(2,453개 중 496). 양쪽 영업이익률 2% 이상 조건을 두면 9~12%로 줄고, 0 근처의 뒤집힘이 빠진다. 전년 동기 영업이익이 음수인 경우가 1/3이라 영업이익 증가율(%)은 쓰지 않는다.
  - 금융형의 "매출액"은 이자·수수료·금융상품 손익을 합친 영업수익이라 일반형 매출과 의미가 다르다. 같은 문턱값을 쓰면 잘못된 신호가 된다. 비원화 기업은 원화 기준값을 적용할 수 없다(25개사).
  - 조건(문턱값)은 실제 분포로 정했다: 2026년 2분기 기준 매출 +30% 이상 18%, −20% 이하 8%, 영업이익률 ±10%p 19%, 전환 11%, 부채비율 급등 3.6%, 자본잠식 3.1%의 기업에서 나온다. 한 기업에 한 분기 0~4개가 나오며 절반은 0개다.
- **검토한 대안**
  - 모든 지표·기간 조합(전분기 대비, 누적 대비, 4분기 포함): 신호 수가 늘고 계산 오차·계절성이 변화로 보인다.
  - 누적(연초부터) 기준 판정: 안정적이지만 "언제 변했는가"가 흐려지고, 보고서마다 한 번씩이라는 기준이 깨진다.
  - 업종별 문턱값: 업종 분류·표본이 필요하다. 동종업계 비교 신호를 만들 때 함께 검토한다.
- **재검토 조건**: 골든셋 검토(architecture.md §10 6단계)에서 신호가 과하거나 부족할 때 문턱값을 조정한다(규칙 버전 올림). 동종업계 비교 신호는 동종업계 정의(ai-analysis.md §3.4)를 구현할 때 추가한다.

## D-36. 신호 상태를 활성·이력·철회로 나눈다

- **결정**
  - `company_signal`의 활성 여부를 상태 세 가지로 바꾼다.
    - 활성(ACTIVE): 지금도 성립한다. 변화 신호는 그 기업의 최신 재무 기간에서 나온 것, 상태 신호는 최신 기간에도 조건이 이어지는 것.
    - 이력(PAST): 그 기간에는 성립했고 지금은 최신이 아니다. 타임라인에 쓴다.
    - 철회(WITHDRAWN): 다시 계산했더니 같은 자연키로 성립하지 않는다(정정 공시로 값이 바뀌었거나 규칙 버전이 바뀜). 화면·AI 입력에서 뺀다. 행은 남긴다.
  - 행은 지우지 않는다(D-29 유지). 상태가 바뀐 시각과 규칙 버전을 남긴다.
- **이유**
  - D-29는 "조건이 사라지면 비활성으로 남겨 타임라인에 쓴다"였다. 그런데 재무는 정정으로 과거 값이 바뀌므로(D-32), 과거 기간의 신호가 "이제는 사실이 아니게 되는" 경우가 생긴다. 활성/비활성 둘로는 "지나간 사실"과 "틀린 것으로 밝혀진 것"을 구분할 수 없어, 철회된 신호가 타임라인에 변화로 보이게 된다.
  - 이력과 철회를 나눠 두면 분석 스냅샷(D-25)에 남은 과거 설명이 왜 지금 화면과 다른지도 설명할 수 있다.
- **검토한 대안**: 철회된 신호를 지우기(D-29 위반, 과거 분석이 참조한 자연키가 사라진다), 활성/비활성 유지 후 철회 사유 컬럼만 추가(조회 조건이 복잡해진다).

## D-37. 재무 시계열은 최신 기간의 기준(연결/별도)·통화로 고정한다

- **결정**
  - 한 기업의 재무 시계열(추이, 지속 계산)은 최신 재무 기간의 기준(연결이 있으면 연결)과 통화로 고정한다. 그 기준의 보고서가 없는 과거 기간은 다른 기준으로 채우지 않고 빈 기간으로 둔다.
  - 같은 보고서 안의 전년 동기 비교(D-33)는 보고서마다 그 보고서의 기준으로 한다(항상 같은 기준이다).
  - 최근 12분기 안에서 기준이 바뀐 기업은 "재무 기준 전환" 데이터 한계 신호를 둔다.
- **이유**: 연결 재무제표 유무가 기간에 따라 바뀌는 기업이 115개사(4.5%)였다(2026-09-25 로컬 데이터). architecture.md §4.3의 "기간마다 연결 우선"을 시계열에 그대로 쓰면 한 차트에 연결과 별도가 섞여, 자회사 편입·제외가 매출 급변처럼 보인다.
- **검토한 대안**: 기간마다 연결 우선(원안, 위 문제), 별도로 통일(지주회사 등 연결이 본질인 기업의 실적을 못 본다).

## D-38. 재무 쉬운 설명의 AI 입력은 코드가 만든 사실표와 신호 참조뿐이다

- **결정**
  - AI 입력은 코드가 재무 요약(`FinancialSummary`)과 `company_signal`로 만든 **설명용 사실 묶음**이다(ai-analysis.md §4.4).
    - 사실표: 자리표시자 키, 한국어 이름, 표시 값(코드가 형식화), 부호. 최신 기간과 최근 3개 사업연도의 지표·전년 동기 값·변화량, 최신 기간 말 재무상태, 코드가 센 흐름 사실(같은 방향 연속 기간 수).
    - 신호: 활성 신호와 입력 범위 안의 이력 신호(최대 4개)를 짧은 참조(`S1`…)와 유형·방향·심각도·기간·지속으로. 데이터 한계 신호는 신호가 아니라 제한 코드로 준다.
    - 코드가 정한 섹션 목록, 설명하면 안 되는 지표 목록, 변화 유무(`change_status`).
  - 넣지 않는 것: `financial_line` 원천 행과 원천 계정명, 분기별 시계열 전체(8~12분기 값), 신호의 `calc_values` 원문, 공시번호·내부 ID, 공시 제출인·원문 텍스트, 철회 신호.
  - 분기 추이는 화면 차트(코드)가 보여 준다. AI는 코드가 센 흐름 사실로만 추이를 말한다.
- **이유**
  - 분기 시계열을 주면 AI가 전분기 대비·평균·추세 같은 계산을 스스로 하게 된다. D-35가 뺀 비교(전분기 대비, 파생 4분기 비교)가 설명으로 되살아난다.
  - 입력에 없는 값은 출력에 나올 수 없다. 입력을 사실표로 좁히는 것이 검증보다 먼저인 방어다.
  - 원천 계정명·공시 텍스트는 외부 문자열이다. 넣지 않으면 프롬프트 주입 경로가 없고, 입력은 공개 재무 수치와 기업명뿐이라 개인정보도 없다.
  - 공시번호·기준일은 설명에 필요 없고 틀리게 옮겨 적힐 위험만 있다. 근거는 코드가 자리표시자의 기간으로 연결한다.
- **검토한 대안**: §3.8 원안대로 최근 8분기 값을 모두 입력(위 문제), 신호만 입력(수준 값이 없어 "지금 상태"를 설명할 수 없다).
- **영향**: ai-analysis.md §3.8의 "최근 8분기(AI 입력)"를 이 결정으로 바꾼다. 3-3.1에서 미룬 지표별 사유 코드는 이 입력을 만드는 코드(`financial` 패키지)에서 계산한다. 비율 공식은 신호 계산기와 같은 코드를 써야 설명과 신호의 숫자가 어긋나지 않는다.

## D-39. 재무 쉬운 설명은 코드가 정한 섹션에 자리표시자·신호 참조만 쓰는 짧은 글이고, 강도 표현은 신호가 있을 때만 쓴다

- **결정**
  - 출력은 섹션 네 개(`overview`, `sales_profit`, `structure`, `history`)의 짧은 글이다. 어떤 섹션을 쓸지는 입력의 섹션 목록(코드)이 정하고, AI는 그 목록만 채운다.
  - 글 안의 숫자·기간·신호는 모두 토큰이다: `{fin.…}`(사실), `{per.…}`(기간 라벨), `{sig.S1}`(신호). AI 글에는 숫자를 쓰지 않는다(연도·분기 포함).
  - "크게", "급격히", "뚜렷하게" 같은 강도 표현과 "전환", "지속" 같은 판정어는 신호 참조가 있는 문장에서만 쓴다. 변화 신호가 없으면(`change_status = NONE`) 강도 표현을 쓰지 않고 "규칙상 큰 변화로 표시된 항목이 없다"는 사실과 수준만 쓴다.
  - 같은 기간에 함께 나온 신호는 코드가 **기간·주제로 묶어** 순서를 정한다. 묶음은 "같은 시기에 함께 나타난 변화"이며 같은 원인이라는 뜻이 아니다. 방향이 엇갈리면 두 사실을 나란히 쓰고 종합 판정을 하지 않는다.
  - 이력 신호는 `history` 섹션에서만 과거형으로 쓴다. 활성 신호는 현재 섹션에서 쓴다.
  - 기준(연결/별도·통화·기간 종료일), 출처 공시, 데이터 한계 문구, AI 생성 표시는 코드가 렌더링한다. AI는 데이터 한계를 설명하지 않고, 입력에 없는 지표를 언급하지 않는다.
  - 검증을 하나라도 통과하지 못하면 결과 전체를 게시하지 않는다(부분 게시 없음). 게시본이 없으면 화면은 코드가 만든 숫자·차트·신호만 보여 준다.
  - 골든셋 검토를 통과하기 전까지 생성 결과는 초안으로만 저장하고 게시하지 않는다.
- **이유**
  - 실제 데이터에서 ACTIVE 기업의 약 절반(1,228/2,553)이 활성 변화·상태 신호가 없다. "변화 없음"이 가장 흔한 경우라 AI가 변화를 지어내지 않게 하는 장치가 필요하다.
  - 같은 기간에 신호가 2~3개 겹치는 경우가 412건(매출·영업이익률 같은 방향이 대부분)이고, 방향이 엇갈리는 조합(매출 증가 + 이익률 악화 등)도 37건이다. 코드가 묶고 순서를 정해야 같은 사실의 반복과 임의의 종합 판정을 막을 수 있다.
  - 섹션 구조가 고정되어야 화면이 안정적으로 렌더링되고, 검증기가 섹션별 규칙(이력은 과거형 등)을 적용할 수 있다.
  - 숫자·기간을 토큰으로만 쓰면 "글자에 숫자가 있는가"만으로 숫자 오류를 기계적으로 잡을 수 있다.
- **검토한 대안**: 자유 서술 한 덩어리(렌더링·검증이 어렵다), AI가 섹션·순서를 정함(중요도 판정을 AI가 하게 된다), 부분 게시(설명 일부만 보여 주면 맥락이 끊겨 오해가 생긴다).

## D-40. 재무 쉬운 설명의 지문은 입력에 쓴 원천 식별자 집합이고, 철회된 신호를 참조한 게시본은 내린다

- **결정**
  - 지문 = 입력에 쓴 보고서의 공시번호 집합 + 입력한 신호의 자연키·상태·방향·심각도·규칙 버전 + 제한 코드 집합 + 입력 구성 버전. 값의 해시는 쓰지 않는다(D-08).
  - 정정(공시번호가 바뀜), 새 보고서, 신호 철회·상태 변경, 규칙 버전 변경은 지문을 바꿔 재생성 대상이 된다. 프롬프트·모델 변경은 자동 재생성 조건이 아니다(D-08 유지).
  - 게시본이 참조한 신호가 철회되었거나, 참조한 사실의 보고서가 정정되어 공시번호가 바뀌었으면, 재생성 전이라도 화면에서 AI 설명을 내리고 "재무 자료가 바뀌어 설명을 다시 만드는 중"을 표시한다. 새 보고서가 나온 것만으로는 내리지 않는다(설명의 기준 기간을 표시하므로 틀린 것이 아니다).
- **이유**
  - 원안의 지문(최신 재무 기간 + 출처 공시번호)은 과거 연도 보고서의 정정, 신호 철회, 규칙 버전 변경을 놓친다. 설명은 최신 기간뿐 아니라 3개 사업연도와 이력 신호도 쓴다.
  - 철회는 "그 신호가 사실이 아니게 됨"(D-36)이다. 재생성이 예산·실패로 늦어져도 틀린 설명이 화면에 남으면 안 된다.
- **검토한 대안**: 입력 전체 해시(표시 형식·입력 구성 변경에도 대량 재생성, D-08 위반), 원안 지문 유지(위 누락).
- **후속 (2026-09-25)**: 구현이 무효화를 "지문 전체 비교"로 판정해 새 보고서만으로도 게시본을 내리는 문제가 확인되어 D-42로 판정 기준과 지문 구성을 구체화했다.

## D-41. 재무 금액은 한국어 수 단위와 통화명으로 코드가 렌더링할 때 표시하고, 환산하지 않는다

- **결정**
  - 금액 표시는 통화와 관계없이 한국어 수 단위(조·억·만)로 줄이고 통화명을 붙인다: 원화 "1.2조원", "8,768.6억원", "5,325만원", 위안 "13.7억위안", 달러 "1.2억달러", 엔 "3,456만엔", 파운드 "2.1억파운드". 1만 미만은 자리 구분 쉼표를 넣은 정수. 이름을 정하지 않은 통화는 코드("12.3억 CHF").
  - 원화로 환산하지 않는다. 헤더와 데이터 한계 문구(코드)가 "이 회사는 ○○로 보고해 원화로 바꾸지 않은 값"임을 알린다.
  - 표시 문자열은 렌더링할 때 원값·단위·통화로 코드가 만든다. 값 스냅샷의 원값이 기준이고, 저장된 표시 문자열은 감사용이다. AI 입력의 표시 값도 같은 서식 코드로 만든다.
  - 비원화 기업의 매출 증가율은 AI 입력·화면에 주지 않는다(`NON_KRW`). 증가율은 기준값(원화 분기 10억 원) 확인이 가능한 경우에만 보여 준다. 영업이익률·부채비율처럼 기준값이 필요 없는 비율은 비원화도 보여 준다.
  - `revenue_yoy_run`(매출 같은 방향 연속 분기 수)은 최신 기간의 `revenue_yoy`를 줄 수 있을 때만 준다(금융형·비원화·기준값 미만·전년 값 ≤ 0이면 주지 않는다).
- **이유**
  - 구현은 원화만 억·조로 줄이고 비원화는 "1366952305CNY"처럼 원값을 그대로 붙였다. 원화도 1억 미만이면 "53254120원"이 된다(원화 영업이익·순이익 값의 2.1%, 1,736/81,108). 사용자가 크기를 읽을 수 없고, 화면과 AI 입력이 같은 문제를 갖는다.
  - 억·조는 통화 단위가 아니라 한국어의 수 단위라 어느 통화에나 쓸 수 있고, 사용자가 이미 익숙하다.
  - 환산은 환율이라는 새 외부 데이터와 새 계산(기준일·환율 선택)이 필요하고, 환율 변동이 기업의 변화처럼 보인다. 이 제품은 한 기업을 그 기업의 보고 통화로 본다(D-37).
  - 서식을 렌더링 시점에 만들면 서식을 고쳐도 다시 생성하지 않아도 된다(서식은 지문 대상이 아니다, D-08).
  - 증가율은 기준값 확인 없이 보여 주면 작은 기준값의 과장(D-35)이 그대로 나온다. 연속 증감 수는 증가율의 부호로 만든 사실이므로 증가율을 주지 않는 경우에 주면 "보여 주지 않기로 한 지표의 추세"를 AI가 말하게 된다.
- **검토한 대안**: 통화 코드 + 쉼표 원값("1,366,952,305 CNY", 크기를 읽기 어렵다), 환율 환산(위 문제), 비원화 증가율 제공(기준값 확인 불가).
- **관계**: D-35(비원화 매출 신호 제외)·D-37(시계열 통화 고정)·D-38(입력 사실표)을 바꾸지 않고 표시와 제공 조건을 정한다. ai-analysis.md §3.6·§4.4.2의 "비원화는 비율은 계산"을 "기준값이 필요 없는 비율만"으로 구체화한다.

## D-42. 게시본은 참조한 것이 틀려졌을 때만 내리고, 지문은 입력 내용을 바꾸는 식별자로만 만든다

- **결정**
  - **무효화(화면에서 내림)**: 게시본의 값 스냅샷이 참조한 것 중 하나라도 다음에 해당할 때만 내린다.
    - 참조한 신호(`{sig}`)가 철회되었거나 방향이 바뀌었다.
    - 참조한 사실(`{fin}`)의 기간·기준(연결/별도)에 해당하는 보고서의 현재 공시번호가 스냅샷과 다르거나 보고서가 없어졌다.
  - 무효화가 아닌 것: 새 보고서 도착, 참조 신호의 활성→이력 전환·심각도 변경, 규칙 버전 변경만으로 같은 신호가 그대로 성립하는 경우, 시계열 기준 전환(스냅샷의 사실은 그 기준으로 여전히 맞다), 데이터 한계 신호 변화. 이런 경우 게시본은 기준 기간을 표시한 채 남고, 지문이 바뀌었으면 재생성 대상이 된다.
  - 무효화 판정은 스냅샷에 적힌 자연키·기간·기준으로 현재 신호 상태와 현재 공시번호만 조회한다. 입력 전체를 다시 만들지 않는다.
  - **지문**: 입력에 쓴 보고서 공시번호 + 입력 신호(자연키·상태·방향·심각도·규칙 버전) + **`unavailable` 항목(지표·사유) 집합** + 입력 구성 버전. 데이터 한계 신호 코드 자체는 넣지 않는다(입력 내용을 바꾸는 한계는 `unavailable`과 섹션 구성에 이미 드러난다).
  - **헤더·데이터 한계 문구**(코드)는 렌더링 시점의 현재 값으로 보여 준다(예: 설명 생성 뒤 "최신 재무 미확인"이 된 경우). AI 문장만 스냅샷을 쓴다.
- **이유**
  - D-40의 목적은 "틀린 설명이 화면에 남지 않게"다. 구현은 지문 전체 비교로 판정해, 정상적인 새 분기 보고서만 와도(공시번호 집합이 바뀌고 이전 활성 신호가 이력이 된다) 모든 게시본을 내린다. 제출 기한 직후 AI 적용 대상 대부분의 설명이 동시에 사라지고, 생성이 3회 실패하면(§6.1) 틀리지 않은 설명이 관리자 조치 전까지 가려진다. 규칙 버전을 올리면 모든 게시본이 한꺼번에 내려간다.
  - 구현은 화면을 그릴 때마다 기업의 재무 요약·신호 전체로 입력을 다시 만든다. 조회 경로의 비용이 분석 생성과 같아진다(architecture.md §1.3 원칙 1의 취지에 어긋난다).
  - 데이터 한계 코드 중 "최신 재무 미확인"은 날짜가 지나면 바뀌지만 입력 사실은 그대로다. 지문에 넣으면 내용이 같은 설명을 다시 만들고, 원 구현에서는 게시본까지 내린다.
- **검토한 대안**: 지문 비교 유지(위 과잉 무효화), 무효화 없이 재생성만(재생성이 늦거나 실패하면 철회·정정된 사실이 화면에 남는다, D-40 위반).
- **관계**: D-40의 결정(철회·정정 시 내림, 새 보고서만으로는 내리지 않음, 원천 식별자 지문)을 그대로 따르며 판정 기준과 지문 구성만 구체화한다. D-36(신호 상태)·D-37(시계열 기준)과 함께 쓴다.

## D-43. "최신 재무 미확인"은 가장 긴 법정 기한으로 판정하고, 판정이 알려 준 날에만 시간으로 다시 판정하며, 다음 보고서가 오면 이력이 된다

`FIN_DATA_STALE`(D-35의 데이터 한계 신호 "최신 재무 미확인")의 판정 기준, 다시 판정하는 시점, 상태 전이를 정한다. 신호의 뜻("최신 기간 다음 보고서가 기한이 지났는데 수집되지 않았다. 미제출이 아니라 수집 기준 미확인")과 쓰임(데이터 한계 문구)은 바꾸지 않는다.

- **결정**
  - **판정** (최신 기간 P = 시계열 기준(D-37)에서 가장 뒤 기간)
    - 다음 기간 종료일은 P 종료일에서 3개월 뒤 **그 달의 말일**이다. 이 기업의 다음 보고서는 P가 회계연도 3분기면 사업보고서, 아니면 분기·반기보고서다.
    - 기한일은 다음 기간 종료일 + **60일**(분기·반기보고서) 또는 **120일**(사업보고서)이다. 상장사에 적용되는 가장 긴 기한을 모든 기업에 쓴다.
    - 기한은 **달력일**로 센다. 휴일·영업일은 따지지 않는다. 기한일 뒤 **7일 유예**가 휴일 순연과 수집 시차를 흡수한다.
    - 판정일(서비스 시간대 기준 오늘)이 기한일 + 8일 이상이고 최신 기간이 아직 P이면 `FIN_DATA_STALE`을 둔다. 근거 키는 P다. 기한일 + 7일까지는 두지 않는다. 계산값에 기한일을 남긴다(감사용).
    - 재무가 전혀 없는 기업은 대상이 아니다(기준이 될 기간이 없다).
  - **다시 판정하는 시점**
    - 재판정 계기는 기존 계기(규칙 버전 변경, 그 기업 재무 변경, 이전 판정 오류)에 **"판정이 시간만으로 바뀔 수 있는 날의 도래"**를 더한다.
    - 그 날은 판정할 때 판정 자신이 계산해 결과와 함께 남긴다. STALE이 아니면 P의 기한일 + 8일이고, 이미 STALE이면 그런 날이 없다. 매 실행은 이 날이 지난 기업만 추가로 다시 판정한다.
    - 기한 계산은 규칙 카탈로그 한 곳에만 둔다. 판정과 재판정일 계산이 같은 계산을 쓴다.
    - 매일 전체 재판정은 하지 않는다.
  - **상태 전이** (D-36의 세 상태를 그대로 적용한다)
    - **활성**: 최신 기간이 P이고 판정일이 유예 뒤다. 같은 P가 정정되어 다시 판정해도 근거 키가 같아 활성으로 남는다. 상태가 그대로이므로 상태 변경 시각도 바뀌지 않는다.
    - **이력**: P보다 뒤 기간의 보고서가 수집되어 최신 기간이 바뀌었다. 그때는 성립했고 지금은 최신이 아니다. 해소는 철회가 아니므로 철회 수와 철회 급증 경고에 넣지 않는다.
    - 새로 수집된 기간 P′도 이미 유예가 지났으면 같은 판정에서 `STALE(P′)`가 활성이 된다(여러 기간을 한꺼번에 늦게 낸 경우). `STALE(P)`는 이력이 된다.
    - **철회**: 최신 기간이 P보다 뒤로 가지 않았는데 성립하지 않게 되었다. 규칙 버전 변경(기한 변경), 또는 P 보고서가 없어져 최신 기간이 앞으로 돌아간 경우다.
    - 이력·철회된 STALE은 화면 타임라인과 AI 입력에 넣지 않는다(ai-analysis.md §3.2·§4.4.2의 기존 규칙). 데이터 한계 문구는 활성만 렌더링 시점에 보여 준다(D-42). STALE은 지문·무효화 대상이 아니다(D-42).
  - 기한과 말일 계산이 바뀌므로 규칙 버전을 올린다(`fin-2`).
- **이유**
  - **시간 조건은 한 기간에 한 번만 바뀐다.** 기한 전에서 기한 후로 한 번 바뀌고, 최신 기간이 그대로면 되돌아가지 않는다. 판정 결과가 시간으로 바뀌는 날을 판정할 때 이미 알 수 있으므로, 그날만 그 기업을 다시 판정하면 된다. 이미 STALE인 기업은 재판정일이 없으니 날마다 중복 계산하지 않는다. 현재 구현은 이 계기가 없어서, 첫 전체 실행 뒤에는 새로 기한이 지나는 기업(이 신호의 대상)이 다시 판정되지 않는다.
  - **45일·90일 기준은 일부 기업에 틀린 표시를 한다** (2026-09-25 로컬 데이터).
    - 2026년 반기보고서 원 공시 2,457건 중 31건이 기한(8/14) 뒤에, 27건이 유예(8/21) 뒤에 접수되었다. 27개사는 모두 ACTIVE이고 8/25~9/1에 냈다.
    - 같은 기업들이 2025년 3분기(11/28~12/1)와 2026년 1분기(5/28~6/2)에도 종료 후 약 60일에 냈다. 60일째가 토요일이면 다음 월요일에 냈다.
    - 그중 외국 기업(크리스탈신소재, 헝셩그룹, 윙입푸드 등)은 2025 사업보고서를 4/20~4/30(약 120일)에 냈다.
    - 기업 구분에 따라 법정 기한이 다르다고 본다. 법령상 근거는 확인하지 않았다 [미확인].
    - 45일·90일 기준이면 이 기업들은 분기마다 3~10일 동안 "제출 기한이 지났다"는 사실과 다른 표시를 받는다.
  - **기업별 기한 대신 가장 긴 기한을 쓴다.** 기업별로 나누려면 외국법인·연결 첫해 같은 구분 데이터가 새로 필요하다(범위 밖). 가장 긴 기한은 새 데이터 없이 틀린 표시를 없앤다. 대신 일반 기업의 지연을 분·반기 15일, 사업보고서 30일 늦게 알린다. 모든 값에 기간 종료일을 표시하므로(ai-analysis.md §3.8, D-42 헤더) 이 늦음은 받아들인다. 기한 전인 기업에 기한이 지났다고 말하는 것이 늦게 알리는 것보다 나쁘다.
  - **휴일을 따지지 않는 이유**
    - 기한일이 토요일·공휴일이면 제출은 다음 영업일로 미뤄진다(관찰: 60일째 8/29 토 → 8/31 월 제출 9건). 네 기한 무렵(3월 말, 5월 말, 8월 말, 11월 말)에는 긴 연휴가 없어 순연은 며칠이다.
    - 7일 유예가 이 순연과 새벽 수집 시차(D-34, 하루)를 함께 흡수한다.
    - 휴장일 테이블(D-24)은 증시 휴장일이라 법정 기한이 미뤄지는 날(공휴일)과 다르다. 그 테이블을 쓰면 핵심 신호가 선택 모듈 데이터에 기대게 된다(D-22).
  - **말일 기준으로 계산한다.** 현재 구현은 종료일에 3개월을 더해 9월 30일 → 12월 30일이 된다. 가장 흔한 3분기 → 사업보고서 경로에서 기한이 하루 이르다.
  - **해소는 이력으로 둔다.** 해소를 철회로 두면 D-36의 철회("틀린 것으로 밝혀짐")와 뜻이 어긋난다. 늦은 제출이 몰리는 날에는 철회 급증 경고도 잘못 켜진다.
- **검토한 대안**
  - **작업이 기업마다 최신 기간을 따로 조회해 기한 경과 여부를 원천 버전에 넣기** (implementation-plan.md §8.4의 원안 A): 작업과 계산기가 "최신 기간"과 기한을 따로 계산하게 되어 어긋날 수 있다. 기준 전환(D-37)이나 결산기 변경 기업에서 특히 그렇다.
  - **매일 전체 재판정** (B): 2,545개사에 약 25초라 비용은 작다. 하지만 매 실행이 "전체 재계산"(대상 50% 초과)으로 분류되어 철회 급증 경고가 영구히 꺼진다. 날마다 모든 신호 행도 다시 쓴다.
  - **읽을 때 판정하고 저장하지 않기** (C): D-35의 저장 신호에서 빠진다. 신호를 읽는 곳(화면, AI 입력, 한계 문구)이 같은 계산을 따로 해야 하고, 언제부터 미확인이었는지 기록(D-29)이 남지 않는다.
  - **12월 결산 기한 다음 날에만 전체 재판정**: 12월 결산이 아닌 기업을 놓친다.
  - **45일·90일을 유지하고 문구만 완화**: 기한 전인 기업은 아직 낼 보고서가 없으므로 "최신이 아닐 수 있다"는 표시 자체가 틀리다.
  - **계산기가 공시번호의 접수일로 과거 STALE을 매번 재현**: 주요계정 API는 마지막 정정의 공시번호만 준다(implementation-plan.md §4.1). 그래서 원래 제출일을 알 수 없다.
- **재검토 조건**: 가장 긴 기한보다 늦게 내는 기업 무리가 확인될 때, 기한 무렵 연휴로 유예를 넘는 순연이 생길 때, 기업별 기한 구분 데이터가 생길 때.
- **관계**
  - D-35의 데이터 한계 신호 목록은 그대로다. 기준값은 ai-analysis.md §3.7에서만 바꾼다.
  - D-36의 세 상태 정의를 그대로 적용한다. 구현이 해소를 철회로 처리하던 것을 이력으로 바로잡는다.
  - D-34(새벽 수집)의 시차는 유예가 흡수한다.
  - D-42(한계 문구는 렌더링 시점 현재 값, 지문·무효화에서 제외)와 함께 쓴다. 그래서 STALE이 바뀌어도 AI 재생성이나 게시본 내림이 일어나지 않는다.
  - 다른 데이터 한계 신호도 새 분기마다 근거 키가 바뀌어 철회된다. 이 문제는 이 결정에 넣지 않고 implementation-plan.md §3에 판단 대기로 둔다.

## D-44. 재무 쉬운 설명 호출은 확장 사고(thinking)를 끈다

- **결정**: `AnthropicLlmClient`가 `financial_explain`을 호출할 때 `thinking: {type: "disabled"}`를 명시한다(SDK가 이 값을 그대로 받는 모델일 때만 가능하며, 현재 모델 `claude-sonnet-5`는 받는다). `max_tokens`는 기존 값(2,000)을 그대로 둔다.
- **이유**
  - 실제 인증키로 처음 호출해 보니(2026-09-26) 이 모델은 `thinking`을 켜지 않아도 기본으로 확장 사고를 한다. 골든셋 12개사 전부가 사고 토큰만으로 `max_tokens`를 소진해 응답이 잘렸다(`MAX_TOKENS`, 재시도까지 12개사 전부 실패). 사고 토큰은 기업 하나당 약 1,000~1,100개였고, 실제 필요한 본문은 400~1,000개 수준이었다(회사별 사실·신호 개수에 따라 다름).
  - 이 분석은 코드가 판정을 모두 끝낸 사실표·신호를 정해진 섹션·토큰 문법으로 옮겨 쓰는 역할뿐이다(D-06, D-38, D-39). 새 계산·새 비교·새 판정을 하지 않으므로 다단계 추론이 필요 없다. 확장 사고를 켜 둘 이유가 없다.
  - `max_tokens`를 사고 토큰까지 감안해 올리는 방법(예: 8,000)도 시도했으나, 기업마다 사고 길이가 달라 일부는 8,000에서도 잘렸다(재현: 2개사). 사고를 끄는 쪽이 예측 가능하고 비용도 적다.
  - 사고를 끈 뒤 같은 12개사를 다시 호출하면 전부 `end_turn`으로 정상 완료되고(잘림 없음), 출력 토큰은 1,000~1,700개(재시도 포함 2회 합)로 `max_tokens=2,000`(1회당)에 여유 있게 들어간다. 호출당 비용은 약 $0.015~0.031로 ai-analysis.md §9의 원래 가정(약 $0.02)과 다시 맞아떨어진다(2026-09-26 실측, 재무 쉬운 설명만 해당).
- **검토한 대안**
  - `max_tokens`만 올리고 사고는 그대로 둠: 기업마다 사고 길이가 달라 일부는 여전히 잘리고, 잘리지 않는 경우도 사고 토큰만큼 비용이 사실상 두 배 가까이 든다(관측: 사고 포함 시 출력 토큰이 사고 없을 때의 약 1.5~2배).
  - `effort`를 낮춰 사고 깊이만 줄임: 이 모델(`claude-sonnet-5`)은 `disabled`를 그대로 받아들이므로 더 단순한 방법(끄기)이 있다. `effort`는 사고를 켠 채로 깊이만 조절하는 값이라 이 상황에는 맞지 않는다.
  - 다른 모델로 교체: 근거 없이 모델을 바꾸지 않는다(이번 조사 범위 밖, D-09).
- **위험과 완화**: Anthropic 문서상 사고를 끄면 안내문(전용 태그 등)이 본문에 새어 들어가는 경우가 보고된 모델도 있다. 이 호출은 도구 호출이 없고 구조화 출력(JSON 스키마)으로 강제하므로 그 경로의 위험은 낮지만, 실제 12개사 검증에서 이 문제가 나타나는지 함께 확인했다(§7.4 참고, implementation-plan.md). 나타나면 이 결정을 재검토한다.
- **재검토 조건**: 모델을 바꿀 때(새 모델이 `disabled`를 받지 않으면 `effort` 조절로 대체), 다른 분석 종류(기업 이해·향후 전망 등)를 구현할 때 그 종류의 입력 성격(원문 요약처럼 다단계 추론이 실제로 필요한지)에 따라 따로 판단한다. 이 결정은 재무 쉬운 설명에만 적용한다.
- **관계**: D-06(계산과 판단은 코드)·D-09(동기 호출·단일 모델)·D-38~D-40(입력·출력·지문 계약)을 바꾸지 않는다. ai-analysis.md §8(모델 설정)·§9(비용 가정)를 이 결정에 맞게 구체화한다.

## D-45. 흐름 사실은 history가 아니라 sales_profit에서 현재형으로 쓴다; 개요와 다른 섹션은 서로 다른 사실 토큰을 쓴다

- **결정**
  - `FinancialExplainInputBuilder`는 `history` 섹션을 이력(PAST) 신호가 있을 때만 연다. 흐름 사실(`revenue_yoy_run`, `operating_loss_run`)은 더 이상 `history`를 여는 조건이 아니다(둘 다 최신 기간까지 거꾸로 센 "지금 이어지는" 값이라 끝난 과거가 아니다).
  - 프롬프트(v1.md)는 흐름 사실을 `sales_profit`에서 현재형으로만 쓰게 명시하고 `history`에는 쓰지 않는다고 못박는다. `FinancialExplainValidator` 규칙 7을 확장해 흐름 사실 토큰이 `history`에 나오면 실패로 잡는다(최종 판정은 코드가 한다).
  - 프롬프트는 "개요(overview)에서 쓴 사실 토큰은 다른 섹션에서 다시 쓰지 않는다"를 명시하고, 같은 지표를 두 번 언급해야 하면 개요는 변화량 사실(`_yoy`, `_diff`)을, 다른 섹션은 원값 사실(`revenue`, `operating_income` 등)을 쓰도록 구체적인 예시를 준다.
  - 프롬프트는 "한 문장에 사실 토큰을 여러 개 써도 된다"는 것과 사실 2개를 한 문장에 묶는 예시를 추가한다.
  - §4.4.3의 섹션별 문장·토큰 수 상한(overview 2/3, sales_profit 4/6, structure 3/4, history 3/∞)은 **바꾸지 않는다**.
- **이유**
  - 2026-09-26 실제 12개사 검증(§7.4.1)에서 규칙 7(이력 시제) 4/12, 규칙 4(토큰 반복) 8/12, 규칙 10(분량) 9/12가 반복 실패했다. 검증을 그대로 느슨하게 만들지 말고 구조적 원인을 확인해 달라는 요청에 따라 다음을 확인했다.
    1. **history 조건 자체가 AI에게 암묵적 판정을 떠넘기고 있었다.** 기존 §4.4.3은 "흐름 사실은 history에서 과거형, 다만 지금도 이어지는 상태는 sales_profit에서 현재형"이라고 적어 "이 흐름 사실이 지금도 이어지는 상태인지"를 AI가 그때그때 판단하게 했다. 그런데 `revenue_yoy_run`·`operating_loss_run`은 계산 자체가 최신 분기에서 거꾸로 센 "지금까지 이어진 연속" 값이라(`FinancialExplainInputBuilder.FactCollector#addFlowFacts`), 이 둘은 애초에 항상 "지금도 이어지는 상태"이지 순수한 과거 종료 사건이 아니다. 908(STX) 진단에서 실제로 활성 신호가 `history` 안에 섞여 나온 사례가 이 판정 떠넘김의 결과로 보인다. "판정은 코드, 설명은 AI"(D-06) 원칙대로 이 배치를 코드가 고정하면 AI가 판단할 여지 자체가 없어진다.
    2. **개요·손익 섹션의 토큰 반복은 프롬프트가 회피 방법을 알려주지 않았을 뿐, 입력에는 회피 수단(원값 사실과 변화량 사실이 별도 키로 이미 존재)이 있었다.** 908 사례에서 모델은 개요에 쓴 `revenue_yoy`·`operating_margin_diff`를 손익 섹션에서 그대로 다시 썼는데, 입력에는 이미 `revenue`(원값)·`operating_margin`(원값) 같은 별도 사실 키가 있어 반복하지 않고도 손익 섹션을 채울 수 있었다. 입력 계약(D-38)의 문제가 아니라, 프롬프트가 이 두 종류 키를 섹션별로 나눠 쓰라고 지시하지 않은 문제다.
    3. **분량 상한은 사실 개수 대비 넉넉하다**(예: sales_profit 사실 6개/문장 4개), 다만 프롬프트 예시가 "토큰 하나당 문장 하나"만 보여줘 모델이 사실마다 새 문장을 만드는 경향을 보였다(9/12 초과). 상한을 올리는 대신 여러 사실을 한 문장에 묶는 예시를 프롬프트에 추가해 상한 안에서 쓰게 한다.
    4. **규칙 2·3(토큰 이탈·원문 숫자)은 진단(2906)에서 확인됐지만, 원인이 특정 프롬프트 문구나 검증 허점이 아니라 구조화 출력에서도 모델이 "절대 금지" 규칙을 놓칠 수 있다는 일반적 신뢰성 문제로 보인다.** JSON 스키마에 정규식 패턴(예: 중괄호 밖 숫자 금지)을 넣어 API 단에서 강제하는 방안도 검토했으나, 이 SDK·모델이 구조화 출력의 `pattern` 제약을 생성 단계에서 실제로 강제하는지 문서로 확인되지 않아(추측으로 적용하지 않는다는 이번 세션 원칙) 이번에는 적용하지 않는다. 검증기(규칙 2·3)가 이미 이 실패를 정확히 잡아 재시도·거절로 이어지므로, 당장 게시본에 새어나갈 위험은 없다.
- **검토한 대안**
  - §4.4.3 상한을 올려 분량 위반을 줄임 — 사용자가 명시적으로 "단순히 완화하지 말라"고 지시했고, 위 분석상 상한 자체보다 문장 결합 지시 부재가 원인이라 상한을 올리는 것은 근본 처방이 아니다.
  - 규칙 7·4를 완화(흐름 사실의 history 배치 허용, 반복 허용 횟수 증가) — 같은 이유로 기각. 대신 규칙 7을 **확장**(더 엄격하게)해 흐름 사실의 history 배치 자체를 코드로 막았다.
  - JSON 스키마에 숫자 패턴 제약 추가 — SDK의 실제 강제 동작을 검증하지 못해 이번에는 보류(후속 조사 대상).
  - 재시도 횟수(현재 1회)를 늘림 — 근본 원인(섹션 배치 판정 떠넘김, 반복 회피 지시 부재)을 고치지 않고 시도 횟수만 늘리면 비용만 늘고 통과율 개선을 보장하지 못한다. 이번엔 적용하지 않는다.
- **위험과 완화**: history 조건 변경으로 흐름 사실만 있고 이력 신호가 없는 기업은 `sections`에 `history`가 아예 빠진다(이전에는 포함됐다). `FinancialExplainInputBuilderTest`에 이 경로를 다루는 기존 테스트가 없어 회귀 위험은 낮지만, 실제 골든셋 재검증(§7.4.2)으로 확인한다.
- **재검토 조건**: 재검증에서 규칙 2·3(토큰 이탈) 실패가 반복되면 JSON 스키마 패턴 제약을 다시 검토한다(이번에 보류한 이유는 "확인 안 됨"이지 "효과 없음"이 아니다). 흐름 사실 종류가 늘어나면(현재 2종) 이 결정의 "항상 현재형" 전제를 다시 본다.
  - **후속 확인 (2026-09-26, implementation-plan.md §7.4.3)**: 재검증에서 규칙 2가 3건(716·908·2906) 반복돼 위 재검토 조건에 해당한다. 다시 검토했지만 SDK가 구조화 출력의 `pattern` 제약을 생성 단계에서 실제로 강제하는지는 여전히 확인하지 못해 스키마 변경은 적용하지 않았다(현재 수준에서 허용으로 판정 — 검증기가 이미 정확히 방어하고 있어 급하지 않다). `history` 조건 변경(위 "위험과 완화")은 `GoldenSetDumpRunner`로 820·1640의 입력을 다시 만들어 의도대로 동작함을 직접 확인했다(회귀 없음).
- **관계**: D-06(판정은 코드)·D-38(입력 계약)·D-39(출력 계약)·D-44(thinking 비활성화)를 바꾸지 않는다. ai-analysis.md §4.4.2·§4.4.3·§4.4.7을 이 결정에 맞게 구체화한다.

## D-46. changeStatus가 NONE일 때 개요의 수준 사실은 선택이고, 다른 섹션과 겹치면 생략한다

- **결정**
  - 프롬프트(v1.md)를 보강해 `changeStatus: NONE`일 때 `overview`의 "수준 사실 하나"를 **필수에서 선택**으로 바꾼다. 우선순위: (1) 그 지표의 변화량 사실(`revenue_yoy`, `operating_margin_diff`, `debt_ratio_diff` 등, 신호로 이어지지 않았어도 존재하면 쓸 수 있다) → (2) 손익·재무상태 섹션이 쓰지 않을 다른 원값(예: `net_income`) → (3) 겹치지 않는 사실이 없으면 사실 없이 "규칙상 큰 변화로 표시된 항목은 없어요" 문장만 쓴다.
  - 프롬프트 버전을 `fx-v1` → `fx-v2`로 올린다(`FinancialExplainPrompt.PROMPT_VERSION`). D-45의 개요 관련 문구 보강도 버전에 안 남아 있었으므로, 이번이 v1.md 최초의 버전 표시 갱신이다.
  - 출력 계약(4섹션, 토큰 문법, §4.4.3 분량 상한)과 `FinancialExplainValidator` 규칙 4는 바꾸지 않는다. `overview`가 사실 토큰 0개인 것은 기존 규칙 1(스키마)·규칙 10(상한, 최댓값만 검사)에 이미 부합한다 — 검증기 코드 변경이 필요 없다.
- **이유**
  - implementation-plan.md §7.4.3에서 규칙 4 잔여 5건이 **전부** `changeStatus: NONE`임을 확인했다. `sales_profit`은 항상 매출 원값(`revenue`)부터, `structure`는 항상 부채비율(또는 자본총계)부터 시작하도록 §4.4.3이 고정해 두었기 때문에, NONE의 "수준 사실 하나"가 무엇을 고르든 이 두 섹션의 시작 사실과 겹칠 수밖에 없는 구조였다. `CHANGED` 경로는 신호가 변화량 사실을 자연스럽게 공급해 이 충돌이 없었다(D-45로 확인: 이번 라운드 CHANGED 기업 중 규칙 4 재발 0건).
  - 겹치지 않는 사실이 항상 있는 것도 아니다(§7.4.3 확인: 810·1016은 `_yoy`/`_diff`류 변화량 사실 자체가 입력에 없다). "사실 반드시 하나"를 유지한 채로는 이런 기업에서 프롬프트만으로 반복을 피할 방법이 없었다 — 사실을 선택으로 바꾸는 것이 유일하게 항상 성립하는 해법이다.
- **검토한 대안**
  - 수준 사실을 필수로 유지하고 "겹치지 않는 사실을 찾아 써라"라고만 지시 — 810·1016처럼 겹치지 않는 사실이 아예 없는 기업은 여전히 실패할 수밖에 없어 근본 해법이 아니다.
  - `sales_profit`/`structure`의 시작 지표를 상황에 따라 바꿈(개요가 매출을 썼으면 손익은 영업이익부터 시작 등) — §4.4.3의 고정 순서를 깨서 기업마다 문장 구조가 달라지고, 규칙 10(분량)과 얽혀 새로운 조합이 늘어난다. "가장 작은 변경" 원칙에 어긋나 기각.
  - `FinancialExplainValidator` 규칙 4를 완화(중복 허용 횟수 증가) — 사용자가 명시적으로 금지했고, 토큰 반복 금지의 원래 취지(같은 정보를 두 번 설명하지 않음, D-39)를 해친다.
- **위험과 완화**: `overview`가 사실 없이 문장만 쓰는 경우가 늘어날 수 있다(정보 밀도가 다소 낮아짐). 다만 §4.4.3은 이미 "변화가 없다는 사실 자체가 정보다"를 원칙으로 두고 있어, 수준 사실이 없어도 `overview`의 핵심 목적("이번엔 큰 변화가 없다"는 상태 전달)은 그대로 유지된다.
- **재검토 조건**: 실제 재검증(implementation-plan.md §7.4.4)에서 NONE 경로의 규칙 4가 계속 발생하면, 이 우선순위 설명이 모델에게 충분히 명확하지 않은 것으로 보고 예시를 더 추가하거나 다른 접근(예: NONE 전용 스키마 필드 분리)을 검토한다.
  - **결과 확인 (2026-09-26, implementation-plan.md §7.4.4)**: 같은 12개사로 재검증한 결과 규칙 4는 **5건 → 0건**으로 완전히 해소됐다(REJECTED 8건 중 규칙 4는 한 건도 없음). 통과한 810·1016·2386의 실제 텍스트로 세 우선순위(변화량 사실 사용/겹치지 않는 원값 사용/생략)가 각각 실제로 나타남을 확인했다 — 재검토 조건은 발동하지 않았다. 다만 같은 라운드에서 이번 변경과 무관한 경로(`changeStatus: CHANGED`)의 872·820이 이전보다 나빠졌는데(872: 통과→REJECTED 규칙5, 820: 규칙6 단독→규칙3·6·5), 이 두 기업은 NONE 경로 코드를 타지 않으므로 이 결정의 영향일 수 없다 — 모델 생성의 비결정성으로 보고 있으며, 이 결정과 별개의 관찰로만 기록한다.
- **관계**: D-06(판정은 코드)·D-38(입력 계약)·D-39(출력 계약)·D-44(thinking 비활성화)·D-45(흐름 사실·개요 토큰 분리)를 바꾸지 않는다. ai-analysis.md §4.4.3, `prompts/financial_explain/v1.md`, `FinancialExplainPrompt.PROMPT_VERSION`을 이 결정에 맞게 반영한다.
