# 데이터·AI 분석 명세

| 항목 | 내용 |
|---|---|
| 상태 | 확정 (MVP 기준) |
| 최종 수정 | 2026-09-26 |
| 관련 문서 | [제품 정의](product.md), [시스템 설계](architecture.md), [설계 결정 기록](decisions.md) |

이 문서는 코드가 만드는 판단 근거(지표·신호·이벤트)와 AI 분석의 입력, 출력, 재생성 기준, 검증, 비용을 정의한다. AI가 제품에서 갖는 역할과 한계(판정은 코드, 설명은 AI)의 원칙은 [제품 정의 §8](product.md#8-ai가-제품에서-갖는-역할)을 따른다. 이 문서는 그 원칙을 분석 종류별로 구체화한 명세다.

---

## 1. 역할 분담

| 코드가 하는 일 | AI가 하는 일 |
|---|---|
| 재무 지표·변화율·동종업계 비교 계산 | 코드 산출물과 원문을 쉬운 말로 설명 |
| 등락 순위, 시장·업종 대비 차이 계산 | 원문(사업보고서) 서술 요약 |
| 신호의 방향·심각도 판정과 선별 | 신호가 왜 중요한지 설명 |
| 향후 이벤트 추출과 날짜 | — |
| 분석 대상 선정, 재생성 판단, 예산 관리 | — |
| 결과 검증, 섹션 조립, 숫자 채우기, 면책·출처·기준일 표시 | — |

AI는 방향(좋다/나쁘다), 중요도, 수치, 미래를 판정하지 않는다. AI가 원문을 요약할 때는 출처 섹션을 함께 반환한다.

---

## 2. 분석 계층

```
원천 데이터 (공시·원문·재무·시세·뉴스)
   │  코드
   ▼
코드 산출물: 재무 지표 · 동종업계 비교 · 등락 순위 · 기업 신호 · 향후 이벤트
   │
   ├─▶ 1차 분석 (AI): 기업 이해 · 재무 쉬운 설명 · 일일 변동
   │        │
   │        ▼
   └─▶ 2차 분석 (AI): 향후 전망 · 경쟁사 비교    ← 1차 결과와 코드 산출물만 입력
            │
            ▼
      화면 조립 (코드): 섹션 배치 · 숫자 채우기 · 면책·출처·기준일
```

2차 분석은 원문을 다시 읽지 않는다. 입력이 작아 저렴하고, 1차 분석과 같은 사실을 공유하므로 내용이 서로 어긋나지 않는다.

## 3. 기업 신호

기업 신호는 코드가 규칙으로 판정한 사실이다. 리스크 섹션과 향후 전망의 판단 근거는 모두 기업 신호에서 나온다. 저장 위치는 `company_signal` 테이블이다.

### 3.1 필드

| 필드 | 설명 |
|---|---|
| 유형 | 규칙 카탈로그의 신호 유형 코드 |
| 근거 키 | 신호를 만든 원천의 식별자 (재무 기간, 공시번호 등). **자연키 = 기업 + 유형 + 근거 키**이며, 지문과 AI 출력의 신호 참조는 모두 이 자연키를 쓴다. 대리키는 신호를 다시 계산할 때마다 바뀔 수 있으므로 참조에 쓰지 않는다 |
| 성격 | **상태**(현재 어떤 상태인가) 또는 **변화**(최근 무엇이 바뀌었거나 예정되었나) |
| 방향 | 긍정, 부정, 불확실. **실적과 재무 건전성에 대한 영향** 기준이며 주가 영향이 아니다. 상황에 따라 방향이 달라지는 유형은 불확실로 둔다 |
| 심각도 | 낮음, 중간, 높음. 규칙이 계산값(변화 폭, 매출 대비 금액 비중 등)으로 정한다 |
| 발생 기준일 | 변화가 일어난 시점. 재무 신호는 해당 재무 기간의 종료일, 공시 신호는 공시 접수일이다. "언제 변했는가"(product.md §4)에 답하고 타임라인 정렬 기준이 된다 |
| 지속 | 같은 방향의 변화가 연속으로 나타난 기간 수(예: 매출 감소 3분기 연속). 판정 방법은 §3.7. 재무 신호만 해당하며 코드가 계산한다. "일시적인가, 지속적인가"(product.md §4)의 판단 근거다 |
| 계산값 | 판정에 쓴 수치. 자리표시자 키와 값 |
| 확인 지표 | 이 신호가 있을 때 앞으로 지켜볼 지표 키 |
| 상태 | 신호 계산 때마다 다시 판정한다([D-36](decisions.md)). **활성**: 지금도 성립(변화 신호는 최신 재무 기간에서 나온 것, 상태 신호는 최신 기간에도 조건이 이어지는 것). **이력**: 그 기간에는 성립했고 지금은 최신이 아님. **철회**: 다시 계산했더니 같은 자연키로 성립하지 않음(정정·규칙 변경). **행은 지우지 않는다.** 이력은 타임라인에 쓰고, 철회는 화면·AI 입력에서 뺀다 |
| 규칙 버전 | 판정에 쓴 규칙 카탈로그 버전. 버전이 바뀌면 전체를 다시 판정한다 |

규칙 카탈로그(유형, 판정 조건, 성격, 방향, 심각도 기준, 확인 지표)는 코드로 관리한다. 유형별 쉬운 설명은 정적 콘텐츠로 관리한다.

### 3.2 화면 배치

| 섹션 | 사용하는 신호 |
|---|---|
| 최근 변화 (타임라인) | 성격이 변화인 신호(활성·이력, 최근 N개 기간)와 향후 이벤트가 아닌 지난 이벤트. 발생 기준일 순. 철회 신호와 데이터 한계 신호는 넣지 않는다 |
| 앞으로 지켜볼 점 (향후 전망) | 활성 변화 신호의 확인 지표, 방향이 불확실인 신호(모든 성격), 향후 이벤트 |
| 리스크 | 성격이 상태이고 방향이 부정인 활성 신호 |

데이터 한계 신호(방향 불확실)는 향후 전망의 "해석할 때 참고할 점"과 재무 섹션의 참고 표시로만 쓴다.

리스크와 향후 전망은 성격과 방향으로 나눠 같은 신호가 중복되지 않게 한다. 최근 변화 타임라인은 이력이므로 향후 전망의 긍정·부정 신호와 같은 신호를 보여 주되, 향후 전망에서 만든 신호별 설명을 그대로 재사용한다 (architecture.md §6.2).

### 3.3 변화와 근거의 연결 (코드)

"무엇과 관련되어 있는가"(product.md §4)는 코드가 연결한다. AI는 코드가 연결한 근거를 설명할 뿐 스스로 연결하지 않는다.

- 재무 신호에는 같은 재무 기간(기간 시작일 ~ 해당 정기보고서 접수일) 안에 접수된 해당 기업의 주요 공시를 연결한다.
- 공시 신호에는 그 공시 자체와, 이후 처음 나온 정기보고서의 재무 변화 신호를 연결한다.
- 연결은 저장하지 않고 조회·입력 구성 시점에 계산한다. 규칙이 바뀌어도 데이터를 다시 만들 필요가 없게 하기 위함이다.
- 연결은 "같은 시기에 함께 일어났다"는 사실이며 인과를 뜻하지 않는다. 인과 서술 규칙은 §7.2를 따른다.
- 정정 공시는 원 공시와 한 묶음으로 본다([D-31](decisions.md)). 연결·입력에는 묶음당 한 건만 넣고, 보고서명과 내용은 최신본, 시점은 원 공시 접수일을 쓴다. 같은 사건이 정정 횟수만큼 반복되어 보이지 않게 하기 위함이다.

### 3.4 MVP 신호 목록 (초안)

| 분류 | 유형 | 성격 | 방향 | 확인 지표 |
|---|---|---|---|---|
| 재무 | 매출 큰 폭 증가 / 감소 (전년 동기 대비) | 변화 | 긍정 / 부정 | 매출 증가율 |
| 재무 | 영업이익률 큰 폭 개선 / 악화 (전년 동기 대비) | 변화 | 긍정 / 부정 | 영업이익률 |
| 재무 | 흑자 전환 / 적자 전환 (영업이익, 전년 동기 대비) | 변화 | 긍정 / 부정 | 영업이익, 영업이익률 |
| 재무 | 부채비율 급등 (전기말 대비) | 변화 | 부정 | 부채비율 |
| 재무 | 영업적자 지속 (4분기 이상) | 상태 | 부정 | 영업이익 |
| 재무 | 자본잠식 (부분·완전) | 상태 | 부정 | 자본총계 |
| 재무 | 이익과 영업현금흐름의 엇갈림 (2년 연속, 후보: 현금흐름 적재 뒤 분포 확인 후 켬, [D-48](decisions.md)) | 상태 | 불확실 | 영업활동 현금흐름, 영업이익 |
| 공시 | 공급계약 체결 (심각도는 매출액 대비 비율로 판정) | 변화 | 긍정 | 매출 증가율 |
| 공시 | 대규모 시설투자 | 변화 | 불확실 | 매출 증가율, 영업이익률 |
| 공시 | 유상증자, 전환사채·신주인수권부사채 발행 | 변화 | 불확실 | 부채비율 |
| 공시 | 최대주주 변경, 합병·분할 | 변화 | 불확실 | — |
| 공시 | 감사의견 비적정, 관리종목 지정, 투자주의환기종목 지정 (거래소 공시 기준) | 상태 | 부정 | — |
| 공시 | 주요 소송 | 상태 | 부정 | — |
| 업계 비교 | 동종업계 대비 성장률 상회 / 하회 (동종업계 정의 구현 후) | 변화 | 긍정 / 부정 | 매출 증가율 |
| 데이터 한계 | 재무 이력 부족, 금융업 지표 해석 제한, 매출액 없음, 재무 기준 전환, 결산기 변경, 재무 데이터 불일치, 최신 재무 미확인, 사업보고서 오래됨, 정정공시 빈번 | 상태 | 불확실 | — |
| 데이터 한계 | 긍정·부정 신호 상충 | 상태 | 불확실 | — |

- 공시 신호의 근거 키는 원 공시의 공시번호이고 발생 기준일은 원 공시 접수일이다. 정정 공시로 별도 신호를 만들지 않고, 정정으로 내용이 바뀌면 최신본으로 다시 판정한다. "정정공시 빈번"은 코드가 기간 안의 정정 표시 공시 수로 판정한다.
- 공시 기반 신호 중 금액 비교가 필요한 유형은 OpenDART 구조화 API로 제공되는 것부터 구현한다. 나머지는 공시 유형(제목) 기준으로 판정한다.
- 공급계약 체결은 거래소 공시라서 구조화 API가 없다. 공시 문서의 "매출액 대비" 항목을 추출해 심각도를 정하고, 추출에 실패하면 심각도를 낮음으로 둔다.
- 시장경보(투자주의·경고·위험)는 공시가 아니라 시장 조치이므로 MVP 신호에 넣지 않는다.
- 재무 신호의 판정 조건·심각도·근거 키·지속은 §3.7을 따른다([D-35](decisions.md)). 초안의 "매출 성장 가속·둔화"와 "높은 부채비율"은 뺐다.
- **동종업계 정의**: 확정 경쟁사가 3개 이상이면 확정 경쟁사를 쓴다. 아니면 산업코드 중분류(앞 2자리)가 같은 기업 중 매출액 상위 10개를 쓴다. 비교 대상이 5개 미만이면 업계 비교 신호를 만들지 않는다. 업계 기준값은 중앙값을 쓴다.

### 3.5 재무 지표의 원천 (코드)

재무 신호와 재무 쉬운 설명의 숫자는 모두 코드가 `financial_line`(주요계정 원천 행)에서 계산한다. 저장 형태와 기간 규칙은 architecture.md §4.2·§4.3과 [D-32](decisions.md)·[D-33](decisions.md)을 따른다.

| 지표 키 | 원천 계정명 | 규칙 |
|---|---|---|
| 매출액 | 매출액 | 금융형은 없을 수 있다 |
| 영업이익 | 영업이익, 영업이익(손실) | 두 이름은 같은 계정이다(같은 기업도 연결·별도에서 이름이 다를 수 있다) |
| 당기순이익 | 당기순이익(손실) | 한 보고서에 두 번 나온다(실제 26/26건 같은 값). 순서(`ord`)가 작은 행을 쓰고, 값이 다르면 경고를 남긴다 |
| 자산총계·부채총계·자본총계·자본금 | 같은 이름 | 자본잠식은 자본총계와 자본금으로 판정한다 |
| 유동자산·유동부채 | 같은 이름 | 유동비율([D-47](decisions.md)). 일반형에만 있다 |
| (형식 판별) | 유동자산 | 있으면 일반형, 없으면 금융형 |
| 영업·투자·재무활동 현금흐름, 기말 현금 | 전체 재무제표 API 현금흐름표의 **표준 계정 ID**: `ifrs-full_CashFlowsFromUsedInOperatingActivities`, `ifrs-full_CashFlowsFromUsedInInvestingActivities`, `ifrs-full_CashFlowsFromUsedInFinancingActivities`, `dart_CashAndCashEquivalentsAtEndOfPeriodCf` | 계정명으로 찾지 않는다. 분기·반기 값은 회계연도 누적이다. 주요계정 보고서와 공시번호·통화가 같을 때만 쓴다([D-48](decisions.md)) |

- 계산 지표: 영업이익률(영업이익 ÷ 매출액), 부채비율(부채총계 ÷ 자본총계), 전년 동기 대비 증가율, 4분기 단독값. 모두 읽을 때 계산하고 저장하지 않는다.
- 전년 동기 대비는 같은 보고서의 당기·전기 값으로 계산한다(분기: 3개월 단독끼리, 누적끼리. 연간: 당기·전기·전전기). 4분기는 파생값(연간 − 3분기 누적)이며 전년 대비 비교를 하지 않는다(§3.6, D-35).
- 지표에 필요한 계정이 없으면 그 지표와 그 지표를 쓰는 신호를 만들지 않는다. 값을 추정하지 않는다.
- 금융형: "금융업 지표 해석 제한" 신호를 둔다. 매출액이 있어도 이자·수수료·금융상품 손익을 합친 영업수익이므로 "영업수익"으로 표시하고, 매출 기반 신호(매출 증감, 영업이익률)와 부채비율 신호를 만들지 않는다. 흑자·적자 전환은 연간으로만, 영업적자 지속과 자본잠식은 일반형과 같다 ([D-35](decisions.md)).
- 매핑에 없는 계정(이자수익, 예수부채, 보험계약부채 등)은 저장만 하고 MVP 지표에 쓰지 않는다. 금융업 전용 지표는 필요가 확인되면 추가한다.
- 주요계정 API에는 "영업수익"이라는 계정명이 없다(2026-09-25, 저장된 계정 행 298,265건 전수 확인: 매출 계열은 "매출액" 26,600행뿐). 금융형 중 증권·투자사는 "매출액"으로 오고 화면·AI에서는 "영업수익"이라는 이름으로 보여 주며(금융형 56개사 중 27개사), 은행·보험은 매출 계정이 없다(`ACCOUNT_MISSING`). 매핑에는 실제 응답에서 확인한 계정명만 추가한다.
- 시계열은 최신 기간의 기준(연결/별도)·통화로 고정하고, 그 기준이 없는 기간은 빈 기간으로 둔다([D-37](decisions.md)). 12개월이 아닌 회계연도는 비교하지 않는다. 둘 다 "데이터 한계" 신호의 근거로 쓴다.
- 금액을 기업끼리 비교(매출액 순위, 동종업계 매출 상위)할 때는 원화 기업만 쓴다. 비율 비교는 통화와 무관하다.

### 3.6 재무 지표 (코드, 읽을 때 계산)

지표는 저장하지 않고 화면·신호 계산·AI 입력을 만들 때 원천 행(`financial_line`, 현금흐름표 행)에서 계산한다. 이 표에 없는 지표(순이익률, ROA, EPS·BPS, 잉여현금흐름 등)는 만들지 않는다([D-47](decisions.md)). PER·PBR 등 시장 가격이 필요한 밸류에이션 지표는 핵심 범위에 두지 않는다([D-49](decisions.md)). ROE·유동비율·현금흐름은 [D-47](decisions.md)·[D-48](decisions.md)로 추가하는 지표이며 아직 구현하지 않았다.

- **기간과 비교** ([D-33](decisions.md)·[D-35](decisions.md))
  - 분기 시계열: 1분기(1분기 보고서 당기), 2분기(반기 보고서 당기 = 3개월), 3분기(3분기 보고서 당기), 4분기(연간 − 3분기 누적, 파생값). 비12월 결산도 회계연도 시작일 기준으로 1~4분기를 센다(기간 키·계산의 기준). 표시 라벨은 모든 자리가 한 규칙을 쓴다: 비12월 결산의 분기는 회계연도 분기 번호 없이 달로("2026년 4~6월"), 12개월이 아닌 회계연도는 실제 기간으로 쓴다([D-59](decisions.md)·[D-62](decisions.md), §4.4.2의 "기간 라벨").
  - 전년 동기 비교는 같은 보고서의 당기·전기 값으로만 한다. 4분기 파생값은 추이 표시와 영업적자 지속 계산에만 쓰고, 전년 대비 비교를 하지 않는다(연간 비교가 대신한다).
  - 4분기 파생값은 사업보고서와 3분기 보고서의 기준·통화·회계연도 시작일이 같고, 파생 매출이 0 이상일 때만 쓴다(아니면 `DERIVED_INVALID`, 실제 12개사).
  - 전분기 대비는 계절성이 커서 변화율로 계산하지 않는다. 추이는 분기 값을 순서대로 보여 준다.
- **시계열 기준**: 최신 기간의 기준(연결 우선)·통화로 고정한다. 그 기준이 없는 기간은 빈 기간(`BASIS_GAP`)이다 ([D-37](decisions.md)).
- **범위**: 최근 12분기와 3개 사업연도(사업보고서의 당기·전기·전전기로 3년 연간 값을 얻는다).
- **데이터 점검**: 보고서마다 자산총계 = 부채총계 + 자본총계(차이 0.5% 이내)를 확인한다. 어긋나면(실제 5벌) 그 기간의 재무상태표 지표와 신호를 만들지 않고 `INCONSISTENT_BALANCE`로 둔다.
- **비원화**: 지표는 그 통화로 계산하고 환산하지 않는다. 원화 기준값이 필요한 매출 기반 신호와 매출 증가율은 만들지 않는다(`NON_KRW`). 영업이익률·부채비율처럼 기준값이 필요 없는 비율은 계산한다. 금액 표시는 [D-41](decisions.md).

### 3.7 재무 신호 판정 (코드)

[D-35](decisions.md)의 결정을 구현하는 규칙이다. 문턱값·심각도 구간은 규칙 카탈로그(코드)의 초기값이며 규칙 버전과 함께 관리한다. 초기값의 근거는 2026-09-25 로컬 데이터 분포다(implementation-plan.md §6).

**공통**

- 판정 단위는 재무 기간 하나(보고서 하나)다. 1분기·반기·3분기 보고서는 분기 3개월 값, 사업보고서는 연간 값으로 판정한다. 한 기간에 한 유형은 최대 한 건이다.
- 대상은 시계열 기준의 최근 12분기와 3개 사업연도다. 계산할 때마다 기업의 대상 기간 전체를 다시 판정하고 자연키로 반영한다(없어진 것은 철회, [D-36](decisions.md)).
- 기준값: 매출 비교는 전년 동기 매출이 분기 10억 원, 연간 40억 원 이상일 때만 한다.
- 근거 키: 변화 신호는 `회계연도 시작일:기간 구분`(예: `2026-01-01:H1`), 상태 신호는 조건이 이어진 구간의 첫 기간 키, 부채비율 급등은 `회계연도 시작일:FYDEBT`(같은 회계연도 안에서는 한 건).
- 발생 기준일: 변화 신호는 기간 종료일, 상태 신호·부채비율 급등은 조건이 처음 성립한 기간의 종료일.
- 근거 공시: 그 기간 보고서의 `receipt_no`(최신 정정본)를 계산값에 남긴다. 화면·AI에는 그 공시가 속한 정정 묶음(원 공시 + 정정, D-31)과 §3.3으로 연결한 같은 시기 공시를 준다.
- 지속: 매출 증감·영업이익률 변화 신호는 이번 기간을 포함해 직전 기간들에서 같은 방향(부호 기준, 문턱값 아님)의 전년 동기 변화가 이어진 수. 분기 신호는 분기끼리, 연간 신호는 연간끼리 센다. 비교하지 않는 기간(4분기 파생값 등)이나 빈 기간에서 끊긴다. 흑자·적자 전환과 부채비율 급등은 지속을 두지 않는다(영업이익의 연속은 영업적자 지속이 말하고, 부채비율은 분기마다 같은 기준점과 비교해 셈이 무의미하다, [D-61](decisions.md)). 상태 신호는 조건이 이어진 분기 수. 재무 쉬운 설명의 흐름 사실(§4.4.2)도 같은 셈이다.
- 계산값: 현재값, 전년 동기(또는 전기말) 값, 변화량, 기준(연결/별도), 통화, 기간 라벨, 출처 공시번호를 자리표시자 키와 값으로 남긴다.

| `FIN_DATA_IRREGULAR_PERIOD` | 최근 3개 사업연도에 12개월이 아닌 회계연도(결산기 변경) |
| `FIN_DATA_INCONSISTENT` | 최신 기간의 자산총계 ≠ 부채총계 + 자본총계 |
| `FIN_DATA_STALE` | 최신 기간 P 다음 보고서의 기한일(다음 기간 종료 월의 말일 + 분기·반기 60일, 사업 120일, 상장사에 적용되는 가장 긴 기한)에 7일을 더한 날이 지났는데 P보다 뒤 기간의 보고서가 수집되지 않음. 달력일로 세고 휴일은 따지지 않는다. 근거 키는 P. 다음 보고서가 수집되면 이력, 규칙 변경 등으로 같은 P에서 성립하지 않으면 철회. 시간이 지나 판정이 바뀌는 날에만 다시 판정한다([D-43](decisions.md)). "미제출"이 아니라 "수집 기준 미확인"으로 표현한다 |

- 이름·설명은 사실만 말한다. "위험", "좋다·나쁘다", 투자 관련 표현을 쓰지 않는다. 방향은 실적·재무 건전성에 대한 영향 기준이다(§3.1).

### 3.8 재무 결과 구조 (코드 → 화면·AI)

코드는 기업마다 아래 구조의 **재무 요약**을 만든다. 화면과 AI 입력은 같은 구조를 쓴다. 숫자는 모두 자리표시자 키로 참조한다(D-17).

| 부분 | 내용 |
|---|---|
| 기본 | 시계열 기준(연결/별도), 통화, 재무제표 형식(일반/금융), 최신 기간(키·라벨·종료일·출처 공시번호) |
| 플래그 | 사유 코드 목록(`NON_KRW`, `BASIS_GAP`, `DERIVED_INVALID`, `SMALL_BASE`, `INCONSISTENT_BALANCE`, `NOT_APPLICABLE_FORMAT` 등)과 해당 기간. 사유별 쉬운 설명은 정적 콘텐츠 |
| 분기 | 최근 12분기(화면·신호 판정). AI 입력에는 분기 시계열을 넣지 않는다(§4.4.2, [D-38](decisions.md)). 기간마다 키, 라벨, 종료일, 출처(공시번호 또는 파생), 지표별 {값, 전년 동기 값, 변화량, 단위, 상태 또는 사유 코드} |
| 연간 | 최근 3개 사업연도. 분기와 같은 형식 |
| 재무상태 | 기간 말 자산·부채·자본·자본금, 부채비율과 전기말 대비 변화, 잠식률 |
| 신호 | 대상 기간의 활성·이력 재무 신호(자연키, 유형, 방향, 심각도, 발생 기준일, 지속, 계산값, 확인 지표, 근거 공시) |

- 자리표시자 키: `fin.{지표}.{기간 키}`, 변화량은 `fin.{지표}_yoy.{기간 키}`(증가율 %) 또는 `fin.{지표}_diff.{기간 키}`(%p). 기간 키는 `회계연도 시작 연월.분기`(예: `2026-01.Q2`, 연간은 `2025-01.FY`).
- 표시 형식은 코드가 정한다: 금액은 한국어 수 단위(조·억·만)와 통화명(원·위안·달러·엔·파운드, 그 밖은 통화 코드), 비율은 소수 한 자리 %, 차이는 %p. 표시 문자열은 렌더링할 때 원값으로 만든다([D-41](decisions.md)). 기준값 미만 증가율처럼 계산하지 않은 값은 숫자 대신 사유 코드가 들어가고, AI는 그 값을 언급하지 않는다.
- 이 구조는 화면과 신호 계산의 기준이다. AI 입력은 이 구조에서 코드가 골라 만든 사실표다(§4.4.2). 신호가 없는 기간을 AI가 변화로 서술하거나, 계산하지 않은 비교를 만들지 않는다.
- [D-47](decisions.md)·[D-48](decisions.md)을 구현하면 분기·연간 기간에 유동자산·유동부채, 연간에 ROE 입력(전전기말 자본총계), 기간별 현금흐름(누적 기간 키)이 더해진다. 현금흐름은 손익과 기간의 뜻이 다르므로(누적) 분기 기간과 섞지 않고 따로 둔다.

### 3.9 지표 보기 (코드 → 화면, [D-47](decisions.md))

재무 섹션은 지표를 나열하지 않고 **지표 보기** 단위로 보여 준다. 지표 보기는 코드가 모두 만들고, AI는 관여하지 않는다(재무 쉬운 설명은 이 중 일부 사실만 쓴다, §4.4). 이 절은 정보 구조이며 화면 배치는 화면 설계에서 정한다. 판정 표시는 [D-60](decisions.md), 지표별 비교는 [D-61](decisions.md), 표시 일치(기간 라벨·비교 기준·부호)는 [D-62](decisions.md)를 따른다.

**묶음과 지표**

| 묶음 | 지표 | 사용자가 얻는 답 |
|---|---|---|
| 성장 | 매출액·매출 증가율(금융형은 영업수익, 증가율 없음), 영업이익, 당기순이익 | 얼마나 팔고 벌었나, 전년 같은 기간보다 늘었나 |
| 수익성 | 영업이익률(일반형), ROE(연간) | 판 것·가진 자본에 비해 얼마나 남겼나 |
| 안정성 | 부채비율(일반형), 유동비율(일반형), 자본총계·자본금(잠식) | 빚이 자본에 비해 얼마나 되나, 1년 안에 갚을 빚을 감당할 자산이 있나 |
| 현금흐름 | 영업·투자·재무활동 현금흐름, 기말 현금(일반형) | 이익이 현금으로 들어왔나, 번 돈을 어디에 쓰나 |

**지표 보기의 구성**

| 부분 | 내용 | 만드는 곳 |
|---|---|---|
| 정의 | 쉬운 말 한두 문장(예: "ROE는 회사가 가진 자기 돈(자본)으로 1년에 얼마를 벌었는지예요") | 정적 콘텐츠 |
| 현재 값 | 값, 기간 라벨(누적이면 "1~6월"), 기준(연결/별도), 통화, 출처 공시 | 코드 |
| 비교 | 지표마다 정한 기준(전년 같은 기간 또는 직전 사업연도 말)의 값, 변화량(%·%p·금액), 산술 방향(늘었다·줄었다·같다), 같은 방향이 이어진 기간 수. 무엇을 쓸 수 있는지는 지표별로 다르다: 부호가 바뀔 수 있는 금액은 두 값이 모두 양수일 때만 방향을 말하고, 이어진 기간 수는 뜻이 있는 지표에만 쓴다([D-61](decisions.md)). 기준의 종류·시점이 보이고, 부호와 증감 어휘를 겹쳐 쓰지 않는다([D-62](decisions.md)) | 코드 |
| 큰 변화 여부 | 이 지표를 **근거 지표**로 하는 활성 신호가 있으면 신호 배지(확인 지표는 "앞으로 지켜볼 점"에서만 쓴다). 없으면 네 상태를 구분한다: 신호 있음 / 판정했고 성립하지 않음("규칙상 큰 변화로 표시되지 않음"은 이 상태에만) / 판정 대상 아님(사유) / 판정 규칙 없음([D-60](decisions.md)) | 코드(신호) |
| 해석 참고 | 지표별 정적 문구(예: "업종에 따라 보통 수준이 크게 달라요", "현금흐름은 계절에 따라 누적 중간에 마이너스가 되기도 해요") | 정적 콘텐츠 |
| 계산하지 않음 | 숫자 대신 사유 코드의 정적 문구. 사유는 값·비교·판정 자리에 따로 둔다(값은 있고 비교만 없으면 값은 보인다, [D-60](decisions.md)) | 코드 + 정적 콘텐츠 |

- 산술 방향은 좋고 나쁨이 아니다. 좋고 나쁨의 방향(§3.1)은 신호에만 있다. 신호가 없는 변화에 색·아이콘으로 평가를 덧씌우지 않는다.
- 부호로 정해지는 사실(흑자·적자, 현금 유입·유출, 자본잠식)은 코드가 사실로 표시한다. 수준 판정(높다·낮다·양호·위험), 묶음별·종합 점수, 등급은 만들지 않는다.
- 업종 맥락은 동종업계 정의(§3.4)를 구현한 뒤 동종업계 중앙값을 "참고 값"으로 나란히 두는 방식으로만 준다. 순위·평가어는 붙이지 않는다.
- **요약 재무제표**는 지표의 근거로 둔다. 손익(매출액·영업이익·당기순이익), 재무상태(유동자산·자산총계·유동부채·부채총계·자본금·자본총계), 현금흐름(세 합계·기말 현금)의 최신 기간과 비교 기간 값이다. 전체 재무제표는 출처 공시 링크로 대신한다.
- 계산할 수 없거나 데이터가 부족하면 값을 추정하거나 빈칸으로 두지 않는다. "계산하지 않음"과 사유를 보여 준다. 기업 전체에 걸친 한계는 데이터 한계 신호(§3.7)의 문구로 보여 준다.

## 4. 분석 종류

### 4.1 공통 규칙

- 출력은 JSON 스키마로 강제한다(구조화 출력).
- 결과마다 지문, 스키마 버전, 프롬프트 버전, 모델, 토큰, 비용을 기록한다.
- 코드가 계산한 수치는 AI가 자리표시자(`{지표키}`)로만 쓰고, 코드가 값을 채운다. 지표 키별 표시 형식(%, 억원, 배 등)은 코드의 지표 목록에서 정한다.
- 입력에 준 자리표시자 값은 결과와 함께 **값 스냅샷**으로 저장하고, 화면은 스냅샷으로 숫자를 채운다. 동종업계 중앙값처럼 나중에 바뀌는 값이 있어도 설명과 숫자가 어긋나지 않게 하기 위함이다.
- 원문을 인용한 수치(예: 사업보고서의 매출 비중)는 입력 원문에 있는 값이어야 한다.
- 분석 대상은 기업 또는 경쟁사 쌍이다. 경쟁사 쌍의 대상 키는 두 기업 ID를 정렬해 만든다.
- **스키마 호환**: 화면은 현재 스키마 버전과 직전 버전을 함께 지원한다. 스키마를 바꾸면 구버전 결과를 점진적으로 재생성하고, 모두 바뀐 뒤 직전 버전 지원을 제거한다.

### 4.2 요약

| 일일 변동 (시세 모듈) | `daily_move` | 1차 | 코드가 고른 등락 기업 (AI 적용 대상과 무관) | 거래일 + 근거 ID 집합 | — |

최소 재생성 간격은 분석 종류별 설정값이다.

### 4.3 기업 이해 (`company_profile`)

| 항목 | 내용 |
|---|---|
| 입력 | 사업보고서 "사업의 내용" 섹션(토큰 상한 적용), 기업 개황, 연간 핵심 지표, 동종업계 후보 목록(코드가 산업코드 중분류·매출액 기준으로 약 20개 선정) |
| 토큰 상한 | 하위 섹션 우선순위대로 넣고 상한에 닿으면 뒤 섹션부터 줄인다. 우선순위: 사업의 개요 → 주요 제품 및 서비스 → 매출 및 수주상황 → 원재료 및 생산설비 → 기타 참고사항 → 나머지. 표는 텍스트로 압축한다 |
| 출력 | 한 줄 요약, 기업 소개, 사업구조, 주요 제품·고객, 사업상 위험 서술, **실적 영향 요인**, 경쟁사 선택 |
| 실적 영향 요인 | 최대 5개. 요인 ID, 이름, 설명, 출처 섹션. **방향(좋다/나쁘다)을 붙이지 않는다.** 향후 전망의 "주요 요인" 원천이다 |
| 경쟁사 선택 | 후보 목록 안에서만 최대 5개와 근거. 목록 밖 기업은 선택할 수 없다 |
| 경쟁사 확정 | 두 기업이 서로를 선택하면 코드가 자동으로 확정한다. 한쪽만 선택했으면 관리자 검토 대기로 둔다. 관리자는 언제든 확정·해제할 수 있다 |
| 지문 | 최신 사업보고서 공시번호 |
| 비고 | 사업보고서가 없는 기업(신규 상장 등)은 생성하지 않고 데이터만 보여 준다 |

### 4.4 재무 쉬운 설명 (`financial_explain`)

| 항목 | 내용 |
|---|---|
| 목적 | 기업의 최근 재무 상태와 중요한 변화를 "무엇이 언제 얼마나 변했나"와 항목 사이의 관계로 쉽게 설명한다 |
| 입력 | 코드가 만든 설명용 사실 묶음(§4.4.2, [D-38](decisions.md)). 원천 행·분기 시계열·원문은 넣지 않는다 |
| 출력 | 섹션 4개의 짧은 글. 숫자·기간·신호는 토큰으로만 쓴다(§4.4.4, [D-39](decisions.md)) |
| 지문 | 입력에 쓴 원천 식별자 집합(§4.4.6, [D-40](decisions.md)) |
| 대상·시점 | AI 적용 대상 + 골든셋. 재무 신호 계산(07:00) 뒤 분석 동기화 실행에서 |

#### 4.4.1 역할과 경계

| 코드 | AI |
|---|---|
| 지표·변화량 계산, 계산할 수 없는 지표와 사유 판단 | — |
| 신호 판정, 입력에 넣을 신호 선별, 기간·주제로 묶기, 순서 정하기 | 묶음 순서대로 문장으로 풀어 쓰기 |
| 쓸 섹션 결정, 변화 유무(`change_status`) 결정 | 정해진 섹션만 채우기 |
| 기간 라벨, 숫자 표시 형식, 기준(연결/별도)·통화·기준일·출처 공시 표시, 데이터 한계 문구 | — |
| 검증, 게시 판단 | — |

AI는 새 계산(합계·차이·평균·배수·순위), 새 비교(전분기 대비, 기업 간 비교), 새 판정(중요도, 좋다·나쁘다), 원인 추정, 미래 서술을 하지 않는다. 재무 쉬운 설명에는 원문 입력이 없으므로 원인을 서술할 근거가 없다(§7.2 "왜" 규칙의 (1)이 해당하지 않는다).

#### 4.4.2 입력 (코드가 구성)

> 현재 계약: [D-54](decisions.md)(섹션 배정)·D-54 보완(모든 섹션 사실 배정, `history` 시간순)·[D-55](decisions.md)(관계 서술)·[D-59](decisions.md)(표시 문자열 제거, 사실 이름 방향, 12개월이 아닌 회계연도 제외). 2026-09-27 구현(입력 구성 `fx-input-6`, 프롬프트 `fx-v13`, 검증기 `fxv-8`, implementation-plan.md §7.4.34). 골든셋 실제 재검증 자동 검증 11/12, 첫 시도 규칙 3(라벨·표시 값 복사) 0/12(§4.4.8 사람 검토는 2026-09-27 이 결과로 마쳤다 — implementation-plan.md §7.4.35. 820 거절 1건이 남아 골든셋 전체 자동 검증 통과는 아니고, 게시는 꺼져 있다). 이전에 저장된 입력에는 없는 필드가 있다: `fx-input-2` 이하는 `section`·`sectionFacts`, `fx-input-3` 이하는 `relations`, `fx-input-3`은 `sectionFacts`가 `overview`·`structure`뿐이다. `fx-input-5` 이하는 `facts[].display`·`periods[].label`이 있고 `periods[].kind`가 없다.

```

latest         { period: "2026-01.Q2", kind: QUARTER|ANNUAL }
changeStatus   CHANGED | NONE
sections       ["overview", "sales_profit", "structure", "history"]   // 코드가 정한 포함 여부·순서
periods        [{ key: "2026-01.Q2", kind: QUARTER|ANNUAL }, ...]      // {per.*} 대상. 라벨·표시 값은 없다(D-59) —
                  // 렌더링할 때 코드가 만든다. 12개월이 아닌 회계연도(결산기 변경)는 실제 기간으로, 비12월 결산
                  // 분기는 회계연도 분기 번호 없이 달로만 렌더링된다(예: "2026년 4~6월")
facts          [{ key: "fin.revenue_yoy.2026-01.Q2", name: "매출 증가율(전년 같은 분기 대비)",
                  sign: "+", period: "2026-01.Q2" }, ...]
                  // 사실표 = sectionFacts의 합집합. 흑자·적자 상태·전환 사실도 사실이다(표시는 렌더링할 때 만든다,
                  // D-55·D-59 — AI는 값을 몰라도 정해진 문형이 방향과 무관하게 성립한다). 이름의 방향(증가율/감소율,
                  // 상승폭/하락폭)은 실제 부호를 따른다(D-59)
signals        [{ ref: "S1", type, status: ACTIVE|PAST, nature, direction, severity, period,
                  section: sales_profit|structure|history, persistence, factKeys: [...] }, ...]
                  // period = 설명 기준 기간(활성: 최신 기간, 이력: 성립 기간), section = 코드가 정한 섹션 (D-54)
groups         [{ section, period, topic: SALES_PROFIT|STRUCTURE, refs: ["S1","S2"], mixedDirection }, ...]
sectionFacts   { overview: [...], sales_profit: [...], structure: [...], history: [] }
                  // 섹션마다 쓸 수 있는 사실 키. 코드가 상한 이하로 배정, 한 사실은 한 섹션에만 (D-54, D-54 보완)
relations      [{ type: OPERATING_INCOME_DIRECTION, factKeys: [최신 영업이익, 전년 영업이익], value: UP|DOWN|SAME },
                { type: STATE_DIFFERENCE, factKeys: [순이익 상태·전환 사실, 최신 영업이익], value: DIFFERENT }]
                  // 코드가 판정한 관계(D-55 R2·R5). 토큰이 아니고 값 스냅샷에도 없다. 두 사실이 모두 배정됐을 때만
unavailable    [{ metric: "revenue_yoy", reason: "SMALL_BASE" }, ...]      // 설명하면 안 되는 지표
doNotMention   ["부채비율", ...]                                         // 형식·통화별 금지 용어
```

**사실표(`facts`)의 후보** — 계산식·사유 코드는 §3.6, 신호 계산기와 같은 코드를 쓴다. 코드는 아래 후보를 계산한 뒤 **섹션에 배정된 것만** 사실표에 넣는다(아래 "섹션 배정", D-54 보완). 값 스냅샷도 같은 사실만 담는다.

| 묶음 | 사실 키(지표) | 기간 |
|---|---|---|
| 최신 손익 | `revenue`, `revenue_yoy`, `operating_income`, `operating_income_prior`, `operating_margin`, `operating_margin_diff`, `net_income` (`revenue_prior`·`operating_margin_prior`·`net_income_prior`는 계산하지만 배정하지 않는다: 변화량이 있으면 같은 정보이고, 없으면 코드가 일부러 방향을 주지 않은 경우라 원값 짝이 그 방향을 되살린다, D-35·D-41) | 최신 보고서가 분기(1분기·반기·3분기)면 그 분기 3개월, 사업보고서면 연간. 파생 4분기는 최신 손익으로 쓰지 않는다 |
| 흑자·적자 ([D-55](decisions.md)) | `net_income_status`(표시 "흑자"/"적자", 순이익에만), `operating_income_turn`·`net_income_turn`(표시 "적자에서 흑자로"/"흑자에서 적자로") | 최신 기간. 상태는 값이 0이 아닐 때, 전환은 같은 보고서의 최신·전년 같은 기간 부호가 다를 때(둘 다 0이 아님)만. 전환은 신호와 무관한 부호 사실이다(D-54 보완 "전환의 정의") |
| 연간 | `revenue`, `revenue_yoy`, `operating_income`, `operating_margin`, `net_income` | 최근 3개 사업연도, 각 사업보고서의 당기·전기 |
| 최신 재무상태 ([D-54](decisions.md)) | 일반형: `debt_ratio`, `debt_ratio_diff`(전기말 값이 있을 때) + 활성 자본잠식 신호가 있을 때만 `total_equity`·`capital_stock`. 부채비율을 계산할 수 없는 일반형과 금융형: `total_equity` + (활성 자본잠식이면) `capital_stock`. 최대 4개 = `structure` 상한. `debt_ratio_prior_end`·`total_assets`·`total_liabilities`·`impairment_ratio`는 AI 입력과 값 스냅샷에 넣지 않는다(화면은 재무 요약에서 코드가 보여 준다) | 최신 보고서 기간 말, 변화량은 같은 보고서의 전기말 대비 |
| 흐름 | `revenue_yoy_run`(최신 기간까지 전년 동기 대비 같은 방향이 이어진 분기 수, 부호 포함), `operating_loss_run`(연속 영업적자 분기 수) | 2 이상일 때만. 코드가 센다. `revenue_yoy_run`은 최신 기간의 `revenue_yoy`를 줄 수 있을 때만 준다([D-41](decisions.md)) |
| 신호 근거 | 활성 신호의 `factKeys`가 가리키는 사실(배정된 것만). 이력 신호의 `factKeys`는 비어 있다(`history`는 기간 토큰과 배지로만 쓴다, D-54 보완) | 최신 기간([D-54](decisions.md)) |

- 계산할 수 없는 지표는 사실표에 넣지 않고 `unavailable`에 사유와 함께 넣는다. 금융형은 매출 증가율·영업이익률·부채비율, 비원화는 매출 증가율(기준값이 필요 없는 비율은 계산, [D-41](decisions.md)), 재무상태표 불일치 기간은 재무상태 지표 전체를 뺀다.
- `doNotMention`: 금융형이면 "부채비율", "영업이익률", "매출"(영업수익은 사실 이름 "영업수익"으로만), 매출액이 없는 일반형이면 "매출"을 넣는다. 사실표에 없는 지표 이름이 글에 나오지 않게 하기 위함이다.
- 예상 크기: 사실 25~40개, 신호 8개 이하, 약 2~3천 토큰(시스템 프롬프트 제외).

**신호 선별과 묶음**

- 활성 변화·상태 신호는 모두 넣고, 이력 신호는 입력 범위(최근 8분기·3개 사업연도) 안에서 심각도·최근성 순 최대 4개를 넣는다. 철회 신호와 데이터 한계 신호는 넣지 않는다(데이터 한계는 `unavailable`과 코드 렌더링으로).
- 신호 유형 → 사실 키: 매출 증감 → `revenue`·`revenue_yoy`, 영업이익률 변화 → `operating_margin`·`operating_margin_diff`, 흑자·적자 전환 → `operating_income`·`operating_income_turn`(전환 사실 하나, D-55), 부채비율 급등 → `debt_ratio`·`debt_ratio_diff`, 영업적자 지속 → `operating_loss_run`, 자본잠식 → `total_equity`·`capital_stock`. 활성 신호는 **최신 기간**의 사실을 가리킨다. 상태 신호와 같은 회계연도 동안 활성인 부채비율 급등은 발생 기간이 과거여도 최신 사실로 이어진다([D-54](decisions.md)). 신호의 `calc_values`는 입력에 쓰지 않는다(감사용).
- 신호 `period`와 `section` ([D-54](decisions.md))
  - 활성 신호: `period`는 최신 기간이다. `section`은 주제 섹션이다(손익 → `sales_profit`, 재무 구조 → `structure`).
  - 이력 신호: `period`는 성립 기간, `section`은 `history`다.
  - 조건이 처음 성립한 기간(발생 기준일)은 AI 입력에 넣지 않는다. 배지가 연결되는 타임라인(코드)이 보여 준다.
- 묶음: 같은 섹션·같은 설명 기준 기간·같은 주제(손익: 매출·영업이익률·전환·적자 지속 / 재무 구조: 부채비율·자본잠식)의 신호를 한 묶음으로 둔다. 묶음은 한 섹션 안에서만 만든다. 그래서 활성 신호와 이력 신호가 한 묶음이 되는 일은 없다([D-54](decisions.md)). 묶음은 "같은 시기에 함께 나타난 변화"이며 원인이 같다는 뜻이 아니다.
  - 묶음 안 순서: 흑자·적자 전환 → 매출 → 영업이익률 → 적자 지속.
  - 묶음 간 순서: 활성 변화 → 활성 상태 → 이력. 활성 무리 안에서는 최고 심각도, 최근 기간 순. **이력 묶음은 서술 순서라 설명 기준 기간의 종료일 내림차순(최근 → 과거)**이고 같은 기간끼리만 심각도 순이다(D-54 보완). 이력 신호를 고르는 기준(심각도·최근성 최대 4개)은 그대로다.
  - 방향이 서로 다르면 `mixedDirection = true`.
- **섹션 배정 (`sectionFacts`, [D-54](decisions.md)·D-54 보완)**: 네 섹션 모두 코드가 배정하고, 사실표는 배정의 합집합이다. 한 사실은 한 섹션에만 있다. 금지 용어(`doNotMention`)나 `unavailable`과 이름이 모순되는 사실은 어느 섹션에도 배정하지 않는다.
  - **개요**(상한 3): 코드가 지정한 변화 근거 사실만. `CHANGED`면 첫 묶음 신호의 변화량 사실(`_yoy`·`_diff`), 흑자·적자 전환 신호면 그 전환 사실(2026-09-27 구현 중 보정, D-55 구현 기록). `NONE`이면 매출 증가율 → 영업이익률 변화 → 부채비율 변화 순서로 처음 있는 하나. 없으면 비운다.
  - **`structure`**(상한 4): 위 "최신 재무상태" 구성에서 개요에 지정한 사실을 뺀 나머지.
  - **`sales_profit`**(상한 6): 우선순위대로 채우고 넘치면 뒤를 뺀다. 순이익과 그 상태·전환 사실은 관계 단위라 쪼개지 않는다.
    1. 최신 매출·영업이익(규모)
    2. 이 섹션 활성 신호의 최신 근거 사실(전환 신호면 영업이익 전환 사실)
    3. 순이익 + 상태 또는 전환 사실: 순이익이 전년과 비교해 바뀌었으면 전환, 아니면 영업이익과 상태가 다를 때만 상태
    4. 영업이익률
    5. 흐름 사실: 연속 영업적자 → 매출 연속 흐름
    6. 전년 같은 기간과의 영업이익 비교: 부호가 같으면 전년 영업이익(둘 다 흑자면 방향 관계 R2 함께, 둘 다 적자면 값만), 부호가 바뀌었는데 전환 신호가 없으면 영업이익 전환 사실
    7. 최근 사업연도 사실 하나(최신 기간이 분기일 때만): 매출 증가율, 없으면 영업이익
  - **`history`**: 사실을 배정하지 않는다(빈 목록).
- **관계 항목 (`relations`, [D-55](decisions.md))**: R2(`OPERATING_INCOME_DIRECTION`)는 최신·전년 영업이익이 모두 흑자이고 전년 영업이익이 배정됐을 때 산술 방향을 준다(수치 없음). R5(`STATE_DIFFERENCE`)는 순이익의 상태·전환 사실이 배정됐고 순이익과 영업이익의 흑자·적자가 다를 때 준다.
- `changeStatus`: 활성 **변화** 신호가 하나라도 있으면 `CHANGED`, 없으면 `NONE`(활성 상태 신호만 있어도 `NONE`).
- 섹션: 배정된 사실이나 신호가 있으면 연다.
  - `overview`는 항상 연다.
  - `sales_profit`은 배정된 손익 사실이나 손익 주제의 활성 신호가 있으면 연다.
  - `structure`는 `sectionFacts.structure`나 재무 구조 주제의 활성 신호가 있으면 연다. 최신 재무상태표 불일치로 사실이 없고 활성 신호만 있으면 배지만으로 쓴다(D-52).
  - `history`는 이력(PAST) 신호가 있으면 연다.
  - 흐름 사실(`revenue_yoy_run`, `operating_loss_run`)은 최신 기간까지 이어지는 상태라 그 자체로는 `history`를 열지 않는다([D-45](decisions.md)).

**기간 라벨(코드, [D-59](decisions.md))**: 12월 결산은 "2026년 2분기", "2025년(연간)"(12개월짜리). 그 밖의 결산월은 분기를 달로만("2026년 4~6월" — 회계연도 분기 번호는 흔히 쓰는 달력 분기와 부딪혀 쓰지 않는다), 12개월짜리 연간은 "2025.04~2026.03 회계연도". 12개월이 아닌 회계연도(결산기 변경)는 실제 시작~끝 달로("2025.11~12 회계연도") — "(연간)"이라고 하면 1년 치처럼 읽힌다. 전년 동기는 사실 이름에 "전년 같은 분기"(최신이 분기)·"전년 같은 기간"(최신이 사업보고서)으로 적는다. AI는 기간을 `{per.…}` 토큰으로만 쓰고, 라벨·표시 값은 입력에 없다(D-59) — 렌더링할 때 코드가 만든다.

**넣지 않는 것 (D-38)**: `financial_line` 원천 행과 원천 계정명, 8~12분기 시계열 값(차트는 코드가 그린다), 신호 `calc_values`, 공시번호·공시 제출인·원문, 내부 ID, 철회 신호.

#### 4.4.3 설명 구조와 작성 규칙

| 섹션 | 쓰는 내용 | 분량 |
|---|---|---|
| `overview` | 최신 기간({per})의 한 줄 상태와 변화 유무. `CHANGED`면 첫 묶음의 배지와 `sectionFacts.overview`에 있는 사실을 **하나도 빠짐없이** 쓴다(대개 하나, 첫 묶음에 신호가 둘이면 둘 다 — 지표마다 자기 배지로, [D-57](decisions.md)). `NONE`이면 "{per} 기준으로는 규칙상 큰 변화로 표시된 항목이 없어요"를 쓴다. 사실은 변화량, 전환 신호면 전환 사실만 쓰고, 변화량은 증감 어휘와 함께 변화로 쓴다(예: "영업이익률은 전년 같은 분기보다 {…} 높아졌어요"). "{…} 수준이에요"처럼 변화량을 값으로 쓰지 않는다. 지정된 사실이 없으면 사실 없이 쓴다([D-54](decisions.md). D-46의 "겹치지 않는 원값" 경로는 없앴다). 개요에 쓴 사실은 다른 섹션에서 다시 쓰지 않는다 | 2문장, 사실 토큰 3개 이하 |
| `sales_profit` | `sectionFacts.sales_profit`의 사실과 손익 주제의 활성 신호. 매출(규모) → 영업이익·영업이익률(얼마나 남겼나) → 그 밖의 사실 순서. 순이익은 코드가 배정했을 때만(전환했거나 영업이익과 상태가 다를 때, D-54 보완) 상태·전환 사실 토큰과 함께. 흐름 사실(`revenue_yoy_run`, `operating_loss_run`)은 현재형([D-45](decisions.md)). 최근 사업연도 사실은 그 기간의 `{per}` 토큰으로 가리킨다 | 4문장, 사실 토큰 6개 이하(코드가 6개 이하만 배정) |
| `structure` | `sectionFacts.structure`의 사실과 재무 구조 주제의 활성 신호만. 부채비율(자본에 비해 빚이 얼마나 되나)과 지난 회계연도 말 대비 변화("전기말"은 쓰지 않는다, [D-56](decisions.md)) → 활성 자본잠식 신호가 있을 때만 자본총계·자본금 비교. 금융형은 자본총계(잠식이면 자본금 비교)만. 잠식 신호가 없으면 자본총계·자본금을 비교하지 않는다([D-54](decisions.md)) | 3문장, 사실 토큰 4개 이하(코드가 4개 이하만 배정) |
| `history` | 이력(PAST) 신호만 과거형으로, 입력 묶음 순서(최근 → 과거)대로("지난 {per}에는 …"). 사실 토큰은 쓰지 않는다(D-54 보완). 흐름 사실(`revenue_yoy_run`, `operating_loss_run`)은 지금도 이어지는 상태이므로 여기 쓰지 않고 `sales_profit`에서 현재형으로 쓴다([D-45](decisions.md)). 이력 신호가 여러 개면 같은 기간끼리 한 문장에 묶어 쓴다 — 신호마다 새 문장을 만들면 상한(3문장)을 넘기 쉽다([D-51](decisions.md)). 서로 다른 기간이 3개 이상(상한과 같거나 넘음)이면 서두 문장 없이 기간당 정확히 한 문장만 쓰고, 그래도 넘으면 가장 오래된 기간부터 개수만 언급해 뭉친다([D-52](decisions.md)) | 3문장 |

- **관계 서술 ([D-55](decisions.md))**: AI가 쓰는 관계(증감·흑자/적자·대소·시간 순서)는 코드가 입력에 준 관계뿐이고, 각 관계에는 **자기 종류의 근거**가 같은 문장에 있어야 한다. 목록 밖의 관계는 쓰지 않고 두 값을 차례로 적기만 한다(비교는 읽는 사람이 한다).

  | 관계 | 같은 문장의 근거 | 쓰는 방법 |
  |---|---|---|
  | 증감(R1) | 변화량 사실·`revenue_yoy_run`의 부호, 신호 유형별 산술 방향(매출·영업이익률 신호는 방향대로, 부채비율 급등은 높아짐) | 근거와 같은 방향의 증감 어휘(늘다·줄다·높아지다·낮아지다·증가·감소) |
  | 영업이익 증감(R2) | `relations`의 방향 관계와 두 영업이익 토큰(둘 다 같은 문장) | 그 방향의 증감 어휘. 관계가 없으면(둘 다 적자 등) 값만 |
  | 흑자·적자(R3·R4) | 상태·전환 사실 토큰 | 토큰이 글자를 보여 준다. 글자로 흑자·적자·손실·손해를 쓰지 않는다. 전환은 "바뀌다·돌아서다" |
  | 순이익과 영업이익의 상태 차이(R5) | `relations`의 상태 차이에 걸린 순이익 사실 토큰 | "영업이익과 달리 {…}" |
  | 자본총계 < 자본금(R6) | 활성 자본잠식 배지 | 배지와 두 사실을 한 문장에 |
  | 이어짐(R7) | 흐름 사실 토큰 | "영업적자가 {…}째 이어지고 있어요"("영업적자"는 이 문장에서만 글자로), "매출 감소가 {…}째 이어지고 있어요" |
  | 시간 순서(R8) | `history`의 기간 토큰(입력 순서) | "지난 {per}에는", "그보다 앞선 {per}에는". 시간 어휘는 `history`에서만 |
  | 나란히 놓기(R9) | 절마다 자기 근거 | "{sig.S1} 매출은 {…}로 전년 같은 분기보다 늘었지만, {sig.S2} 영업이익률은 {…}로 낮아졌어요". 배지 하나로 두 지표의 증감을 말하지 않는다. **앞머리 배지 뒤 같은 절에는 그 신호 지표의 사실 토큰이 와야 한다**([D-58](decisions.md), 규칙 14 확장) — 배지만 쓰고 사실을 다른 절로 미루지 않는다 |

  - 늘 쓰지 않는 관계: 비슷함·같은 수준, 신호 없는 정도 표현(훨씬·폭), 정도를 줄이는 표현(조금·약간·살짝, [D-58](decisions.md)), 서로 다른 지표 사이의 크기 비교(예외 R6), 적자끼리의 크기 변화("적자 폭").
  - 서로 다른 지표를 "(으)로"로 잇지 않는다("영업이익은 {…}로 영업이익률은 {…}였어요"가 아니라 쉼표로 차례로). "로"는 같은 지표의 값과 그 비교를 이을 때만 쓴다. 검증기가 확인한다([D-58](decisions.md)).
  - 평가어(개선·악화·좋아지다·나빠지다)는 방향이 같은 신호 토큰이 있는 문장에서만 쓴다. 좋고 나쁨은 신호에만 있다(§3.9).
  - "~때문에", "~덕분에", "~로 인해" 같은 원인 서술은 쓰지 않는다.
- 엇갈리는 묶음에 종합 판정("전체적으로 좋아졌다")을 붙이지 않는다.
- 반복 방지: 같은 사실 토큰은 결과 전체에서 한 번만, 같은 신호 참조는 최대 두 번(개요 1회 + 그 신호의 섹션 1회). 사실표를 차례로 읊지 않고, 신호 묶음의 사실과 섹션 핵심 수준 사실만 쓴다. 개요 사실은 코드가 다른 섹션과 겹치지 않게 지정한다(`sectionFacts.overview`, [D-54](decisions.md)).
- 신호는 코드가 정한 `section`에서 쓴다. 활성 신호는 발생 기간이 과거여도(상태 신호, 같은 회계연도의 부채비율 급등) 현재형으로 주제 섹션에서 쓴다. `history`에는 이력 신호만 있다([D-54](decisions.md)).
- 변화가 없을 때: 강도 표현 없이 수준을 담담하게 쓴다. 변화가 없다는 사실 자체가 정보다. 상태(STATE) 신호(영업적자 지속·자본잠식)는 `changeStatus`가 NONE이어도 신호 자체는 활성 사실이지만, "지속"·"잠식" 단어는 강도 표현 금지에 걸린다 — 흐름 사실이나 사실 비교("자본총계가 자본금보다 적어요")로 그 단어 없이 서술한다([D-51](decisions.md)). 자본 비교는 활성 자본잠식 신호가 있을 때만, 배지와 같은 문장에 쓴다(그때만 두 사실이 배정된다, [D-54](decisions.md)·D-55 R6). 이 사실 비교에 쓰는 사실(`total_equity`·`capital_stock` 또는 `operating_loss_run`)이 `facts`에 없으면(예: 재무상태표 불일치로 `unavailable`) 비교 문장을 만들지 않고 신호 참조만으로 쓴다 — 사실을 지어내 대신 채우지 않는다([D-52](decisions.md)).
- 데이터 한계: AI는 한계를 설명하지 않는다. `unavailable`·`doNotMention`의 지표를 언급하지 않고, 한계 문구는 코드가 정적 콘텐츠로 섹션 옆에 표시한다.
- 문체는 §8 스타일 가이드(초등 고학년, 짧은 문장, 해요체). 전문용어 툴팁은 코드가 단다.

#### 4.4.4 출력 계약 (AI)

```
{ "overview": string, "sales_profit": string|null, "structure": string|null, "history": string|null }
```

- `sections`에 있는 섹션은 비어 있지 않은 문자열, 없는 섹션은 null이다.
- 글 안의 토큰: `{fin.<지표>.<기간 키>}`(사실), `{per.<기간 키>}`(기간 라벨), `{sig.S<n>}`(신호). 숫자(연도·분기 포함)는 토큰 밖에 쓰지 않는다. 마크다운·링크를 쓰지 않는다.
- 코드는 토큰을 값 스냅샷으로 바꿔 렌더링한다. `{sig}`는 신호 유형의 정적 이름(예: "매출 큰 폭 감소") 배지로, 누르면 최근 변화 타임라인의 그 신호로 간다. 흑자·적자 상태·전환 사실도 다른 사실처럼 스냅샷의 표시 값(닫힌 문구)으로 바뀐다.
- 렌더링 결과는 전체가 HTML 이스케이프된다 — 토큰 값뿐 아니라 토큰 사이의 AI 문장도 외부 입력으로 다룬다(2026-09-27 보안 점검, implementation-plan.md §7.4.28).

#### 4.4.5 저장과 렌더링

> [D-58](decisions.md) 구현(2026-09-27, implementation-plan.md §7.4.34): 앞머리 배지는 문자열 결과에서 `[이름]`으로 괄호 쳐 구분한다("… 신호가 있어요" 앞의 이름 배지는 그대로 문장 속 말이다). 화면(Thymeleaf)이 아직 없어 조각(Fragment) 자료 구조는 만들지 않았다 — 화면을 만들 때 이 괄호 표기를 칩으로 바꾼다. AI 문장 안의 변화량(%p, `_yoy`의 %)은 부호 없이 보인다(방향은 절의 증감 어휘가 말하고 규칙 6이 일치를 보장한다). 기간 라벨은 렌더링할 때 기간 정보(회계연도 시작·기간 끝·결산월)로 만든다(D-59).

`analysis` 행(architecture.md §4.2)에 저장한다.

| 필드 | 내용 |
|---|---|
| 결과 JSON | AI 출력 그대로(토큰 포함) |
| 입력 JSON | §4.4.2 입력 전체. 공개 재무 수치만 들어 있으므로 그대로 보관한다(재현·골든셋 재실행·감사용) |
| 값 스냅샷 | 사실 키 → {표시 값, 원값, 단위, 기간 키, 기간 종료일, 출처 공시번호, 기준, 통화}, 기간 키 → 라벨, 신호 참조 → {자연키, 유형, 상태, 방향, 심각도, 발생 기준일, 근거 공시번호}, 제한 코드 목록, 헤더(기준·통화·형식·최신 기간) |
| 버전 | 스키마 버전, 프롬프트 버전, 모델, 입력 구성 버전(초기 `fx-input-1`), 입력 신호의 규칙 버전 |
| 기타 | 지문, 상태(§6.3), 토큰·비용, 검증 실패 사유(마지막 시도), 시도 횟수 |
| 시도 기록 | 시도마다 결과(통과·거절·JSON 파싱 실패·잘림/거절·호출 실패), 실패 규칙, 파싱한 출력, 파싱 실패 원문, 검증기 버전. 거절된 결과도 남긴다(원인 분석·검증기 변경 뒤 재판정용). 게시·렌더링·무효화는 읽지 않는다([D-53](decisions.md)) |

- 표시 값: AI 문장의 토큰은 값 스냅샷의 **원값·단위·통화**로 렌더링할 때 서식을 만든다(저장된 표시 문자열은 감사용이고, 단위를 모를 때만 쓴다, [D-41](decisions.md)·[D-56](decisions.md)). 비율은 수준에 '+'를 붙이지 않고 변화량(`_yoy`의 %, %p)에만 부호를 붙인다.
- 조사: 토큰 바로 뒤의 조사(으로/로, 이었/였, 이에요/예요, 을/를, 은/는, 이/가, 과/와)는 렌더러가 렌더링 값의 끝소리에 맞춘다(D-56). AI가 어느 쪽을 써도 된다.
- 문장 목록: 렌더러는 섹션 글을 검증기와 같은 문장 경계로 나눈 목록도 준다. 화면은 문장마다 줄을 바꾼다(D-56).
- 근거 연결: 섹션마다 쓴 사실 토큰의 기간을 모아 "근거: 반기보고서(2026.06, 공시 링크)"를 코드가 붙인다. 신호 배지는 근거 공시번호로 연결한다. 공시 링크는 공시번호로 코드가 만든다(D-31 묶음의 최신본).
- 헤더(코드): 기준(연결/별도), 통화(비원화는 "원화로 바꾸지 않은 값" 안내), 설명 기준 기간, AI 생성 표시, 면책 문구. 기준·통화·설명 기준 기간은 스냅샷 값, 최신 재무 기간과 데이터 한계 문구는 렌더링 시점의 현재 값이다([D-42](decisions.md)).
- 섹션 옆 참고(코드): 그 섹션 지표에 해당하는 제한 코드의 정적 문구(예: "은행·보험 같은 금융회사는 부채비율로 재무 구조를 보지 않아요").

#### 4.4.6 대상·시점·지문·무효화

- 대상: AI 적용 대상(`company.ai_covered`)과 골든셋 목록(설정). 재무 보고서가 없는 기업은 만들지 않는다(화면은 코드 숫자만).
- 시점: 분석 동기화 실행(§6.1)에서, 재무 신호 계산 뒤. 최소 재생성 간격은 없고 예산 우선순위(§6.2)를 따른다.
- 지문 ([D-40](decisions.md), [D-42](decisions.md)): 입력에 쓴 보고서 공시번호 집합 + 입력 신호의 (자연키, 상태, 방향, 심각도, 규칙 버전) + `unavailable` 항목(지표·사유) 집합 + 입력 구성 버전. 정렬해 이어 붙인 문자열의 해시. 값·표시 형식·데이터 한계 신호 코드는 넣지 않는다.
- 같은 지문의 게시·숨김 결과가 있으면 건너뛴다(§6.1). 입력을 만들 때마다 같은 순서·같은 형식이 나와야 한다(결정적 입력).
- 무효화 ([D-42](decisions.md)): 화면을 그릴 때 게시본의 값 스냅샷이 **참조한 것만** 확인한다. 참조한 신호가 철회되었거나 방향이 바뀌었으면, 또는 참조한 사실의 기간·기준 보고서의 현재 공시번호가 스냅샷과 다르거나 보고서가 없으면 AI 설명을 내리고 "재무 자료가 바뀌어 설명을 다시 만드는 중이에요"를 보여 준다. 새 보고서 도착, 신호의 활성→이력 전환·심각도 변경, 규칙 버전 변경, 시계열 기준 전환, 데이터 한계 변화만으로는 내리지 않는다(기준 기간을 표시하므로). 판정은 스냅샷의 자연키·기간·기준으로 현재 신호 상태와 공시번호만 조회하며 입력을 다시 만들지 않는다.

#### 4.4.8 골든셋과 사람 검토

- 재무 쉬운 설명 골든셋(§8의 20개와 겹쳐도 됨)은 아래 경우를 모두 포함한다: 변화 없음, 같은 방향 신호 묶음, 방향이 엇갈리는 묶음, 흑자·적자 전환, 영업적자 지속 + 자본잠식, 부채비율 급등, 금융형(은행·보험·증권), 비원화, 3월·6월 결산, 기준 전환, 결산기 변경, 재무상태표 불일치, 최신 보고서가 사업보고서인 경우, 최근 정정으로 신호가 철회된 경우.
- 골든셋 입력은 로컬 DB에서 만든 §4.4.2 입력 JSON을 저장소에 고정해 둔다(공개 재무 수치만 들어 있다). 프롬프트·모델을 바꾸면 같은 입력으로 다시 생성해 비교한다.
- 사람 검토 항목: 사실 일치(토큰 치환 후 문장이 사실표와 맞는가), 없는 비교·계산이 없는가, 원인·판정·미래 서술이 없는가, 같은 내용 반복이 없는가, 초등 고학년이 읽고 "무엇이 언제 얼마나 변했나"를 말할 수 있는가, 코드의 한계 문구와 충돌하지 않는가.
- 게시 조건: 골든셋 전체가 자동 검증을 통과하고(재시도 포함), 사람 검토에서 사실 오류·금지 표현 0건. 통과 전까지는 초안으로만 저장한다([D-39](decisions.md)).
- 운영 중: 정기보고서 제출 기한 뒤마다 게시본 10건을 무작위로 골라 같은 항목으로 검토하고 결과를 기록한다. 자동 검증 오탐·미탐 사례는 사전·패턴에 반영한다.

#### 4.4.9 확장: 새 지표와 현금흐름 ([D-50](decisions.md), 설계 확정·미적용)

골든셋 사람 검토(§4.4.8)를 마친 뒤 적용한다. 그 전까지 §4.4.1~§4.4.8이 기준이다. 사람 검토는 2026-09-27에 마쳤다(implementation-plan.md §7.4.35). 다만 적용 전에 아래 `cash_flow` 작성·검증 규칙을 D-55 계약으로 다시 정해야 한다(implementation-plan.md §9.7 6)).

- **새 지표(ROE, 유동비율)는 입력에 넣지 않는다.** 화면의 지표 보기(§3.9)가 보여 준다. 넣는 조건은 (1) 그 지표를 쓰는 신호가 생기거나, (2) 골든셋 사람 검토에서 그 지표 없이는 상태를 설명할 수 없다고 확인될 때다. 넣을 때는 사실표에 키만 추가하고 출력 계약은 바꾸지 않는다.
- **현금흐름 사실** (일반형, [D-48](decisions.md)의 정합성 통과 시)

| 사실 키 | 기간 |
|---|---|
| `operating_cf`, `operating_cf_prior`, `investing_cf`, `financing_cf` | 최신 보고서의 누적 기간(분기·반기) 또는 연간. 누적 기간은 분기와 다른 기간 키 종류를 쓰고 라벨은 "2026년 1~6월"처럼 누적으로 보인다 |
| `operating_cf` | 최근 사업연도(연간) |

- 계산하지 않은 현금흐름 지표는 `unavailable`에 사유(`NOT_APPLICABLE_FORMAT`, `ACCOUNT_MISSING`, `CF_NOT_COLLECTED`, `CF_PENDING`)와 함께 넣는다. 지문에는 `unavailable` 집합으로 반영된다([D-42](decisions.md)).
- `FIN_CASH_PROFIT_GAP`을 켜면 신호로 넣고 새 주제 묶음 `CASH`에 둔다. 신호 유형 → 사실 키: `operating_cf`(당기·전기 연간), `operating_income`(연간).
- **선택 섹션 `cash_flow`**: 현금흐름 사실이 있을 때만 코드가 `sections`에 넣는다(`structure` 뒤, `history` 앞). 사실은 D-54의 원칙대로 코드가 `sectionFacts.cash_flow`에 상한(3개) 이하로 배정한다. 2문장, 사실 토큰 3개 이하. 출력 계약은 `{ …, "cash_flow": string|null }`으로 넓힌다(스키마 버전 올림, §4.1 스키마 호환 규칙).
- **작성 규칙**: 영업활동 현금흐름의 부호와 전년 같은 기간 값을 쓴다. 영업이익과는 나란히 놓기만 한다("이익은 났지만 영업으로 들어온 현금은 마이너스였어요"). 원인(재고·매출채권 등)은 입력에 없으므로 쓰지 않는다. 투자·재무활동은 돈이 들어왔는지 나갔는지만 쓴다(무엇에 썼는지는 입력에 없다).
- **검증**: 규칙 6에 현금 어휘(들어오다·들어왔다 / 나가다·빠져나갔다)와 부호의 일치를 더한다. 규칙 9의 금지 주제는 "사실표에 없는 주제"로 일반화한다(현금흐름·ROE는 사실표에 있을 때만 허용. PER·PBR·주가·시가총액·배당은 계속 금지, [D-49](decisions.md)). 규칙 7: `cash_flow`에는 이력 신호를 쓰지 않는다.
- **바뀌지 않는 것**: 토큰 문법, 기존 네 섹션의 규칙·상한(D-39·D-45·D-46), 지문 구성과 참조 기반 무효화(D-42). 현금흐름 사실의 출처 공시번호는 같은 정기보고서 공시번호다. 입력 구성 버전·프롬프트 버전·스키마 버전을 올린다.

## 5. 향후 전망 분석

### 5.1 목적과 범위

기업의 향후 실적에 영향을 줄 수 있는 요인과 앞으로 확인할 점을 쉽게 설명한다. **예측이 아니라 앞으로 지켜볼 점을 정리하는 분석이다.**

| 한다 | 하지 않는다 |
|---|---|
| 실적을 좌우하는 요인 설명 | 주가·목표가격 예측, 매수·매도 추천 |
| 코드가 판정한 긍정·부정 신호 설명 | 실적 수치 예측 (매출·이익 전망치) |
| 앞으로 확인할 지표·이벤트 안내 | AI가 요인의 방향이나 중요도를 판정 |
| 현재 판단하기 어려운 점 설명 | 저평가·고평가 등 가치 판정, 종합 평가 |

화면 제목은 "향후 전망"이고, 코드가 부제로 "예측이 아니라 앞으로 지켜볼 점입니다"를 표시한다.

### 5.2 화면 구성

| 하위 섹션 | 내용 | 코드 | AI |
|---|---|---|---|
| 한 줄 정리 | 핵심 요인과 확인할 점 | — | 판정 없는 한 문장 |
| 주요 요인 | 실적을 좌우하는 구조적 요인 | 기업 이해의 실적 영향 요인 목록 | 요인별 쉬운 설명 |
| 긍정 요인 | 방향이 긍정인 변화 신호 | 신호 선별·배치, 수치 | 신호별 설명 |
| 부정 요인 | 방향이 부정인 변화 신호 | 신호 선별·배치, 수치 | 신호별 설명 |
| 확인할 지표·이벤트 | 신호의 확인 지표와 향후 이벤트 | 지표 목록과 현재 값, 이벤트 날짜, 이벤트 유형 설명(정적) | 지표별 "왜 봐야 하나" |
| 불확실성 | 현재 판단하기 어려운 점 | 불확실 신호 선별·배치 | 신호별 설명, 확인이 필요한 보도(뉴스 모듈, 최대 2건) |

- 기업 상세에서는 긍정·부정 요인의 신호별 설명을 "최근 변화" 타임라인의 해당 변화 옆에 보여 주고, 나머지는 "앞으로 지켜볼 점" 섹션에 보여 준다 (architecture.md §6.2, D-28). 분석의 입력·출력은 같다.
- 타임라인에 있지만 이번 선별(최대 8개)에 들지 않은 신호는 신호 유형별 정적 설명과 코드가 채운 수치로 보여 준다. 타임라인 때문에 AI 호출을 늘리지 않는다.
| 면책·기준일 | — | 고정 문구, 데이터 기준일 | — |

- 해당 방향의 신호가 없으면 코드가 고정 문구를 표시한다 (예: "현재 데이터에서 뚜렷한 긍정 요인이 확인되지 않았어요"). AI가 빈자리를 채우지 않는다.
- 향후 이벤트는 AI 출력에 넣지 않고 코드가 조회 시점에 표시한다. 날짜가 지난 이벤트는 자동으로 빠진다.
- 현재 상태의 위험(상태·부정 신호)은 리스크 섹션에서 다루고, 향후 전망에는 리스크 섹션으로 가는 링크만 둔다.

### 5.3 입력 (코드가 구성)

| 항목 | 내용 |
|---|---|
| 기업 기본 | 이름, 업종, 결산월, 재무제표 형식(일반/금융)·기준(연결/별도)·통화 (코드 판별) |
| 기업 이해 결과 | 한 줄 요약, 사업구조 요약, 실적 영향 요인(ID·설명·출처 섹션) |
| 재무 | §4.4.2와 같은 코드로 만든 사실표(최신 기간·3개 사업연도·재무상태·흐름 사실, 자리표시자 키와 값)와 제한 코드 |
| 선별 신호 | 활성 변화 신호와 불확실 신호 중 코드가 심각도·최근성 순으로 고른 최대 8개. 자연키, 유형, 방향, 심각도, 발생 기준일, 지속, 계산값, 확인 지표, 그리고 §3.3 규칙으로 연결된 관련 공시 제목(신호당 최대 3건) |
| 동종업계 비교 | 업계 중앙값 대비 성장률·이익률 (자리표시자) |
| 최근 뉴스 (뉴스 모듈) | 최근 30일 제목 최대 10건 (ID, 날짜, 제목). 뉴스 모듈이 꺼져 있으면 넣지 않는다 |

원문(사업보고서)은 다시 넣지 않는다. 입력은 약 5~6천 토큰이다. 뉴스가 없어도 향후 전망은 생성된다.

**뉴스의 역할**: 신호 설명의 맥락을 보조하거나, 불확실성 섹션의 "확인이 필요한 보도"로만 쓴다. 뉴스 기사의 방향은 코드로 신뢰성 있게 판정할 수 없으므로 **뉴스만으로 긍정·부정 요인을 만들지 않는다.**

### 5.4 AI 출력

| 필드 | 내용 |
|---|---|
| `summary` | 한 줄 정리. 종합 판정 없이 핵심 요인과 확인할 점만 담는다 |
| `driver_notes[]` | 실적 영향 요인 ID별 설명 |
| `signal_notes[]` | 신호 자연키별 설명 |
| `watch_notes[]` | 확인 지표 키별 "왜 봐야 하나" |
| `news_notes[]` | 뉴스 ID별 "확인이 필요한 보도" 설명. 최대 2건, 선택. 뉴스 모듈이 꺼져 있으면 비어 있다 |

AI는 항목을 어느 섹션에 둘지 정하지 않는다. 코드가 신호의 방향에 따라 긍정·부정·불확실 섹션에 배치한다. 따라서 AI는 신호의 방향을 바꿀 수 없다.

### 5.5 지문과 재생성

- **지문**: 기업 이해 결과 ID + 최신 재무 기간 + 선별 신호 집합(신호 자연키와 심각도)
- **지문에 넣지 않는 것**
  - 뉴스: 매일 바뀌므로 넣으면 매일 재생성된다
  - 향후 이벤트: 코드가 조회 시점에 표시한다
- **최소 재생성 간격**: 7일. 새로운 심각도 높음 신호가 생기면 간격과 무관하게 재생성한다.
- 기업 이해 결과가 없는 기업은 향후 전망을 만들지 않는다.

### 5.6 검증 (§7 공통 규칙에 추가)

- 참조한 요인·신호·지표·뉴스 ID가 모두 입력에 있어야 한다.
- 입력의 심각도 높음 신호는 모두 설명이 있어야 한다.
- `summary`에 종합 판정 표현이 없어야 한다.
- 미래를 단정하는 표현이 없어야 한다. 조건·가능성 표현만 허용한다.

### 5.7 비용

- 호출 1회: 입력 약 6K, 출력 약 1.5K 토큰 → 약 $0.027 (Claude Sonnet 5, 동기 호출 기준)
- 기업당 월 평균 약 2회 재생성을 가정하면 약 300개 기업에서 월 약 $16

## 6. 분석 동기화

### 6.1 절차

스케줄 실행마다 분석 종류별로 다음을 수행한다.

1. 대상을 정한다 (§4.2).
2. 대상마다 기대 지문을 계산한다.
3. 같은 지문의 결과가 **게시 또는 숨김** 상태로 이미 있으면 건너뛴다. 숨김은 관리자가 처리를 끝낸 것으로 보고 자동으로 다시 만들지 않는다.
4. 최소 재생성 간격 안이면 건너뛴다 (예외 규칙 적용).
5. 같은 지문으로 실패(거절·실패)한 기록이 있으면 마지막 시도 후 24시간이 지난 뒤에 다시 시도한다. 같은 지문으로 누적 3회 실패하면 알림을 보내고, 프롬프트 버전이 바뀌거나 관리자가 재시도하기 전까지 자동 시도를 멈춘다.
6. AI 예산(일·월)이 남았는지 확인한다.
7. 입력 구성 → AI 호출 → 검증 → 통과하면 게시, 실패하면 거절로 기록하고 이전 게시본을 유지한다.

작업 큐가 없으므로, 배포나 재시작으로 중간에 끊겨도 다음 실행이 그대로 이어받는다.

### 6.2 실행 순서와 우선순위

- 같은 실행 안에서 1차 분석을 먼저, 2차 분석을 나중에 처리한다.
- 예산 우선순위: 일일 변동 > 기업 이해 > 재무 쉬운 설명 > 향후 전망 > 경쟁사 비교. 같은 종류 안에서는 매출액 순으로 처리한다.
- 예산은 일 한도와 월 한도를 함께 둔다. 정기보고서 제출 기한 직후처럼 재생성이 몰리는 시기에는 일 한도에 걸려도 다음 실행에서 이어서 처리한다.
- AI 동시 호출 수는 설정값으로 제한한다 (초기값 4).

### 6.3 분석 결과 상태

| 상태 | 의미 |
|---|---|
| 초안 | 관리자 미리보기용이며 게시되지 않는다 |
| 게시 | 화면에 보이는 현재 버전. 대상·분석 종류당 1개 |
| 거절 | 검증 실패. 이전 게시본을 유지한다 |
| 실패 | 호출 오류 |
| 숨김 | 관리자가 내린 게시본 |

### 6.4 프롬프트·모델 변경

- 프롬프트나 모델 변경은 자동 재생성 조건이 아니다.
- 관리자가 대상 수와 예산을 정해 점진적으로 재생성한다.
- 결과마다 프롬프트 버전과 모델이 남으므로 구버전으로 만든 결과를 찾을 수 있다.

| 가치 판정 | 저평가, 고평가, 싸다, 비싸다, 유망하다 |
| 미래 단정 | ~할 것이다, ~할 것으로 예상된다, 확실히, 반드시 |
| 종합 판정 | 전반적으로 긍정적·부정적, 좋은 기업, 나쁜 기업 |
| 인과 단정 | 원문에 원인이 적혀 있지 않은데 "~때문에 ~했다"로 단정하는 서술 |

- 허용하는 표현: 조건·가능성 표현("~라면 ~할 수 있어요"), 출처를 밝힌 서술("회사는 사업보고서에서 ~라고 설명해요").
- **"왜"에 대한 서술**: 원인은 (1) 원문(사업보고서·공시)이 밝힌 원인을 출처와 함께 옮기거나, (2) 코드가 연결한 같은 시기의 근거를 "같은 시기에 ~이 있었어요"처럼 함께 일어난 사실로 전한다. 원문 근거 없이 AI가 원인을 추정해 단정하지 않는다 (product.md §11-5). 인과 단정은 패턴 검사로 완전히 걸러지지 않으므로 골든셋 검토 항목에 포함한다.
- 금지 표현 사전과 패턴은 코드로 관리한다. 오탐이 확인되면 사전을 조정한다.

### 7.3 실패 처리

- 한 번의 실행에서 검증에 실패하면 1회 다시 생성한다. 다시 실패하면 거절로 기록하고 이전 게시본을 유지한다. 이것을 실패 1회로 센다.
- 실행 간 재시도와 알림은 §6.1의 5번 규칙을 따른다.
- 응답이 출력 한도에서 잘리거나(`max_tokens`) 모델이 거절하면(`refusal`) 검증 실패와 같게 처리한다.

## 8. 프롬프트와 모델

| 항목 | 규칙 |
|---|---|
| 위치 | `src/main/resources/prompts/{분석 키}/v{n}.md`와 `schema.json`, 공통 스타일 가이드 |
| 스타일 가이드 | 초등 고학년 수준, 짧은 문장, 비유는 1개 이내, 전문용어는 쉽게 풀어 쓰기(툴팁은 코드가 단다), 모르면 모른다고 쓰기, 입력에 없는 사실 금지 |
| 외부 데이터 | 구분자로 감싸고, 데이터 안의 지시를 따르지 않도록 명시한다 |
| 프롬프트 캐싱 | 공통 스타일 가이드와 스키마 설명을 시스템 프롬프트 앞부분에 고정한다. 날짜 같은 가변값을 넣지 않는다. 최소 캐시 길이(Claude Sonnet 5 기준 1,024 토큰) 이상이어야 적용된다 |
| 모델 | 초기 기본값은 Claude Sonnet 5. 골든셋으로 상위 모델(Opus급)과 비교한 뒤 분석 종류별로 확정한다. 모델을 여러 개 섞으면 캐시가 모델별로 나뉜다 |
| 확장 사고(thinking) | 재무 쉬운 설명은 `thinking: {type: "disabled"}`로 끈다([D-44](decisions.md)). 이 분석은 코드가 판정을 끝낸 사실·신호를 옮겨 쓰기만 해 다단계 추론이 필요 없고, 켜 두면(모델 기본값) 사고 토큰이 `max_tokens`를 먼저 소진해 구조화 출력이 잘린다(2026-09-26 실측). 다른 분석 종류를 구현할 때는 그 종류가 실제로 원문 요약 등 다단계 추론이 필요한지에 따라 따로 정한다 |
| 골든셋 | 업종이 다양한 기업 20개 (제조, 금융, 바이오, 지주사, 플랫폼, 신규 상장 등). 프롬프트·모델을 바꿀 때 초안을 만들어 사람이 비교 검토한다. 재무 쉬운 설명의 필수 경우와 게시 조건은 §4.4.8 |
| 초안 미리보기 | 관리자 화면에서 기업 하나를 초안으로 생성해 현재 게시본과 나란히 비교한 뒤 게시한다 |
| 출력 스키마 | 구조화 출력이 지원하는 단순한 형태(객체, 배열, 문자열, 열거형)로 만든다. 개수·길이 제한은 스키마가 아니라 코드 검증에서 확인한다 |
| 호출 설정 | 출력이 긴 분석(기업 이해)은 스트리밍 또는 충분한 타임아웃을 쓴다. 동시 호출 수는 조직 사용 등급의 분당 토큰 한도에서 역산한다 |
| API 키 | 개발용과 운영용 키를 분리하고 각각 지출 한도를 둔다 |

## 9. 비용

**가정**
- 단가: Claude Sonnet 5 기준 100만 토큰당 입력 $2, 출력 $10 (2026-06 기준 가격이며 바뀔 수 있다)
- 동기 호출, AI 적용 대상 약 300개
- 한국어 토큰 수는 실측 후 보정한다

| 분석 | 호출당 (입력 / 출력) | 빈도 | 비용 |
|---|---|---|---|
| 기업 이해 | 40K / 5K, 약 $0.13 | 연 1회 + 프롬프트 개선 시 | 1회 전체 실행 약 $40 |
| 재무 쉬운 설명 | 5K / 1K(시스템 프롬프트 약 2K는 캐시), 약 $0.02. 확장 사고를 끈 상태의 가정이다([D-44](decisions.md)). 켜면(모델 기본값) 사고 토큰이 더해져 출력 토큰이 약 1.5~2배가 되고 잘림(`MAX_TOKENS`) 위험도 생긴다 | 분기 + 정정·신호 변경 시 | 분기 약 $6 |
| 일일 변동 (시세 모듈) | 6K / 1K, 약 $0.022 | 하루 최대 약 50개 | 월 약 $23 |
| 향후 전망 | 6K / 1.5K, 약 $0.027 | 기업당 월 약 2회 | 월 약 $16 |
| 경쟁사 비교 | 6K / 1.5K, 약 $0.027 | 약 450쌍, 1차 결과가 바뀔 때 | 1회 전체 실행 약 $12 |

- 운영 중 비용은 핵심 범위만이면 월 약 $20~45, 시세 모듈의 일일 변동을 켜면 월 약 $40~70이다. 프롬프트 캐싱으로 입력 비용이 더 줄어든다.
- 최초 전체 생성(기업 이해·재무 설명·향후 전망·경쟁사 비교 각 1회)에 약 $70이 든다. 비용은 정기보고서 제출 기한 직후에 몰린다.
- 공통 시스템 프롬프트가 최소 캐시 길이보다 짧으면 캐싱이 적용되지 않는다. 응답 사용량의 캐시 읽기 토큰으로 적용 여부를 확인한다.
- 개발 단계의 프롬프트 반복 비용을 줄이기 위해 골든셋에서 먼저 다듬고 전체에 적용한다.
- **실측 (2026-09-26, 재무 쉬운 설명, 확장 사고 끔, 골든셋 12개사)**: 입력 2,190~5,871토큰, 출력 956~1,736토큰(검증 실패 시 재시도 1회 포함 2회 합계), 호출당 비용 $0.015~0.031. 위 가정("5K/1K, 약 $0.02")과 대체로 맞는다. 사고를 켠 상태로 같은 12개사를 먼저 호출했을 때는 출력 토큰의 대부분(약 1,000~1,100개)이 사고 토큰이었고 12개사 전부 `MAX_TOKENS`로 잘렸다(§7.4, implementation-plan.md).

**예산 장치**
- 앱 내부 일일 AI 예산: 초과하면 우선순위가 낮은 분석부터 멈추고 알림을 보낸다
- Anthropic 콘솔 월 지출 한도
- AWS Budgets 알림

**확장 시 절감 수단**
- Batch API: 50% 할인, 결과는 최대 24시간 안에 온다(보장 아님), 캐싱 할인과 중첩된다. 전 종목에 AI를 적용할 때 도입한다.
