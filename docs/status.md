## 3. 발견한 문제와 판단 대기

| 문제 | 내용 | 제안 |
|---|---|---|
| 상장폐지 기업이 EXCLUDED로 남음 | 고유번호 파일과 기업개황은 상장폐지 기업의 종목코드를 계속 준다(예: 하나은행 004940, 쌍방울). 실제 동기화에서 상장사 3,994개 중 1,238개가 이런 "기타 시장"이었다. 기업개황 법인구분이 E(기타)로 바뀌므로 현재 코드는 이런 기업을 DELISTED가 아니라 EXCLUDED(OTHER_MARKET)로 저장한다. 수집 대상에서 빠지는 결과는 같지만 "상장폐지" 표시와 감지일이 남지 않는다 | 이전에 KOSPI·KOSDAQ이던 기업의 법인구분이 E가 되면 DELISTED로 바꾸는 규칙을 기업 목록 동기화에 추가. 기존 동작 변경이라 이번 작업에서는 하지 않음 |
| 확정 뒤 ACTIVE가 된 기업의 과거 공시 | 코넥스→코스닥 이전상장 기업은 이전 날짜의 공시를 받지 않는다 (D-31 한계) | 필요해지면 해당 기업만 고유번호 지정 조회로 채움 |
| 같은 이름 원 공시가 여럿일 때 정정 연결 | 앞선 것 중 가장 최근 것에 연결하므로 드물게 틀릴 수 있다 (D-31 한계) | 화면·분석에서 문제가 되면 원문의 정정 대상 정보 활용 검토 |
| 과거 날짜에 공시가 뒤늦게 추가되는지 | 확정 후 다시 읽지 않으므로, 접수일이 지난 날짜에 공시가 추가되면 놓친다. 아직 사례를 확인하지 못했다 | 데이터 점검(4단계 전)에서 확정 날짜의 건수를 가끔 다시 세어 비교 |
| 재무 초기 적재 속도 | 2025 회계연도 전체(4개 보고서, 보고서 약 18,000벌) 적재에 20분 이상 걸렸다(계정 행을 한 줄씩 insert). 3년 초기 적재는 1시간 안팎으로 예상된다. 호출 수 문제는 아니다 | 3-2 설계·동작은 그대로 두고, 필요하면 계정 행을 배치 insert로 바꾼다(동작 변경 없음) |
| AI 적용 대상 선정 미구현 | D-23(최근 연간 매출액 상위 약 300개 + 관리자 추가)을 계산해 `company.ai_covered`를 채우는 코드가 없다. 모든 기업이 false | 3-4는 골든셋 목록(설정)으로 초안만 만든다. 게시를 켜기 전에 대상 선정 작업을 만든다(원화·연결 우선 매출액, 금융형·비원화 제외 후 관리자 추가) |
| 신호 계산값 형식 | `company_signal.calc_values`의 키(`revenueYoyPct`, `current`, `periodLabel` 등)가 자리표시자 체계(`fin.{지표}.{기간 키}`)와 다르고, 연간 라벨은 "2026-01-01 연간", 데이터 한계 신호는 날짜 문자열이다 | AI 입력·화면은 `calc_values`를 쓰지 않고 사실표를 따로 만든다(D-38). 계산값은 감사용으로 두고, 형식을 맞출 필요가 생기면 규칙 버전을 올려 다시 계산한다 |
| ~~`AccountMapper`가 "영업수익"을 인식하지 못함~~ → **원인 오진, 유지** (§8.1) | 주요계정 API에는 "영업수익" 계정명이 없다(저장 행 전수 확인). 금융형 증권·투자사는 "매출액"으로 와서 이미 "영업수익"으로 표시되고, 은행·보험은 매출 계정이 없다. 신호·AI 입력 계약 영향 없음 | 코드 수정 없음. 인접 문제(`revenue_yoy_run` 제공 조건)는 D-41로 정해 §8.6에서 수정 |
| ~~비원화 금액의 표시 형식 미정~~ → **결정·구현 완료 D-41** (§8.2, §8.7) | 비원화는 원값+코드("1366952305CNY"), 원화 1억 미만도 원값으로 나왔다 | 한국어 수 단위 + 통화명, 환산 없음, 렌더링 시점 서식. 2026-09-26 구현·실데이터 확인 완료(§8.7·§8.8) |
| ~~`AnalysisRenderer.isInvalidated`의 과잉 무효화~~ → **결정·구현 완료 D-42** (§8.3, §8.7) | 지문 전체 비교라 새 보고서·규칙 버전 변경·데이터 한계 변화만으로도 게시본을 내리고, 화면마다 입력 전체를 다시 만들었다 | 참조한 신호·사실만으로 판정, 지문은 `unavailable` 집합 사용. 2026-09-26 구현·테스트 완료(§8.7·§8.8) |
| ~~`FIN_DATA_STALE`이 제때 켜지지 않을 수 있음~~ → **결정·구현 완료 D-43** (§8.4, §8.7) | 날짜로 판정하는 신호인데 재무가 바뀐 기업만 다시 판정했다. 새 보고서가 없는 기업(이 신호의 대상)이 다시 판정되지 않았다. 확인 중 45일·90일 기준이 60일·120일에 내는 기업(반기 27개사)에 틀린 표시를 하고, 해소가 철회로 처리되며, 3분기 → 사업보고서 기한이 하루 이른 것도 찾았다 | 가장 긴 기한(60·120일, 말일 기준, 달력일 + 7일), 판정이 남긴 재판정일에만 시간 재판정, 해소는 이력. 2026-09-26 구현·실데이터 확인 완료(§8.7·§8.8) |
| 최신 기간 근거 데이터 한계 신호가 새 분기마다 철회됨 (§8.4에서 발견) | `FIN_DATA_` 중 `HISTORY_SHORT`·`FINANCIAL_FORMAT`·`REVENUE_MISSING`·`BASIS_CHANGED`·`INCONSISTENT`는 근거 키가 "현재 최신 기간"이라, 새 분기가 오면 조건이 그대로여도 옛 키는 철회되고 새 키가 활성이 된다. spec/signals-financial.md §3.7의 "근거 키 = 처음 확인된 기간"과 다르고, D-36의 철회 뜻과도 다르다. 이런 신호가 있는 기업은 170개사(6.7%)라, 제출 기한 직후 철회 급증 경고(대상의 10%)에 가까운 잡음이 된다 | 판단 대기. 화면·AI는 활성만 쓰므로 사용자 영향은 없다. 선택지: 근거 키를 처음 확인된 기간으로 고정, 또는 D-43처럼 최신 기간이 바뀌면 이력으로 처리. 데이터 한계 신호를 읽는 화면(4단계) 전에 정한다 |

## 5. 구현할 때 점검할 제품 경계

product.md를 기준으로 구현 중 판단이 필요할 때 적용한다.

| 경계 | 점검 질문 | 근거 |
|---|---|---|
| 판정 ↔ 설명 | 방향·심각도·선별·연결을 코드가 하고 있는가? AI 프롬프트나 출력에 판정이 들어가 있지 않은가? | product.md §8, D-06 |
| 변화 ↔ 상태 | 새 화면·데이터가 "무엇이 언제 얼마나 변했나"에 답하는가, 상태 나열인가? | product.md §4, §11-1, D-28 |
| 연결 ↔ 나열 | 데이터를 보여 줄 때 변화·다른 데이터와 연결되는가? 연결 없는 목록이 늘어나지 않는가? | product.md §11-2, §12 |
| 이해 ↔ 판단 | 예측·추천·가치 판정·종합 평가·근거 없는 인과가 들어가지 않는가? | product.md §10, spec/analyses.md §7.2 |
| 근거 | 결과에 출처(공시번호·재무 기간)와 기준일을 붙일 수 있는가? 수집 단계에서 출처 식별자를 버리지 않는가? | product.md §11-5 |
| 핵심 ↔ 선택 모듈 | OpenDART만으로 동작하는가? 시세·뉴스가 없을 때의 동작이 정의되어 있는가? | D-22 |
| 시간 | 수집·신호 데이터에 발생 시점이 남는가? 이력을 덮어쓰지 않는가? | D-29 |

3-1 점검 결과: 공시는 공시번호(근거)와 접수일(기준일)을 반드시 저장하고, 정정 전 공시를 지우지 않으며(시간), 원 공시 연결은 코드가 한다(판정 ↔ 설명). 화면·AI·신호는 추가하지 않았다.
